    최근 학습 현황¶

    AWS 인프라부터 캐싱, DB 심화, 장애 대응까지 꽤 넓은 범위를 훑었다. 이론보다 실제로 헷갈렸던 지점과 설정을 잘못 잡았을 때 어떤 일이 벌어지는지를 기록한다.

    AWS 인프라¶

    EKS vs ECS, Fargate가 끼어드는 지점¶

    ECS는 Task Definition만 작성하면 되니까 진입 장벽이 낮다. EKS는 Pod, Deployment, Service, Ingress까지 따로 관리해야 하지만 Kubernetes 생태계(HPA, PDB, RBAC 등)가 그대로 붙어 있다는 게 핵심 차이다.

    Fargate는 EC2 노드를 직접 관리하지 않아도 된다는 점에서 편하지만, 노드 수준에서 DaemonSet을 못 쓰는 제약이 있다. Fluentd나 Datadog Agent처럼 사이드카가 아닌 노드 단위 에이전트가 필요한 경우에는 EC2 노드그룹을 섞어야 한다.

    Auto Scaling 설정에서 CPU 임계값을 70%로 잡는 경우를 많이 보는데, HPA는 실제 요청 큐나 메모리 기반으로 잡는 편이 더 정확하다. CPU가 70%인데 응답 지연이 없는 상황에서 스케일아웃이 계속 일어나면 비용만 나간다.

    # HPA — CPU 기반보다 커스텀 메트릭이 실제 부하를 더 잘 반영한다
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  metrics:
  - type: External
    external:
      metric:
        name: sqs_queue_depth
      target:
        type: AverageValue
        averageValue: "100"

    Kinesis vs SQS 선택 기준¶

    SQS는 메시지 하나를 한 컨슈머가 가져가는 구조다. Kinesis는 파티션(샤드) 기반이라 같은 파티션 키의 레코드 순서가 보장된다. 실시간 클릭스트림처럼 사용자별 이벤트 순서가 중요하면 Kinesis, 단순 작업 큐는 SQS가 맞다.

    Kinesis 샤드 수는 초당 처리량 기준으로 잡는다. 샤드 하나당 쓰기 1MB/s, 읽기 2MB/s다. 샤드가 부족하면 ProvisionedThroughputExceededException이 나오는데, 이걸 보고 나서야 샤드를 늘리면 이미 늦다.

    EventBridge가 SNS/SQS 조합보다 나은 경우¶

    SNS → SQS 팬아웃 구조는 직접 관리해야 할 구독이 늘어날수록 복잡해진다. EventBridge는 이벤트 버스 하나에 여러 룰을 걸어서 다른 AWS 서비스로 라우팅할 수 있다. 특히 Step Functions나 Lambda를 트리거할 때 코드 없이 콘솔에서 룰만 추가하면 된다.

    단점은 이벤트 스키마가 잘 정의되어 있지 않으면 룰 작성이 지저분해진다. detail-type과 source로 필터링하는데, 이 값을 일관되게 관리하지 않으면 나중에 디버깅하기 힘들다.

    네트워킹 — Security Groups vs NACLs 혼동 포인트¶

    Security Groups는 상태 저장(stateful)이다. 인바운드 허용하면 응답 트래픽은 아웃바운드 규칙 없이도 나간다. NACLs는 상태 비저장(stateless)이라 인바운드, 아웃바운드를 각각 설정해야 한다.

    실수가 자주 나는 지점은 NACLs로 임시 포트(Ephemeral Ports, 1024-65535)를 열지 않는 경우다. 클라이언트가 응답을 받지 못해서 타임아웃이 나는데, Security Groups 문제라고 착각하고 한참 헤맨다.

    Transit Gateway를 쓰면 VPC 수십 개를 허브-스포크 구조로 연결할 수 있다. VPC Peering은 1:1이라 VPC가 늘수록 관리할 피어링 수가 제곱으로 늘어난다. Transit Gateway는 라우팅 테이블을 한 곳에서 관리한다는 게 핵심이다.

    WAF에서 실제로 막힌 것들¶

    ALB 앞에 WAF를 붙이면 AWS Managed Rules로 OWASP 기반 공격을 차단할 수 있다. 문제는 정상 요청이 차단되는 경우가 생각보다 많다. SQL 키워드가 포함된 검색 쿼리, Base64 인코딩된 JSON 페이로드가 SQLi 규칙에 걸리는 경우가 있었다.

    카운트 모드로 먼저 며칠 돌려서 어떤 요청이 매칭되는지 확인하고 나서 블록 모드로 전환해야 한다. 바로 블록 모드로 켜면 정상 트래픽이 갑자기 403을 받는 상황이 생긴다.

    X-Ray 분산 추적에서 놓치기 쉬운 것¶

    X-Ray는 트레이스 ID를 HTTP 헤더(X-Amzn-Trace-Id)로 전파한다. Lambda, ECS는 SDK를 붙이면 자동으로 세그먼트를 생성하지만, 서비스 간 내부 HTTP 호출에서 헤더를 명시적으로 포워딩하지 않으면 트레이스가 끊긴다.

    Spring Boot에서는 AWS X-Ray SDK를 쓰거나, Micrometer + X-Ray 익스포터를 쓴다. 직접 RestTemplate 인터셉터로 헤더를 넘기는 방법도 있다.

    // X-Ray 트레이스 헤더 전파 — 인터셉터에서 처리
public class XRayTraceInterceptor implements ClientHttpRequestInterceptor {
    @Override
    public ClientHttpResponse intercept(HttpRequest request, byte[] body,
            ClientHttpRequestExecution execution) throws IOException {
        Entity entity = AWSXRay.getCurrentSegmentOptional().map(seg -> (Entity) seg)
            .orElse(AWSXRay.getCurrentSubsegmentOptional().orElse(null));
        if (entity != null) {
            request.getHeaders().add("X-Amzn-Trace-Id", entity.getTraceId().toString());
        }
        return execution.execute(request, body);
    }
}

    캐싱 전략¶

    Cache-Aside에서 캐시 스탬피드가 나는 상황¶

    Cache-Aside(Lazy Loading)는 캐시에서 먼저 읽고, 없으면 DB에서 가져와 캐시에 쓰는 패턴이다. 문제는 TTL이 만료되는 순간에 동시 요청이 쏟아지면 전부 DB로 가버린다는 것이다. 이걸 캐시 스탬피드(Cache Stampede)라고 한다.

    대응 방법은 두 가지다. 하나는 분산 락으로 DB 접근을 하나만 허용하고 나머지는 대기시키는 것, 다른 하나는 PER(Probabilistic Early Recomputation)로 TTL 만료 전에 확률적으로 미리 갱신하는 것이다.

    // Redis + Redisson으로 분산 락 적용
public String getWithLock(String key) {
    String cached = redis.get(key);
    if (cached != null) return cached;

    RLock lock = redisson.getLock("lock:" + key);
    try {
        if (lock.tryLock(500, 3000, TimeUnit.MILLISECONDS)) {
            // 락 획득 후 다시 확인 (다른 스레드가 이미 캐싱했을 수 있다)
            cached = redis.get(key);
            if (cached != null) return cached;

            String value = db.load(key);
            redis.setex(key, 300, value);
            return value;
        }
    } finally {
        if (lock.isHeldByCurrentThread()) lock.unlock();
    }
    return db.load(key); // 락 실패 시 DB에서 직접 읽는다
}

    Write-Through와 Write-Behind의 선택¶

    Write-Through는 쓰기 요청마다 DB와 캐시를 함께 업데이트한다. 데이터 일관성은 높지만, 실제로 읽히지 않는 데이터도 캐시에 올라가 메모리를 낭비한다.

    Write-Behind(Write-Back)는 캐시에 먼저 쓰고 DB 반영을 비동기로 처리한다. 쓰기 성능은 높아지지만 캐시 서버가 장애 나는 순간 아직 DB에 반영 안 된 데이터가 날아간다. 금융 트랜잭션 같은 곳에는 쓰면 안 된다.

    Caffeine(로컬) vs Redis(분산) 선택 기준¶

    Caffeine은 프로세스 내 메모리에 올라가서 Redis보다 훨씬 빠르다. 네트워크 왕복이 없으니 마이크로초 단위다. 하지만 인스턴스가 두 개 이상 뜨는 순간 각 인스턴스의 캐시가 달라진다.

    코드 테이블, 공통 설정처럼 변경이 드물고 읽기 빈도가 높은 데이터는 Caffeine으로 충분하다. 세션, 장바구니, 분산 락처럼 여러 인스턴스가 공유해야 하는 데이터는 Redis가 맞다.

    두 계층을 함께 쓰는 경우도 있다. Redis에서 가져온 값을 Caffeine에 짧은 TTL로 올려두면 Redis 호출 빈도를 줄일 수 있다. 단, Caffeine TTL이 짧아야 Redis 업데이트가 결국 전파된다.

    데이터베이스 심화¶

    Connection Pool 설정에서 자주 틀리는 것¶

    HikariCP의 maximumPoolSize 기본값은 10이다. 스레드가 100개인데 커넥션이 10개면 90개 스레드가 대기한다. 그렇다고 무조건 크게 잡으면 DB 서버가 버틸 수 있는 커넥션 수를 초과한다.

    실무에서 많이 쓰는 공식은 CPU 코어 수 * 2 + 유효 스핀들 수인데, 클라우드 환경에서는 그냥 부하 테스트로 적정값을 찾는 게 현실적이다. 설정이 잘못됐을 때 나타나는 증상은 Connection is not available, request timed out after NNNms 에러다.

    spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.connection-timeout=3000
spring.datasource.hikari.idle-timeout=600000
spring.datasource.hikari.max-lifetime=1800000

    max-lifetime은 DB의 wait_timeout보다 짧게 잡아야 한다. DB가 커넥션을 끊었는데 풀은 살아있다고 생각하면 Communications link failure 에러가 난다.

    Optimistic Lock vs Pessimistic Lock 선택¶

    Optimistic Lock은 DB에 락을 걸지 않고 버전 번호로 충돌을 감지한다. 실패하면 OptimisticLockException을 던진다. 충돌이 드문 상황에서 성능이 높다.

    @Entity
public class Product {
    @Version
    private Long version; // 업데이트마다 1씩 증가
}

// 두 트랜잭션이 동시에 같은 버전을 읽고 업데이트하면
// 나중에 커밋하는 쪽이 OptimisticLockException을 받는다

    Pessimistic Lock(SELECT FOR UPDATE)은 트랜잭션 동안 다른 트랜잭션이 해당 행을 수정하지 못하게 한다. 재고 차감, 좌석 예약처럼 충돌 빈도가 높고 실패 시 재시도 비용이 큰 경우에 쓴다.

    데드락 주의가 필요하다. 두 트랜잭션이 서로 다른 순서로 락을 잡으면 교착 상태가 된다. 락 순서를 일관되게 유지하거나, 락 타임아웃을 설정해야 한다.

    @Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints({@QueryHint(name = "javax.persistence.lock.timeout", value = "3000")})
Optional<Product> findById(Long id);

    N+1 문제는 반드시 프로파일러로 확인한다¶

    N+1은 @OneToMany, @ManyToOne 관계에서 Lazy Loading이 반복 실행되는 문제다. 코드만 봐서는 잘 안 보이기 때문에 Hibernate가 실제로 몇 개의 쿼리를 날리는지 로그를 직접 봐야 한다.

    logging:
  level:
    org.hibernate.SQL: DEBUG
    org.hibernate.orm.jdbc.bind: TRACE

    해결 방법은 Fetch Join 또는 @EntityGraph다. Fetch Join은 JPQL에 직접 쓰고, @EntityGraph는 메서드 단위로 어떤 연관관계를 함께 로딩할지 지정한다.

    @EntityGraph(attributePaths = {"orderItems", "orderItems.product"})
List<Order> findByStatus(OrderStatus status);

    주의할 점은 컬렉션 Fetch Join을 여러 개 쓰면 카테시안 곱이 생겨 데이터가 뻥튀기된다. DISTINCT를 써도 메모리에서만 제거되고 DB 쿼리는 그대로 비대해진다. 이 경우 @BatchSize로 IN 쿼리로 묶어서 가져오는 게 낫다.

    파티셔닝은 인덱스 설계와 함께¶

    테이블이 수억 건을 넘어가면 풀 인덱스 스캔만으로도 느려진다. Range 파티셔닝은 날짜 컬럼으로 월별/년별로 잘라두면 특정 기간 조회 시 파티션 프루닝이 동작해서 스캔 범위가 줄어든다.

    주의할 점은 파티션 키가 WHERE 절에 항상 포함되어야 프루닝이 된다는 것이다. 파티션 키 없이 조회하면 전체 파티션을 다 읽는다. EXPLAIN PARTITIONS로 확인할 수 있다.

    장애 대응¶

    Circuit Breaker 설정값을 잘못 잡으면¶

    Resilience4j의 Circuit Breaker는 슬라이딩 윈도우로 실패율을 계산한다. failureRateThreshold가 50이면 최근 N번의 호출 중 50% 이상 실패할 때 회로가 열린다.

    CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)           // 50% 실패 시 열림
    .waitDurationInOpenState(Duration.ofSeconds(30))  // 30초 후 Half-Open 시도
    .slidingWindowSize(10)              // 최근 10번 기준
    .minimumNumberOfCalls(5)            // 최소 5번 이상 호출 후 통계 적용
    .permittedNumberOfCallsInHalfOpenState(3)
    .build();

    minimumNumberOfCalls를 너무 낮게 잡으면 초반 몇 번의 실패로 회로가 바로 열린다. 반대로 너무 높으면 장애 감지가 늦어진다. 서비스 특성에 맞게 잡아야 하는데, 트래픽이 적은 내부 API는 10~20, 트래픽이 많은 외부 API는 50~100 정도로 시작해서 조정한다.

    Retry에서 Jitter를 안 넣으면 생기는 일¶

    Exponential Backoff만 쓰면 모든 클라이언트가 같은 시점에 재시도를 보낸다. 서비스가 막 복구되는 시점에 재시도 트래픽이 몰려서 다시 죽이는 상황(Thundering Herd)이 생긴다.

    Jitter는 재시도 간격에 랜덤 편차를 추가해서 요청을 분산시킨다.

    RetryConfig retryConfig = RetryConfig.custom()
    .maxAttempts(3)
    .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(
        1000,   // 초기 1초
        2.0,    // 2배씩 증가
        0.5     // 50% 랜덤 지터
    ))
    .retryExceptions(ConnectException.class, SocketTimeoutException.class)
    .ignoreExceptions(BusinessException.class)  // 비즈니스 예외는 재시도 안 함
    .build();

    재시도 대상 예외를 명확히 설정해야 한다. 4xx 클라이언트 에러를 재시도하면 의미 없이 서버에 부하만 준다.

    Liveness vs Readiness 헷갈리는 지점¶

    Liveness 프로브는 프로세스가 살아있는지 확인한다. 실패하면 Pod를 재시작한다. Readiness 프로브는 트래픽을 받을 준비가 됐는지 확인한다. 실패하면 Service에서 해당 Pod를 제외한다.

    Liveness에 DB 연결 확인을 넣으면 안 된다. DB가 일시적으로 응답이 느려질 때 전체 Pod가 재시작되는 사태가 벌어진다. Liveness는 최대한 단순하게(프로세스 생존 여부만), Readiness에 DB, Redis, 외부 API 연결 확인을 넣는다.

    // Liveness — 프로세스가 살아있으면 충분하다
@GetMapping("/health/live")
public ResponseEntity<Void> liveness() {
    return ResponseEntity.ok().build();
}

// Readiness — 실제로 요청을 처리할 수 있는지 확인
@GetMapping("/health/ready")
public ResponseEntity<Void> readiness() {
    try {
        dataSource.getConnection().close();  // DB 연결 확인
        redis.ping();                         // Redis 연결 확인
        return ResponseEntity.ok().build();
    } catch (Exception e) {
        return ResponseEntity.status(503).build();
    }
}

    Fallback은 단순히 기본값을 반환하는 것도 있지만, 캐시에서 오래된 데이터를 내려주거나 다른 서비스를 호출하는 것도 있다. 중요한 건 Fallback이 또 다른 장애를 유발하지 않도록 최대한 단순해야 한다는 것이다.

    AWS 비용 & 거버넌스¶

    Organizations + SCP로 계정별 권한을 제한하는 구조는 한 번 잘 잡아두면 감사 대응이 편하다. 개발 계정에서는 특정 고비용 인스턴스 타입을 SCP로 막아두면 실수로 c5.4xlarge를 켜놓는 상황을 원천 차단할 수 있다.

    Cost Explorer에서 태그 기반으로 비용을 나누려면 리소스에 태그가 제대로 달려있어야 한다. 팀, 서비스명, 환경(dev/staging/prod)을 필수 태그로 강제하지 않으면 비용 분석이 의미 없어진다. AWS Config 규칙으로 필수 태그 없는 리소스를 탐지할 수 있다.

    브라우저 렌더링 파이프라인¶

    리플로우와 리페인트를 구분해야 하는 이유¶

    브라우저가 화면을 그리는 과정은 DOM 파싱 → CSSOM 생성 → 렌더 트리 결합 → 레이아웃(리플로우) → 페인트 → 컴포짓 순서다. 자바스크립트로 DOM을 건드릴 때마다 이 과정 일부가 다시 돌아간다.

    리플로우(Layout)는 요소의 크기나 위치가 바뀔 때 발생한다. width, height, margin, padding, top, left 같은 속성이 바뀌면 해당 요소와 자식, 경우에 따라 형제 요소까지 레이아웃을 다시 계산한다. 이게 반복되면 프레임 드랍이 생긴다.

    리페인트는 위치는 그대로인데 외관이 바뀔 때다. color, background-color, visibility 변경이 여기에 해당한다. 리플로우보다 가볍지만 GPU 처리가 들어간다.

    컴포짓 레이어로 올라간 요소는 리플로우/리페인트 없이 GPU가 직접 처리한다. transform과 opacity 변경이 여기에 해당한다. 애니메이션을 구현할 때 left/top 대신 transform: translate()를 쓰는 이유다.

    // 리플로우를 반복 유발하는 패턴 — 루프마다 레이아웃을 강제로 읽고 씀
for (let i = 0; i < elements.length; i++) {
    elements[i].style.width = elements[i].offsetWidth + 10 + 'px'; // 읽기 + 쓰기 반복
}

// 읽기를 먼저 모아두고 쓰기를 나중에
const widths = elements.map(el => el.offsetWidth);
elements.forEach((el, i) => { el.style.width = widths[i] + 10 + 'px'; });

    offsetWidth, scrollTop, getBoundingClientRect() 같은 속성을 읽으면 브라우저가 최신 레이아웃을 계산해야 해서 강제로 리플로우가 일어난다. DOM 쓰기와 읽기를 번갈아 하면 루프마다 리플로우가 발생한다.

    will-change의 양면¶

    will-change: transform을 쓰면 브라우저가 해당 요소를 미리 별도 레이어로 분리한다. 애니메이션 시작 시 레이어 생성 비용이 없어져 첫 프레임이 부드럽다. 하지만 레이어마다 GPU 메모리를 잡아먹는다. 화면에 있는 요소 전부에 will-change를 달면 오히려 성능이 나빠진다.

    실제로 문제가 확인된 곳에만, 애니메이션이 시작되기 직전에 JS로 붙이고 끝나면 제거하는 방식이 낫다.

    React 상태관리¶

    useState와 useReducer의 실제 분기점¶

    useState는 상태 하나를 독립적으로 관리할 때 쓴다. 상태가 서로 연관되어 있고, 다음 상태가 이전 상태에 따라 달라지는 경우가 많아지면 useReducer로 옮기는 게 낫다.

    가장 흔한 패턴은 폼 상태다. 필드가 3개를 넘어가거나 필드 간 의존성이 생기면 useState 여러 개보다 useReducer 하나가 훨씬 추적하기 쉽다.

    type FormState = {
    name: string;
    email: string;
    isSubmitting: boolean;
    error: string | null;
};

type FormAction =
    | { type: 'SET_FIELD'; field: 'name' | 'email'; value: string }
    | { type: 'SUBMIT_START' }
    | { type: 'SUBMIT_SUCCESS' }
    | { type: 'SUBMIT_FAIL'; error: string };

function formReducer(state: FormState, action: FormAction): FormState {
    switch (action.type) {
        case 'SET_FIELD':
            return { ...state, [action.field]: action.value };
        case 'SUBMIT_START':
            return { ...state, isSubmitting: true, error: null };
        case 'SUBMIT_SUCCESS':
            return { ...state, isSubmitting: false };
        case 'SUBMIT_FAIL':
            return { ...state, isSubmitting: false, error: action.error };
    }
}

    useReducer의 dispatch는 렌더 사이에 참조가 안정적이라 useCallback으로 감쌀 필요가 없다.

    Context API가 리렌더링을 유발하는 방식¶

    Context는 Provider의 value가 바뀌면 해당 Context를 구독하는 모든 컴포넌트를 리렌더링한다. value를 인라인 객체 리터럴로 넣으면 매 렌더마다 새 참조가 생겨서 모든 Consumer가 리렌더링된다.

    // 매 렌더마다 새 객체가 생성되어 모든 Consumer가 리렌더링
function BadProvider({ children }) {
    const [user, setUser] = useState(null);
    return (
        <UserContext.Provider value={{ user, setUser }}>
            {children}
        </UserContext.Provider>
    );
}

// useMemo로 안정화
function GoodProvider({ children }) {
    const [user, setUser] = useState(null);
    const value = useMemo(() => ({ user, setUser }), [user]);
    return <UserContext.Provider value={value}>{children}</UserContext.Provider>;
}

    자주 바뀌는 상태와 잘 안 바뀌는 상태를 같은 Context에 넣으면 안 된다. 테마 설정은 ThemeContext, 인증 정보는 AuthContext처럼 관심사별로 나눠야 불필요한 리렌더링을 줄일 수 있다.

    Redux Toolkit 실무 패턴¶

    createSlice와 Immer¶

    RTK의 createSlice는 내부적으로 Immer를 쓴다. reducer에서 상태를 직접 변이하는 것처럼 쓰면 Immer가 불변 업데이트로 바꿔준다.

    const cartSlice = createSlice({
    name: 'cart',
    initialState: { items: [], total: 0 } as CartState,
    reducers: {
        addItem(state, action: PayloadAction<CartItem>) {
            const existing = state.items.find(item => item.id === action.payload.id);
            if (existing) {
                existing.quantity += 1;  // Immer가 불변 업데이트로 바꿔준다
            } else {
                state.items.push(action.payload);
            }
            state.total += action.payload.price;
        },
        removeItem(state, action: PayloadAction<string>) {
            const index = state.items.findIndex(item => item.id === action.payload);
            if (index !== -1) {
                state.total -= state.items[index].price * state.items[index].quantity;
                state.items.splice(index, 1);
            }
        },
    },
});

    Immer를 쓸 때 주의할 점이 있다. 새 값을 return하거나 기존 상태를 변이(mutate)하거나 둘 중 하나만 해야 한다. 둘 다 하면 런타임 에러가 난다.

    createAsyncThunk와 extraReducers¶

    비동기 처리는 createAsyncThunk로 처리하고, slice에서 extraReducers로 pending/fulfilled/rejected 상태를 관리하는 게 표준 패턴이다.

    export const fetchUser = createAsyncThunk(
    'user/fetch',
    async (userId: string, { rejectWithValue }) => {
        try {
            return await userApi.getUser(userId);
        } catch (e) {
            return rejectWithValue((e as Error).message);
        }
    }
);

const userSlice = createSlice({
    name: 'user',
    initialState: { data: null, loading: false, error: null } as UserState,
    reducers: {},
    extraReducers: (builder) => {
        builder
            .addCase(fetchUser.pending, (state) => {
                state.loading = true;
                state.error = null;
            })
            .addCase(fetchUser.fulfilled, (state, action) => {
                state.loading = false;
                state.data = action.payload;
            })
            .addCase(fetchUser.rejected, (state, action) => {
                state.loading = false;
                state.error = action.payload as string;
            });
    },
});

    RTK Query는 이 패턴을 더 줄여준다. API 엔드포인트를 정의하면 fetching, caching, invalidation까지 자동으로 처리한다. 서버 상태 관리에 Redux를 쓰는 경우라면 RTK Query를 먼저 고려하는 게 낫다.

    Zustand¶

    Redux 없이 전역 상태를 관리하는 방법¶

    Zustand는 store를 만들고 컴포넌트에서 필요한 상태 조각만 selector로 구독한다. 구독한 상태 조각만 바뀔 때 해당 컴포넌트가 리렌더링된다.

    import { create } from 'zustand';

type CartStore = {
    items: CartItem[];
    addItem: (item: CartItem) => void;
    removeItem: (id: string) => void;
    total: () => number;
};

const useCartStore = create<CartStore>((set, get) => ({
    items: [],
    addItem: (item) => set((state) => ({
        items: [...state.items, item]
    })),
    removeItem: (id) => set((state) => ({
        items: state.items.filter(i => i.id !== id)
    })),
    total: () => get().items.reduce((sum, item) => sum + item.price * item.quantity, 0),
}));

// 컴포넌트에서 사용
function CartCount() {
    const count = useCartStore(state => state.items.length);  // count만 구독
    return <span>{count}</span>;
}

    state.items.length만 구독했기 때문에 아이템의 가격이 바뀌어도 이 컴포넌트는 리렌더링되지 않는다. Context API보다 세밀한 구독이 가능하다.

    Context API와 비교하면 Provider 래핑이 없어서 컴포넌트 트리 구조가 단순해진다. zustand/middleware의 devtools로 Redux DevTools에도 연결할 수 있다.

    React Query / SWR¶

    서버 상태와 클라이언트 상태를 분리해야 하는 이유¶

    서버에서 가져온 데이터를 Redux에 넣어서 관리하는 패턴은 문제가 있다. 서버 데이터는 언제든 바뀔 수 있는데, Redux는 클라이언트가 직접 dispatch하기 전에는 상태가 바뀌지 않는다. 캐시 무효화, 백그라운드 갱신, 중복 요청 제거 같은 걸 전부 직접 구현해야 한다.

    React Query는 이 문제를 해결한다. 쿼리 키로 캐시를 관리하고, 설정한 staleTime이 지나면 자동으로 백그라운드에서 다시 가져온다.

    function useUserProfile(userId: string) {
    return useQuery({
        queryKey: ['user', userId],
        queryFn: () => userApi.getUser(userId),
        staleTime: 5 * 60 * 1000,  // 5분간 fresh로 간주
        gcTime: 10 * 60 * 1000,    // 10분 후 캐시에서 제거
    });
}

function useUpdateUser() {
    const queryClient = useQueryClient();
    return useMutation({
        mutationFn: userApi.updateUser,
        onSuccess: (data) => {
            // 업데이트 성공 시 해당 쿼리 무효화 → 자동으로 다시 가져옴
            queryClient.invalidateQueries({ queryKey: ['user', data.id] });
        },
    });
}

    staleTime과 gcTime의 차이를 헷갈리는 경우가 있다. staleTime은 데이터가 fresh로 간주되는 시간이다. 이 시간 내에는 캐시에서 바로 반환하고 네트워크 요청을 보내지 않는다. gcTime은 컴포넌트가 언마운트된 후 캐시가 메모리에서 유지되는 시간이다.

    SWR과의 비교¶

    SWR은 Vercel의 라이브러리로 API가 단순하고 번들 크기가 작다. React Query는 기능이 더 많다(무한 쿼리, 낙관적 업데이트, prefetching, Suspense 모드 등). 복잡한 서버 상태 관리가 필요하면 React Query, 단순한 데이터 페칭이면 SWR로 충분하다.

    React Hooks 심화¶

    useCallback과 useMemo를 남발하면 안 되는 이유¶

    useCallback과 useMemo는 참조를 안정화하는 게 목적이다. 메모이제이션 자체도 비용이 든다. 의존성 배열 비교 비용과 이전 결과를 저장하는 메모리 비용이 생긴다. 리렌더링 비용이 이보다 낮은 경우에 쓰면 오히려 성능이 나빠진다.

    useCallback이 실제로 의미 있는 경우는 두 가지다. React.memo로 감싼 자식 컴포넌트에 콜백을 넘기는 경우, 그리고 useEffect의 의존성 배열에 함수가 들어가는 경우다.

    // 이 경우는 useCallback이 의미 없다
// 부모가 리렌더링되면 MyComponent도 어차피 리렌더링된다
function Parent() {
    const handleClick = useCallback(() => {
        console.log('click');
    }, []);

    return <MyComponent onClick={handleClick} />;
}

// React.memo로 최적화된 자식에 넘기는 경우에 의미가 있다
const MemoizedChild = React.memo(function Child({ onAction }) {
    return <button onClick={onAction}>Action</button>;
});

function Parent() {
    const handleAction = useCallback(() => {
        doSomethingExpensive();
    }, []);  // 참조가 안정적이어야 MemoizedChild가 스킵될 수 있다

    return <MemoizedChild onAction={handleAction} />;
}

    Closure가 만드는 stale state 문제¶

    useEffect, useCallback 안에서 state 값을 참조하면 의존성 배열에 넣지 않은 경우 클로저가 닫힌 시점의 값을 캡처한다. 이걸 stale closure라고 한다.

    function Counter() {
    const [count, setCount] = useState(0);

    useEffect(() => {
        const interval = setInterval(() => {
            // count가 클로저에 캡처된 초기값 0이라
            // 1초마다 setCount(0 + 1)을 실행한다
            setCount(count + 1);
        }, 1000);
        return () => clearInterval(interval);
    }, []);  // 의존성 배열에 count가 없어서 초기값이 캡처됨

    return <div>{count}</div>;
}

    setter의 함수형 업데이트로 해결할 수 있다. 함수형 업데이트는 클로저의 state를 참조하지 않고 현재 state를 인자로 받는다.

    useEffect(() => {
    const interval = setInterval(() => {
        setCount(prev => prev + 1);  // 현재 state를 prev로 받아 사용
    }, 1000);
    return () => clearInterval(interval);
}, []);  // count 의존성이 없어도 동작한다

    컴포넌트 패턴¶

    Compound Components¶

    연관된 컴포넌트들이 상태를 암묵적으로 공유하는 패턴이다. <select> + <option> 관계와 유사하다. Context로 부모 상태를 자식에게 내려준다.

    const TabContext = createContext<{
    active: string;
    setActive: (id: string) => void;
} | null>(null);

function Tabs({ children, defaultTab }: { children: ReactNode; defaultTab: string }) {
    const [active, setActive] = useState(defaultTab);
    return (
        <TabContext.Provider value={{ active, setActive }}>
            <div className="tabs">{children}</div>
        </TabContext.Provider>
    );
}

function Tab({ id, children }: { id: string; children: ReactNode }) {
    const ctx = useContext(TabContext);
    if (!ctx) throw new Error('Tab must be used within Tabs');
    return (
        <button
            className={ctx.active === id ? 'active' : ''}
            onClick={() => ctx.setActive(id)}
        >
            {children}
        </button>
    );
}

Tabs.Tab = Tab;

    <Tabs defaultTab="first">
    <Tabs.Tab id="first">첫 번째</Tabs.Tab>
    <Tabs.Tab id="second">두 번째</Tabs.Tab>
</Tabs>

    Custom Hook으로 로직 분리¶

    UI 컴포넌트에 비즈니스 로직이 섞이면 테스트하기 어렵고 재사용도 힘들다. Custom Hook으로 상태와 핸들러를 분리해두면 컴포넌트는 렌더링만 담당하게 된다.

    function useProductList(categoryId: string) {
    const [filters, setFilters] = useState<Filters>({ sort: 'latest', minPrice: 0 });
    const { data, isLoading } = useQuery({
        queryKey: ['products', categoryId, filters],
        queryFn: () => productApi.list(categoryId, filters),
    });

    const updateFilter = useCallback((key: keyof Filters, value: unknown) => {
        setFilters(prev => ({ ...prev, [key]: value }));
    }, []);

    return { products: data?.items ?? [], isLoading, filters, updateFilter };
}

// 컴포넌트는 Hook에서 받아서 렌더링만
function ProductList({ categoryId }: { categoryId: string }) {
    const { products, isLoading, filters, updateFilter } = useProductList(categoryId);
    // 렌더링
}

    Node.js 동시성과 CPU 블로킹¶

    이벤트 루프가 막히는 순간¶

    Node.js는 단일 스레드 이벤트 루프다. I/O는 비동기로 처리해서 대기 시간에 다른 작업을 처리할 수 있지만, CPU 연산은 메인 스레드를 점유한다.

    수십 MB JSON 파싱, 중첩 루프로 대규모 배열 처리가 그동안 새 HTTP 요청을 막는다. setTimeout(fn, 0)으로 스케줄링해봐야 현재 실행 중인 동기 코드가 끝나야 callback이 실행되므로 의미 없다.

    // 이 함수가 실행되는 동안 다른 요청은 전부 대기한다
app.get('/compute', (req, res) => {
    const result = heavyComputation(req.body.data);  // 2초짜리 CPU 연산
    res.json({ result });
});

    Worker Threads로 CPU 연산 분리¶

    worker_threads 모듈로 CPU 집약적 작업을 별도 스레드로 옮길 수 있다. 메인 스레드는 이벤트 루프를 계속 돌리고, Worker가 독립적인 V8 인스턴스에서 연산을 처리한다.

    // worker.js
const { workerData, parentPort } = require('worker_threads');

function heavyComputation(data) {
    let result = 0;
    for (let i = 0; i < data.length; i++) {
        result += complexCalculation(data[i]);
    }
    return result;
}

parentPort.postMessage(heavyComputation(workerData));

    // main.js
const { Worker } = require('worker_threads');

function runInWorker(data) {
    return new Promise((resolve, reject) => {
        const worker = new Worker('./worker.js', { workerData: data });
        worker.on('message', resolve);
        worker.on('error', reject);
    });
}

app.get('/compute', async (req, res) => {
    const result = await runInWorker(req.body.data);  // 메인 스레드는 블로킹되지 않는다
    res.json({ result });
});

    Worker Thread마다 생성 비용이 있어서 요청마다 새 Worker를 만들면 오버헤드가 크다. 실제 서비스에서는 Worker Pool을 만들어두고 재사용하는 게 낫다. piscina 라이브러리가 이 패턴을 구현해준다.

    child_process vs worker_threads¶

    child_process.fork()는 완전히 독립된 프로세스다. 메모리를 공유하지 않고 데이터를 IPC로 직렬화해서 주고받는다. 큰 데이터를 다룰 때 직렬화 비용이 크다.

    worker_threads는 같은 프로세스 내 스레드다. SharedArrayBuffer로 메모리를 공유할 수 있어 대규모 데이터 처리에 유리하다. 단, 공유 메모리 접근 시 동기화 문제를 직접 처리해야 한다.

    일반적인 API 서버에서 CPU 블로킹이 문제라면 worker_threads로 충분하다. 플러그인 실행이나 신뢰할 수 없는 코드 실행처럼 완전 격리가 필요한 경우는 child_process를 쓴다.
