    백엔드 신입 필독 20선¶

    백엔드 개발자로 첫 취업을 준비하거나 막 입문한 사람을 위해 정리했다. 순서에 의도가 있다. 언어 → 네트워크 → 데이터베이스 → 클라우드 → 설계 순으로 읽어야 각 단계에서 배운 개념이 다음 단계의 기반이 된다. VPC부터 보면 서브넷 분리가 왜 필요한지 실감이 안 나고, SSH를 모르는 상태에서 EC2를 보면 "접속은 어떻게 하나?"에서 막힌다.

    1단계 — 언어와 JVM¶

    왜 JVM부터 시작하나¶

    자바 백엔드 개발자로 일하면서 JVM을 모르면 OOM이 났을 때 로그를 봐도 무슨 말인지 모른다. java.lang.OutOfMemoryError: Java heap space와 java.lang.OutOfMemoryError: Metaspace는 원인이 다르고 해결 방법도 다르다. 이걸 구분하려면 Heap, Metaspace, Stack이 무엇인지 먼저 알아야 한다.

    1. JVM 구조 및 메모리 관리

    Heap/Stack/Metaspace의 역할 구분이 핵심이다. GC가 언제 돌고 어떤 객체를 수거하는지 흐름을 잡아야 한다. 면접에서 "GC가 뭔가요?" 수준이 아니라 "Minor GC와 Major GC의 차이는?" 수준이 나온다. Young 영역의 Eden→Survivor→Old 이동 흐름을 손으로 그릴 수 있을 정도로 봐야 한다.

    1. JVM Options and Memory Management

    개발 환경에서는 기본값으로 문제없다가 스테이징에 올리면 OOM이 터지는 경우가 있다. 그때 -Xmx, -Xms, GC 관련 옵션을 건드려야 하는데 아무 설정도 모르면 손을 못 댄다. 적어도 -Xmx와 -XX:+UseG1GC 정도는 눈에 익혀둬야 한다.

    # 실행 중인 JVM의 GC 상태를 1초 간격으로 10번 출력
# PID는 jps 명령어로 확인
jstat -gcutil <pid> 1000 10

# 출력 예시
#  S0     S1     E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
#   0.00  58.33  34.56  23.12  94.34  91.22    12    0.234     1    0.456    0.690
#
# E(Eden), O(Old) 영역이 계속 100%에 가까우면 GC가 감당 못하고 있다는 신호다.
# FGC(Full GC) 횟수가 계속 오르면 OOM이 멀지 않은 상태다.
    1. 객체지향 프로그래밍 — Marker Interface

    Serializable이나 Cloneable처럼 메서드 없이 타입만 부여하는 패턴이다. 직접 만들 일은 드물지만 Spring 프레임워크 코드를 읽다가 마주치고 당황하는 경우가 많다. 패턴 자체보다 "왜 이렇게 설계했는가"를 이해하는 것이 핵심이다.

    1. ES6 Class

    Node.js로 백엔드를 짜거나 프론트엔드 코드를 같이 읽어야 하는 상황이 생긴다. ES6 이전의 프로토타입 기반 상속과 class 문법의 차이를 모르면 레거시 코드가 낯설다. 특히 super() 호출 순서나 정적 메서드의 동작 방식은 Java와 다른 점이 있다.

    1. Interface Deep Dive

    API 스펙을 TypeScript로 정의하는 팀이 늘고 있다. 인터페이스와 타입 별칭(type alias)의 차이, 인덱스 시그니처 등을 모르면 타입 정의 파일을 읽는 데 시간이 걸린다. Java의 interface 개념과 비슷해 보이지만 동작 방식이 다른 부분이 있어서 비교하며 읽으면 빠르다.

    2단계 — 네트워크와 HTTP¶

    백엔드 개발자로 일하면서 가장 자주 마주치는 문제는 "왜 API 응답이 안 오나?"다. 그 답을 찾으려면 HTTP 계층부터 L2까지 흐름을 알아야 한다. 이 5편은 API 디버깅의 기반이 된다.

    1. HTTP

    신입이 가장 허술하게 넘어가는 주제다. POST와 PUT의 차이, 상태 코드 200/201/204/400/401/403/404/500의 의미, 헤더에서 Content-Type과 Authorization이 왜 중요한지 정확히 알아야 한다. REST API 설계 면접에서 기초가 흔들리면 설명이 엉킨다. 특히 401과 403의 차이를 묻는 면접관이 많은데, 둘 다 "접근 불가"처럼 보여서 헷갈린다.

    1. MacAddress

    EC2 인스턴스가 VPC 안에서 통신할 때 내부적으로 L2 계층을 탄다. "MAC 주소가 왜 백엔드 개발자한테 필요하냐"고 생각하기 쉬운데, 네트워크 트러블슈팅 시 ARP 테이블이나 ENI를 봐야 할 때 기초가 된다. 클라우드 네트워크 문서를 읽을 때 L2 개념이 없으면 용어가 막힌다.

    1. SSH

    첫 배포 서버에 붙으려면 SSH부터 써야 한다. 비밀번호 인증 방식의 위험성, RSA 키 페어 생성 및 등록, ~/.ssh/config로 다중 서버 관리하는 방법 정도는 알아야 팀 서버에 처음 붙을 때 헤매지 않는다.

    # ~/.ssh/config로 다중 서버 관리
Host dev-server
    HostName 10.0.1.100
    User ec2-user
    IdentityFile ~/.ssh/dev-key.pem
    ServerAliveInterval 60

Host prod-bastion
    HostName 54.x.x.x
    User ec2-user
    IdentityFile ~/.ssh/prod-key.pem

# 설정해두면 ssh dev-server 한 줄로 접속 가능
# IdentityFile 권한이 400이 아니면 Permission denied 뜬다 (chmod 400 ~/.ssh/dev-key.pem)
# ServerAliveInterval은 세션 끊김 방지 — 없으면 idle 타임아웃으로 연결이 끊긴다
    1. 네트워크 관리

    netstat -tulnp로 어떤 포트가 열려있는지, ss -s로 소켓 상태 요약, tcpdump로 실제 패킷 확인하는 법은 실무에서 생각보다 빠르게 필요한 순간이 온다. 포트 충돌 문제나 보안 그룹 설정 확인할 때 이 명령어들로 시작한다.

    1. 네트워크 트러블슈팅

      연결 타임아웃이 났을 때 서버 문제인지, 네트워크 문제인지, 보안 그룹 문제인지 구분하는 흐름이 핵심이다. ping → traceroute → telnet <host> <port> → curl -v 순서로 레이어를 좁혀가는 방식을 익혀야 한다. 흔히 막히는 지점은 보안 그룹이 ICMP(ping)는 허용하면서 TCP 포트는 막는 경우다. ping이 되는데 curl이 안 되면 포트 레벨 문제다.

    3단계 — 데이터베이스¶

    쿼리는 짤 줄 아는데 인덱스를 왜 걸어야 하는지 모르는 상태로 취업하는 경우가 많다. 이 4편은 "쿼리 작성" 수준에서 "데이터베이스를 다루는" 수준으로 올라가는 과정이다.

    1. RDS

      EC2에 MySQL 직접 설치하는 것과 RDS의 차이를 정확히 알아야 한다. 자동 백업, Multi-AZ, 읽기 전용 복제본이 각각 어떤 상황에서 필요한지, 비용은 어떻게 다른지가 실무 설계 결정에 직접 영향을 준다. Multi-AZ가 고가용성 목적이고 Read Replica가 읽기 분산 목적이라는 차이를 면접에서 자주 묻는다.

    2. Aurora DB

      RDS MySQL과 Aurora MySQL은 엔진 레벨에서 다르다. Aurora의 스토리지가 6개 복사본을 3개 AZ에 분산 저장한다는 구조를 모르면 "Aurora가 더 비싼데 왜 쓰나요?" 질문에 대답 못한다. Serverless v2가 나오고 나서 소규모 서비스에서도 Aurora를 쓰는 경우가 늘었다.

    3. 인덱스 가능성

      가장 실무적인 내용이다. 어떤 쿼리에 인덱스가 탈지, 왜 LIKE '%keyword'는 인덱스를 못 타는지, 복합 인덱스의 컬럼 순서가 왜 중요한지를 여기서 잡아야 한다. 인덱스를 무조건 많이 걸면 오히려 INSERT/UPDATE 성능이 떨어진다는 것도 함께 이해해야 한다.

    -- EXPLAIN으로 인덱스 사용 여부 확인
EXPLAIN SELECT * FROM orders
WHERE user_id = 100 AND status = 'PENDING'
ORDER BY created_at DESC;

-- type 컬럼이 'ALL'이면 풀스캔
-- 'ref'나 'range'면 인덱스를 탄 것
-- rows 숫자가 클수록 느리다

-- 복합 인덱스 순서 예시
-- (user_id, status)로 인덱스를 걸면 user_id 단독 조회는 타지만
-- status 단독 조회는 인덱스를 못 탄다
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- LIKE 검색: 앞에 와일드카드가 있으면 인덱스를 못 탄다
SELECT * FROM users WHERE name LIKE '%김%';   -- 풀스캔
SELECT * FROM users WHERE name LIKE '김%';    -- 인덱스 탐

    1. 컬럼 접미 패턴

      팀에서 _at, _id, _yn, _count 같은 접미사 규칙을 맞추는 건 코드 리뷰에서 바로 지적받는 사항이다. 신입 때는 "이런 거 왜 신경 써야 하나" 싶지만, 컬럼명 규칙이 일관되지 않으면 나중에 쿼리 짤 때 is_deleted인지 deleted_yn인지 매번 스키마를 뒤져야 한다. 레거시 코드베이스일수록 이 혼선이 심하다.

    4단계 — 클라우드 입문¶

    AWS를 처음 접할 때 서비스가 너무 많아서 어디서부터 시작해야 할지 모르는 경우가 있다. EC2 → ECS → VPC 순서로 보면 컴퓨팅 → 컨테이너 → 네트워크 레이어가 쌓이면서 전체 그림이 잡힌다.

    1. EC2

      인스턴스 유형(t3, m5, c5)의 차이, 온디맨드/스팟/예약 구매 옵션의 비용 구조, EBS 볼륨 붙이는 법을 알아야 한다. 첫 배포 서버를 만들 때 인스턴스 타입을 잘못 골라서 나중에 마이그레이션하는 사태를 방지하려면 기초를 짚고 가야 한다. t3.micro와 t3.medium의 CPU 버스팅 동작 방식 차이도 알아두면 좋다.

    2. ECS

      EC2에 직접 Docker를 띄우는 것과 ECS Fargate의 차이를 이해해야 한다. Fargate는 서버 관리 없이 컨테이너를 실행하는데, Task Definition에서 CPU/메모리 할당과 환경 변수 설정이 실무에서 가장 자주 건드리는 부분이다. 처음 마주치는 어려운 지점은 IAM 역할 — Task Role과 Task Execution Role의 용도가 다르다.

    3. VPC

      서브넷을 퍼블릭/프라이빗으로 나누는 이유, 인터넷 게이트웨이와 NAT 게이트웨이의 역할 차이, 보안 그룹과 NACL이 각각 어디서 동작하는지가 핵심이다. VPC를 모르면 "왜 EC2가 외부와 통신이 안 되나?" 문제를 만났을 때 어디서부터 확인해야 할지 모른다. 보안 그룹은 스테이트풀, NACL은 스테이트리스라는 차이가 실제 트러블슈팅에서 자주 나온다.

    5단계 — 설계와 운영¶

    코드를 짜는 것과 시스템을 운영하는 것은 다른 기술이다. 이 단계는 "코드가 돌아가는 환경"에 대한 감각을 키우는 과정이다.

    1. CI/CD Pipeline

      GitHub Actions 기준으로, 코드를 Push하면 테스트 → 빌드 → 배포까지 자동으로 돌아가는 파이프라인 흐름을 잡아야 한다. 파이프라인이 실패했을 때 원인을 직접 찾지 못하고 선배에게 묻는 상황이 신입 때 자주 생긴다. 로그를 읽는 방법과 스텝별 실패 원인을 구분하는 법을 함께 본다.

    2. Prometheus & Grafana

      장애가 나고 "언제부터 문제가 생겼나요?" 질문을 받을 때 Grafana 대시보드가 없으면 로그를 직접 뒤져야 한다. Prometheus가 메트릭을 수집하고 Grafana가 시각화하는 구조, 알림 임계값 설정 방법을 기초 수준에서 알아야 온콜 대응에 참여할 수 있다. CPU/메모리/JVM 힙 메트릭을 보는 것부터 시작한다.

    3. Infrastructure Design Principles

      확장성, 가용성, 비용의 균형을 맞추는 결정이 실제로 어떻게 이루어지는지를 다룬다. 면접에서 "트래픽이 10배 늘면 어떻게 할 것인가?" 질문에 답하는 기반이 된다. 스케일 아웃 vs 스케일 업, 스테이트리스 설계가 왜 중요한지를 여기서 잡는다. 이론적 이해보다 실제로 어느 지점에서 무엇을 선택하는지 판단 기준을 익히는 게 목적이다.

    20편을 마친 다음¶

    MSA 아키텍처나 Kafka로 넘어가면 된다. 이 20편이 기반이 되어 있으면 MSA의 서비스 분리 이유가 단순히 "트렌드라서"가 아니라 "단일 서버의 어떤 한계 때문에"로 읽힌다.
