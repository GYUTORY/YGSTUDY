    함수 종속¶

    정의¶

    함수 종속(Functional Dependency)은 한 릴레이션에서 속성 집합 X의 값이 결정되면 속성 집합 Y의 값이 하나로 결정되는 관계다. X → Y로 표기하며 "X가 Y를 함수적으로 결정한다" 또는 "Y는 X에 함수 종속된다"고 읽는다.

    주문번호 → 주문일자는 주문번호가 정해지면 주문일자가 하나로 결정된다는 뜻이다. 주문일자 → 주문번호는 성립하지 않는다. 같은 날 주문이 여러 건일 수 있기 때문이다.

    공식적으로 릴레이션 R에서 모든 튜플 t1, t2에 대해 t1[X] = t2[X]이면 t1[Y] = t2[Y]가 성립할 때 X → Y라고 한다.

    함수 종속은 데이터 인스턴스가 아니라 비즈니스 규칙에서 나온다. 현재 테이블에 담긴 데이터만 보고 함수 종속을 판단하면 틀린다. 우연히 모든 행의 Y값이 동일하더라도 비즈니스 규칙상 X가 Y를 결정하지 않으면 함수 종속이 아니다.

    종류¶

    완전 함수 종속¶

    X → Y이고, X의 어떤 진부분집합(proper subset) X'에 대해서도 X' → Y가 성립하지 않을 때 Y는 X에 완전 함수 종속(Full Functional Dependency)이라고 한다. X 전체가 있어야만 Y를 결정할 수 있다.

    수강 테이블: (학번, 과목코드, 성적, 학생명)
기본키: (학번, 과목코드)

성적은 학번만으로도 안 되고, 과목코드만으로도 안 된다.
학번 + 과목코드 둘 다 있어야 특정 성적이 결정된다.
→ 성적은 (학번, 과목코드)에 완전 함수 종속

    부분 함수 종속¶

    X → Y이고, X의 진부분집합 X'에 대해서도 X' → Y가 성립할 때 Y는 X에 부분 함수 종속(Partial Functional Dependency)이라고 한다. 복합키의 일부만으로도 Y를 결정할 수 있다는 뜻이다.

    수강 테이블: (학번, 과목코드, 성적, 학생명)
기본키: (학번, 과목코드)

학생명은 학번만 알면 결정된다. 과목코드가 없어도 된다.
→ 학생명은 (학번, 과목코드)에 부분 함수 종속
  (기본키 전체가 아닌 일부인 학번에만 종속)

    부분 함수 종속이 있으면 2NF를 위반한다. 학생명처럼 학번만으로 결정되는 속성이 수강 테이블에 있으면, 한 학생이 여러 과목을 수강할 때마다 학생명이 중복 저장된다. 학생명을 바꾸면 해당 학생의 모든 수강 행을 전부 업데이트해야 한다.

    이행 함수 종속¶

    A → B이고 B → C이지만 B → A는 성립하지 않을 때, C는 A에 이행 함수 종속(Transitive Functional Dependency)이라고 한다. A → C가 직접 성립하되, 중간에 B를 경유해서 결정된다.

    직원 테이블: (직원ID, 직원명, 부서ID, 부서명)
기본키: 직원ID

직원ID → 부서ID  (직원이 결정되면 소속 부서가 결정됨)
부서ID → 부서명  (부서ID가 결정되면 부서명이 결정됨)
→ 직원ID → 부서명  (이행 함수 종속)

    이행 함수 종속이 있으면 3NF를 위반한다. 부서명이 직원 테이블에 있으면 같은 부서 소속 직원이 100명일 때 부서명이 100번 중복 저장된다. 부서명을 "AI팀"에서 "ML팀"으로 바꾸려면 100개 행을 모두 업데이트해야 한다.

    자명한 함수 종속¶

    Y가 X의 부분집합이면 X → Y는 항상 성립한다. 이를 자명한 함수 종속(Trivial Functional Dependency)이라고 한다.

    {학번, 과목코드} → {학번}     -- 자명 (학번은 {학번, 과목코드}의 부분집합)
{학번, 과목코드} → {과목코드}  -- 자명
{학번} → {학번}               -- 자명

    자명한 함수 종속은 항상 성립하므로 정규화 분석에서 제거 대상이 아니다. Armstrong 공리 중 반사율(Reflexivity)이 이를 공식화한다.

    다치 종속¶

    함수 종속과 별개로, 다치 종속(Multi-valued Dependency)은 X값 하나에 Y값 집합이 대응되는 관계다. X →→ Y로 표기한다.

    강의 테이블: (교수, 과목, 교재)
한 교수가 여러 과목을 담당하고, 각 과목에 여러 교재를 사용한다고 할 때
교수 →→ 과목
교수 →→ 교재

    다치 종속은 4NF와 관련 있고 함수 종속의 일반화된 형태다.

    Armstrong 공리¶

    Armstrong 공리는 함수 종속의 도출 규칙이다. 주어진 함수 종속 집합 F에서 논리적으로 유도할 수 있는 모든 함수 종속을 구할 때 사용한다. 세 가지 기본 공리가 건전성(soundness)과 완전성(completeness)을 보장한다.

    반사율(Reflexivity): Y ⊆ X이면 X → Y

    X가 Y를 포함하면 X → Y는 항상 성립한다. 자명한 함수 종속이 이 규칙으로 나온다.

    부가율(Augmentation): X → Y이면 XZ → YZ

    함수 종속에 같은 속성 집합을 양쪽에 추가해도 성립한다. 직원ID → 부서ID이면 {직원ID, 직원명} → {부서ID, 직원명}도 성립한다.

    이행율(Transitivity): X → Y이고 Y → Z이면 X → Z

    연쇄 함수 종속이다. 이행 함수 종속이 바로 이 규칙에서 나온다.

    이 세 공리에서 추가로 유도되는 규칙들:

    분해(Decomposition): X → YZ이면 X → Y, X → Z

    합병(Union): X → Y이고 X → Z이면 X → YZ

    가이행율(Pseudotransitivity): X → Y이고 WY → Z이면 WX → Z

    실무에서 Armstrong 공리를 직접 쓸 일은 드물지만, "이 속성이 저 속성을 결정하는가?"를 따질 때 암묵적으로 적용한다.

    함수 클로저¶

    속성 집합 X의 함수 클로저 X+는 X로부터 F에 있는 함수 종속들을 Armstrong 공리로 도출할 수 있는 모든 속성의 집합이다.

    F = {A → B, B → C, A → D}일 때 A+를 구하면:

A → B    (F에서 직접)
A → C    (A → B, B → C, 이행율로 도출)
A → D    (F에서 직접)
A → A    (반사율)

A+ = {A, B, C, D}

    X가 후보키인지 확인하려면 X+가 릴레이션의 모든 속성을 포함하는지 보면 된다. 이게 후보키 판별의 알고리즘이다.

    실무에서 함수 종속 식별하기¶

    비즈니스 규칙에서 시작한다¶

    ERD를 그리기 전에 요구사항 문서나 도메인 전문가와의 대화에서 함수 종속을 식별한다. "어떤 값이 고유하게 결정되는가?"와 "무엇이 무엇을 결정하는가?"를 따진다.

    주문 도메인 요구사항:
- 주문번호는 고유하다 → 주문번호가 다른 모든 주문 속성을 결정한다
- 한 주문에는 하나의 배송지만 있다 → 주문번호 → 배송지
- 상품코드는 고유하다 → 상품코드 → 상품명, 단가, 카테고리
- 주문 + 상품 조합이 주문 아이템을 결정한다 → (주문번호, 상품코드) → 주문수량

    테이블에서 문제 찾기¶

    같은 값이 반복되는 컬럼 확인

    수백 개 행에 걸쳐 department_name이 "개발팀"으로 반복된다면, department_name이 다른 컬럼(department_id)에 종속된 상태로 테이블에 같이 있을 가능성이 높다.

    복합키 테이블에서 키 일부에만 종속된 컬럼 확인

    -- 주문_상품 매핑 테이블
CREATE TABLE order_products (
    order_id     BIGINT,
    product_id   BIGINT,
    quantity     INT,
    product_name VARCHAR(100),  -- product_id만으로 결정됨 → 부분 함수 종속
    PRIMARY KEY (order_id, product_id)
);

    product_name이 product_id만 알아도 결정된다면 여기 있으면 안 된다.

    기본키가 아닌 컬럼이 다른 기본키 아닌 컬럼을 결정하는 경우

    CREATE TABLE employees (
    emp_id    BIGINT PRIMARY KEY,
    dept_id   INT,
    dept_name VARCHAR(50),   -- dept_id → dept_name (이행 종속)
    salary    DECIMAL(10,2)
);

    dept_name의 값이 같은 dept_id를 가진 행끼리 동일하면 이행 종속이 있다.

    이상 현상으로 역추적하기¶

    이미 만들어진 테이블에서 함수 종속 문제를 찾는 실용적인 방법은 이상 현상(Anomaly)을 확인하는 것이다.

    • 삽입 이상: 특정 데이터를 넣으려면 불필요한 다른 데이터도 같이 넣어야 하는 경우
    • 수정 이상: 한 사실을 수정하려면 여러 행을 동시에 업데이트해야 하는 경우
    • 삭제 이상: 행을 하나 지우면 의도치 않은 다른 정보도 사라지는 경우

    삭제 이상이 가장 잘 안 보인다. 수강 신청이 한 건인 학생이 수강 취소를 하면, 그 학생에 대한 유일한 정보(학생명, 연락처)도 함께 사라지는 구조가 대표적이다.

    정규화 단계별 함수 종속 제거¶

    2NF: 부분 함수 종속 제거¶

    기본키가 단일 컬럼이면 2NF는 자동으로 만족된다. 부분 함수 종속은 복합키에서만 생긴다.

    -- 2NF 위반: (order_id, product_id)가 기본키인데 product_name은 product_id에만 종속
CREATE TABLE order_items (
    order_id     BIGINT,
    product_id   BIGINT,
    product_name VARCHAR(100),  -- 부분 함수 종속
    unit_price   DECIMAL(10,2), -- 부분 함수 종속 (product_id → unit_price)
    quantity     INT,
    PRIMARY KEY (order_id, product_id)
);

-- 2NF 적용: 부분 종속 속성을 별도 테이블로 분리
CREATE TABLE products (
    product_id   BIGINT PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    unit_price   DECIMAL(10,2) NOT NULL
);

CREATE TABLE order_items (
    order_id   BIGINT,
    product_id BIGINT REFERENCES products(product_id),
    quantity   INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);

    단, 주문 시점의 단가를 보존해야 하는 비즈니스 요구가 있다면 unit_price를 order_items에 남겨두는 게 맞다. 상품 단가가 나중에 바뀌더라도 주문 당시 단가를 보여줘야 하기 때문이다. 이건 3NF 위반이 아니라 비즈니스 요구사항이다.

    3NF: 이행 함수 종속 제거¶

    -- 3NF 위반
CREATE TABLE employees (
    emp_id    BIGINT PRIMARY KEY,
    emp_name  VARCHAR(50),
    dept_id   INT,
    dept_name VARCHAR(50),  -- dept_id → dept_name (이행 종속)
    city      VARCHAR(50),  -- dept_id → city (부서 위치, 이행 종속)
    salary    DECIMAL(10,2)
);

-- 3NF 적용
CREATE TABLE departments (
    dept_id   INT PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL,
    city      VARCHAR(50)
);

CREATE TABLE employees (
    emp_id   BIGINT PRIMARY KEY,
    emp_name VARCHAR(50) NOT NULL,
    dept_id  INT REFERENCES departments(dept_id),
    salary   DECIMAL(10,2)
);

    3NF 분리 후 직원 목록에 부서명을 보여줄 때 JOIN이 필요해진다. 인덱스를 제대로 걸면 성능 문제는 거의 없다. 부서명이 바뀔 때 departments 테이블 한 행만 수정하면 된다는 점이 JOIN 비용보다 크다.

    BCNF: 결정자가 후보키가 아닌 경우 제거¶

    3NF를 만족하더라도 BCNF를 위반하는 경우가 있다. 결정자(→의 왼쪽)가 후보키가 아닌 경우다.

    과목_교수 릴레이션
속성: {학번, 과목명, 교수명}
비즈니스 규칙:
  - {학번, 과목명} → 교수명  (학생은 특정 과목에서 한 교수만 수강)
  - 교수명 → 과목명          (교수는 한 과목만 담당)

후보키: {학번, 과목명} 또는 {학번, 교수명}

교수명 → 과목명이 성립하는데, 교수명은 후보키가 아니다 → BCNF 위반

    -- BCNF 위반 상태
CREATE TABLE enrollment (
    student_id  BIGINT,
    course_name VARCHAR(50),
    professor_id BIGINT,
    PRIMARY KEY (student_id, course_name)
);

-- BCNF 적용: 교수 → 과목 종속을 별도 테이블로
CREATE TABLE professor_course (
    professor_id BIGINT PRIMARY KEY,
    course_name  VARCHAR(50) NOT NULL
);

CREATE TABLE student_professor (
    student_id   BIGINT,
    professor_id BIGINT REFERENCES professor_course(professor_id),
    PRIMARY KEY (student_id, professor_id)
);

    BCNF 분리의 문제점은 원래 테이블에 있던 {학번, 과목명} → 교수명 종속을 단일 테이블로 표현할 수 없게 된다는 점이다. "학생이 어떤 과목을 수강하는가"를 알려면 professor_course를 거쳐야 한다. BCNF는 3NF와 달리 의존성 보존을 항상 보장하지 않는다. 실무에서 BCNF까지 가는 경우가 적은 이유가 여기 있다. 3NF까지 적용하면 대부분의 이상 현상은 제거된다.

    4NF: 다치 종속 제거¶

    다치 종속이 있는 릴레이션은 BCNF를 만족하더라도 중복이 발생한다.

    교수_과목_교재 릴레이션
속성: {교수명, 과목명, 교재명}
비즈니스 규칙:
  - 한 교수가 여러 과목을 담당한다
  - 교재 선택은 과목과 무관하게 교수가 결정한다

교수명 →→ 과목명
교수명 →→ 교재명
    교수명 과목명 교재명
    김교수 데이터베이스 DB Bible
    김교수 데이터베이스 SQL 실습
    김교수 알고리즘 DB Bible
    김교수 알고리즘 SQL 실습

    김교수가 교재를 하나 추가하면 담당 과목 수만큼 행을 INSERT해야 한다. 다치 종속에서 오는 중복이다.

    -- 4NF 적용: 다치 종속을 별도 테이블로 분리
CREATE TABLE professor_course (
    professor_id BIGINT,
    course_id    BIGINT,
    PRIMARY KEY (professor_id, course_id)
);

CREATE TABLE professor_textbook (
    professor_id BIGINT,
    textbook_id  BIGINT,
    PRIMARY KEY (professor_id, textbook_id)
);

    4NF는 실무에서 거의 적용하지 않는다. 이런 구조가 나오면 모델링 자체를 다시 검토하는 경우가 더 많다. 다치 종속이 생기는 상황은 초기 설계에서 관계를 잘못 잡은 신호일 수 있다.

    주의사항¶

    정규화는 "완전히 정규화된 상태"를 목표로 삼지 않는다. 비즈니스 요구와 성능 요구를 보고 어느 단계까지 정규화할지 판단한다.

    함수 종속을 잘못 파악하는 경우가 가장 흔한 실수다. 데이터를 보고 판단하지 말고 비즈니스 규칙을 보고 판단해야 한다. 현재 데이터에서 우연히 1:1 관계처럼 보여도, 비즈니스 규칙상 1:N이 가능하면 함수 종속이 아니다.

    BCNF 이상으로 정규화하면 의존성 보존이 깨지는 경우가 있다. 분리된 테이블에서 JOIN해야 표현되는 비즈니스 규칙이 생기고, JOIN을 빠뜨리면 데이터 정합성을 확인할 방법이 없어진다.
