    갱신 이상¶

    갱신 이상(Update Anomaly)은 한 사실을 수정하려면 여러 행을 동시에 업데이트해야 하는 상황이다. 업데이트 대상 행이 누락되거나 중간에 트랜잭션이 실패하면 같은 사실에 대해 서로 다른 값이 공존하는 상태가 된다.

    정규화.md에서 이상 현상의 한 유형으로 짧게 다뤘는데, 갱신 이상은 삽입·삭제 이상과 달리 런타임에 데이터 불일치가 조용히 쌓이는 방식으로 문제가 생긴다. 삽입·삭제 이상은 그 행위 자체가 실패하거나 원치 않는 결과를 내놓지만, 갱신 이상은 UPDATE 자체는 성공하면서 DB 내부의 일관성만 무너진다.

    발생 원인¶

    갱신 이상이 생기는 핵심 원인은 데이터 중복이다. 중복은 두 가지 구조적 문제에서 온다.

    부분 함수 종속¶

    복합키 테이블에서 키의 일부에만 종속된 속성이 있으면, 그 속성값이 여러 행에 걸쳐 반복 저장된다.

    CREATE TABLE order_items (
    order_id     BIGINT,
    product_id   BIGINT,
    product_name VARCHAR(100),   -- product_id → product_name
    category     VARCHAR(50),    -- product_id → category
    unit_price   DECIMAL(10,2),  -- product_id → unit_price (주문 당시 단가라면 예외)
    quantity     INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);

    product_name은 product_id만 알면 결정된다. order_id와는 무관하다. 이 상황에서 상품명이 "무선 마우스"에서 "블루투스 마우스"로 바뀌면 이 테이블에서 해당 product_id를 가진 모든 행을 찾아 업데이트해야 한다.

    -- 이 상품이 10만 건 주문에 포함됐다면 10만 행을 업데이트해야 한다
UPDATE order_items SET product_name = '블루투스 마우스' WHERE product_id = 42;

    이행 함수 종속¶

    기본키가 아닌 컬럼이 다른 비기본키 컬럼을 결정하는 경우, 결정되는 쪽 값이 역시 여러 행에 중복된다.

    CREATE TABLE employees (
    emp_id     BIGINT PRIMARY KEY,
    emp_name   VARCHAR(50),
    dept_id    INT,
    dept_name  VARCHAR(50),   -- dept_id → dept_name
    dept_city  VARCHAR(50),   -- dept_id → dept_city
    salary     DECIMAL(10,2)
);

    emp_id → dept_id → dept_name이 성립한다. 같은 부서 소속 직원이 200명이면 dept_name이 200개 행에 동일한 값으로 저장된다. 부서명을 "플랫폼팀"에서 "인프라팀"으로 바꿀 때 200개 행을 전부 업데이트해야 한다.

    트랜잭션 실패와 병렬 쿼리에서의 불일치¶

    갱신 이상이 실제 장애로 이어지는 경로는 두 가지다.

    부분 커밋¶

    100만 행짜리 order_items 테이블에서 특정 상품명을 업데이트하는 배치가 50만 행을 처리하다 서버가 죽으면, 절반은 새 이름, 절반은 이전 이름인 상태로 커밋된다. InnoDB는 행 단위 잠금이라 트랜잭션 안에 담으면 원자성이 보장되는데, 메모리 제한이나 배치 설계 실수로 단일 트랜잭션에 담지 않고 청크 단위로 나눠 커밋하면 중간 실패 시 정합성이 깨진다.

    -- 잘못된 패턴: 청크별 커밋 도중 실패 시 불일치 발생
UPDATE order_items SET product_name = '블루투스 마우스'
WHERE product_id = 42 AND order_id BETWEEN 1 AND 100000;
COMMIT;

-- 여기서 프로세스가 죽으면 order_id 100001 이후는 이전 이름 유지
UPDATE order_items SET product_name = '블루투스 마우스'
WHERE product_id = 42 AND order_id BETWEEN 100001 AND 200000;
COMMIT;

    병렬 쿼리 경쟁¶

    읽기 쿼리가 갱신 도중 끼어드는 경우다. MySQL InnoDB에서 UPDATE는 갱신 중인 행에만 행 잠금을 건다. 업데이트가 순차적으로 진행되는 동안, SELECT 쿼리는 이미 변경된 행과 아직 변경되지 않은 행을 동시에 읽을 수 있다.

    -- Session A: 상품명 변경 중
UPDATE order_items SET product_name = '블루투스 마우스' WHERE product_id = 42;
-- 아직 완료되지 않은 상태

-- Session B: 같은 테이블 읽기 (READ COMMITTED 격리 수준)
SELECT order_id, product_name FROM order_items WHERE product_id = 42;
-- 일부 행은 '블루투스 마우스', 일부 행은 '무선 마우스' 반환

    REPEATABLE READ라면 Session B는 트랜잭션 시작 시점의 스냅샷을 읽으므로 섞이지 않는다. 하지만 읽은 데이터를 다른 곳에 캐시하거나 파일로 내보낸 뒤 Session A의 업데이트가 완료되면, 캐시와 DB 사이에 불일치가 남는다.

    정규화로 해결¶

    갱신 이상의 근본 원인은 중복 저장이다. 중복을 없애면 갱신 대상이 한 행으로 줄어든다.

    2NF: 부분 함수 종속 제거¶

    부분 함수 종속 속성을 별도 테이블로 분리한다. product_id에만 종속된 product_name, category를 products 테이블로 뺀다.

    CREATE TABLE products (
    product_id   BIGINT PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    category     VARCHAR(50),
    base_price   DECIMAL(10,2) NOT NULL
);

CREATE TABLE order_items (
    order_id   BIGINT,
    product_id BIGINT NOT NULL REFERENCES products(product_id),
    unit_price DECIMAL(10,2) NOT NULL,  -- 주문 당시 단가, 의도적 중복
    quantity   INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);

    product_name이 바뀌면 products 한 행만 업데이트하면 된다. order_items 는 건드릴 필요가 없다.

    unit_price는 products.base_price와 별개로 order_items에 남겨뒀다. 나중에 상품 가격이 바뀌어도 주문 당시 단가를 보존해야 하는 요구사항이 있기 때문이다. 겉으로는 부분 함수 종속처럼 보이지만 비즈니스 규칙이 이 중복을 요구한다. 정규화 적용 전에 "이 컬럼이 왜 여기 있어야 하는가"를 먼저 따져야 한다.

    3NF: 이행 함수 종속 제거¶

    이행 함수 종속 속성을 별도 테이블로 분리한다. dept_id → dept_name, dept_city이므로 부서 정보를 departments 테이블로 뺀다.

    CREATE TABLE departments (
    dept_id   INT PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL,
    dept_city VARCHAR(50)
);

CREATE TABLE employees (
    emp_id   BIGINT PRIMARY KEY,
    emp_name VARCHAR(50) NOT NULL,
    dept_id  INT NOT NULL REFERENCES departments(dept_id),
    salary   DECIMAL(10,2)
);

    부서명을 바꿀 때 departments 한 행만 수정하면 된다. 직원이 200명이어도 UPDATE 대상은 1행이다. 직원 목록 조회 시 부서명을 보려면 JOIN이 필요해지지만, dept_id에 인덱스가 걸려 있으면 조인 비용은 크지 않다.

    정규화 전후 UPDATE 대상 행 수 차이는 데이터 규모가 클수록 명확하다.

    -- 정규화 전: 직원 200명이 같은 부서면 200행 업데이트
UPDATE employees SET dept_name = '인프라팀' WHERE dept_id = 10;
-- Rows matched: 200  Changed: 200

-- 정규화 후: 1행만 업데이트
UPDATE departments SET dept_name = '인프라팀' WHERE dept_id = 10;
-- Rows matched: 1  Changed: 1

    비정규화 환경에서의 실무 패턴¶

    운영 중인 서비스에서는 정규화 원칙과 충돌하는 현실적인 이유로 비정규화 구조를 유지하는 경우가 있다. 조회 쿼리의 JOIN 비용이 실측으로 확인된 병목이거나, 레거시 구조를 당장 뜯기 어려운 상황이다. 이때 갱신 이상을 완전히 없애는 대신 관리 범위를 좁히는 방법을 쓴다.

    애플리케이션 레벨 동기화¶

    원본 데이터 변경 시 복사본도 함께 업데이트하는 로직을 서비스 레이어에 둔다. 단일 트랜잭션 안에서 처리해야 원자성이 보장된다.

    async updateProductName(productId: number, newName: string): Promise<void> {
  await this.dataSource.transaction(async (manager) => {
    await manager.update(Product, productId, { productName: newName });
    // 비정규화된 복사본 동기화
    await manager.update(
      OrderItem,
      { productId },
      { productName: newName },
    );
  });
}

    서비스 레이어가 여러 곳에 흩어져 있으면 누락 위험이 있다. 상품명 변경 로직이 관리자 API, 배치, 이벤트 핸들러 등 여러 경로에 있다면 한 경로에서 동기화 코드를 빠뜨렸을 때 불일치가 생긴다.

    DB 트리거¶

    원본 테이블 변경 시 트리거가 자동으로 복사본을 업데이트한다.

    CREATE TRIGGER sync_product_name
AFTER UPDATE ON products
FOR EACH ROW
BEGIN
    IF OLD.product_name != NEW.product_name THEN
        UPDATE order_items
        SET product_name = NEW.product_name
        WHERE product_id = NEW.product_id;
    END IF;
END;

    누락 위험은 없지만 트리거는 숨겨진 동작이라 디버깅이 어렵다. 특히 대량 배치로 products를 업데이트할 때 트리거가 건당 실행되면 order_items가 수백만 행인 경우 배치 시간이 수십 배 늘어나는 문제가 생긴다.

    -- products 100건 업데이트 → order_items에서 해당 상품 주문 100만 건 업데이트
-- 트리거가 건당 실행되므로 100번의 대량 UPDATE 발생
UPDATE products SET product_name = CONCAT(product_name, ' v2')
WHERE category = '전자기기';

    배치 업데이트 전후로 트리거를 비활성화하고 별도 동기화 쿼리를 실행하는 방법을 쓰기도 하는데, 그러면 중간 실패 시 불일치가 다시 생긴다.

    배치 재집계¶

    주기적으로 복사본을 원본 기준으로 재계산해서 덮어쓴다. 실시간 정합성이 필요 없고 어느 정도 지연을 허용할 수 있는 집계성 컬럼에 쓴다.

    -- 매시간 실행: products의 review_count, average_rating 재계산
UPDATE products p
JOIN (
    SELECT product_id,
           COUNT(*)            AS review_count,
           AVG(rating)         AS average_rating
    FROM reviews
    GROUP BY product_id
) r ON p.product_id = r.product_id
SET p.review_count    = r.review_count,
    p.average_rating  = r.average_rating;

    상품명 같은 마스터 데이터에는 적합하지 않다. 배치 주기 동안 갱신 이상이 존재하는 상태를 허용하는 방식이라 어떤 값을 보여도 되는 시간 범위를 팀이 합의해야 한다.

    갱신 이상을 감수하는 경우¶

    모든 비정규화가 문제는 아니다. 특정 상황에서는 갱신 이상을 설계 선택으로 인정한다.

    주문 테이블에 주문 당시 상품 단가와 고객 등급을 저장하는 경우가 대표적이다. 나중에 상품 가격이 올라도, 고객 등급이 내려가도, 주문 당시 상태를 그대로 보여줘야 하는 요구사항이 있다. 이 경우 orders에 unit_price와 customer_grade를 컬럼으로 두는 게 맞다. 현재 마스터 데이터와 다른 값이 orders에 저장되는 것은 정합성 오류가 아니라 이력 보존이다.

    CREATE TABLE orders (
    order_id       BIGINT PRIMARY KEY,
    customer_id    BIGINT NOT NULL,
    customer_grade VARCHAR(20) NOT NULL,  -- 주문 당시 등급 보존
    ordered_at     TIMESTAMP NOT NULL
);

CREATE TABLE order_items (
    order_id   BIGINT,
    product_id BIGINT,
    unit_price DECIMAL(10,2) NOT NULL,  -- 주문 당시 단가 보존
    quantity   INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);

    이 경우 customers.grade가 바뀐다고 orders.customer_grade를 동기화하면 안 된다. 이력 데이터가 오염된다. 갱신 이상처럼 보이지만 의도된 구조다.

    갱신 이상 탐지¶

    운영 중인 DB에서 갱신 이상이 실제로 발생했는지 확인하는 쿼리다. 같은 키 값에 대해 다른 값이 존재하면 불일치 상태다.

    -- 같은 product_id인데 product_name이 다른 행이 있는지 확인
SELECT product_id, COUNT(DISTINCT product_name) AS name_count
FROM order_items
GROUP BY product_id
HAVING COUNT(DISTINCT product_name) > 1;

    이 쿼리 결과가 나온다면 갱신 이상이 실제로 발생한 것이다. 어떤 값이 맞는지는 products 테이블의 현재값을 기준으로 판단하거나, 변경 이력 테이블이 있다면 그 시점의 값을 확인해야 한다.

    불일치 행이 많지 않으면 직접 보정하고, 이 쿼리를 모니터링 쿼리로 등록해서 주기적으로 실행하면 갱신 이상이 누적되는 것을 조기에 발견할 수 있다.
