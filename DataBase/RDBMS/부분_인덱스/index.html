    부분 인덱스¶

    부분 인덱스(partial index)는 테이블 전체가 아닌 조건을 만족하는 행에만 인덱스를 구성하는 방식이다. WHERE 절로 인덱스 범위를 좁히기 때문에 인덱스 자체 크기가 줄고, 쓰기 시 갱신 대상 행도 적어진다.

    PostgreSQL은 CREATE INDEX ... WHERE 구문으로 지원한다. MySQL은 부분 인덱스를 지원하지 않는다.

    기본 문법¶

    -- PostgreSQL
CREATE INDEX idx_orders_pending
    ON orders (created_at)
    WHERE status = 'PENDING';

    이 인덱스는 status = 'PENDING'인 행만 포함한다. 나머지 상태의 행은 인덱스 자체에 없다.

    옵티마이저가 이 인덱스를 타려면 쿼리의 WHERE 절에 인덱스 조건이 포함되어야 한다.

    -- 인덱스 사용됨
SELECT * FROM orders WHERE status = 'PENDING' AND created_at > '2026-01-01';

-- 인덱스 사용 안 됨 (status 조건 없음)
SELECT * FROM orders WHERE created_at > '2026-01-01';

    실사용 패턴¶

    소프트 삭제 필터¶

    소프트 삭제 구조에서 deleted_at IS NULL 조건이 대부분의 쿼리에 붙는다. 이 경우 삭제된 레코드를 인덱스에서 제외하면 인덱스 크기가 크게 줄어든다.

    CREATE INDEX idx_users_active
    ON users (email)
    WHERE deleted_at IS NULL;

    삭제 비율이 30% 이상인 테이블에서 이 패턴의 효과가 크다. 운영 6개월이 지난 서비스라면 전체 레코드 중 삭제 처리된 비율을 먼저 확인해라.

    SELECT
    COUNT(*) FILTER (WHERE deleted_at IS NOT NULL) AS deleted,
    COUNT(*) AS total,
    ROUND(COUNT(*) FILTER (WHERE deleted_at IS NOT NULL) * 100.0 / COUNT(*), 1) AS pct
FROM users;

    삭제 비율이 낮다면(5% 미만) 인덱스 크기 절감 효과가 미미하다.

    상태 컬럼 조건¶

    전체 레코드 중 특정 상태의 비율이 작은 경우 유효하다. 주문 테이블에서 status = 'PENDING'인 행이 전체의 2~5%라면, 해당 상태만 색인하는 인덱스가 훨씬 가볍다.

    CREATE INDEX idx_jobs_waiting
    ON background_jobs (scheduled_at)
    WHERE status = 'WAITING';

CREATE INDEX idx_jobs_failed
    ON background_jobs (failed_at)
    WHERE status = 'FAILED';

    배치 처리 대기열, 재시도 큐 같은 구조에서 자주 쓴다. 처리 완료된 레코드는 인덱스에 포함할 필요가 없다.

    반대로, status = 'DONE'처럼 대다수 행이 해당하는 조건으로 부분 인덱스를 만들면 오히려 손해다. 인덱스 크기는 줄지 않고 관리 비용만 는다.

    NULL 제외¶

    NULL이 포함된 컬럼에 인덱스를 걸면 NULL 값도 색인에 포함된다. 비즈니스 로직상 NULL인 행을 조회할 일이 없다면 제외한다.

    -- phone 컬럼이 NULL인 유저는 조회 대상에서 빠지는 경우
CREATE INDEX idx_users_phone
    ON users (phone)
    WHERE phone IS NOT NULL;

    NULL을 제외하면 UNIQUE 부분 인덱스와 조합해서 의미 있는 중복 방지도 구현할 수 있다. 동일 이메일을 가진 활성 유저는 한 명만 허용하되, 탈퇴 유저는 중복 허용하는 경우가 대표적이다.

    CREATE UNIQUE INDEX idx_users_email_active
    ON users (email)
    WHERE deleted_at IS NULL;

    인덱스 크기와 성능 실측¶

    아래는 1,000만 건 테이블(소프트 삭제 비율 40%)에서 비교한 수치다.

    -- 인덱스 크기 확인
SELECT
    indexname,
    pg_size_pretty(pg_relation_size(indexname::text)) AS index_size
FROM pg_indexes
WHERE tablename = 'orders';
    인덱스 종류 대상 행 크기
    전체 인덱스 (email) 10,000,000 412 MB
    부분 인덱스 (deleted_at IS NULL) 6,000,000 248 MB

    쓰기 쪽 영향도 있다. 삭제 처리(UPDATE ... SET deleted_at = now())가 발생하면 전체 인덱스는 해당 행의 인덱스 엔트리를 갱신하지만, deleted_at IS NULL 부분 인덱스는 해당 행이 조건에서 벗어나므로 인덱스에서 제거만 한다. 처리 경로가 다르다.

    INSERT는 deleted_at IS NULL 인 새 행이 들어오면 부분 인덱스에도 추가된다. 처음부터 deleted_at이 있는 행(논리적으로는 없겠지만)이 들어오면 부분 인덱스 대상에서 제외된다.

    옵티마이저가 부분 인덱스를 타는 조건¶

    쿼리가 부분 인덱스를 쓰려면 옵티마이저가 인덱스 조건을 쿼리 조건의 부분집합으로 판단해야 한다. PostgreSQL은 이 판단을 구문 수준에서 한다.

    -- 인덱스 조건: deleted_at IS NULL
-- 아래 쿼리는 인덱스 사용 가능
SELECT * FROM users WHERE deleted_at IS NULL AND email = 'test@example.com';

-- 아래 쿼리는 인덱스 사용 불가
-- 옵티마이저가 "deleted_at IS NULL" 조건을 쿼리에서 명시적으로 못 찾음
SELECT * FROM users WHERE email = 'test@example.com';

    애플리케이션에서 항상 deleted_at IS NULL을 붙이는 구조라면 문제없다. TypeORM, Hibernate 같은 ORM에서 소프트 삭제 플러그인이 WHERE 절을 자동으로 추가하는 방식이 이 조건을 만족한다.

    -- status 인덱스 조건이 리터럴로 정확히 일치해야 함
CREATE INDEX idx_jobs_waiting ON background_jobs (scheduled_at) WHERE status = 'WAITING';

-- 사용됨
SELECT * FROM background_jobs WHERE status = 'WAITING' AND scheduled_at < now();

-- 사용 안 됨: status를 파라미터로 넘기는 경우
-- (파라미터 바인딩 시점에 옵티마이저가 값을 모름)
SELECT * FROM background_jobs WHERE status = $1 AND scheduled_at < now();
-- $1 = 'WAITING' 이더라도 부분 인덱스를 타지 않는다

    파라미터 바인딩은 대부분의 ORM과 prepared statement에서 기본 동작이다. 실무에서 부분 인덱스가 타지 않는 가장 흔한 원인이다.

    EXPLAIN 으로 확인하면 바로 보인다.

    EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM background_jobs WHERE status = 'WAITING' AND scheduled_at < now();

    출력에 Index Scan using idx_jobs_waiting이 나오면 타는 것이고, Seq Scan이나 다른 인덱스가 나오면 타지 않는 것이다.

    MySQL 미지원과 대안¶

    MySQL은 부분 인덱스를 지원하지 않는다. 조건 기반으로 인덱스 범위를 제한하는 기능 자체가 없다.

    대신 함수 기반 인덱스(MySQL 8.0.13+)로 비슷한 효과를 낼 수 있다.

    -- MySQL: 가상 컬럼 + 인덱스
ALTER TABLE users
    ADD COLUMN is_active TINYINT GENERATED ALWAYS AS (
        IF(deleted_at IS NULL, 1, NULL)
    ) STORED;

CREATE INDEX idx_users_active_email ON users (is_active, email);

    이 방식은 is_active = 1 조건을 명시해야 인덱스를 탄다. NULL 값은 인덱스에서 제외되는 MySQL의 동작을 이용한 것이다. PostgreSQL의 부분 인덱스와 완전히 같지는 않고, 테이블에 컬럼을 추가해야 한다는 차이가 있다.

    또 다른 대안은 인덱스 자체보다 파티셔닝으로 물리 분리하는 방식이다. 상태 기반으로 파티션을 나누면 각 파티션에 인덱스가 별도로 생기므로 부분 인덱스와 비슷한 효과를 얻는다. 단, 파티셔닝은 스키마 변경 비용이 크다.

    운영 중 CONCURRENTLY 생성 시 주의사항¶

    운영 중인 테이블에 인덱스를 생성할 때 CONCURRENTLY 없이 실행하면 테이블에 공유 잠금이 걸린다. 인덱스 생성이 끝날 때까지 쓰기가 블로킹된다.

    -- 위험: 테이블 잠금 발생
CREATE INDEX idx_orders_pending ON orders (created_at) WHERE status = 'PENDING';

-- 안전: 잠금 없이 생성
CREATE INDEX CONCURRENTLY idx_orders_pending ON orders (created_at) WHERE status = 'PENDING';

    CONCURRENTLY는 인덱스 생성 중에도 INSERT, UPDATE, DELETE가 가능하다. 대신 생성 시간이 일반 방식보다 길고, 두 번의 테이블 스캔이 발생한다.

    주의해야 할 상황이 몇 가지 있다.

    트랜잭션 안에서 실행 불가. CONCURRENTLY는 트랜잭션 블록 안에서 실행할 수 없다. BEGIN ... COMMIT 없이 단독으로 실행해야 한다.

    -- 에러 발생
BEGIN;
CREATE INDEX CONCURRENTLY idx_test ON test_table (col);
COMMIT;

    실패 시 INVALID 상태. 생성 중 오류가 나거나 프로세스가 죽으면 인덱스가 INVALID 상태로 남는다. 이 인덱스는 쿼리에 사용되지 않지만 쓰기 시에는 갱신된다. 삭제하고 다시 만들어야 한다.

    -- INVALID 인덱스 확인
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders'
  AND pg_index.indisvalid = false
JOIN pg_class ON pg_class.relname = indexname
JOIN pg_index ON pg_index.indexrelid = pg_class.oid;

-- 더 간단한 방법
SELECT schemaname, tablename, indexname
FROM pg_indexes
WHERE tablename = 'orders'
  AND indexname IN (
    SELECT relname FROM pg_class
    JOIN pg_index ON indexrelid = pg_class.oid
    WHERE NOT indisvalid
  );

    vacuum autovacuum과 충돌. 인덱스 생성 중 autovacuum이 같은 테이블을 처리하면 생성이 지연될 수 있다. 트래픽이 낮은 시간대에 실행하는 게 낫다.

    진행 상황 모니터링. 큰 테이블에서 CONCURRENTLY 생성은 수십 분이 걸리기도 한다. 진행 상황은 pg_stat_progress_create_index에서 확인한다.

    SELECT
    phase,
    blocks_done,
    blocks_total,
    ROUND(blocks_done * 100.0 / NULLIF(blocks_total, 0), 1) AS pct
FROM pg_stat_progress_create_index
WHERE relid = 'orders'::regclass;

    주의사항 정리¶

    부분 인덱스를 남용하면 관리 부담이 커진다. 인덱스가 많아질수록 쓰기 성능은 떨어지고, 인덱스마다 조건이 다르면 어떤 쿼리가 어떤 인덱스를 쓰는지 파악하기 어려워진다.

    부분 인덱스가 적합한 상황은 세 가지로 좁힐 수 있다.

    • 특정 조건의 행만 반복적으로 조회하고, 해당 행이 전체의 10~20% 이하일 때
    • 소프트 삭제처럼 조건이 고정적이고 쿼리마다 동일하게 붙을 때
    • 인덱스 크기가 디스크나 메모리에 부담이 될 정도로 클 때

    조건이 자주 바뀌거나 파라미터로 동적으로 결정되는 경우라면 부분 인덱스는 맞지 않는다. 전체 인덱스에 복합 컬럼을 추가하는 방식이 낫다.
