    비정규화¶

    비정규화(Denormalization)는 정규화를 되돌리는 게 아니다. 정규화된 구조를 유지하면서, 조회 성능을 위해 의도적으로 중복 데이터를 추가하는 작업이다. 차이가 중요하다. 처음부터 비정규화된 구조를 만들면 이상 현상에 그대로 노출된다. 정규화 후 성능 문제를 실측하고, 필요한 지점만 선택적으로 비정규화해야 동기화 부담을 통제할 수 있다.

    실무에서 흔한 실수는 두 가지다. "JOIN이 여러 개니까 느릴 것 같다"는 추측으로 비정규화하는 것, 그리고 동기화 방법을 설계하지 않은 채 컬럼을 복사하는 것. 전자는 없는 문제를 만드는 것이고 후자는 데이터 불일치를 예약하는 것이다.

    EXPLAIN으로 병목 실증하기¶

    비정규화 전에 병목이 실제로 어디에 있는지 확인해야 한다. 슬로우 쿼리 로그에서 쿼리를 발견하고 나면 EXPLAIN으로 실행 계획을 들여다본다.

    MySQL에서 주문 목록 조회 쿼리를 예로 보자.

    EXPLAIN SELECT
    o.order_id,
    c.customer_name,
    c.customer_grade,
    p.product_name,
    oi.quantity,
    oi.unit_price
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id
WHERE o.ordered_at >= '2026-01-01'
ORDER BY o.ordered_at DESC
LIMIT 50;

    문제 있는 실행 계획에서는 이런 결과가 나온다.

    +----+-------------+-------+------+---------------+------+---------+------+----------+-----------------------------+
| id | select_type | table | type | possible_keys | key  | key_len | rows | filtered | Extra                       |
+----+-------------+-------+------+---------------+------+---------+------+----------+-----------------------------+
|  1 | SIMPLE      | o     | ALL  | NULL          | NULL | NULL    | 8M   |    12.50 | Using where; Using filesort |
|  1 | SIMPLE      | c     | eq_ref | PRIMARY     | PRIMARY | 8    |   1  |   100.00 |                             |
|  1 | SIMPLE      | oi    | ref  | order_id_idx  | order_id_idx | 8 | 3 |  100.00 |                             |
|  1 | SIMPLE      | p     | eq_ref | PRIMARY     | PRIMARY | 8    |   1  |   100.00 |                             |
+----+-------------+-------+------+---------------+------+---------+------+----------+-----------------------------+

    orders 테이블에서 type: ALL이 나왔다. 800만 건 풀 스캔이다. ordered_at에 인덱스가 없어서 생긴 문제다. 비정규화가 필요한 상황이 아니라 인덱스 누락이다.

    CREATE INDEX idx_orders_ordered_at ON orders(ordered_at);

    인덱스 하나로 해결되는 경우가 많다. JOIN 자체는 문제가 아닌데 JOIN을 원인으로 지목하는 실수가 자주 나온다.

    PostgreSQL에서는 EXPLAIN ANALYZE로 실제 실행 시간까지 측정한다.

    EXPLAIN (ANALYZE, BUFFERS) SELECT
    o.order_id,
    c.customer_name,
    ...
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
...;

    출력에서 봐야 할 항목:

    • Seq Scan: 테이블 풀 스캔. 인덱스가 없거나 쿼리 플래너가 인덱스를 포기한 것이다
    • actual time: 계획 시간과 실제 시간의 차이가 크면 통계가 오래됐을 수 있다
    • rows=10000 (actual rows=850000): 예측 행 수와 실제 행 수 차이. 차이가 크면 ANALYZE로 통계를 갱신해야 한다
    • Buffers: hit=15000 read=8000: hit가 적고 read가 많으면 캐시 미스가 많은 것이다

    진짜 JOIN 비용이 병목임이 확인된 상황:

    • 인덱스가 모두 있는데도 집계 쿼리가 수초
    • 실시간 대시보드에서 같은 집계 쿼리를 초당 수십 번 실행
    • 수천만 건 테이블을 GROUP BY와 함께 여러 번 JOIN

    이 세 조건 중 하나 이상이 맞으면 비정규화를 검토한다.

    패턴별 선택 기준¶

    컬럼 추가¶

    JOIN 대상 테이블에서 자주 읽지만 거의 변경되지 않는 컬럼을 복사하는 방법이다.

    적합한 경우:

    • 조회 빈도가 높고 변경 빈도가 낮은 컬럼
    • 조인 대상 테이블에 단일 컬럼만 필요한 경우
    • 변경 시 동기화 경로가 단일한 경우

    주문 목록에서 고객명을 매번 customers 테이블과 JOIN해서 읽는 상황이라고 하자. 고객명 변경은 드물고 주문 조회는 초당 수천 번이다.

    ALTER TABLE orders ADD COLUMN customer_name VARCHAR(50);

-- 기존 데이터 백필
UPDATE orders o
JOIN customers c ON o.customer_id = c.customer_id
SET o.customer_name = c.customer_name;

    동기화는 서비스 레이어에서 트랜잭션으로 묶어야 한다.

    async updateCustomerName(customerId: number, newName: string): Promise<void> {
    await this.dataSource.transaction(async (manager) => {
        await manager.update(Customer, customerId, { name: newName });
        // 비정규화 컬럼 동기화
        await manager.update(Order, { customerId }, { customerName: newName });
    });
}

    트랜잭션 밖에서 처리하면 고객명은 바뀌고 주문 테이블은 그대로인 상태가 생긴다.

    주의사항:

    주문 당시 고객명을 이력으로 보존해야 하는 경우와 현재 고객명을 동기화해야 하는 경우를 구분해야 한다. 고객명이 바뀔 때 주문 테이블도 업데이트하면 과거 주문 내역의 고객명이 바뀐다. 영수증에서 주문 당시 이름을 보여줘야 한다면 동기화하면 안 된다. 반대로 항상 최신 이름을 보여야 한다면 동기화해야 한다. 어느 쪽인지를 먼저 결정하고 설계해야 한다.

    집계 컬럼도 컬럼 추가의 일종이다. 상품 리뷰 수와 평균 별점을 매번 집계하면 느린 경우다.

    ALTER TABLE products ADD COLUMN review_count INT NOT NULL DEFAULT 0;
ALTER TABLE products ADD COLUMN avg_rating DECIMAL(3,2);

    리뷰 등록/삭제 시 함께 갱신한다.

    async addReview(productId: number, req: ReviewCreateRequest): Promise<void> {
    await this.dataSource.transaction(async (manager) => {
        await manager.save(Review, { productId, ...req });
        await this.productRepository.incrementReviewStats(productId, req.rating);
    });
}

    UPDATE products
SET review_count = review_count + 1,
    avg_rating = (avg_rating * review_count + :newRating) / (review_count + 1)
WHERE product_id = :productId;

    리뷰 삭제 시 역산이 필요한데, 평균 별점의 역산은 오차가 생길 수 있다. 정밀도가 중요하면 삭제 시마다 재집계하거나 배치로 주기적으로 덮어쓰는 방법을 택한다.

    요약 테이블 (Summary Table)¶

    집계 결과를 별도 테이블에 저장하고, 배치로 주기적으로 갱신하는 방법이다.

    적합한 경우:

    • 복잡한 집계 쿼리가 자주 실행되는 경우
    • 어느 정도 지연을 허용할 수 있는 집계 (일별 매출, 주간 통계 등)
    • 원본 테이블이 너무 커서 집계 자체가 오래 걸리는 경우
    CREATE TABLE daily_sales_summary (
    summary_date  DATE         NOT NULL,
    product_id    BIGINT       NOT NULL,
    order_count   INT          NOT NULL DEFAULT 0,
    total_qty     INT          NOT NULL DEFAULT 0,
    total_revenue DECIMAL(15,2) NOT NULL DEFAULT 0,
    refreshed_at  TIMESTAMP    NOT NULL,
    PRIMARY KEY (summary_date, product_id)
);

    배치 갱신 쿼리:

    INSERT INTO daily_sales_summary
    (summary_date, product_id, order_count, total_qty, total_revenue, refreshed_at)
SELECT
    DATE(o.ordered_at),
    oi.product_id,
    COUNT(DISTINCT o.order_id),
    SUM(oi.quantity),
    SUM(oi.unit_price * oi.quantity),
    NOW()
FROM orders o
JOIN order_items oi ON o.order_id = oi.order_id
WHERE DATE(o.ordered_at) = CURDATE() - INTERVAL 1 DAY
GROUP BY DATE(o.ordered_at), oi.product_id
ON DUPLICATE KEY UPDATE
    order_count   = VALUES(order_count),
    total_qty     = VALUES(total_qty),
    total_revenue = VALUES(total_revenue),
    refreshed_at  = NOW();

    주의사항:

    배치가 실패하면 어제 또는 그 이전 데이터가 그대로 노출된다. refreshed_at을 별도로 노출하거나, 배치 실패 시 알림을 보내는 모니터링이 필요하다. 데이터 신선도를 UI에서 보여주는 방법도 있다 ("마지막 업데이트: 1시간 전").

    당일 집계는 배치 주기마다 달라진다. 대시보드에서 당일 실시간 수치가 필요하다면 당일 데이터는 원본 테이블에서 직접 집계하고, 과거 데이터는 요약 테이블에서 읽는 이중 구조를 쓴다.

    테이블 병합¶

    1:1 관계 테이블을 하나로 합치는 방법이다.

    적합한 경우:

    • 항상 함께 조회되는 1:1 관계
    • 두 테이블이 같은 생명주기를 가지는 경우 (하나가 존재하면 다른 하나도 항상 존재)
    • 테이블 분리의 원인이 정규화보다 초기 설계 관행이었던 경우
    -- 분리된 구조
-- users: user_id, email, name, created_at
-- user_settings: user_id(FK), theme, language, notification_enabled

-- 항상 함께 쓰인다면
ALTER TABLE users
    ADD COLUMN theme VARCHAR(20) NOT NULL DEFAULT 'light',
    ADD COLUMN language VARCHAR(10) NOT NULL DEFAULT 'ko',
    ADD COLUMN notification_enabled BOOLEAN NOT NULL DEFAULT TRUE;

-- user_settings 테이블 제거
DROP TABLE user_settings;

    주의사항:

    한쪽 테이블이 NULL을 많이 가질 수 있는 경우에는 병합을 재고해야 한다. user_profiles 테이블에 SNS 연동, 프리미엄 사용자 전용 컬럼이 섞여 있다면 병합하면 일반 사용자 행에 NULL이 가득 찬다.

    병합 후 테이블이 너무 넓어지면 (컬럼이 50개 이상) 오히려 페이지 크기 초과로 I/O가 늘어날 수 있다. InnoDB에서 행 크기가 페이지 크기(기본 16KB)를 초과하면 오버플로우 페이지를 사용하게 되어 성능이 나빠진다.

    Materialized View¶

    복잡한 JOIN과 집계를 미리 계산해서 저장해두는 방법이다.

    PostgreSQL:

    CREATE MATERIALIZED VIEW product_sales_summary AS
SELECT
    p.product_id,
    p.product_name,
    c.category_name,
    COUNT(oi.order_id)          AS order_count,
    SUM(oi.quantity)            AS total_qty,
    SUM(oi.unit_price * oi.quantity) AS total_revenue,
    AVG(r.rating)               AS avg_rating
FROM products p
JOIN categories c ON p.category_id = c.category_id
LEFT JOIN order_items oi ON p.product_id = oi.product_id
LEFT JOIN reviews r ON p.product_id = r.product_id
GROUP BY p.product_id, p.product_name, c.category_name;

CREATE UNIQUE INDEX ON product_sales_summary(product_id);

    갱신은 명시적으로 실행해야 한다.

    -- CONCURRENTLY: 갱신 중에도 조회 가능, 단 UNIQUE INDEX 필요
REFRESH MATERIALIZED VIEW CONCURRENTLY product_sales_summary;

    CONCURRENTLY 없이 REFRESH하면 뷰 전체에 락이 걸려 갱신 동안 조회가 블로킹된다. 운영 환경에서는 반드시 CONCURRENTLY를 쓰고, 이를 위해 UNIQUE INDEX가 필요하다.

    MySQL에는 Materialized View가 없다. 별도 테이블을 만들고 배치나 이벤트 스케줄러로 갱신하는 방식을 쓴다.

    -- MySQL: 별도 테이블로 구현
CREATE TABLE product_sales_mv (
    product_id    BIGINT       NOT NULL PRIMARY KEY,
    product_name  VARCHAR(100) NOT NULL,
    category_name VARCHAR(50),
    order_count   INT          NOT NULL DEFAULT 0,
    total_qty     INT          NOT NULL DEFAULT 0,
    total_revenue DECIMAL(15,2) NOT NULL DEFAULT 0,
    avg_rating    DECIMAL(3,2),
    refreshed_at  TIMESTAMP    NOT NULL
);

-- MySQL 이벤트 스케줄러로 매 시간 갱신
CREATE EVENT refresh_product_sales_mv
ON SCHEDULE EVERY 1 HOUR
DO
  INSERT INTO product_sales_mv (product_id, product_name, ...)
  SELECT p.product_id, p.product_name, ...
  FROM products p
  ...
  ON DUPLICATE KEY UPDATE
    order_count   = VALUES(order_count),
    refreshed_at  = NOW();

    적합한 경우:

    • 다수 테이블을 JOIN하는 복잡한 집계가 대시보드나 리포트에서 반복 실행되는 경우
    • 집계 결과가 수 분~수 시간 단위로 갱신해도 충분한 경우
    • 원본 테이블이 INSERT/UPDATE 위주이고 SELECT가 많지 않은 경우

    실시간 재고 수량이나 결제 금액처럼 정확성이 즉각 반영돼야 하는 데이터에는 쓰지 않는다.

    동기화 장애 시나리오¶

    비정규화의 핵심 리스크는 동기화 실패다. 실무에서 자주 마주치는 장애 패턴들이다.

    다중 진입점에서의 누락¶

    상품명을 비정규화해서 order_items.product_name을 저장해뒀다. 상품명 변경 로직이 관리자 API, 자동 배치, 외부 연동 이벤트 세 경로에 있다. 관리자 API와 배치에는 동기화 코드가 있는데 외부 연동 이벤트 핸들러에 빠졌다.

    // 관리자 API - 동기화 있음
async adminUpdateProduct(productId: number, req: ProductUpdateRequest): Promise<void> {
    await this.dataSource.transaction(async (manager) => {
        await manager.update(Product, productId, { name: req.name });
        await manager.update(OrderItem, { productId }, { productName: req.name }); // OK
    });
}

// 외부 연동 이벤트 핸들러 - 동기화 누락
async onProductSyncEvent(event: ProductSyncEvent): Promise<void> {
    await this.productRepository.updateName(event.productId, event.name);
    // orderItemRepository.updateProductName() 빠짐
}

    이 경우 외부 시스템에서 상품명이 바뀌면 products.product_name은 바뀌고 order_items.product_name은 구버전 그대로 남는다. 발견도 늦다. 조회 화면에서 같은 상품인데 목록과 상세에서 이름이 다르게 보이는 버그로 이어진다.

    해결 방법은 동기화 로직을 단일 진입점으로 모으는 것이다. 도메인 이벤트나 메시지 큐를 통해 상품명 변경 이벤트를 발행하고, 비정규화 컬럼 갱신은 구독자 하나에서만 처리한다.

    배치 부분 실패¶

    집계 컬럼을 매일 새벽 배치로 갱신하는 구조다. 배치가 상품 100만 건 중 60만 건을 처리하고 서버가 재시작됐다. 나머지 40만 건의 집계값은 어제 배치가 갱신한 값 그대로다.

    배치를 멱등(Idempotent)하게 설계하면 재실행으로 복구된다. 문제는 배치 실패를 모르거나, 재실행 없이 넘어가는 경우다.

    -- 멱등한 배치: 실행할 때마다 같은 결과
INSERT INTO daily_sales_summary (summary_date, product_id, ...)
SELECT DATE(ordered_at), product_id, ...
FROM orders
WHERE DATE(ordered_at) = :targetDate
GROUP BY DATE(ordered_at), product_id
ON DUPLICATE KEY UPDATE
    order_count = VALUES(order_count),
    refreshed_at = NOW();

    refreshed_at 컬럼으로 어느 데이터가 오래된 집계값인지 탐지할 수 있다.

    -- 24시간 이상 갱신되지 않은 요약 데이터
SELECT summary_date, COUNT(*) AS stale_count
FROM daily_sales_summary
WHERE refreshed_at < NOW() - INTERVAL 24 HOUR
GROUP BY summary_date;

    Materialized View 갱신 중 블로킹¶

    PostgreSQL에서 REFRESH MATERIALIZED VIEW (CONCURRENTLY 없이) 실행하면 뷰 전체에 ExclusiveLock이 걸린다. 갱신에 5분이 걸리면 그 동안 뷰를 조회하는 모든 쿼리가 대기한다.

    -- 위험: 갱신 중 전체 블로킹
REFRESH MATERIALIZED VIEW product_sales_summary;

-- 안전: 갱신 중에도 조회 가능 (UNIQUE INDEX 필요)
REFRESH MATERIALIZED VIEW CONCURRENTLY product_sales_summary;

    CONCURRENTLY도 완전히 무결하진 않다. 갱신 완료 전까지는 이전 데이터를 읽는다. 갱신 주기보다 자주 데이터가 바뀌면 항상 오래된 데이터를 보는 상태가 된다.

    트리거로 인한 배치 지연¶

    products 테이블 변경 시 order_items의 비정규화 컬럼을 갱신하는 트리거가 걸려 있다. 카테고리 전체 상품의 이름에 접미사를 붙이는 배치를 돌렸다.

    -- 상품 5만 건 업데이트
UPDATE products
SET product_name = CONCAT(product_name, ' (리뉴얼)')
WHERE category_id = 10;

    트리거가 건당 실행된다. 5만 건 상품 각각에 대해 order_items에서 해당 product_id 행을 찾아 업데이트한다. 상품당 주문 건이 평균 200개면 1,000만 번의 UPDATE가 발생한다. 배치가 예상 시간 3분에서 실제 2시간으로 늘어나는 원인이 이것이다.

    대량 배치 전에 트리거를 비활성화하고 배치 완료 후 일괄 동기화하는 방법을 쓰는데, 그 사이에 장애가 나면 불일치가 생긴다. 트리거 기반 비정규화는 단건 업데이트에는 안전하지만 배치에는 취약하다.

    불일치 탐지 쿼리¶

    비정규화한 컬럼과 원본 사이에 불일치가 생겼는지 확인하는 쿼리를 주기적으로 실행하면 조기에 발견할 수 있다.

    파생 컬럼 vs 원본 비교¶

    -- orders.customer_name과 customers.customer_name 불일치 확인
SELECT o.order_id, o.customer_id,
       o.customer_name AS cached_name,
       c.customer_name AS actual_name
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
WHERE o.customer_name != c.customer_name
LIMIT 100;

    이 쿼리 결과가 나오면 동기화 누락이다. 결과 건수가 많으면 특정 변경 경로에서 동기화가 빠진 것이다.

    집계 컬럼 vs 실제 집계 비교¶

    -- products.review_count와 실제 reviews 건수 불일치
SELECT p.product_id,
       p.review_count        AS cached_count,
       COUNT(r.review_id)    AS actual_count,
       p.review_count - COUNT(r.review_id) AS diff
FROM products p
LEFT JOIN reviews r ON p.product_id = r.product_id
GROUP BY p.product_id, p.review_count
HAVING ABS(p.review_count - COUNT(r.review_id)) > 0
ORDER BY ABS(diff) DESC
LIMIT 50;

    diff가 양수면 실제보다 많이 집계됐고, 음수면 적게 집계됐다. 음수가 나오면 리뷰 등록 시 동기화 누락, 양수가 나오면 삭제 시 동기화 누락이다.

    요약 테이블 신선도 확인¶

    -- daily_sales_summary에서 오늘 기준 48시간 이상 갱신 안 된 레코드
SELECT summary_date,
       MIN(refreshed_at) AS oldest_refresh,
       MAX(refreshed_at) AS latest_refresh,
       COUNT(*)          AS product_count
FROM daily_sales_summary
WHERE summary_date >= CURDATE() - INTERVAL 7 DAY
GROUP BY summary_date
HAVING MIN(refreshed_at) < NOW() - INTERVAL 48 HOUR
ORDER BY summary_date DESC;

    불일치 자동 복구¶

    탐지 쿼리를 모니터링 시스템에 등록하고, 불일치 건수가 임계값을 넘으면 알림을 보내는 구조가 기본이다. 더 나아가 탐지 후 자동 복구 배치를 돌리는 방법도 있다.

    -- review_count 불일치 자동 복구
UPDATE products p
JOIN (
    SELECT product_id, COUNT(*) AS cnt
    FROM reviews
    GROUP BY product_id
) r ON p.product_id = r.product_id
SET p.review_count = r.cnt
WHERE p.review_count != r.cnt;

    자동 복구를 걸어두면 불일치가 생겨도 배치 주기 내에 수습된다. 하지만 근본 원인(동기화 누락 경로)은 별도로 찾아 고쳐야 한다. 자동 복구가 있다고 동기화 버그를 방치하면 복구 배치가 DB 부하를 지속적으로 유발한다.

    비정규화 안티패턴¶

    EXPLAIN 없이 비정규화¶

    JOIN이 느릴 것 같다는 직관으로 컬럼을 복사하는 것이다. 실제 병목은 인덱스 누락이거나 쿼리 자체의 문제인 경우가 많다. 비정규화는 쓰기 비용을 올리고 동기화 책임을 생성하는데, 읽기 성능이 개선되지도 않으면서 이 비용만 지는 상황이 된다.

    자주 바뀌는 값 복사¶

    재고 수량, 현재 가격, 실시간으로 변하는 상태값을 여러 테이블에 복사해두는 것이다. 변경이 잦은 값일수록 동기화 실패 확률이 올라간다. 재고가 수십 곳에 복사돼 있으면 초과 판매가 발생하거나 재고 현황 조회가 항상 틀린 값을 보여준다.

    실시간 재고는 한 곳에서만 관리한다. 다른 곳에서 필요하면 JOIN하거나 조회 시 계산한다.

    동기화 방법 없이 컬럼 추가¶

    "지금은 일단 컬럼만 추가하고 동기화는 나중에"라는 방식이다. 나중은 오지 않는다. 컬럼을 추가할 때 동기화 코드와 탐지 쿼리까지 같이 붙여야 한다. 동기화가 없는 비정규화 컬럼은 시간이 지날수록 원본과 멀어진다.

    캐싱으로 해결할 수 있는 문제를 비정규화로 해결¶

    조회 결과를 Redis에 캐싱하면 DB 비정규화 없이 읽기 성능을 올릴 수 있다. 특히 집계 결과처럼 계산 비용은 높지만 원본 데이터가 자주 바뀌지 않는 경우에 적합하다.

    비정규화는 DB 스키마 변경을 수반하고 동기화 책임이 남는다. 캐싱은 캐시 만료와 무효화를 관리해야 하지만 스키마 변경이 없다. 둘 다 정합성 문제가 있지만 비정규화의 정합성 문제는 영속적이고, 캐싱의 정합성 문제는 일시적이다.

    읽기 부하가 문제라면 캐싱을 먼저 검토하고, 쓰기/읽기가 섞인 상황에서 집계 정확도가 중요하다면 비정규화를 검토한다.

    비정규화 결정을 개발자 개인이 하는 것¶

    비정규화는 정합성 보장 책임을 코드로 가져오는 것이다. 팀이 알아야 하고, 어떤 컬럼이 비정규화된 것인지, 동기화 경로가 어디인지, 탐지 쿼리가 있는지를 문서나 코드 주석으로 남겨야 한다. 6개월 뒤 다른 사람이 그 테이블을 수정할 때 비정규화 컬럼을 모르고 동기화 코드를 빠뜨리는 것이 가장 흔한 후속 장애다.
