    복합 인덱스 선두 컬럼¶

    복합 인덱스(composite index)는 여러 컬럼을 하나의 인덱스로 묶는다. B-Tree 구조상 왼쪽부터 순서대로 정렬되기 때문에, 어떤 컬럼을 앞에 두느냐에 따라 인덱스 활용 범위가 완전히 달라진다.

    좌측 선두 접두사 규칙¶

    (a, b, c) 순서로 인덱스를 만들면 옵티마이저가 이 인덱스를 쓸 수 있는 경우는 다음과 같다.

    • a 단독 조건
    • a + b 조건
    • a + b + c 조건

    b만 있거나 c만 있거나 b + c만 있는 쿼리는 이 인덱스를 타지 않는다. a가 없으면 인덱스 탐색 시작점 자체를 정할 수 없기 때문이다.

    CREATE INDEX idx_orders ON orders (status, user_id, created_at);

-- 인덱스 사용됨
SELECT * FROM orders WHERE status = 'PAID';
SELECT * FROM orders WHERE status = 'PAID' AND user_id = 123;
SELECT * FROM orders WHERE status = 'PAID' AND user_id = 123 AND created_at > '2026-01-01';

-- 인덱스 사용 안 됨 (선두 컬럼 없음)
SELECT * FROM orders WHERE user_id = 123;
SELECT * FROM orders WHERE user_id = 123 AND created_at > '2026-01-01';

    등치 조건과 범위 조건의 순서 원칙¶

    범위 조건(>, <, BETWEEN, LIKE 'x%')이 나오면 그 이후 컬럼은 인덱스를 통한 탐색에서 실질적으로 빠진다. 범위 조건 이후 컬럼들은 인덱스에서 걸러내는 게 아니라 스캔 중 필터링하는 수준으로만 쓰인다.

    CREATE INDEX idx_wrong ON orders (created_at, status, user_id);

-- created_at 범위 이후 status, user_id는 인덱스 범위 좁히기에 기여 못 함
SELECT * FROM orders
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31'
  AND status = 'PAID'
  AND user_id = 123;

    등치 조건을 먼저, 범위 조건을 나중에 배치해야 한다.

    CREATE INDEX idx_correct ON orders (status, user_id, created_at);

-- status, user_id 등치로 먼저 범위를 좁힌 뒤 created_at 범위 스캔
SELECT * FROM orders
WHERE status = 'PAID'
  AND user_id = 123
  AND created_at BETWEEN '2026-01-01' AND '2026-01-31';

    같은 데이터에 대해 인덱스 순서만 바꿨을 때 스캔 행 수가 10배 이상 차이나는 경우도 흔하다. EXPLAIN ANALYZE의 rows 수치로 확인할 수 있다.

    카디널리티와 쿼리 패턴 기준 순서 설계¶

    카디널리티(컬럼의 고유값 수)만 보고 무조건 높은 것을 앞에 두는 방식은 잘못된 접근이다. 카디널리티는 참고 지표일 뿐, 실제 쿼리 패턴이 우선이다.

    user_id 카디널리티가 아무리 높아도, 쿼리에서 항상 status가 먼저 나오는 패턴이라면 status를 선두에 둬야 한다.

    실무 결정 순서:

    1. 어떤 컬럼이 WHERE 절에서 등치 조건으로 가장 자주 나오는지 확인한다.
    2. 그 중 카디널리티가 높은 컬럼을 앞에 배치한다.
    3. 범위 조건은 마지막에 놓는다.
    4. ORDER BY, GROUP BY에 쓰이는 컬럼은 범위 조건 뒤라도 의미가 있다.
    -- 쿼리 패턴 분석 예시
-- 패턴 1: WHERE tenant_id = ? AND status = ? AND created_at > ?
-- 패턴 2: WHERE tenant_id = ? AND user_id = ?

-- tenant_id가 모든 쿼리에 등장 → 무조건 선두
-- status, user_id 중 더 자주 나오는 쪽을 두 번째
-- created_at은 범위 조건 → 마지막

CREATE INDEX idx_events ON events (tenant_id, status, created_at);
-- 패턴 2는 tenant_id + user_id 별도 인덱스가 필요할 수 있음

    잘못된 순서가 실제 플랜에 미치는 영향¶

    아래는 실제 EXPLAIN 결과에서 순서 차이가 드러나는 사례다.

    -- 테이블: 주문 1,000만 건
-- status 카디널리티: 5종 (DRAFT, PAID, SHIPPED, DELIVERED, CANCELED)
-- user_id 카디널리티: 100만
-- created_at: 날짜 범위

-- 잘못된 인덱스 순서
CREATE INDEX idx_bad ON orders (created_at, status, user_id);

EXPLAIN SELECT * FROM orders
WHERE created_at > '2026-07-01'
  AND status = 'PAID'
  AND user_id = 456;
-- type: range, rows: 500,000 (created_at 범위 전체 스캔)

-- 올바른 인덱스 순서
CREATE INDEX idx_good ON orders (status, user_id, created_at);

EXPLAIN SELECT * FROM orders
WHERE status = 'PAID'
  AND user_id = 456
  AND created_at > '2026-07-01';
-- type: range, rows: 12 (status + user_id로 좁힌 후 날짜 범위)

    rows 수치가 500,000 vs 12다. 인덱스 순서 하나가 이 차이를 만든다.

    MySQL 8.0 Index Skip Scan¶

    MySQL 8.0.13부터 Index Skip Scan이 도입됐다. 선두 컬럼 조건 없이도 특정 조건에서 복합 인덱스를 활용할 수 있게 됐다.

    동작 조건은 다음과 같다.

    • 선두 컬럼의 카디널리티가 낮아야 한다(수십~수백 개 수준).
    • 선두 이후 컬럼에 등치 또는 범위 조건이 있어야 한다.
    • 옵티마이저가 Skip Scan 비용이 풀 인덱스 스캔보다 낮다고 판단해야 한다.
    CREATE INDEX idx_events ON events (status, created_at);

-- status 조건 없이도 Skip Scan 가능 (status 카디널리티가 낮을 때)
SELECT * FROM events WHERE created_at > '2026-07-01';

    내부적으로는 status의 고유값을 순회하면서 각 값에 대해 status = 'X' AND created_at > '2026-07-01' 범위 스캔을 반복한다. status 고유값이 5개라면 범위 스캔을 5번 하는 것과 같다.

    카디널리티가 높은 선두 컬럼에서는 Skip Scan이 오히려 느리다. 고유값 수만큼 스캔을 반복하기 때문이다. status 같은 열거형 컬럼에서만 의미 있다.

    -- Skip Scan 동작 여부 확인
EXPLAIN FORMAT=JSON SELECT * FROM events WHERE created_at > '2026-07-01'\G
-- "index_name": "idx_events", "using_index_for_skip_scan": true 확인

    MySQL 8.0 이전이라면 Skip Scan은 없고, 선두 컬럼 없이 인덱스를 타는 방법은 없다.

    EXPLAIN으로 선두 컬럼 활용 여부 확인¶

    MySQL¶

    EXPLAIN SELECT * FROM orders WHERE status = 'PAID' AND user_id = 123 AND created_at > '2026-01-01';
    컬럼 확인 포인트
    type ref, range이면 인덱스 사용. ALL이면 풀 스캔
    key 실제 사용된 인덱스명
    key_len 인덱스에서 몇 바이트까지 사용됐는지. 선두 컬럼만 쓰이면 그 컬럼 크기만큼만 표시됨
    rows 예상 스캔 행 수
    Extra Using index condition: ICP 동작. Using where: 인덱스 이후 추가 필터

    key_len이 중요하다. 예를 들어 (status VARCHAR(20), user_id INT, created_at DATETIME) 인덱스에서 status만 쓰이면 key_len이 약 83바이트(utf8mb4 기준 20*4+3)다. status + user_id까지 쓰이면 87바이트로 늘어난다.

    -- key_len으로 인덱스 사용 깊이 확인
EXPLAIN SELECT * FROM orders WHERE status = 'PAID';
-- key_len: 83 → status 컬럼만 사용

EXPLAIN SELECT * FROM orders WHERE status = 'PAID' AND user_id = 123;
-- key_len: 87 → status + user_id 사용

    PostgreSQL¶

    EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'PAID' AND user_id = 123 AND created_at > '2026-01-01';

    출력의 Index Cond에 실제로 인덱스 조건으로 들어간 컬럼이 나온다. Filter에 나오는 조건은 인덱스 이후에 행 단위로 필터링한다는 뜻이다.

    Index Scan using idx_orders on orders
  Index Cond: ((status = 'PAID') AND (user_id = 123) AND (created_at > '2026-01-01'))
  Buffers: shared hit=5

    vs

    Index Scan using idx_orders on orders
  Index Cond: ((status = 'PAID'))
  Filter: ((user_id = 123) AND (created_at > '2026-01-01'))
  Rows Removed by Filter: 8432

    후자라면 인덱스가 status 조건만 쓰고, 나머지는 행을 꺼낸 후 필터링하고 있다. Rows Removed by Filter가 크면 인덱스 설계를 다시 봐야 한다.

    여러 쿼리 패턴을 하나의 인덱스로 커버하는 설계¶

    실무에서는 한 테이블에 쿼리 패턴이 여러 개다. 쿼리마다 인덱스를 따로 만들면 쓰기 성능이 나빠지고 관리가 복잡해진다.

    공통 선두 컬럼을 찾아 하나의 인덱스로 여러 패턴을 커버하는 방식이 낫다.

    -- 쿼리 패턴 목록
-- Q1: WHERE tenant_id = ? AND status = ? ORDER BY created_at DESC
-- Q2: WHERE tenant_id = ? AND status = ? AND user_id = ?
-- Q3: WHERE tenant_id = ? AND user_id = ? ORDER BY created_at DESC

-- tenant_id가 공통 선두 → 무조건 첫 번째
-- Q1, Q2에서 status가 두 번째 자주 등장
-- Q3는 user_id가 두 번째

-- 인덱스 1: (tenant_id, status, created_at) → Q1, Q2 커버
-- 인덱스 2: (tenant_id, user_id, created_at) → Q3 커버

    인덱스 2개로 3개 패턴을 커버한다. 만약 인덱스를 1개로 줄이려면 쿼리 빈도를 봐야 한다. Q3가 전체 트래픽의 5% 미만이라면 Q3 때문에 인덱스를 추가하는 게 손해일 수 있다.

    또 다른 패턴은 커버링 인덱스 설계다. SELECT 컬럼까지 인덱스에 포함해서 테이블 접근 자체를 없애는 방식이다.

    -- 쿼리: SELECT id, status, created_at FROM orders WHERE tenant_id = ? AND status = ?
-- 인덱스에 SELECT 컬럼까지 포함
CREATE INDEX idx_covering ON orders (tenant_id, status, created_at, id);

-- EXPLAIN에서 Extra: Using index 가 나오면 테이블 접근 없이 인덱스만으로 처리

    커버링 인덱스는 인덱스 크기가 커지는 단점이 있다. SELECT 컬럼이 자주 바뀌는 쿼리에는 맞지 않는다.

    실무에서 자주 하는 실수¶

    ORDER BY 컬럼을 범위 조건 앞에 두는 경우.

    -- 잘못된 설계 의도: ORDER BY created_at을 위해 앞에 배치
CREATE INDEX idx_wrong ON orders (created_at, status);

SELECT * FROM orders WHERE status = 'PAID' ORDER BY created_at DESC;
-- status 조건이 인덱스 탐색에 기여 못 함 → 인덱스 풀 스캔 후 필터

    ORDER BY 정렬 방향이 인덱스 순서와 맞으면 filesort를 피할 수 있지만, 그것보다 WHERE 절 효율이 먼저다. 정렬 최적화는 WHERE 조건 컬럼을 모두 처리한 뒤 남은 자리에 ORDER BY 컬럼을 넣는 방식으로 접근해야 한다.

    선두 컬럼에 함수를 쓰는 경우.

    -- 인덱스 무효화
SELECT * FROM orders WHERE DATE(created_at) = '2026-07-15' AND status = 'PAID';
-- DATE() 함수 때문에 created_at 인덱스 못 씀

-- 범위 조건으로 바꿔야 함
SELECT * FROM orders
WHERE created_at >= '2026-07-15 00:00:00'
  AND created_at < '2026-07-16 00:00:00'
  AND status = 'PAID';

    ORM에서 날짜 처리 시 암묵적으로 함수가 들어가는 경우가 있다. 생성된 SQL을 직접 확인해봐야 한다.

    멀티 테넌트 구조에서 tenant_id를 선두에 빼먹는 경우.

    -- tenant_id 없는 인덱스
CREATE INDEX idx_orders ON orders (status, created_at);

-- tenant_id = 1인 PAID 주문만 보는 쿼리
SELECT * FROM orders WHERE tenant_id = 1 AND status = 'PAID';
-- tenant_id 조건이 후처리 필터로 빠짐 → 전체 테넌트 PAID 주문 스캔 후 필터

    멀티 테넌트 테이블은 거의 모든 쿼리에 tenant_id가 붙는다. tenant_id 없는 인덱스는 실질적으로 의미 없다.

    선두 컬럼 무력화와 key_len 진단¶

    복합 인덱스에서 선두 컬럼이 무력화되면 두 번째, 세 번째 컬럼도 함께 죽는다. key_len이 예상보다 작거나 0이면 선두 컬럼이 인덱스 탐색에 기여하지 못하는 것이다.

    key_len 바이트 계산¶

    NULL 허용 여부에 따라 1바이트 차이가 난다.

    타입 NOT NULL NULL 허용
    TINYINT 1 2
    INT 4 5
    BIGINT 8 9
    DATETIME (MySQL 5.6.4+) 5 6
    VARCHAR(n) utf8mb4 n×4+2 n×4+3
    CHAR(n) utf8mb4 n×4 n×4+1 
    -- (tenant_id BIGINT NOT NULL, event_type VARCHAR(20) NOT NULL, created_at DATETIME NOT NULL)
CREATE INDEX idx_events ON events (tenant_id, event_type, created_at);
-- tenant_id만: 8
-- tenant_id + event_type: 8 + (20×4+2) = 90
-- 세 컬럼 모두: 90 + 5 = 95

EXPLAIN SELECT * FROM events WHERE tenant_id = 100;
-- key_len: 8

EXPLAIN SELECT * FROM events WHERE tenant_id = 100 AND event_type = 'CLICK';
-- key_len: 90

EXPLAIN SELECT * FROM events WHERE tenant_id = 100 AND event_type = 'CLICK' AND created_at > '2026-07-01';
-- key_len: 95

    key_len이 95가 나와야 하는데 8이 나온다면, event_type 조건이 인덱스 탐색에 기여하지 못하고 있는 것이다.

    함수 래핑으로 인한 선두 컬럼 무력화¶

    선두 컬럼에 함수를 씌우면 복합 인덱스 전체가 무력화된다. B-Tree에 저장된 값과 함수 결과가 달라서 탐색 시작점을 정할 수 없기 때문이다.

    CREATE INDEX idx_orders ON orders (status VARCHAR(20), user_id BIGINT, created_at DATETIME);
-- 세 컬럼 모두 NOT NULL 기준 최대 key_len: 82 + 8 + 5 = 95

-- 선두 컬럼(status)에 UPPER() 래핑 → 인덱스 전체 무력화
EXPLAIN SELECT * FROM orders WHERE UPPER(status) = 'PAID' AND user_id = 123;
-- key: NULL, type: ALL, rows: 9823000
-- status가 죽으면서 user_id도 인덱스로 못 씀

-- 후행 컬럼에 함수를 써도 선두 컬럼은 살아있음
EXPLAIN SELECT * FROM orders WHERE status = 'PAID' AND DATE(created_at) = '2026-07-15';
-- key: idx_orders, key_len: 82 (status만), type: ref
-- created_at은 행 단위 필터(Extra: Using where)로 처리

    선두 컬럼에 함수가 들어가는 상황은 ORM 레이어에서 주로 나온다. Querydsl에서 StringExpressions.upperCase()를 선두 조건에 쓰거나, JPQL에서 UPPER(e.status)를 쓰면 생성된 SQL에 함수가 포함된다.

    // Querydsl: 대소문자 무시 검색 의도로 UPPER 적용
orders.where(order.status.upper().eq("PAID"))
// 생성 SQL: WHERE UPPER(status) = 'PAID' → 복합 인덱스 전체 무력화

// 해결: 저장 시 대문자로 통일하고 함수 제거
orders.where(order.status.eq("PAID"))

    타입 불일치로 인한 선두 컬럼 무력화¶

    선두 컬럼 타입과 바인딩 파라미터 타입이 다르면 MySQL이 암묵적 형변환을 한다. 문자열 컬럼에 숫자 리터럴이 오면 MySQL이 컬럼 전체를 숫자로 변환해야 하므로 인덱스가 죽는다.

    CREATE INDEX idx_users ON users (phone VARCHAR(20), status VARCHAR(10));

-- 선두 컬럼 타입 불일치 → 복합 인덱스 전체 무력화
EXPLAIN SELECT * FROM users WHERE phone = 01012345678 AND status = 'ACTIVE';
-- key: NULL, type: ALL, rows: 5823412

-- 문자열 리터럴로 수정
EXPLAIN SELECT * FROM users WHERE phone = '01012345678' AND status = 'ACTIVE';
-- key: idx_users, key_len: 93 (phone 82 + status 11), type: ref, rows: 1

    ORM에서 자주 발생한다.

    // JPA Repository: phone이 VARCHAR인데 Long 타입으로 바인딩
List<User> findByPhoneAndStatus(Long phone, String status);
// 생성 SQL: WHERE phone = 01012345678 → 인덱스 무력화

// 올바른 타입
List<User> findByPhoneAndStatus(String phone, String status);

    MyBatis에서는 jdbcType을 명시하지 않으면 Java 파라미터 타입을 보고 바인딩 방식을 결정한다.

    <!-- phone VARCHAR 컬럼 -->
<!-- jdbcType 없을 때: Java Integer 파라미터 → 숫자 리터럴 → 인덱스 무력화 -->
WHERE phone = #{phone}

<!-- jdbcType 명시: VARCHAR로 바인딩 -->
WHERE phone = #{phone, jdbcType=VARCHAR}

    key_len=0으로 떨어진 케이스¶

    key에 인덱스명이 찍혀 있는데 type: index이고 rows가 전체 테이블 수에 가까운 경우가 있다.

    CREATE INDEX idx_orders ON orders (user_id BIGINT NOT NULL, status VARCHAR(20) NOT NULL, created_at DATETIME NOT NULL);
-- 최대 key_len: 8 + 82 + 5 = 95

-- 문제 쿼리: 인덱스명은 나오는데 느림
EXPLAIN SELECT * FROM orders WHERE user_id = '456' AND status = 'PAID';
-- key: idx_orders
-- key_len: 0
-- type: index
-- rows: 9823400

    type: index는 인덱스를 순차적으로 풀 스캔하는 것이다. key_len이 0이면 인덱스 구조만 참조하고 범위 탐색에는 쓰지 못하는 상태다. BIGINT 컬럼에 문자열 리터럴 '456'을 넣어서 생긴 문제로, MySQL 버전과 SQL 모드에 따라 key_len이 0으로 떨어진다.

    -- 수정: BIGINT 컬럼에 정수 리터럴 사용
EXPLAIN SELECT * FROM orders WHERE user_id = 456 AND status = 'PAID';
-- key: idx_orders
-- key_len: 90  (user_id 8 + status 82)
-- type: ref
-- rows: 3

    key_len이 0에서 90으로 올라오고 rows가 980만에서 3으로 줄어든다. 쿼리 수정 없이 파라미터 타입 하나만 바꾼 결과다.
