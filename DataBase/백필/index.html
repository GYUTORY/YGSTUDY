    백필¶

    백필은 새로운 컬럼, 인덱스, 집계 테이블, 이벤트 스트림 등이 추가됐을 때 과거 데이터를 소급해서 채우는 작업이다. 스키마 변경이나 피처 추가 이후 거의 반드시 따라온다.

    백필이 필요한 상황¶

    신규 컬럼 추가 후 기존 데이터 채우기

    users 테이블에 grade 컬럼을 추가했다고 하면, 기존 1000만 행은 전부 NULL이다. 앱 코드는 grade가 있다고 가정하고 동작하므로, 새 컬럼 추가와 백필은 세트다.

    이벤트 리플레이

    Kafka 토픽을 신규 구독자가 처음 붙었을 때, 과거 이벤트를 처음부터 다시 처리해야 하는 경우다. 토픽 retention 기간을 벗어나면 DB에서 직접 꺼내 다시 발행해야 한다.

    검색 인덱스 재구성

    Elasticsearch에 새 필드를 추가하거나 analyzer를 바꿨을 때, 기존 도큐먼트를 전부 재색인해야 한다. 인덱스를 새로 만들고 alias를 교체하는 방식(zero-downtime reindex)으로 처리한다.

    집계 테이블 재산출

    통계/집계 테이블의 로직이 변경됐을 때, 특정 날짜 범위의 집계를 다시 계산해야 하는 경우다. 일별 매출 집계 테이블에 버그가 있었다면 수정 후 해당 기간을 재산출한다.

    대용량 테이블 청크 분할 패턴¶

    수천만 행 테이블에서 UPDATE users SET grade = ...를 한 번에 날리면 두 가지 문제가 생긴다. 첫째, 트랜잭션이 너무 길어서 undo log가 폭발한다. 둘째, 테이블 락 혹은 갭 락이 길게 잡혀서 서비스 쿼리가 블로킹된다.

    PK 범위 기반 청크 분할이 가장 안전하다. OFFSET을 쓰지 않는 게 핵심이다.

    -- 범위를 확인한다
SELECT MIN(id), MAX(id) FROM users;

-- 청크 단위로 처리한다 (예: 1000건씩)
UPDATE users
SET grade = calculate_grade(total_purchase)
WHERE id BETWEEN 1 AND 1000
  AND grade IS NULL;

UPDATE users
SET grade = calculate_grade(total_purchase)
WHERE id BETWEEN 1001 AND 2000
  AND grade IS NULL;
-- ...

    OFFSET 기반(LIMIT 1000 OFFSET 0, LIMIT 1000 OFFSET 1000)은 쓰지 않는다. 테이블이 클수록 OFFSET이 커지면서 매 쿼리마다 앞에서부터 다시 스캔하기 때문에 뒤로 갈수록 느려진다. PK 범위는 인덱스 레인지 스캔이므로 일정한 성능이 나온다.

    실제 운영 스크립트 패턴¶

    import time
import pymysql

conn = pymysql.connect(host='...', user='...', password='...', db='myapp')

chunk_size = 1000
cursor = conn.cursor()

cursor.execute("SELECT MIN(id), MAX(id) FROM users WHERE grade IS NULL")
min_id, max_id = cursor.fetchone()

current_id = min_id
while current_id <= max_id:
    end_id = current_id + chunk_size - 1

    cursor.execute("""
        UPDATE users
        SET grade = CASE
            WHEN total_purchase >= 1000000 THEN 'GOLD'
            WHEN total_purchase >= 300000  THEN 'SILVER'
            ELSE 'BRONZE'
        END
        WHERE id BETWEEN %s AND %s
          AND grade IS NULL
    """, (current_id, end_id))

    conn.commit()
    affected = cursor.rowcount
    print(f"processed id {current_id}~{end_id}, affected={affected}")

    current_id = end_id + 1
    time.sleep(0.05)  # DB 부하 조절

cursor.close()
conn.close()

    time.sleep(0.05)는 선택이 아니다. 청크 사이에 짧은 쉬는 시간을 두지 않으면 DB CPU가 100%에 붙어서 서비스 쿼리 응답 시간이 튄다. 슬레이브 복제 지연도 같이 발생한다.

    실패 지점 재시작¶

    백필 도중 프로세스가 죽거나 DB 연결이 끊기면, 처음부터 다시 돌리면 이미 처리한 범위를 또 건드린다. 시간 낭비이고, 조건부 UPDATE가 아니면 데이터 오염이 생길 수 있다.

    진행 상태를 별도 테이블에 저장하고, 재시작 시 마지막 처리 지점부터 이어간다.

    CREATE TABLE backfill_checkpoint (
    job_name    VARCHAR(100) NOT NULL,
    last_id     BIGINT       NOT NULL DEFAULT 0,
    updated_at  DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    PRIMARY KEY (job_name)
);

    def get_last_id(job_name):
    cursor.execute(
        "SELECT last_id FROM backfill_checkpoint WHERE job_name = %s",
        (job_name,)
    )
    row = cursor.fetchone()
    return row[0] if row else 0

def save_checkpoint(job_name, last_id):
    cursor.execute("""
        INSERT INTO backfill_checkpoint (job_name, last_id)
        VALUES (%s, %s)
        ON DUPLICATE KEY UPDATE last_id = %s
    """, (job_name, last_id, last_id))
    conn.commit()

# 사용
JOB_NAME = "users_grade_backfill"
start_id = get_last_id(JOB_NAME) + 1  # 마지막 처리 id 다음부터

current_id = start_id
while current_id <= max_id:
    end_id = current_id + chunk_size - 1
    # ... UPDATE 처리 ...
    save_checkpoint(JOB_NAME, end_id)
    current_id = end_id + 1

    체크포인트는 청크 단위로 저장한다. 행 단위로 저장하면 checkpoint 쓰기 자체가 병목이 된다.

    운영 중 백필: 쓰기 충돌 방지¶

    백필이 돌아가는 동안 앱도 같은 컬럼을 쓰는 경우가 있다. 이때 백필이 앱의 변경을 덮어쓰면 데이터 손실이다.

    조건부 UPDATE¶

    앱이 이미 grade를 설정한 행은 건드리지 않도록 WHERE 조건을 달아야 한다.

    -- 잘못된 방식: 앱이 쓴 값을 덮어쓴다
UPDATE users
SET grade = 'BRONZE'
WHERE id BETWEEN 1 AND 1000;

-- 올바른 방식: NULL인 것만 처리한다
UPDATE users
SET grade = 'BRONZE'
WHERE id BETWEEN 1 AND 1000
  AND grade IS NULL;

    앱이 NULL이 아닌 명시적 초기값을 쓰는 구조면, NULL 조건 대신 백필 전용 marker 값을 쓴다.

    -- 컬럼 추가 시 sentinel 값으로 초기화
ALTER TABLE users ADD COLUMN grade VARCHAR(20) DEFAULT 'PENDING';

-- 백필은 PENDING인 것만 처리
UPDATE users
SET grade = calculate_grade(total_purchase)
WHERE id BETWEEN %s AND %s
  AND grade = 'PENDING';

    이렇게 하면 앱이 먼저 grade를 설정한 행은 백필이 건드리지 않는다.

    낙관적 잠금 패턴¶

    컬럼 단위가 아니라 로우 단위 충돌을 피해야 하는 경우, updated_at으로 체크한다.

    -- 백필 실행 전 updated_at을 기록해두고
UPDATE users
SET grade = %s
WHERE id = %s
  AND updated_at = %s  -- 읽어온 시점의 updated_at과 같아야만 UPDATE

    행이 그 사이 앱에 의해 변경됐으면 UPDATE가 0 rows affected를 반환한다. 이 경우 그냥 건너뛰면 된다. 앱이 이미 올바른 값을 썼을 가능성이 높다.

    백필 진행률 추적¶

    1000만 행 백필을 실행하면서 "지금 몇 % 진행됐는지" 알 수 없으면 운영이 힘들다.

    -- 진행률 추적용 컬럼을 미리 알아두기
SELECT COUNT(*) FROM users WHERE grade IS NULL;     -- 남은 건수
SELECT COUNT(*) FROM users WHERE grade IS NOT NULL; -- 완료 건수
SELECT COUNT(*) FROM users;                         -- 전체

-- 또는 체크포인트 테이블로 계산
SELECT
    last_id AS processed_up_to,
    (SELECT MAX(id) FROM users) AS total_max_id,
    ROUND(last_id / (SELECT MAX(id) FROM users) * 100, 1) AS progress_pct
FROM backfill_checkpoint
WHERE job_name = 'users_grade_backfill';

    백필 스크립트에서 주기적으로 로그를 남긴다.

    total_rows = max_id - min_id
while current_id <= max_id:
    # ... 처리 ...
    processed = current_id - min_id
    pct = processed / total_rows * 100
    if processed % (chunk_size * 100) == 0:  # 100청크마다 로그
        print(f"[backfill] {pct:.1f}% done (id={current_id})")

    Prometheus/Grafana로 시각화하려면 처리 건수를 게이지 메트릭으로 내보내거나, 주기적으로 DB를 쿼리해서 대시보드에 뿌린다.

    카프카 기반 이벤트 백필¶

    Kafka는 기본적으로 토픽 retention 기간(기본 7일)이 지난 이벤트는 읽을 수 없다. 신규 컨슈머가 붙으면 --from-beginning 옵션으로 처음부터 읽을 수 있지만, retention을 넘어선 과거 이력은 없다.

    DB→Kafka 재발행 패턴¶

    과거 데이터를 DB에서 꺼내 Kafka로 다시 발행하는 방식이다.

    @Service
public class OrderEventBackfillService {

    private final OrderRepository orderRepository;
    private final KafkaTemplate<String, OrderEvent> kafkaTemplate;

    public void backfill(LocalDate from, LocalDate to) {
        long lastId = 0;
        int chunkSize = 500;

        while (true) {
            List<Order> chunk = orderRepository.findForBackfill(
                from, to, lastId, chunkSize
            );
            if (chunk.isEmpty()) break;

            for (Order order : chunk) {
                OrderEvent event = OrderEvent.from(order);
                // 백필 헤더를 붙여서 컨슈머가 구분할 수 있게
                kafkaTemplate.send(MessageBuilder
                    .withPayload(event)
                    .setHeader("X-Backfill", "true")
                    .setHeader("X-Original-Time", order.getCreatedAt().toString())
                    .build());
            }

            lastId = chunk.get(chunk.size() - 1).getId();
            Thread.sleep(100);
        }
    }
}

    // Repository
@Query("""
    SELECT o FROM Order o
    WHERE o.createdAt BETWEEN :from AND :to
      AND o.id > :lastId
    ORDER BY o.id
    LIMIT :limit
    """)
List<Order> findForBackfill(
    LocalDate from, LocalDate to,
    long lastId, int limit
);

    컨슈머 쪽에서 X-Backfill: true 헤더를 보고 실시간 이벤트와 다르게 처리해야 할 때가 있다. 예를 들어 실시간 이벤트는 알림을 보내지만 백필 이벤트는 보내지 않아야 한다면, 헤더로 분기한다.

    CDC 기반 이벤트 백필¶

    CDC(Change Data Capture)를 쓰는 환경에서는 binlog replay가 이벤트 백필의 한 방법이다. Debezium 같은 도구는 특정 binlog position부터 다시 읽도록 설정할 수 있다. 하지만 binlog retention도 유한하고, 재처리 범위 제어가 어려워서 실무에서는 DB에서 직접 읽어 재발행하는 방식을 더 많이 쓴다.

    Kafka의 compacted topic을 쓰는 경우, 키별 최신 값만 남기므로 백필이 좀 다르다. 특정 키의 과거 상태가 필요하면 compacted topic에선 가져올 수 없고, 원본 DB나 별도 스냅샷에서 꺼내야 한다.

    Spring Batch로 백필 구현 시 주의사항¶

    Spring Batch는 재시작, Skip, Retry 기능이 내장되어 있어서 백필 배치에 적합하다. 다만 몇 가지 함정이 있다.

    JpaPagingItemReader OFFSET 드리프트 문제¶

    백필에서 읽은 데이터를 처리하면서 해당 행을 UPDATE하는 구조는 JpaPagingItemReader와 맞지 않는다.

    // 문제 상황
@Bean
public JpaPagingItemReader<User> userReader(EntityManagerFactory emf) {
    return new JpaPagingItemReaderBuilder<User>()
        .queryString("SELECT u FROM User u WHERE u.grade IS NULL ORDER BY u.id")
        .pageSize(1000)
        .build();
}

@Bean
public ItemProcessor<User, User> gradeProcessor() {
    return user -> {
        user.setGrade(calculateGrade(user));
        return user;  // 이 행을 UPDATE하면 다음 페이지 OFFSET이 밀린다
    };
}

    1페이지(OFFSET 0)에서 1000건을 읽고 grade를 채웠다. 2페이지(OFFSET 1000)를 읽으러 가면 이미 grade가 NULL인 행이 1000건 줄었으므로, OFFSET 1000은 실제로 2000번째 원래 행부터 읽게 된다. 중간 1000건을 건너뛰는 것이다.

    해결책은 두 가지다.

    1. JpaCursorItemReader 사용

    @Bean
public JpaCursorItemReader<User> userReader(EntityManagerFactory emf) {
    return new JpaCursorItemReaderBuilder<User>()
        .name("userBackfillReader")
        .entityManagerFactory(emf)
        .queryString("SELECT u FROM User u WHERE u.grade IS NULL ORDER BY u.id")
        .build();
}

    커서는 결과 셋을 한 번에 열고 순회하므로 OFFSET 드리프트가 없다. 처리 도중 데이터가 변경돼도 이미 열린 결과 셋에 영향이 없다.

    단점은 Step이 끝날 때까지 DB 커넥션을 잡고 있는다는 점이다. 수천만 건을 처리하면 커넥션 점유 시간이 수 시간이 될 수 있다. MySQL의 wait_timeout, interactive_timeout 설정 값보다 처리 시간이 길면 커넥션이 끊긴다.

    # MySQL에서 장시간 배치를 위한 설정
spring:
  datasource:
    hikari:
      keepalive-time: 60000      # 60초마다 keepalive 쿼리
      connection-timeout: 30000

    2. PK 범위 기반 Native Query

    @Bean
public Step backfillStep(StepBuilderFactory sbf, ...) {
    return sbf.get("userGradeBackfillStep")
        .<Long, Long>chunk(1)
        .reader(chunkRangeReader())   // PK 범위를 청크 단위로 읽는 reader
        .processor(chunkProcessor())  // 범위 내 UPDATE 실행
        .writer(noopWriter())
        .build();
}

    범위 단위로 처리하면 OFFSET 문제가 없고, 커넥션도 청크마다 반납한다.

    JobParameter와 재시작¶

    Spring Batch의 Job 재시작은 동일한 JobParameter로 실행된 Job이 FAILED 상태일 때 이어서 실행하는 기능이다.

    // 재시작이 안 되는 흔한 실수: 매번 새 JobParameter를 쓰는 것
JobParameters params = new JobParametersBuilder()
    .addLong("run.id", System.currentTimeMillis())  // 매번 다른 값
    .toJobParameters();
// 이러면 매번 새로운 JobInstance가 생성되고 재시작이 안 된다

    백필 Job은 날짜나 범위로 파라미터를 고정해서, 실패 시 동일 파라미터로 재실행하면 이어서 처리하도록 구성한다.

    JobParameters params = new JobParametersBuilder()
    .addString("target.date", "2026-08-01")  // 고정 파라미터
    .toJobParameters();

    Chunk Size 설정¶

    백필에서 chunk size와 page size가 다르면 비효율이다.

    // 잘못된 설정
.<User, User>chunk(1000)
.reader(pagingReader)  // pageSize = 100이면, 1 chunk를 채우려고 10번 쿼리

    pageSize와 chunkSize를 같게 맞춘다. 백필처럼 단순 UPDATE 배치에서는 500~2000 정도가 무난하다. 너무 크면 트랜잭션이 길어지고, 너무 작으면 커밋 오버헤드가 크다.

    트러블슈팅 경험¶

    1. 백필 도중 슬레이브 복제 지연

    청크 사이에 sleep 없이 빠르게 돌렸더니 슬레이브 복제 지연이 20초 이상 벌어진 적이 있다. 슬레이브에서 읽기를 하는 서비스가 있으면 즉시 장애로 연결된다. 청크 간 50ms 정도 sleep을 넣거나, pt-online-schema-change처럼 슬레이브 지연을 모니터링하면서 자동으로 속도를 조절하는 방식을 써야 한다.

    2. undo log 폭발

    한 트랜잭션에 10만 건을 업데이트하는 배치를 실행했다가 MySQL InnoDB의 undo tablespace가 급격히 커진 적이 있다. 트랜잭션이 롤백되지 않더라도 긴 트랜잭션은 undo 로그를 오래 유지한다. 청크 크기를 줄이고 자주 커밋하는 것이 답이다.

    3. 동일 행에 백필과 앱이 동시에 쓰는 경우

    백필이 grade = NULL 조건으로만 UPDATE했는데도 문제가 생겼다. 앱이 grade를 한 번 쓰고 난 뒤 다른 컬럼(예: updated_at)을 업데이트하면서 grade를 다시 NULL로 되돌리는 버그가 있었다. 백필만 보면 정상이었고 앱 코드의 문제였다. 백필 전에 앱이 해당 컬럼을 어떻게 다루는지 코드를 먼저 확인해야 한다.

    4. 백필 완료 후 NULL 행이 남는 경우

    PK 범위 기반으로 MIN(id) ~ MAX(id)를 처리했는데, 백필 도중 새로 INSERT된 행의 id가 MAX(id)를 넘으면 처리 대상에서 빠진다. 백필 완료 후 반드시 SELECT COUNT(*) WHERE grade IS NULL로 잔여 행이 없는지 검증한다. 있으면 그 시점부터 다시 범위를 잡아서 처리한다.

    5. Spring Batch OFFSET 드리프트를 몰라서 30% 누락

    JpaPagingItemReader로 grade 백필을 돌렸는데 완료 후 확인해보니 grade IS NULL이 수백만 건 남아있었다. Reader가 WHERE grade IS NULL로 읽고 Processor에서 grade를 채워 Writer가 UPDATE하는 구조였고, OFFSET 드리프트로 중간 청크들을 모두 건너뛴 것이었다. JpaCursorItemReader로 교체하고 재실행했다.
