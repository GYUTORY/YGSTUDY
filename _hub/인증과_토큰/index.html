    인증과 토큰 허브¶

    이 주제를 언제 찾게 되는가¶

    • JWT 토큰을 발급·검증하는 코드를 처음 작성하거나, 보안 이슈(알고리즘 혼동, 만료 처리)를 점검해야 할 때
    • 소셜 로그인(구글, 카카오)이나 외부 인증 서버 연동을 구현해야 할 때
    • 세션 방식과 JWT 중 어느 쪽이 우리 시스템에 맞는지 비교 판단이 필요할 때
    • NestJS에서 Passport 전략이나 Guards를 활용해 인증 미들웨어를 구성할 때
    • MSA 환경에서 서비스 간 인증을 어떻게 전파할지 설계할 때

    인증 방식 핵심 비교¶

    실무에서 인증 방식을 고를 때 가장 많이 막히는 지점은 Session과 JWT의 선택이다. 각 방식이 해결하는 문제가 다르기 때문에 그 차이를 먼저 제대로 이해해야 한다.

    Session 방식은 서버가 상태를 유지한다. 로그인 시 서버에 세션 데이터를 저장하고, 클라이언트는 세션 ID만 쿠키로 들고 다닌다. 서버가 언제든 세션을 무효화할 수 있다는 게 핵심이다. 강제 로그아웃, 계정 정지가 즉시 반영된다. 단점은 분산 환경에서 세션 공유 문제가 생긴다는 것이다. 여러 서버 인스턴스가 있으면 Redis 같은 공유 저장소가 필요하다.

    JWT 방식은 서버가 상태를 유지하지 않는다. 토큰 자체에 사용자 정보와 만료 시간이 들어있어서 서버는 서명만 검증하면 된다. 수평 확장이 쉽고 마이크로서비스 간 전파가 간편하다. 문제는 토큰을 한 번 발급하면 만료 전까지 무효화할 방법이 없다는 것이다. 블랙리스트 구현은 결국 상태를 서버에 저장하는 것이라 Session과 본질적으로 같아진다.

    OAuth2는 인증(Authentication)이 아니라 인가(Authorization) 프로토콜이다. 타사 서비스의 리소스에 접근 권한을 위임받는 용도다. 소셜 로그인에서 OAuth2를 쓰는 건 카카오가 "이 사용자가 맞다"고 확인해주는 흐름이다. OIDC(OpenID Connect)는 OAuth2 위에 인증 레이어를 얹은 것이다.

    API Key는 서버 간 통신이나 개발자 도구 연동에 쓴다. 세션이나 JWT처럼 만료 개념이 없어서 관리가 중요하다. 키 유출 시 즉시 폐기하고 재발급하는 순환(rotation) 체계 없이는 보안 사고로 이어진다.

    방식 상태 유지 즉시 무효화 분산 환경 주 용도
    Session 서버 가능 Redis 등 공유 저장소 필요 웹 앱
    JWT 클라이언트 불가 (만료까지 유효) 별도 공유 저장소 불필요 API, MSA
    OAuth2 인가 서버 토큰 폐기 가능 외부 인증 서버 의존 소셜 로그인, 외부 연동
    API Key 서버 DB 가능 중앙 저장소 필요 서버 간 통신

    선택 기준¶

    Session 방식이 맞는 경우: 강제 로그아웃이나 실시간 권한 변경이 필요한 서비스(금융, 관리자 패널)에 맞다. 서버 인스턴스가 한 대거나, Redis 등 공유 세션 저장소 구성이 가능한 환경이어야 한다. 클라이언트가 브라우저만인 단순 웹 앱은 Session이 구현이 더 단순하다.

    JWT가 맞는 경우: API 서버와 프론트엔드가 분리된 SPA 구조나, 마이크로서비스 환경에서 서비스 간 인증 정보를 전파해야 할 때 적합하다. 모바일 앱처럼 쿠키 관리가 복잡한 환경에서도 JWT가 낫다.

    JWT는 "Stateless니까 편하다"는 이유로 선택하는 경우가 많은데, Refresh Token 관리와 블랙리스트 처리까지 제대로 구현하면 Session보다 복잡해지는 경우가 있다. 단순히 무상태라는 이유만으로 선택하면 나중에 후회한다.

    자주 빠지는 함정¶

    JWT 알고리즘 혼동 (alg confusion)¶

    JWT 헤더의 alg 필드를 서버에서 그대로 신뢰하면 보안 취약점이 된다. 가장 흔한 공격은 RS256으로 서명된 토큰의 알고리즘을 HS256으로 바꾸고, 공개키를 HMAC 비밀키로 사용하는 방식이다.

    // 취약한 코드 — 토큰 헤더의 alg를 그대로 사용
const decoded = jwt.verify(token, publicKey);

// 안전한 코드 — 알고리즘을 서버에서 명시적으로 고정
const decoded = jwt.verify(token, publicKey, { algorithms: ['RS256'] });

    none 알고리즘 공격도 있다. alg: "none" 으로 설정된 토큰을 받아들이는 라이브러리 설정은 서명 없이 토큰을 위조할 수 있게 해준다.

    // 절대 허용하면 안 되는 설정
const decoded = jwt.verify(token, secret, { algorithms: ['HS256', 'none'] });

// none을 명시적으로 제외
const decoded = jwt.verify(token, secret, { algorithms: ['HS256'] });

    Refresh Token 순환(Rotation) 미적용¶

    Access Token 만료를 짧게(15분~1시간) 설정하고, Refresh Token으로 재발급하는 구조를 많이 쓴다. 여기서 Refresh Token을 단순히 DB에 저장하고 유효성만 확인하는 수준으로 구현하면 토큰 탈취 시 감지가 안 된다.

    Refresh Token Rotation은 Refresh Token을 쓸 때마다 새 토큰을 발급하고 기존 것은 폐기한다. 탈취된 토큰을 누군가 먼저 사용하면, 정상 사용자가 구 토큰으로 재발급 요청할 때 이미 폐기된 토큰이라 감지할 수 있다.

    async function rotateRefreshToken(oldRefreshToken) {
  const tokenRecord = await db.refreshTokens.findOne({
    token: oldRefreshToken
  });

  if (!tokenRecord) {
    throw new Error('Invalid refresh token');
  }

  if (tokenRecord.used) {
    // 이미 사용된 토큰 — 탈취 가능성 있음
    // 해당 사용자의 모든 Refresh Token 폐기
    await db.refreshTokens.deleteMany({ userId: tokenRecord.userId });
    throw new Error('Token reuse detected');
  }

  await db.refreshTokens.updateOne(
    { token: oldRefreshToken },
    { $set: { used: true } }
  );

  const newRefreshToken = generateSecureToken();
  await db.refreshTokens.insertOne({
    token: newRefreshToken,
    userId: tokenRecord.userId,
    used: false,
    expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000)
  });

  return newRefreshToken;
}

    JWT Payload에 민감한 정보 저장¶

    JWT는 Base64로 인코딩되어 있을 뿐 암호화되어 있지 않다. 브라우저 개발자 도구에서 토큰을 디코딩하면 Payload 내용이 그대로 보인다.

    // Payload에 넣으면 안 되는 것들
{
  "sub": "user123",
  "password": "...",       // 절대 금지
  "creditCard": "...",     // 절대 금지
  "internalRole": "admin"  // 민감한 권한 정보도 주의
}

// 식별자만 넣고, 상세 정보는 서버에서 조회
{
  "sub": "user123",
  "exp": 1234567890
}

    Access Token을 localStorage에 저장¶

    localStorage는 JavaScript로 접근 가능하기 때문에 XSS 취약점이 있는 페이지에서 토큰을 탈취할 수 있다.

    Access Token은 메모리에 저장하고, Refresh Token은 httpOnly 쿠키로 관리하는 패턴이 안전하다.

    // 취약한 방식
localStorage.setItem('accessToken', token);

// Access Token은 메모리 변수로
let accessToken = null;

function setAccessToken(token) {
  accessToken = token;
}

// Refresh Token은 서버에서 httpOnly 쿠키로 설정
// Set-Cookie: refreshToken=...; HttpOnly; Secure; SameSite=Strict

    OAuth2 state 파라미터 미검증¶

    OAuth2 Authorization Code Flow에서 state 파라미터는 CSRF 공격을 막는다. 인증 요청 시 생성한 state와 콜백에서 받은 state가 일치하는지 검증하지 않으면 CSRF 공격에 노출된다.

    // 취약한 콜백 처리 — state 검증 없음
app.get('/auth/callback', async (req, res) => {
  const { code } = req.query;
  const tokens = await exchangeCodeForTokens(code);
});

// 안전한 콜백 처리
app.get('/auth/callback', async (req, res) => {
  const { code, state } = req.query;

  if (state !== req.session.oauthState) {
    return res.status(400).send('State mismatch');
  }

  delete req.session.oauthState;
  const tokens = await exchangeCodeForTokens(code);
});

    읽는 순서¶

    1. 인증/인가 방식 비교 — 여기까지 읽으면 Session·JWT·OAuth2를 상황별로 선택하는 기준이 잡힌다
    2. JWT + OAuth — JWT 구조와 OAuth 플로우를 각각 문서로 익힌다
    3. JWT 구현 및 보안 — 실제 코드 수준에서 발급·검증·보안 취약점을 처리하는 방법을 구현한다
    4. Token Revocation + Session Management — 토큰/세션 만료와 강제 폐기 전략을 추가한다
    5. MSA 인증 / NestJS Guards — 멀티 서비스 환경이나 특정 프레임워크에서의 적용으로 확장한다
