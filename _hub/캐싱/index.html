    캐싱 허브¶

    이 주제를 언제 찾게 되는가¶

    • 동일 데이터를 반복 조회하는 DB 부하를 줄이기 위해 캐시 레이어를 처음 도입할 때
    • 캐시와 DB 사이의 데이터 불일치(Cache Invalidation) 문제를 해결해야 할 때
    • Redis를 캐시로 쓸 때 TTL·Eviction Policy를 어떻게 설정해야 할지 고민될 때
    • MSA 환경에서 서비스가 여럿일 때 캐시 일관성을 어떻게 유지할지 설계할 때
    • Spring @Cacheable 도입 후 캐시 무효화 타이밍이 맞지 않는 문제가 발생할 때
    • 트래픽 급증 시 Redis에 없는 키를 동시에 수백 개 요청이 몰리는 Cache Stampede를 경험했을 때
    • NestJS Cache Module이나 Node.js 멀티레벨 캐시를 구성할 때

    어떤 캐시 레이어를 써야 하는가¶

    캐시 도입 전에 데이터 특성을 먼저 파악해야 한다. 레이어 선택에서 자주 틀리는 지점은 로컬 캐시(L1)의 인스턴스 격리 문제다. 서버 2대가 각자 다른 값을 갖고 있으면 배포 직후 사용자마다 다른 데이터를 보게 된다.

    // 캐시 레이어 선택 기준 (주석이 판단 로직)

// Q1. 데이터를 여러 서버 인스턴스가 공유해야 하는가?
//   → 재고, 세션, 사용자 상태: Redis(L2) 필수
//   → 코드 테이블, 공지사항처럼 전 서버가 동일하게 읽어도 무방한 데이터: L1 가능

// Q2. Redis 왕복 레이턴시(~1ms)가 병목인가? (초당 수만 QPS)
//   → L1(Caffeine) + L2(Redis) 2단 구성
//   → L1 TTL을 L2보다 짧게 설정해 정합성 손실 구간을 줄인다

// Q3. 정적 파일이나 API 응답을 엣지에서 처리해야 하는가?
//   → CDN 또는 HTTP Cache-Control / ETag

// Spring Boot: Caffeine(L1) + Redis(L2) 2단 구성
@Configuration
@EnableCaching
public class CacheConfig {

    // L1: 로컬 인메모리. 30초 TTL, 최대 500개
    @Bean("caffeineCacheManager")
    public CacheManager caffeineCacheManager() {
        CaffeineCacheManager manager = new CaffeineCacheManager("product-local");
        manager.setCaffeine(
            Caffeine.newBuilder()
                .expireAfterWrite(30, TimeUnit.SECONDS)
                .maximumSize(500)
        );
        return manager;
    }

    // L2: Redis. 정합성이 필요한 데이터는 여기만 사용
    @Bean("redisCacheManager")
    @Primary
    public CacheManager redisCacheManager(RedisConnectionFactory cf) {
        RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(10))
            .disableCachingNullValues();
        return RedisCacheManager.builder(cf).cacheDefaults(config).build();
    }
}

// 사용 시: @Qualifier로 레이어를 명시
@Cacheable(cacheManager = "caffeineCacheManager", value = "product-local", key = "#id")
public Product getProductLocal(Long id) { ... }

    Cache Stampede는 TTL이 만료된 직후 대량 트래픽이 동시에 DB를 찌르는 현상이다. 방지 방법과 LRU 구현은 Node Cache Advanced에 코드로 정리돼 있다. Spring 환경에서는 @DistributedLock + PER(Probabilistic Early Recomputation) 방식으로 대응한다.

    분산 캐싱 패턴 MSA에서 로컬 캐시 vs 공유 캐시, 캐시 정합성 보장 전략 심화
    캐싱 전략 (Node) Node.js 환경에서의 캐싱 패턴 구현 실무
    멀티레벨 캐시 L1(로컬)·L2(Redis) 2단계 캐시 구성 및 동기화 전략 심화
    Node Cache Advanced LRU/LFU 직접 구현, Cache Stampede 방지, 다중 인스턴스 일관성 심화
    NestJS Cache Module NestJS의 CacheManager와 Redis 연동 설정 실무

    읽는 순서¶

    Java/Spring 경로¶

    1. 캐싱 전략 — Cache-Aside가 기본값이 되는 이유, Write-Through와의 트레이드오프를 이해한다
    2. Spring AOP Deep Dive — Spring이 @Cacheable을 AOP 프록시로 처리하는 원리, 자기 호출(Self-invocation)에서 캐시가 동작하지 않는 이유를 파악한다
    3. Redis Cache Strategy — Eviction Policy 선택 기준과 Hot Key 분산 방법을 적용한다
    4. 분산 캐싱 패턴 — 서비스가 여럿일 때 캐시 정합성을 보장하는 아키텍처를 설계한다

    Node.js 경로¶

    1. 캐싱 전략 (Node) — Cache-Aside 기본 구현과 node-cache·Redis 래핑 방법을 익힌다
    2. Redis Cache Strategy — TTL·Eviction Policy와 Hot Key 문제를 다루는 방법을 파악한다
    3. API 캐싱 — HTTP 레이어와 CDN에서의 캐싱으로 범위를 넓힌다
    4. NestJS Cache Module — CacheManager를 Redis에 연결하는 실제 설정을 적용한다
    5. 멀티레벨 캐시 → Node Cache Advanced — L1+L2 조합 구성과 Cache Stampede 방지 패턴으로 마무리한다

    아직 없는 것¶

    • Spring @Cacheable/@CacheEvict/@CachePut 전용 문서 (현재는 AOP_Deep_Dive에 단편적으로 언급만 됨)
    • CDN Cache Purge/Invalidation 전략 (CloudFront 등 실전)
    • 세션 캐시와 데이터 캐시의 분리 설계
    • Valkey로 Redis를 대체할 때의 마이그레이션 포인트
