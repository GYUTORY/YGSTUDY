    메시징과 전달 보장 허브¶

    이 주제를 언제 찾게 되는가¶

    • 주문 완료 후 이메일 발송·재고 차감이 반드시 실행되어야 할 때 메시지 유실 없이 처리하는 방법을 설계해야 할 때
    • at-least-once 전달에서 중복 메시지가 들어올 때 컨슈머를 멱등하게 만들어야 할 때
    • Kafka·RabbitMQ·SQS 중 어느 브로커가 우리 요구사항에 맞는지 비교해야 할 때
    • 트랜잭션 커밋과 메시지 발행을 원자적으로 처리하는 방법(Outbox 패턴)이 필요할 때
    • Bull MQ나 BullMQ로 Node.js 백그라운드 작업 큐를 구성해야 할 때

    전달 보증 3단계 빠른 참조¶

    at-most-once — 최대 한 번¶

    메시지를 잃어도 되지만 중복은 절대 안 되는 경우다. 지표 수집이나 로그 집계처럼 일부 유실을 허용할 수 있을 때만 선택한다. 실제로 이 레벨이 진짜 요구사항인 경우는 드물다.

    Kafka — acks: 0으로 브로커 응답을 기다리지 않고, 컨슈머는 처리 전에 offset을 커밋한다.

    const producer = kafka.producer({ acks: 0 })
await producer.send({ topic: 'metrics', messages: [{ value: data }] })

await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    await consumer.commitOffsets([{ topic, partition, offset: message.offset }])
    await processMessage(message) // 처리 실패해도 재전달 없음
  }
})

    RabbitMQ — 처리 전에 ack을 먼저 보낸다. 처리 중 프로세스가 죽으면 메시지는 사라진다.

    channel.consume(queue, async (msg) => {
  channel.ack(msg)          // 처리 전 ack
  await processMessage(msg) // 실패해도 재전달 없음
})

    SQS — 수신 즉시 삭제한다. 이후 처리 중 실패하면 영구 유실한다.

    const { Messages } = await sqs.receiveMessage({ QueueUrl }).promise()
await sqs.deleteMessage({ QueueUrl, ReceiptHandle: msg.ReceiptHandle }).promise()
await processMessage(msg)

    at-least-once — 최소 한 번¶

    실무에서 기본값으로 선택하는 레벨이다. 유실 없이 전달하되 중복 수신 가능성이 있다. 컨슈머가 멱등하게 구현되어 있으면 된다.

    Kafka — acks: 'all'로 ISR 전체 복제 후 응답을 받고, 처리 완료 후 offset을 커밋한다. 커밋 전에 컨슈머가 재시작하면 같은 메시지를 다시 처리한다.

    const producer = kafka.producer({ acks: 'all', retries: 3 })

await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    await processMessage(message)
    await consumer.commitOffsets([{ topic, partition, offset: message.offset }])
  }
})

    RabbitMQ — 처리 성공 후 ack, 실패 시 nack으로 requeue한다. requeue 루프가 생기면 DLX(Dead Letter Exchange)로 빼야 한다.

    channel.consume(queue, async (msg) => {
  try {
    await processMessage(msg)
    channel.ack(msg)
  } catch {
    channel.nack(msg, false, true) // false: 단일 메시지, true: requeue
  }
})

    SQS — 기본 동작이 at-least-once다. VisibilityTimeout 안에 삭제하지 않으면 다른 컨슈머에게 재전달한다.

    const { Messages } = await sqs.receiveMessage({
  QueueUrl,
  VisibilityTimeout: 60
}).promise()

try {
  await processMessage(msg)
  await sqs.deleteMessage({ QueueUrl, ReceiptHandle: msg.ReceiptHandle }).promise()
} catch {
  // 삭제 안 하면 VisibilityTimeout 후 자동 재전달
}

    exactly-once — 정확히 한 번¶

    브로커 수준의 진짜 exactly-once는 Kafka에서만 가능하다. 트랜잭셔널 프로듀서와 트랜잭셔널 컨슈머를 조합해야 하고, read-process-write 파이프라인 전체가 Kafka 안에 있을 때만 보장된다. RabbitMQ·SQS는 브로커 수준 exactly-once가 없어서 애플리케이션 레벨 멱등성 키로 중복을 걸러낸다.

    Kafka — 트랜잭셔널 프로듀서

    const producer = kafka.producer({
  transactionalId: 'order-producer-1',
  idempotent: true,
  maxInFlightRequests: 1
})
await producer.connect()

await producer.transaction(async (txn) => {
  await txn.send({ topic: 'orders', messages: [{ value: orderData }] })
  await txn.sendOffsets({
    consumerGroupId: 'order-consumer',
    topics: [{ topic: 'input', partitions: [{ partition: 0, offset: nextOffset }] }]
  })
})

    SQS FIFO — 중복 제거 ID

    await sqs.sendMessage({
  QueueUrl: fifoQueueUrl,
  MessageBody: JSON.stringify(order),
  MessageGroupId: `order-${order.userId}`,
  MessageDeduplicationId: order.idempotencyKey // 5분 내 동일 키 재전송 차단
}).promise()

    RabbitMQ — 브로커가 exactly-once를 보장하지 않으므로 DB에 처리 이력을 기록해서 직접 거른다.

    channel.consume(queue, async (msg) => {
  const msgId = msg.properties.messageId
  const alreadyProcessed = await db.query(
    'SELECT 1 FROM processed_messages WHERE id = $1', [msgId]
  )
  if (alreadyProcessed.rows.length > 0) { channel.ack(msg); return }

  await db.transaction(async (trx) => {
    await processMessage(msg, trx)
    await trx.query('INSERT INTO processed_messages(id) VALUES($1)', [msgId])
  })
  channel.ack(msg)
})

    브로커 선택 판단 기준¶

    Kafka¶

    메시지 replay가 필요할 때 선택한다. offset을 되감아서 과거 메시지를 다시 처리할 수 있다는 점이 핵심이다. 여러 컨슈머 그룹이 같은 토픽을 독립적으로 소비해야 하거나, 초당 수십만 건 이상의 처리량이 필요할 때도 Kafka가 맞다. 클러스터 구성이 복잡하고 운영 난도가 높다. 메시지는 소비 후 즉시 삭제되지 않고 보존 기간(기본 7일)이 지나야 정리된다.

    RabbitMQ¶

    라우팅 유연성이 필요할 때 선택한다. Topic Exchange로 패턴 기반 라우팅, Header Exchange로 헤더값 기반 라우팅을 Exchange 설정만으로 처리한다. 메시지 우선순위 큐, TTL, 소비자 중심 푸시 모델이 필요한 태스크 큐에 맞다. Kafka보다 지연이 낮고 구성이 단순하다. 소비 후 즉시 삭제되므로 replay는 불가능하다.

    SQS¶

    AWS 인프라 위에서 운영 부담 없이 쓸 때 선택한다. SNS 팬아웃·Lambda 트리거와 조합해 서버리스 파이프라인을 구성하는 게 자연스럽다. 순서 보장이 필요하면 FIFO 큐를 쓰되 처리량이 낮다(배치 없이 초당 300건, 배치 시 3000건). 표준 큐는 순서 보장 없고 중복 가능성이 있으므로 컨슈머가 멱등해야 한다.

    읽는 순서¶

    1. Message Queue — 여기까지 읽으면 메시지 큐의 역할과 Kafka·RabbitMQ 기본 차이를 이해한다
    2. MQ 전달 보장 심화 — at-most-once·at-least-once·exactly-once 트레이드오프와 DLQ 설계를 익힌다
    3. API 멱등성 — 컨슈머가 중복 메시지를 받아도 안전하게 처리하는 멱등 설계를 구현한다
    4. 트랜잭셔널 아웃박스 패턴 — DB 트랜잭션과 메시지 발행을 원자적으로 묶는 아키텍처를 적용한다
    5. NestJS 작업 큐 Bull MQ / AWS SQS — 사용 환경에 맞는 브로커 구현으로 마무리한다
