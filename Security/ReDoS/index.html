    ReDoS - 정규식 하나가 이벤트 루프를 멈추는 과정¶

    입력 검증에 쓰는 정규식은 코드 리뷰에서 거의 안 읽힌다. 이메일 형식 검사 한 줄이 통과하면 그 뒤로는 아무도 들여다보지 않는다. 그런데 이 한 줄이 36자짜리 문자열 하나로 Node.js 프로세스를 12초 동안 멈춰 세울 수 있다. 공격자는 큰 페이로드도, 많은 요청도 필요 없다. 요청 하나면 된다.

    이 문서는 어떤 모양의 정규식이 터지는지, 터지는 속도가 실제로 얼마인지, 그리고 고치는 방법이 각각 어디서 조용히 실패하는지를 직접 돌려 본 결과로 정리한다. 입력 검증 일반론은 API 입력 검증, 요청 수 제한은 Rate Limiting에 있다. 여기서 다루는 문제는 요청 수 제한으로 막을 수 없다는 점이 핵심이다. 요청이 한 건이기 때문이다.

    왜 문자열 36자가 12초가 되는가¶

    대부분의 언어 표준 라이브러리(Python re, JavaScript, Java, Ruby, PCRE)는 정규식을 백트래킹으로 실행한다. 선택지가 갈리는 지점에서 한쪽을 먼저 시도하고, 나중에 실패하면 돌아와서 다른 쪽을 시도한다. 매칭이 성공하면 이 구조는 빠르다. 문제는 실패할 때 가능한 모든 경로를 다 확인해야 한다는 것이다.

    ^(a+)+$에 aaaa…!를 넣어 보면 이해가 쉽다. a가 n개 있을 때 바깥 +와 안쪽 +가 n개의 a를 나누는 방법은 2^(n-1)가지다. 마지막 ! 때문에 $가 실패하면 엔진은 그 2^(n-1)가지 분할을 전부 시도한 뒤에야 "불일치"를 답한다. 입력이 한 글자 늘 때마다 시간이 두 배가 된다.

    터지는 모양 세 가지¶

    중첩 수량자¶

    ^(a+)+$
^(\w+\s?)*$
^([a-zA-Z0-9]+[._-]?)+@example\.com$

    반복되는 그룹 안에 또 반복이 있고, 안쪽 반복이 같은 글자를 여러 방식으로 나눠 가질 수 있는 모양이다. 세 번째가 실무에서 가장 자주 보이는 이메일 검사 패턴이다. 로컬 파트에 . _ -를 허용하려고 [._-]?를 선택 사항으로 두면, 구분자가 없는 긴 영숫자 열이 곧 (a+)+와 같은 모양이 된다.

    겹치는 선택지¶

    ^(a|aa)+$

    반복 안의 선택지 두 개가 같은 글자열에 동시에 매칭될 수 있다. 증가 속도는 2배가 아니라 피보나치 수열이다.

    인접한 반복 (다항식 폭발)¶

    a*b      # 문자열 어디서든 검색할 때

    search는 매칭이 시작될 위치를 하나씩 옮기며 시도한다. a만 n개인 문자열에서 각 시작 위치마다 끝까지 a를 먹고 b가 없어서 실패하니 총 n²/2번 비교한다. 지수는 아니지만 입력이 길면 똑같이 문제가 된다.

    직접 돌려 본 수치¶

    Python 3.10.12(re)와 Node.js 20.20.0(V8)에서 같은 머신으로 쟀다. 입력은 모두 a를 n개 반복하고 마지막에 !를 붙인 문자열이다. 값은 실행마다 20~40% 흔들린다. 아래는 자릿수를 보기 위한 것이다.

    패턴 Python 3.10 증가 양상
    ^(a+)+$ n=20 0.05초, n=22 0.19초, n=24 1.1초, n=26 6.0초 2글자당 약 4~6배
    ^([a-zA-Z0-9]+[._-]?)+@example\.com$ n=20 0.11초, n=24 2.1초, n=26 8.7초 2글자당 약 4배
    ^(a\|aa)+$ n=28 0.12초, n=32 0.97초, n=34 2.4초 글자당 약 1.6배(피보나치)
    a*b 를 search n=10,000 0.075초, 20,000 0.24초, 40,000 1.5초, 80,000 7.5초 입력 두 배에 4~6배(2차)

    같은 이메일 패턴을 Node.js에서 재면 V8의 상수가 훨씬 작아서 더 긴 입력에서 비슷한 시간에 도달한다(Python은 n=24에서 2.1초).

    입력 길이 n 28 32 34 36 38
    걸린 시간(초) 0.025 0.079 0.285 2.0 9.0

    "V8은 빨라서 괜찮다"가 아니다. 지수 함수라서 상수가 작을 뿐, 몇 글자만 더 붙이면 같은 자리에 도달한다. 공격자는 입력 길이를 마음대로 정한다.

    Node.js의 (a+)+$ 결과는 n=24에서 0.95초, n=26에서 0.84초, n=28에서 3.6초였다. 단조 증가가 아니다. V8은 정규식을 처음 몇 번은 인터프리터로 돌리다가 네이티브 코드로 컴파일하는데(--regexp-tier-up), 그 전환 시점에 측정값이 섞인다. 한 번만 재서 "이 정도면 괜찮다"고 판단하면 틀린다. 길이를 바꿔 가며 반복 측정해야 한다.

    이벤트 루프를 막는다¶

    Node.js에서는 정규식이 메인 스레드에서 도니 다른 요청이 같이 멈춘다. 이메일 검증 엔드포인트와 헬스 체크를 한 프로세스에 띄워서 확인했다.

    // block.js - 서버를 자식 프로세스로 띄우고 부모가 지연을 잰다
const { fork } = require('child_process');
const http = require('http');
if (process.argv[2] === 'server') {
  http.createServer((q, r) => {
    if (q.url.startsWith('/validate')) {
      const v = decodeURIComponent(q.url.split('v=')[1] || '');
      r.end(String(/^([a-zA-Z0-9]+[._-]?)+@example\.com$/.test(v)));
    } else r.end('ok');
  }).listen(3998, () => process.send('up'));
} else {
  const child = fork(__filename, ['server']);
  const get = (path) => new Promise((res) => {
    const t0 = Date.now();
    http.get('http://127.0.0.1:3998' + path, (r) => { r.resume(); r.on('end', () => res(Date.now() - t0)); });
  });
  child.on('message', async () => {
    console.log('health (평상시)      ', await get('/health'), 'ms');
    const slow = get('/validate?v=' + 'a'.repeat(36) + '!');
    await new Promise((r) => setTimeout(r, 100));
    const h = get('/health');
    console.log('validate 응답        ', await slow, 'ms');
    console.log('health (validate 중) ', await h, 'ms');
    child.kill();
  });
}

    health (평상시)       15 ms
validate 응답         12203 ms
health (validate 중)  12103 ms

    /validate 하나가 12초 걸리는 동안 아무 관련 없는 /health도 12초 뒤에야 응답했다. 로드밸런서의 헬스 체크가 타임아웃(보통 2~5초)을 넘기면 인스턴스가 통째로 로테이션에서 빠진다. 요청 하나가 정상 인스턴스를 죽은 것으로 만들고, 다음 인스턴스로 같은 요청을 보내면 거기도 같은 일이 벌어진다. 서버 공격 방어 전반은 서버 취약점 공격 방어를 본다.

    멀티스레드 서버(Java, Python 멀티워커)에서는 영향이 스레드 하나로 한정되지만, 요청 수십 개면 스레드 풀이 모두 CPU를 태우며 막힌다.

    고치는 방법과 각각의 함정¶

    1. 패턴을 고친다 (가장 먼저)¶

    터지는 이유는 "같은 글자를 여러 방식으로 나눠 먹을 수 있다"는 점이다. 반복 경계를 반드시 구분자가 있어야 넘어가는 구조로 바꾸면 분할 방법이 하나로 정해진다.

    전: ^([a-zA-Z0-9]+[._-]?)+@example\.com$
후: ^[a-zA-Z0-9]+(?:[._-][a-zA-Z0-9]+)*@example\.com$

    후자는 "영숫자 덩어리, (구분자 + 영숫자 덩어리)의 반복"이다. 구분자가 있어야 다음 덩어리로 넘어가니 덩어리를 나누는 방법이 하나뿐이다. Python에서 같은 실험을 다시 돌렸다.

    fixed email  n=26      0.0002초
fixed email  n=50000   0.0017초
fixed ^a+$   n=100000  0.0006초

    입력 5만 자에서도 2ms 미만이다. 다만 두 패턴이 받아들이는 입력은 똑같지 않다. 같은 입력을 양쪽에 넣어 비교했다.

    a@example.com       old=True  new=True
a.b.c@example.com   old=True  new=True
a..b@example.com    old=False new=False
a-@example.com      old=True  new=False    <- 달라진다
ab_@example.com     old=True  new=False    <- 달라진다

    원래 패턴은 [._-]?가 마지막 덩어리 뒤에도 올 수 있어서 a-@example.com처럼 구분자로 끝나는 로컬 파트를 통과시켰다. 고친 패턴은 구분자 뒤에 영숫자가 와야 하므로 이런 입력을 거부한다. 이게 버그를 고친 것인지 기존 사용자를 막는 변경인지는 서비스가 정한다. 패턴을 바꿀 때는 기존 테스트 케이스와 운영 데이터에서 뽑은 실제 입력으로 차이를 먼저 확인한다. 정상 입력이 거부되면 그것도 장애다.

    2. 입력 길이를 먼저 자른다¶

    if (email.length > 254) return false;      // 정규식 앞에서
return EMAIL_RE.test(email);

    n이 작으면 지수 함수도 문제가 안 된다. 이메일 최대 길이는 254자(RFC 5321 경로 길이 256에서 꺾쇠 2자를 뺀 값)다. 다만 표에서 봤듯 Node에서 이메일 패턴은 36자에서 이미 2초다. 길이 제한을 254로 두면 위 패턴은 여전히 막지 못한다. 길이 제한은 다항식 폭발(a*b 형)에는 효과적이고, 지수 폭발에는 보조 수단일 뿐이다. 패턴 고치기와 같이 쓴다.

    더 흔한 실수는 순서다. 프레임워크가 요청 본문 전체를 파싱하는 동안 정규식을 쓰는 미들웨어가 먼저 돌면 길이 제한이 아무 소용 없다. 정규식에 문자열이 들어가기 직전에 길이를 확인한다.

    3. 선형 시간 엔진을 쓴다 (RE2)¶

    RE2는 백트래킹 대신 유한 오토마톤으로 매칭해서 입력 길이에 비례하는 시간에 끝난다. google-re2(Python 바인딩 1.1)로 같은 입력을 넣었다.

    re2 match ^(a+)+$  입력 5001자   0.0002초
re2 search a*b     n=80,000      0.0003초   (표준 re 는 7.5초)

    대신 선형 시간을 보장하기 위해 일부 문법을 포기한다. 컴파일 단계에서 에러가 난다.

    re2 backref:   invalid escape sequence: \1
re2 lookahead: invalid perl operator: (?=

    백레퍼런스와 룩어헤드가 쓰인 패턴은 그대로 옮길 수 없다. 기존 정규식을 RE2로 갈아끼우는 PR은 컴파일 에러로 터지거나, 에러를 삼키는 코드라면 검증이 통째로 사라진다. 옮길 때는 패턴 전수를 컴파일해 보는 테스트가 먼저다. Node.js에는 re2 npm 패키지가 있지만 이 문서에서 직접 돌려 보지는 않았다.

    4. 타임아웃이 있는 라이브러리¶

    표준 re에는 타임아웃이 없다. 서드파티 regex 모듈(2026.9.29로 확인)은 timeout 인자가 있다.

    import regex
try:
    regex.match(r'^(a|aa)+$', 'a' * 40 + '!', timeout=0.5)
except TimeoutError:
    ...   # 0.51초 후에 예외

    (a|aa)+는 0.5초에 맞춰 TimeoutError가 났다. 반면 ^(a+)+$와 이메일 패턴은 regex 모듈이 타임아웃에 걸리기 전에 0.000초에 끝냈다. 이 모듈이 일부 패턴을 내부 최적화로 막아 주는 것으로 보이는데, 어떤 패턴까지 막아 주는지 믿을 수 없으니 타임아웃을 안전장치로 쓰고 패턴 자체를 고치는 일을 생략하면 안 된다.

    5. V8의 폴백 플래그 (Node.js)¶

    V8에는 백트래킹이 너무 많아지면 선형 시간 엔진으로 넘어가는 실험 기능이 있다(V8 블로그). Node 20에서 플래그를 켜고 (a+)+$에 a를 40개 넣었다.

    node --enable-experimental-regexp-engine-on-excessive-backtracks redos3.js
# n=40 false 0.0016초   (플래그 없이는 n=28 만으로 3.6초였던 패턴)

    기본값은 꺼져 있고, 지원하지 않는 구문이 있는 패턴은 대상이 아니다(위 V8 블로그에 제약이 정리돼 있다). 실행 플래그라서 배포 환경(NODE_OPTIONS)에 명시해야 하고, 코드만 봐서는 보호되고 있다는 사실이 안 보인다. 개발자 PC에서는 터지고 프로덕션에서는 안 터지는 상황이 생겨 원인 파악을 어렵게 한다.

    6. lookahead + 백레퍼런스로 원자 그룹 흉내¶

    JavaScript에는 원자 그룹((?>...))이 없지만 룩어헤드 캡처와 백레퍼런스로 같은 효과를 낸다. 룩어헤드는 한 번 매칭하면 그 결과를 다시 바꾸러 돌아오지 않는다.

    /^(?=(a+))\1$/.test('a'.repeat(100000) + '!');   // 0.0003초

    패턴을 도저히 단순하게 못 바꾸는 경우의 마지막 수단이다. 그룹 번호가 하나씩 밀리고 읽기 어려워서 유지보수 비용이 크다. Python은 3.11부터 원자 그룹 (?>...)과 소유 수량자(a++)를 re가 직접 지원한다(What's New in 3.11). 이 문서의 실험 환경이 3.10이라 표준 re로는 직접 확인하지 못했고, 서드파티 regex 모듈에서 (?>a+)+와 (a++)+가 둘 다 0.0002초에 끝나는 것만 확인했다.

    코드에서 찾는 법¶

    정적 검사로 완벽히 찾는 것은 어렵다. 중첩 수량자를 grep하는 간단한 휴리스틱을 돌려 봤더니 안전하게 고친 ^[a-z]+(?:[._-][a-z]+)*$까지 "의심"으로 잡았다. 반복 안에 반복이 있다는 이유만으로는 위험 여부를 가를 수 없다. 위험한 것은 안쪽 반복이 바깥 반복과 같은 글자를 나눠 가질 수 있을 때이고, 그건 문법 모양이 아니라 의미다.

    그래서 정적 판별 대신 터지는 입력을 실제로 넣어 보는 방식이 오탐이 적다. 반복 단위를 가진 문자열(a, 1, 공백, a.)을 길이를 키워가며 만들어 마지막에 불일치 문자를 붙이고, 자식 프로세스에서 1초 제한으로 돌린다.

    import multiprocessing as mp, re, time

def _run(pattern, s, q):
    t = time.perf_counter(); re.search(pattern, s); q.put(time.perf_counter() - t)

def timed(pattern, s, limit=1.0):
    q = mp.Queue(); p = mp.Process(target=_run, args=(pattern, s, q))
    p.start(); p.join(limit)
    if p.is_alive():
        p.terminate(); return None
    return q.get()

def probe(pattern, seeds=("a", "1", " ", "a1", "a.", "a ")):
    for seed in seeds:
        for n in (8, 12, 16, 20, 24, 28):
            if timed(pattern, seed * n + "!") is None:
                return f"폭발  seed={seed!r} n={n}"
    return "통과 (이 입력들에서는 터지지 않음 - 증명은 아님)"

    폭발  seed='a' n=28   ^(a+)+$
폭발  seed='a' n=24   ^([a-zA-Z0-9]+[._-]?)+@example\.com$
폭발  seed='a' n=24   ^(\w+\s?)*$
통과                  ^[a-zA-Z0-9]+(?:[._-][a-zA-Z0-9]+)*@example\.com$
통과                  ^\d{3}-\d{4}$

    "통과"는 이 입력들에서 안 터졌다는 뜻이지 안전하다는 증명이 아니다. 시드를 늘릴수록 잡는 범위가 넓어진다. 정규식을 새로 추가하거나 바꾸는 PR의 단위 테스트에 이 프로브를 붙이면 사고가 나기 전에 막을 수 있다.

    정리¶

    • 요청 수 제한으로는 못 막는다. 요청 한 건이 서버를 멈춘다.
    • 사용자 입력에 적용하는 정규식은 중첩 수량자와 겹치는 선택지를 의심한다.
    • 방어 순서는 패턴 재작성이 1순위, 길이 제한과 타임아웃은 보조다. 길이 제한은 지수 폭발에는 모자란다.
    • 엔진을 바꾸면(RE2) 문법 호환이 깨지는 곳이 컴파일 에러로 드러나는지 테스트해 둔다.
    • 측정은 반복해서 한다. V8의 인터프리터-컴파일 전환 때문에 한 번 잰 값은 믿을 수 없다.
