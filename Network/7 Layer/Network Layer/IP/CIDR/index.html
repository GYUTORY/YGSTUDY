    CIDR¶

    CIDR(Classless Inter-Domain Routing)은 IP 주소와 함께 슬래시 뒤에 숫자를 붙여 네트워크 크기를 나타내는 표기법이다. /24 같은 prefix가 그것이다. 1993년 RFC 1519로 표준화됐고, 그전까지는 클래스 단위(A/B/C)로만 주소를 할당해서 낭비가 심했다.

    /prefix 읽는 법과 범위 계산¶

    192.168.1.0/24에서 /24는 32비트 중 앞 24비트가 네트워크 부분이라는 뜻이다. 나머지 8비트(32-24)가 호스트 부분이다.

    192.168.1.0/24

IP:     11000000.10101000.00000001. 00000000
마스크: 11111111.11111111.11111111. 00000000
                                   ^^^^^^^^
                                   호스트 8비트 = 2^8 = 256개 주소

    여기서 세 가지 주소를 계산한다.

    네트워크 주소: 호스트 비트를 전부 0으로 만든 주소다. 192.168.1.0이 된다. 라우팅 테이블에서 이 블록을 대표하는 주소로 쓴다.

    브로드캐스트 주소: 호스트 비트를 전부 1로 만든 주소다. 192.168.1.255가 된다. 서브넷 전체에 패킷을 뿌릴 때 목적지로 쓴다.

    사용 가능한 호스트 범위: 192.168.1.1 ~ 192.168.1.254, 총 254개다. 공식으로는 2^(32-prefix) - 2다. 네트워크 주소와 브로드캐스트 주소를 뺀다.

    prefix가 작아질수록 블록이 커진다.

    prefix 마스크 총 주소 호스트 수 용도
    /30 255.255.255.252 4 2 라우터 P2P 링크
    /29 255.255.255.248 8 6 소규모 세그먼트
    /28 255.255.255.240 16 14 작은 서비스 서브넷
    /27 255.255.255.224 32 30 부서 단위
    /26 255.255.255.192 64 62 중간 크기 서브넷
    /25 255.255.255.128 128 126 큰 서브넷
    /24 255.255.255.0 256 254 일반 서브넷
    /22 255.255.252.0 1,024 1,022 VPC 서브넷
    /20 255.255.240.0 4,096 4,094 큰 VPC
    /16 255.255.0.0 65,536 65,534 VPC 전체

    특이한 두 케이스가 있다. /31은 네트워크·브로드캐스트 주소가 없고 두 호스트만 있다(RFC 3021). 라우터 P2P 링크에서 주소 낭비를 줄이려고 쓴다. /32는 단일 호스트 주소다. 보안그룹에서 특정 IP 하나만 허용할 때 1.2.3.4/32로 쓴다.

    계산 도구¶

    매번 직접 계산하기 번거롭다. Python으로 확인하는 경우가 많다.

    import ipaddress

net = ipaddress.ip_network("192.168.1.0/24", strict=False)

print(net.network_address)   # 192.168.1.0
print(net.broadcast_address) # 192.168.1.255
print(net.netmask)           # 255.255.255.0
print(net.num_addresses)     # 256
print(list(net.hosts())[0])  # 192.168.1.1  (첫 번째 호스트)
print(list(net.hosts())[-1]) # 192.168.1.254 (마지막 호스트)

# 특정 IP가 이 블록에 속하는지 확인
print(ipaddress.ip_address("192.168.1.50") in net)  # True
print(ipaddress.ip_address("192.168.2.1") in net)   # False

    strict=False를 주면 192.168.1.56/24처럼 호스트 비트가 켜진 주소도 네트워크로 해석한다. strict=True(기본값)면 ValueError가 난다. 실수로 호스트 주소를 네트워크 주소 자리에 넣은 경우에 에러가 발생하기 때문에, 입력이 사용자에게서 오는 경우라면 strict=False가 편하다.

    bash에서 빠르게 확인하려면 ipcalc나 sipcalc를 쓴다.

    # ipcalc 설치: apt install ipcalc 또는 yum install ipcalc
ipcalc 10.0.0.0/20

# 출력 예시
Address:   10.0.0.0             00001010.00000000. 0000|0000.00000000
Netmask:   255.255.240.0 = 20   11111111.11111111. 1111|0000.00000000
Wildcard:  0.0.15.255           00000000.00000000. 0000|1111.11111111
=>
Network:   10.0.0.0/20          00001010.00000000. 0000|0000.00000000
HostMin:   10.0.0.1             00001010.00000000. 0000|0000.00000001
HostMax:   10.0.15.254          00001010.00000000. 0000|1111.11111110
Broadcast: 10.0.15.255          00001010.00000000. 0000|1111.11111111
Hosts/Net: 4094

# 두 블록이 겹치는지 확인 (Python)
python3 -c "
import ipaddress
a = ipaddress.ip_network('10.0.0.0/20')
b = ipaddress.ip_network('10.0.8.0/22')
print(a.overlaps(b))  # True: 겹침
"

    슈퍼넷팅과 라우트 집약¶

    여러 개의 작은 블록을 하나의 큰 블록으로 합치는 걸 슈퍼넷팅(supernetting) 또는 라우트 집약(route aggregation)이라고 한다. ISP가 수천 개의 라우팅 테이블 항목을 줄일 때 쓰던 기법인데, VPC 피어링이나 VPN 연결에서도 직접 마주치는 개념이다.

    4개의 /24 블록:
192.168.0.0/24
192.168.1.0/24
192.168.2.0/24
192.168.3.0/24

이진수로 보면:
192.168.0.0  = ...11000000.10101000.000000|00.00000000
192.168.1.0  = ...11000000.10101000.000000|01.00000000
192.168.2.0  = ...11000000.10101000.000000|10.00000000
192.168.3.0  = ...11000000.10101000.000000|11.00000000
                                         ^^ 마지막 2비트만 다름

공통 prefix는 앞 22비트 → 192.168.0.0/22로 집약

    집약이 가능하려면 두 조건을 충족해야 한다. 블록들이 연속해 있어야 하고, 집약 결과 블록의 크기가 2의 제곱수여야 한다. 192.168.1.0/24와 192.168.3.0/24 둘만 묶으려 하면 중간에 192.168.2.0/24가 포함되기 때문에 /22로 집약하면 원치 않는 주소까지 포함된다.

    import ipaddress

nets = [
    ipaddress.ip_network("192.168.0.0/24"),
    ipaddress.ip_network("192.168.1.0/24"),
    ipaddress.ip_network("192.168.2.0/24"),
    ipaddress.ip_network("192.168.3.0/24"),
]

# 집약 결과
for supernet in ipaddress.collapse_addresses(nets):
    print(supernet)  # 192.168.0.0/22

    실제로 이게 필요한 상황은 AWS VPC 피어링 설정이다. 피어링된 VPC의 라우팅 테이블에 /24짜리 4개를 각각 등록하는 대신 /22 하나로 묶으면 관리가 단순해진다. 단, 집약 범위 안에 없는 주소가 실제로 피어링된 VPC에 있으면 라우팅이 잘못 동작한다는 걸 주의해야 한다.

    ACL과 보안그룹에서의 실수¶

    보안 규칙을 CIDR로 작성할 때 가장 흔한 실수 두 가지다.

    의도보다 넓게 열린 경우

    # 특정 사무실 IP(203.0.113.45)만 허용하려 했는데
inbound: 203.0.113.0/24 허용

# 이렇게 하면 203.0.113.0 ~ 203.0.113.255, 즉 254개 IP가 열린다
# /32로 써야 의도한 대로 한 IP만 허용된다
inbound: 203.0.113.45/32

    보안그룹 리뷰를 하다 보면 /24나 /16으로 퍼블릭 IP 대역을 열어둔 케이스가 생각보다 많다. 관리자가 자기 IP로 접속할 때 DHCP로 IP가 바뀌어서 범위를 넓혀놓은 경우다.

    0.0.0.0/0의 의미

    # 이건 모든 IPv4 주소를 의미한다
inbound: 0.0.0.0/0 허용

# IPv6까지 열려면
inbound: ::/0 허용

    AWS에서 아무 생각 없이 인터넷 게이트웨이 설정할 때 라우팅 테이블에 0.0.0.0/0 → IGW를 넣는데, 보안그룹에서도 인바운드에 0.0.0.0/0으로 22번 포트를 열어두는 경우가 있다. 실제로 배스천 호스트에 이런 설정이 있었고 브루트포스 시도 로그가 하루에 수천 건 쌓인 걸 본 적 있다.

    서브넷 주소가 아닌 호스트 주소를 쓴 경우

    AWS 콘솔에서는 192.168.1.50/24를 입력하면 192.168.1.0/24로 자동 교정해준다. 하지만 Terraform이나 API로 직접 넣을 때는 에러가 나거나, 설정에 따라 의도와 다르게 저장되는 경우가 있다. CIDR 블록은 항상 네트워크 주소로 표기한다.

    # 호스트 주소를 네트워크 주소로 변환
import ipaddress

host_with_prefix = "192.168.1.50/24"
network = ipaddress.ip_interface(host_with_prefix).network
print(str(network))  # 192.168.1.0/24

    AWS, k8s, Docker에서의 CIDR 충돌¶

    클라우드 환경에서 여러 네트워크를 연결할 때 CIDR 충돌이 가장 골치 아프다. 충돌이 생기면 라우팅이 애매해지고, 어느 쪽 네트워크로 패킷이 가는지 예측하기 어려워진다.

    AWS VPC 설계¶

    VPC를 나중에 피어링하거나 Direct Connect로 온프레미스와 연결할 계획이라면, VPC CIDR를 처음부터 겹치지 않게 잡는 게 중요하다. 피어링 이후에는 CIDR을 바꿀 수 없다.

    나쁜 예 — 나중에 피어링하려 했는데 겹침:
VPC-A: 10.0.0.0/16 (10.0.0.0 ~ 10.0.255.255)
VPC-B: 10.0.0.0/16  ← 동일 범위, 피어링 불가

좋은 예 — 처음부터 대역을 나눠서 할당:
VPC-A: 10.0.0.0/16  (dev)
VPC-B: 10.1.0.0/16  (staging)
VPC-C: 10.2.0.0/16  (prod)
온프레미스: 10.10.0.0/16

    서브넷 설계도 마찬가지다. 가용 영역 수와 서브넷 역할(public/private/data)을 미리 정하고 CIDR을 나눠야 나중에 추가가 편하다.

    VPC: 10.0.0.0/16

AZ-a:
  public:  10.0.0.0/24
  private: 10.0.10.0/24
  data:    10.0.20.0/24

AZ-b:
  public:  10.0.1.0/24
  private: 10.0.11.0/24
  data:    10.0.21.0/24

AZ-c:
  public:  10.0.2.0/24
  private: 10.0.12.0/24
  data:    10.0.22.0/24

    두 번째 옥텟으로 AZ를 구분(0, 1, 2), 세 번째 옥텟 십의 자리로 역할을 구분(0=public, 10=private, 20=data)하는 식으로 체계를 잡으면 IP만 보고도 어떤 서브넷인지 알 수 있다.

    Kubernetes Pod CIDR 충돌¶

    쿠버네티스 클러스터를 생성할 때 Pod CIDR과 Service CIDR을 지정한다. 이 값이 VPC CIDR나 온프레미스 네트워크와 겹치면 Pod에서 외부로 나가는 트래픽의 라우팅이 깨진다.

    # kubeadm 초기화 예시
kubeadm init \
  --pod-network-cidr=100.64.0.0/16 \
  --service-cidr=10.96.0.0/12

    기본값으로 10.244.0.0/16(flannel), 192.168.0.0/16(calico)을 쓰는 CNI가 많은데, 이 대역이 회사 내부망이나 VPC와 겹치는 경우가 실제로 있다. 특히 192.168.0.0/16는 사무실 WiFi 대역과 겹치기 쉽다.

    EKS를 쓴다면 100.64.0.0/10이나 198.19.0.0/16 같은 예약 대역을 Pod CIDR로 쓰기도 한다. 이 대역은 공인 인터넷에서 라우팅되지 않는 대역이라 VPC와 충돌할 일이 적다.

    겹침 확인은 간단하다.

    import ipaddress

def check_overlap(cidr_list):
    nets = [ipaddress.ip_network(c) for c in cidr_list]
    conflicts = []
    for i, a in enumerate(nets):
        for j, b in enumerate(nets):
            if i >= j:
                continue
            if a.overlaps(b):
                conflicts.append((cidr_list[i], cidr_list[j]))
    return conflicts

cidrs = [
    "10.0.0.0/16",    # VPC
    "10.1.0.0/16",    # 피어링 VPC
    "192.168.0.0/16", # Pod CIDR (문제 가능성)
    "192.168.100.0/24", # 사무실 망
]

for a, b in check_overlap(cidrs):
    print(f"충돌: {a} ↔ {b}")
# 충돌: 192.168.0.0/16 ↔ 192.168.100.0/24

    Docker 네트워크¶

    Docker는 기본 브리지 네트워크로 172.17.0.0/16을 쓴다. docker network create로 커스텀 네트워크를 만들면 172.18.0.0/16, 172.19.0.0/16 순서로 자동 할당한다. 서버에 docker가 설치된 상태에서 172.16.0.0/12 대역(172.16.0.0 ~ 172.31.255.255)을 내부망으로 쓰고 있으면 충돌이 생긴다.

    # Docker가 쓰는 브리지 네트워크 확인
docker network ls
docker network inspect bridge | grep Subnet

# 기본 브리지 CIDR 변경 (/etc/docker/daemon.json)
{
  "bip": "172.26.0.0/16",
  "default-address-pools": [
    {"base": "172.27.0.0/16", "size": 24}
  ]
}

    docker-compose로 서비스를 띄울 때도 기본 네트워크 CIDR이 자동 할당되는데, networks 블록에서 명시하지 않으면 172.x.0.0/16 대역 중 하나가 선택된다. 회사 VPN을 쓰는 환경에서 docker를 사용하다가 VPN 트래픽이 docker 브리지로 라우팅되는 문제가 생기는 경우가 있다. 이럴 때는 daemon.json에서 docker가 쓸 대역을 회사망과 겹치지 않게 고정하는 게 낫다.

    실제 충돌 트러블슈팅¶

    사례 1: VPN 연결 후 특정 서버만 안 되는 문제

    회사 VPN을 연결했는데 특정 내부 서버(10.0.1.50)에 접속이 안 됐다. 다른 서버는 됐다. 원인은 로컬 docker 네트워크가 10.0.0.0/16을 쓰고 있어서 10.0.1.0/24 대역 라우팅을 docker 브리지가 가로챘기 때문이다.

    # 라우팅 테이블 확인
ip route show

# 문제가 된 항목
10.0.0.0/16 dev docker0 proto kernel scope link src 10.0.0.1

# VPN 라우트보다 docker 브리지 라우트가 더 구체적이거나 우선순위가 높아서
# 10.0.1.0/24 트래픽이 VPN이 아닌 docker0으로 갔다

# 확인
ip route get 10.0.1.50
# 10.0.1.50 dev docker0 src 10.0.0.1  ← 잘못된 경로

    해결은 docker 기본 브리지를 다른 대역으로 옮기거나, 해당 경로를 VPN 인터페이스로 명시하는 것이다.

    사례 2: EKS Pod에서 외부 API 호출 실패

    EKS 클러스터에서 Pod가 특정 외부 API(43.200.x.x 대역)를 못 불렀다. Node에서는 됐다. Pod CIDR을 10.0.0.0/8로 잡았는데, 그 외부 API 서버 IP가 10.x.x.x 대역이었다. Pod에서 10.x.x.x로 나가는 트래픽을 클러스터 내부로 라우팅해버렸다.

    Pod CIDR을 10.0.0.0/8처럼 너무 크게 잡으면 이런 일이 생긴다. /16 정도로 충분한 경우가 많다.

    사례 3: Terraform으로 서브넷 생성 실패

    Error: error creating subnet: InvalidSubnet.Conflict: The CIDR '10.0.1.0/24' 
conflicts with another subnet

    같은 VPC에 이미 10.0.0.0/23이 있었다. /23은 10.0.0.0 ~ 10.0.1.255를 포함하기 때문에 10.0.1.0/24가 그 안에 들어간다.

    import ipaddress

existing = ipaddress.ip_network("10.0.0.0/23")
new_subnet = ipaddress.ip_network("10.0.1.0/24")

print(new_subnet.subnet_of(existing))  # True: 기존 서브넷 안에 포함됨
print(existing.overlaps(new_subnet))   # True: 겹침

    Terraform 코드로 서브넷을 여러 개 정의할 때 겹침 없이 CIDR을 자동 계산하는 방법이다.

    import ipaddress

vpc_cidr = "10.0.0.0/16"
vpc = ipaddress.ip_network(vpc_cidr)

# /24 서브넷 10개 생성 (겹치지 않게)
subnets = list(vpc.subnets(new_prefix=24))

for i, subnet in enumerate(subnets[:6]):
    print(f"subnet_{i} = \"{subnet}\"")

# subnet_0 = "10.0.0.0/24"
# subnet_1 = "10.0.1.0/24"
# subnet_2 = "10.0.2.0/24"
# ...
