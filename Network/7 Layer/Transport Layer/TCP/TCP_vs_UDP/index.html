    TCP vs UDP - 실무 선택 기준¶

    핵심 차이¶

    TCP와 UDP는 같은 Transport Layer 프로토콜이지만 설계 목표가 다르다.

    TCP는 연결 지향이다. 3-Way Handshake로 연결을 수립하고, 패킷 순서를 보장하고, 손실된 패킷을 재전송한다. 수신측이 처리할 수 있는 속도를 넘지 않도록 흐름 제어도 한다. 이 모든 기능의 대가가 지연이다.

    UDP는 그냥 보낸다. 연결 수립 없고, 순서 보장 없고, 재전송 없다. 패킷이 중간에 사라지면 그냥 없어진다. 대신 오버헤드가 거의 없다.

    TCP 헤더: 최소 20바이트 (옵션 포함 최대 60바이트)
UDP 헤더: 8바이트 고정
    항목 TCP UDP
    연결 수립 3-Way Handshake 필요 없음
    순서 보장 보장 보장 안 함
    재전송 자동 없음
    흐름 제어 있음 없음
    혼잡 제어 있음 없음
    지연 상대적으로 높음 낮음
    브로드캐스트/멀티캐스트 불가 가능

    실무 선택 기준¶

    "신뢰성이 필요하면 TCP, 속도가 중요하면 UDP"라는 말이 흔히 나오는데, 실제로는 더 복잡하다.

    TCP를 선택하는 경우: - 데이터 유실이 비즈니스 로직을 깨는 경우. 파일 전송, 금융 트랜잭션, HTTP API 응답 등 - 순서가 중요한 경우. DB 쿼리 결과, 메시지 스트림처럼 순서가 뒤바뀌면 의미가 달라지는 데이터 - 재전송 처리를 직접 구현하기 싫은 경우. UDP 위에서 신뢰성을 구현하면 결국 TCP를 다시 만드는 것과 같다

    UDP를 선택하는 경우: - 최신 데이터만 필요하고 오래된 패킷이 도착해도 의미가 없는 경우. 실시간 게임 캐릭터 위치, 센서 데이터 - 지연이 재전송보다 치명적인 경우. 음성/영상 통화에서 100ms 전 데이터는 버리는 게 낫다 - 애플리케이션 레벨에서 손실을 허용할 수 있는 경우. 로그 스트리밍, 모니터링 메트릭

    게임 서버¶

    게임 서버는 UDP를 많이 쓰지만, 모든 것을 UDP로 보내지는 않는다.

    UDP로 보내는 것: 캐릭터 위치, 입력 이벤트, 시야 정보. 이건 60ms 전 위치 정보가 지금 와도 쓸모없다. 도착하면 쓰고 안 오면 다음 프레임 데이터를 기다린다.

    TCP로 보내는 것: 아이템 획득, 스킬 사용, 채팅. 이건 유실되면 안 된다. 아이템 획득 패킷이 사라지면 클라이언트는 아이템을 얻었다고 생각하는데 서버는 모르는 상황이 된다.

    실제 구현에서는 UDP 소켓을 열고 애플리케이션 레벨에서 패킷에 시퀀스 번호를 붙인다. 수신측에서 시퀀스 번호를 보고 오래된 패킷은 버리고, 중요한 이벤트는 ACK를 기다리는 방식으로 부분적인 신뢰성을 구현한다.

    클라이언트 --UDP--> 서버
패킷 구조: [seq: 1234] [type: MOVE] [x: 100, y: 200]

서버는 seq가 이전에 받은 것보다 작으면 드롭
MOVE는 드롭해도 다음 패킷이 오면 됨

    Valve의 Source 엔진이나 Unity Netcode 같은 게임 네트워크 라이브러리가 이 패턴을 구현해둔다.

    스트리밍¶

    비디오 스트리밍은 생각보다 복잡하다.

    RTP(Real-time Transport Protocol): 전통적인 영상 통화, IPTV가 쓰는 방식. UDP 위에서 동작한다. 타임스탬프와 시퀀스 번호가 있어서 수신측이 재생 타이밍을 맞출 수 있다. 패킷이 사라지면 화면에 노이즈가 생기거나 프레임이 빠지는데, 이게 패킷이 오길 기다리다가 영상이 멈추는 것보다 낫다고 판단한 결과다.

    HTTP 기반 스트리밍(HLS, DASH): YouTube나 Netflix가 쓰는 방식. TCP다. 영상을 작은 세그먼트 파일로 나눠서 HTTP로 받는다. 지연이 수 초 발생하지만 버퍼링으로 감춘다. 재전송이 자동으로 되니까 화질이 안정적이다.

    실시간성이 중요한지, 안정성이 중요한지로 나뉜다. 라이브 스포츠 중계는 몇 초 지연이 허용되는지가 관건이다. Zoom 같은 화상회의는 RTP 계열을 쓰면서 패킷 손실이 10% 넘어가면 화질을 낮추는 적응형 비트레이트를 쓴다.

    DNS¶

    DNS는 기본적으로 UDP 포트 53을 쓴다. 요청과 응답이 단순하고 크기가 작아서 연결 수립 없이 한 번에 주고받을 수 있다.

    응답이 512바이트를 넘으면 TCP로 전환한다. DNSSEC 레코드나 큰 zone transfer는 512바이트를 넘는 경우가 많다. 이걸 "TCP fallback"이라고 부른다.

    DNS over TCP가 필요한 상황: - Zone transfer (서버 간 DNS 레코드 동기화): 항상 TCP - 응답이 512바이트 초과: UDP 응답에 TC(Truncation) 플래그가 세팅되면 클라이언트가 TCP로 재시도 - DNS over TLS(DoT): TCP 853 포트

    # tcpdump로 DNS TCP fallback 확인
tcpdump -i eth0 port 53

# 응답에 TC 비트가 세팅되면 TCP 재시도가 일어남
# dig 명령으로 강제 TCP 사용
dig +tcp google.com

    DNS 서버 운영 시 iptables나 보안 그룹에서 TCP 53 포트를 막으면 큰 응답이 오는 쿼리가 실패한다. 이게 의외로 흔한 장애 원인이다.

    파일 전송¶

    파일 전송은 거의 무조건 TCP다. 파일은 한 비트라도 바뀌면 안 된다. 일반 텍스트 파일이야 손상이 눈에 보이지만, 압축 파일이나 바이너리는 패킷 하나만 사라져도 파일 전체가 열리지 않는다.

    FTP, SFTP, SCP, rsync 모두 TCP 기반이다. 속도가 느리다고 느껴지면 대부분 네트워크 지연이나 TCP 윈도우 크기 문제다.

    고속 파일 전송이 필요한 경우에는 TCP 튜닝이 먼저다. 윈도우 크기, 버퍼 크기를 조정하면 같은 대역폭에서 처리량이 크게 달라진다. 그래도 부족하면 QUIC 기반 전송 도구를 고려한다.

    QUIC와 HTTP/3¶

    QUIC는 UDP 위에서 TCP가 주던 신뢰성을 구현한 프로토콜이다. 구글이 만들었고 HTTP/3의 기반이다.

    왜 TCP를 그냥 개선하지 않고 UDP 위에 새로 만들었나:

    TCP는 OS 커널에 구현되어 있다. 커널을 수정하면 모든 운영체제, 모든 네트워크 장비가 업데이트되어야 한다. 실제로 배포가 몇 년이 걸린다. 중간 라우터들이 TCP 헤더를 파싱하고 최적화하는데, TCP 헤더 구조를 바꾸면 이 장비들이 오동작할 수 있다.

    UDP 위에 구현하면 애플리케이션 레벨에서 업데이트할 수 있다. Chrome 브라우저 업데이트 하나로 새 기능을 배포할 수 있다.

    QUIC가 해결하는 TCP의 문제들:

    Head-of-line blocking: TCP는 하나의 스트림이다. 패킷 하나가 유실되면 그 뒤의 모든 데이터가 기다린다. HTTP/2도 TCP 위에서 멀티플렉싱을 하는데, TCP 레벨에서 패킷 유실이 생기면 모든 HTTP 스트림이 멈춘다. QUIC는 스트림을 각각 독립적으로 관리해서, 스트림 A의 패킷이 유실돼도 스트림 B는 계속 진행된다.

    연결 수립 지연: TCP + TLS는 최소 2-RTT가 필요하다. QUIC는 TLS 1.3과 통합되어 1-RTT로 연결을 수립한다. 이전에 연결한 서버라면 0-RTT도 가능하다.

    네트워크 전환: 모바일 환경에서 WiFi에서 LTE로 바뀌면 IP가 바뀐다. TCP는 연결이 끊긴다. QUIC는 Connection ID로 연결을 식별하기 때문에 IP가 바뀌어도 연결이 유지된다.

    # curl로 HTTP/3 테스트
curl -v --http3 https://example.com

# 응답 헤더에서 확인
< HTTP/3 200
< alt-svc: h3=":443"; ma=2592000

    QUIC의 트레이드오프도 있다. UDP는 방화벽에서 막히는 경우가 많다. 기업 네트워크에서 UDP를 제한하면 QUIC가 동작하지 않아서 HTTP/2로 폴백한다. 실제로 HTTP/3 지원 서버에서도 클라이언트 연결의 상당 비율이 아직 HTTP/2다.

    트러블슈팅 경험¶

    UDP 패킷 유실 디버깅

    UDP는 재전송이 없으니 유실을 애플리케이션 레벨에서 감지해야 한다. 시퀀스 번호를 패킷에 붙이고 수신측에서 갭을 추적하는 방식을 많이 쓴다. netstat -su로 UDP receive buffer overflow를 확인한다. 버퍼가 꽉 차서 패킷이 드롭되는 경우가 의외로 많다.

    # UDP 수신 에러 확인
netstat -su | grep -i error

# receive buffer 크기 확인 및 조정
sysctl net.core.rmem_max
sysctl -w net.core.rmem_max=26214400

# SO_RCVBUF 소켓 옵션으로 소켓별 조정도 가능

    TCP인데 왜 느린가

    TCP를 쓰는데 전송 속도가 기대치에 못 미치는 경우, 대부분 RTT가 높거나 TCP 윈도우가 작다. 대역폭 x RTT = BDP(Bandwidth-Delay Product)인데, 윈도우 크기가 BDP보다 작으면 링크를 다 쓰지 못한다. 서울-미국 간 RTT가 150ms이고 대역폭이 1Gbps면 BDP는 약 18MB다. 윈도우 크기가 4MB라면 대역폭의 22%밖에 못 쓴다.

    # TCP 연결 상태와 윈도우 크기 확인
ss -ti dst <서버IP>

# 커널 버퍼 크기 확인
sysctl net.ipv4.tcp_rmem
sysctl net.ipv4.tcp_wmem

    게임 서버에서 UDP 소켓 재사용

    게임 서버에서 UDP를 쓸 때 클라이언트별로 소켓을 만들지 말고 서버 측 소켓 하나로 모든 클라이언트 패킷을 받아야 한다. UDP는 비연결형이라 하나의 소켓에 여러 클라이언트 패킷이 섞여서 들어온다. recvfrom()으로 발신자 주소를 확인해서 어떤 클라이언트인지 구분한다. 클라이언트마다 소켓을 만들면 FD(file descriptor) 부족 문제가 생긴다.

    // UDP 서버에서 발신자 주소 확인
struct sockaddr_in client_addr;
socklen_t addr_len = sizeof(client_addr);
recvfrom(sock_fd, buffer, sizeof(buffer), 0,
         (struct sockaddr*)&client_addr, &addr_len);

// client_addr로 어떤 클라이언트인지 식별

    NAT 환경에서의 UDP

    NAT 뒤에 있는 클라이언트끼리 UDP로 P2P 통신을 하려면 UDP hole punching을 써야 한다. 두 클라이언트가 중간 서버에 UDP 패킷을 보내서 NAT 매핑을 만들고, 서버가 두 클라이언트의 외부 IP/포트를 서로에게 알려준다. 그 후 두 클라이언트가 동시에 상대방에게 패킷을 보내면 NAT 테이블에 매핑이 생기면서 연결이 된다. WebRTC가 이 방식을 쓴다.

    Symmetric NAT는 목적지마다 다른 포트를 할당해서 hole punching이 잘 안 된다. 이 경우 TURN 서버를 통해 중계해야 해서 UDP의 지연 이점이 사라진다.
