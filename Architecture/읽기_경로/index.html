    읽기 경로¶

    전체 구조¶

    클라이언트가 GET /orders/123을 날리면 응답이 돌아오기까지 데이터가 최대 7개 레이어를 거친다. 각 레이어는 자기 캐시에 데이터가 있으면 바로 반환하고, 없으면 다음 레이어로 넘긴다.

    Client
  → CDN
  → Reverse Proxy (nginx / Envoy)
  → App Server
      → Local Cache (in-process)
      → Redis
  → Read Replica
  → Primary DB

    단순해 보이지만 레이어마다 "얼마나 오래된 데이터를 허용할 것인가"의 기준이 달라서 설계 시 꽤 복잡해진다. 레이어가 늘어날수록 성능은 좋아지고 일관성은 약해진다는 게 이 구조의 핵심 트레이드오프다.

    CDN¶

    CDN이 serve하는 경우는 두 가지다: 정적 리소스, 그리고 캐시 가능한 API 응답.

    API 응답을 CDN에 캐싱하려면 조건이 맞아야 한다.

    • 사용자 식별 없이 공통으로 반환되는 데이터 (상품 목록, 카테고리 트리)
    • Cache-Control: public, max-age=N을 응답 헤더에 달 수 있는 경우
    • 수 분에서 수 시간 단위로 stale해도 비즈니스가 수용 가능한 경우

    사용자별로 다른 응답이 나와야 한다면 Cache-Control: private, no-store를 달아서 CDN이 캐싱하지 않게 한다. 여기서 자주 나오는 실수는 인증 없이도 조회할 수 있는 공개 API에 private을 달아두는 경우다. 상품 상세 API가 로그인 없이도 접근 가능한데 private을 달면 CDN 캐싱 혜택을 전혀 못 받는다.

    CDN에서 cache miss가 나면 origin(리버스 프록시)으로 요청이 넘어간다. CDN이 origin에 요청할 때 원본 클라이언트 IP는 X-Forwarded-For 헤더에 들어온다. 이걸 로깅 설정에서 빠뜨리면 트래픽 분석 시 클라이언트 IP 대신 CDN 엣지 서버 IP만 보여서 국가별/사용자별 분석이 불가능해진다.

    리버스 프록시¶

    CDN을 통과한 요청이 nginx나 Envoy에 도달한다. 읽기 경로에서 리버스 프록시는 세 가지 역할을 한다.

    로드밸런싱: 앱 서버가 여러 대면 요청을 분배한다. stateless JWT 인증을 쓴다면 Round-robin으로 충분하다. 세션 기반 인증이면 세션이 붙어있는 서버로 보내는 sticky session이 필요하다.

    SSL 종단: HTTPS를 리버스 프록시에서 끊고 내부 통신은 HTTP로 간다. 인증서 관리를 앱 서버마다 하지 않아도 된다.

    응답 캐싱: nginx의 proxy_cache로 앱 서버 응답을 캐싱할 수 있다. CDN과 역할이 겹쳐 보이지만, CDN은 외부 트래픽만 처리하기 때문에 내부 서비스 간 호출에는 효과가 없다. 서비스 A가 서비스 B를 반복 호출하는 패턴에서 리버스 프록시 캐싱이 유용하다.

    타임아웃 설정을 놓치면 나중에 병목이 된다. nginx의 proxy_read_timeout은 기본값이 60초인데, upstream이 이 시간 동안 응답을 안 하면 클라이언트는 60초를 기다린다. 슬로우 쿼리가 실행 중인 상황에서 요청이 몰리면 연결이 계속 쌓이고 앱 서버 연결 풀이 고갈된다. proxy_connect_timeout과 proxy_read_timeout은 서비스 특성에 맞게 명시적으로 설정해야 한다.

    앱 서버¶

    요청이 앱 서버에 도달하면 로컬 캐시 → Redis → DB 순서로 데이터를 찾는다.

    로컬 캐시¶

    Caffeine(Java), functools.lru_cache(Python) 같은 프로세스 내 캐시다. Redis보다 빠르다. 네트워크 홉이 없기 때문이다.

    문제는 앱 서버가 여러 대일 때다. 서버 A의 로컬 캐시에는 업데이트 전 데이터가 있고, 서버 B는 없는 경우 같은 요청이 어느 서버로 가느냐에 따라 다른 응답이 나온다. 이 불일치를 허용할 수 없는 데이터라면 로컬 캐시를 쓰지 않는다.

    로컬 캐시가 맞는 경우는 변경이 거의 없는 설정값(코드 테이블, 카테고리 구조), TTL이 짧아도 되는 데이터(30초~5분), 일시적인 불일치를 비즈니스가 허용하는 데이터다.

    캐시 invalidation을 명시적으로 해야 한다면 로컬 캐시는 복잡해진다. 서버 A에서 데이터를 변경했을 때 서버 B, C의 로컬 캐시를 무효화하려면 별도 이벤트 브로드캐스트가 필요하다. 이 정도 복잡도면 그냥 Redis를 쓰는 편이 낫다.

    @Bean
public Cache<String, ProductCategory> categoryCache() {
    return Caffeine.newBuilder()
        .expireAfterWrite(5, TimeUnit.MINUTES)
        .maximumSize(1000)
        .build();
}

public ProductCategory getCategory(Long categoryId) {
    return categoryCache.get(
        "category:" + categoryId,
        key -> categoryRepository.findById(categoryId).orElseThrow()
    );
}

    Redis¶

    로컬 캐시에 없으면 Redis로 간다. Redis는 애플리케이션 외부의 분산 캐시라서 앱 서버가 몇 대든 동일한 데이터를 본다.

    hit/miss 흐름은 단순하다. Redis GET으로 데이터가 있으면 역직렬화해서 반환하고, 없으면 DB를 조회한 뒤 Redis에 TTL과 함께 저장하고 응답한다.

    Redis miss 이후 DB 조회와 Redis SET 사이에 경쟁 조건이 생길 수 있다. 동시에 같은 key에 대해 Redis miss가 발생한 요청이 여러 개 들어오면 전부 DB를 조회한다. Cache Stampede라고 부르는 현상이다. 조회량이 많은 key의 캐시가 만료되는 순간 DB에 순간적인 부하가 몰린다.

    실용적인 대응은 TTL에 랜덤 jitter를 추가하는 거다. 만료 시간을 분산시키면 동시 만료 확률이 줄어든다.

    import random

BASE_TTL = 3600  # 1시간

def set_cache(key: str, value: dict) -> None:
    jitter = random.randint(0, BASE_TTL // 10)
    ttl = BASE_TTL + jitter
    redis_client.setex(key, ttl, json.dumps(value))

    Mutex 잠금 방식도 있다. Redis의 SETNX로 잠금을 잡고, 잠금을 획득한 요청만 DB를 조회해 캐시를 갱신하고 나머지는 잠금이 풀릴 때까지 대기 후 캐시에서 읽는다. 구현이 번거롭고 데드락 처리까지 고려하면 jitter 방식보다 실득이 적은 경우가 많다.

    DB 레이어¶

    Redis까지 miss면 DB로 간다.

    Read Replica¶

    읽기 요청은 Read Replica로 보내고 Primary는 쓰기 전용으로 둔다는 게 기본 원칙이다.

    문제는 Replication Lag이다. Primary에 쓰기가 발생하면 그 변경이 Replica에 반영되기까지 시간이 걸린다. MySQL 기준 평상시에는 밀리초 단위지만, 쓰기 부하가 높거나 Replica가 바이너리 로그 처리를 따라가지 못할 때 수십~수백 밀리초까지 벌어진다.

    Lag이 문제가 되는 시나리오는 쓰기 직후 같은 데이터를 읽는 경우다. 사용자가 프로필을 수정하고 바로 수정된 프로필 페이지를 요청하거나, 주문 생성 직후 주문 목록을 조회하면 Read Replica에서는 방금 쓴 데이터가 없을 수 있다.

    쓰기 직후 일정 시간 Primary에서 읽기: 쓰기가 발생한 직후 N밀리초 동안은 Primary에서 읽도록 라우팅한다. 세션에 "최근 쓰기 시각"을 저장하고, 읽기 요청 시 현재 시각과 비교해 Lag 예상 시간 이내면 Primary로 보낸다.

    public DataSource determineDataSource(String operation) {
    if ("write".equals(operation)) {
        return primaryDataSource;
    }

    Long lastWriteTime = (Long) session.getAttribute("lastWriteTime");
    if (lastWriteTime != null &&
        System.currentTimeMillis() - lastWriteTime < REPLICA_LAG_BUFFER_MS) {
        return primaryDataSource;
    }

    return replicaDataSource;
}

    Replica Lag 모니터링 후 임계치 초과 시 Primary 폴백: SHOW SLAVE STATUS의 Seconds_Behind_Master를 주기적으로 체크해서 임계치(예: 5초)를 넘으면 해당 Replica를 읽기 풀에서 제외한다. Spring의 AbstractRoutingDataSource로 동적 라우팅이 가능하다.

    Stale Read 허용: 사용자 피드, 통계 데이터, 추천 목록처럼 최신성이 덜 중요한 데이터는 Replica에서 그냥 읽는다. 1~2초 지연이 있어도 사용자가 체감하기 어렵다.

    어느 데이터가 stale read를 허용할 수 있는지 기준은 서비스마다 다르지만, 실무에서 많이 쓰는 구분선은 "사용자가 직접 변경한 데이터는 즉시 반영, 시스템이 자동 생성하는 집계 데이터는 허용"이다.

    Primary DB 직접 읽기¶

    강한 일관성이 필요한 경우 Primary에서 읽는다. 금융 거래, 재고 수량 확인, 결제 처리 직전 잔고 확인이 여기 해당한다. Primary에서 읽으면 Lag 문제가 없지만 Primary 부하가 증가한다. 읽기 쿼리를 최대한 효율적으로 만들고 인덱스를 철저히 관리해야 한다.

    CQRS 읽기 모델과의 연결¶

    CQRS를 적용하면 읽기 경로가 달라진다. 읽기 모델은 별도 저장소에 미리 계산된 형태로 저장돼 있어서, 복잡한 조인 없이 바로 꺼내 쓴다.

    읽기 경로에서 CQRS가 개입하는 지점은 앱 서버 레이어다. 읽기 서비스가 CQRS 읽기 모델 저장소(Elasticsearch, 별도 DB 등)에 직접 쿼리한다. Redis나 로컬 캐시를 읽기 모델 앞에 두는 것도 가능하다.

    Client → CDN → Reverse Proxy → Read Service → (Redis) → CQRS Read Model Store

    읽기 모델의 일관성 수준은 프로젝션 방식에 따라 결정된다.

    동기 프로젝션: 쓰기와 같은 트랜잭션 내에서 읽기 모델을 업데이트한다. 강한 일관성이 보장되지만 쓰기 성능에 영향을 준다. 읽기 모델 업데이트가 실패하면 쓰기 트랜잭션 전체가 롤백된다.

    비동기 프로젝션: 이벤트 브로커를 통해 읽기 모델을 업데이트한다. 쓰기와 읽기가 분리돼서 쓰기 성능에 영향을 주지 않지만 eventual consistency다. 대부분의 CQRS 구현이 여기 해당한다.

    비동기 프로젝션에서 이벤트 처리가 지연되면 읽기 모델에 반영되지 않은 데이터가 존재한다. Read Replica lag과 본질적으로 같은 문제다. 이 지연을 허용 범위 내로 볼 것인지 오류로 볼 것인지는 서비스 설계 시 명확히 결정해야 한다.

    실무에서 CQRS 읽기 모델에 updatedAt 타임스탬프를 같이 저장해서 데이터가 얼마나 오래된 건지 클라이언트에 알려주는 방식을 쓰기도 한다. 대시보드처럼 통계 데이터를 보여주는 경우 "최근 업데이트: 3분 전" 형태로 표시하면 사용자가 stale read를 인지한 채로 데이터를 해석한다.

    레이어별 일관성 트레이드오프¶

    레이어 일관성 수준 허용 지연 적합한 데이터
    CDN 가장 약함 분~시간 정적 리소스, 공통 API 응답
    로컬 캐시 약함 수십 초~분 설정값, 코드 테이블
    Redis 중간 초~분 사용자별 세션, 조회 캐시
    Read Replica 중간~강함 밀리초~초 일반 비즈니스 데이터
    Primary DB 강함 없음 금융, 재고, 권한

    캐시 무효화 순서도 중요하다. 데이터가 변경되면 Primary → Read Replica 동기 → Redis 무효화 → 로컬 캐시 만료 순서로 갱신이 퍼진다. 각 단계마다 지연이 있어서 같은 데이터를 요청해도 어느 레이어에서 응답하느냐에 따라 다른 결과가 나올 수 있다.

    "모든 데이터는 Primary에서 읽어야 한다"는 원칙은 트래픽이 늘어나면 유지할 수 없다. "모든 데이터를 CDN에서 캐싱한다"는 원칙은 사용자 맞춤 데이터에 적용할 수 없다. 데이터 특성과 비즈니스 요구사항으로 각 레이어의 허용 범위를 결정하고, 그 결정을 문서로 남겨야 나중에 이슈가 발생했을 때 의도한 동작인지 버그인지 구분할 수 있다.
