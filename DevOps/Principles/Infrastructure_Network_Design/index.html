    인프라 네트워크 토폴로지 설계¶

    1. 이 문서의 범위¶

    네트워크는 한 번 그으면 나중에 바꾸기가 제일 어려운 계층이다. 서버는 늘리고 줄일 수 있고 코드는 배포로 되돌릴 수 있지만, CIDR을 잘못 잡거나 서브넷 경계를 애매하게 그어놓으면 그 위에 몇 년치 워크로드가 얹힌 뒤라 손을 못 댄다. 그래서 처음 그릴 때 결정의 무게가 다른 계층보다 훨씬 크다.

    이 문서는 특정 클라우드에 묶이지 않는 네트워크 설계 원칙을 정리한다. AWS VPC 세부 구현은 MSA VPC 설계 문서에, 가용성·SPOF·blast radius의 일반 원칙은 인프라 설계 원칙에 각각 있다. 그 두 문서가 "멀티 AZ 해라", "NAT는 AZ마다 둬라" 정도로만 짚고 넘어간 부분 — 서브넷을 몇 계층으로 나눌지, egress를 어떻게 통제할지, 로드밸런서를 어디에 둘지, 내부망을 어디까지 믿을지 — 를 여기서 다룬다.

    용어는 벤더 중립으로 쓴다. 서브넷, 라우팅 테이블, 게이트웨이 같은 개념은 AWS·GCP·Azure·온프레미스 어디든 이름만 다르고 동작은 같다. 특정 제품 얘기가 필요하면 명시한다.

    2. 서브넷 계층화: public / private / isolated¶

    2.1 왜 3계층인가¶

    처음 클라우드 네트워크를 그릴 때 흔히 public/private 2계층으로 시작한다. 인터넷에서 직접 닿아야 하는 것은 public, 나머지는 private. 이 구조가 한동안은 문제없이 돌아간다. 문제는 데이터베이스가 실수로 인터넷 경로를 갖게 되는 사고가 private 2계층에서 계속 반복된다는 데 있다.

    private 서브넷은 아웃바운드(egress)를 위해 보통 NAT를 거쳐 인터넷으로 나간다. 즉 private 서브넷의 인스턴스는 자기가 먼저 연결을 열면 외부로 나갈 수 있다. 여기에 DB를 두면, 애플리케이션이 감염됐을 때 DB에서 외부로 데이터를 실어 나르는 경로가 이미 열려 있는 셈이다. 라우팅 테이블 한 줄 잘못 건드리면 인바운드 경로까지 생긴다.

    그래서 계층을 하나 더 판다. 아웃바운드조차 인터넷으로 못 나가는 서브넷, 즉 isolated(격리) 계층이다.

                        인터넷
                      │
              ┌───────┴────────┐
              │  Internet GW   │
              └───────┬────────┘
                      │
        ┌─────────────┴──────────────┐
        │        Public Subnet        │   인바운드 O / 아웃바운드 O
        │   [LB] [Bastion] [NAT GW]   │   인터넷에서 직접 도달 가능
        └─────────────┬──────────────┘
                      │ (NAT 경유)
        ┌─────────────┴──────────────┐
        │       Private Subnet        │   인바운드 X / 아웃바운드 O (NAT)
        │   [App] [API] [Worker]      │   내부에서 인터넷으로 나갈 수만 있음
        └─────────────┬──────────────┘
                      │ (인터넷 경로 없음)
        ┌─────────────┴──────────────┐
        │      Isolated Subnet        │   인바운드 X / 아웃바운드 X
        │   [DB] [Cache] [MQ]         │   인터넷 경로 자체가 없음
        └─────────────────────────────┘

    핵심은 라우팅 테이블에 있다. 세 계층의 차이는 방화벽 규칙이 아니라 라우팅 테이블에 뭐가 들어있느냐다.

    계층 라우팅 테이블의 기본 경로(0.0.0.0/0) 실제로 두는 것
    public Internet Gateway로 향함 LB, Bastion, NAT, 프록시
    private NAT Gateway로 향함 애플리케이션 서버, 워커
    isolated 기본 경로 없음 (로컬 라우팅만) DB, 캐시, 메시지 큐, 시크릿 저장소

    isolated 서브넷은 라우팅 테이블에 0.0.0.0/0 엔트리가 아예 없다. 그래서 DB가 아무리 감염돼도 외부로 나갈 경로가 물리적으로 없다. 패치가 필요하면 private 계층에 프록시나 리포지토리 미러를 두고 그쪽으로만 당겨온다.

    2.2 CIDR을 먼저 넉넉히 쪼갠다¶

    서브넷 IP 고갈은 운영 중에 제일 자주 터지는 사고다. 특히 컨테이너 오케스트레이터를 쓰면 Pod 하나가 IP 하나를 먹기 때문에 예상보다 훨씬 빨리 빠진다. 이건 AWS만의 문제가 아니라 IP를 Pod에 직접 할당하는 모든 CNI에서 동일하게 일어난다.

    CIDR을 처음 나눌 때 계층별·AZ별로 미리 구획을 잡아둔다. 나중에 서브넷을 쪼개 붙이는 건 라우팅 테이블 재작업을 부르기 때문에 처음에 크게 잡는 편이 낫다.

    VPC: 10.0.0.0/16   (65,536개)

  AZ-a                          AZ-b                          AZ-c
  ├─ public   10.0.0.0/24       ├─ public   10.0.1.0/24       ├─ public   10.0.2.0/24
  ├─ private  10.0.16.0/20      ├─ private  10.0.32.0/20      ├─ private  10.0.48.0/20
  └─ isolated 10.0.8.0/22       └─ isolated 10.0.12.0/22      └─ isolated 10.0.128.0/22

    private을 /20(4,094개)으로 크게 잡은 이유는 Pod 밀집 때문이다. public은 LB와 NAT만 들어가므로 /24로 충분하다. isolated는 DB 인스턴스 수만큼만 필요하니 /22 정도. 이 숫자는 워크로드마다 다르지만, private을 제일 크게 잡는다는 방향은 대체로 맞는다.

    한 가지 자주 하는 실수는 여러 VPC/계정을 쓸 계획인데 CIDR을 겹치게 잡는 것이다. 10.0.0.0/16을 두 곳에서 쓰면 나중에 두 네트워크를 연결(peering)할 때 라우팅이 안 된다. 조직 전체에서 CIDR 대역을 미리 배분해두고 시작해야 한다.

    3. Egress 통제와 비용¶

    3.1 아웃바운드는 인바운드보다 통제가 어렵다¶

    방화벽 규칙을 짤 때 대부분 인바운드에 집중한다. 밖에서 들어오는 걸 막으면 안전하다고 느끼기 때문이다. 그런데 실제 데이터 유출 사고는 아웃바운드로 나간다. 공격자가 일단 내부에 들어오면 그때부터는 밖으로 데이터를 빼내야 하고, 그게 egress다.

    기본값이 "아웃바운드 전부 허용"인 환경이 대부분이다. 편하니까. 하지만 그 상태에서는 감염된 서버가 임의의 C2 서버로 붙어도 막을 방법이 없다. egress를 통제한다는 건 나가는 트래픽도 명시적으로 허용된 목적지만 허용한다는 뜻이다.

    3.2 NAT vs 프록시¶

    egress를 내보내는 방법은 크게 둘이다. NAT와 프록시(포워드 프록시).

    [NAT 방식]
  App → NAT Gateway → 인터넷
       (L3/L4, IP만 보고 포워딩. 목적지 필터링 못 함)

[프록시 방식]
  App → Forward Proxy → 인터넷
       (L7, 도메인/URL 단위 allow-list 가능)

    NAT는 IP 주소만 바꿔서 내보낸다. 어디로 나가는지는 신경 안 쓴다. 그래서 "우리 앱은 결제 게이트웨이랑 패키지 저장소로만 나가면 된다" 같은 정책을 NAT로는 못 건다. 반면 포워드 프록시는 L7에서 도메인을 보고 allow-list를 걸 수 있다.

    실무에서는 둘을 섞는다. 대부분 트래픽은 NAT로 내보내되, 규제 대상(결제·개인정보)을 다루는 서브넷은 프록시를 강제해서 나가는 도메인을 화이트리스트로 묶는다.

    Squid 같은 포워드 프록시로 도메인 allow-list를 거는 설정은 대략 이렇다.

    # /etc/squid/squid.conf

# 허용할 도메인 목록
acl allowed_domains dstdomain "/etc/squid/allowed_domains.txt"

# 나가는 소스 대역
acl internal_net src 10.0.16.0/20

# 허용 목록에 있는 도메인만 통과
http_access allow internal_net allowed_domains
http_access deny all

# 로그로 무엇이 막혔는지 남긴다
access_log /var/log/squid/access.log squid

    # /etc/squid/allowed_domains.txt
.payments.example.com
.repo.internal.example.com
.mirror.company.io

    애플리케이션 쪽에서는 HTTP_PROXY/HTTPS_PROXY 환경 변수로 프록시를 바라보게 하고, 서브넷 라우팅 테이블에서는 NAT 경로를 빼버려서 프록시를 우회할 수 없게 강제한다. 환경 변수만 걸어두면 앱이 그걸 무시하고 직접 나갈 수 있으니, 라우팅 자체를 막는 게 확실하다.

    3.3 NAT 비용이 새는 지점¶

    NAT는 처리량 기반으로 과금되는 경우가 많다. 시간당 요금에 더해 통과하는 데이터 양(GB)당 요금이 붙는다. 이게 예상보다 크게 튀는 경우가 있는데, 원인은 대개 "인터넷으로 나갈 필요가 없는 트래픽이 NAT를 타는 것"이다.

    같은 클라우드 안의 오브젝트 스토리지나 관리형 서비스를 호출할 때, 그게 NAT를 거쳐 공인 IP로 나갔다가 다시 들어오는 구성을 자주 본다. 이걸 프라이빗 엔드포인트(VPC Endpoint, Private Service Connect 등)로 바꾸면 NAT를 안 거치고 내부 경로로 직접 붙어서 NAT 데이터 요금이 통째로 빠진다. AWS라면 S3·DynamoDB용 Gateway Endpoint는 추가 비용도 거의 없다.

    나가는 목적지 NAT 경유 시 프라이빗 엔드포인트 시
    같은 클라우드 스토리지/관리형 서비스 NAT 데이터 요금 부과 내부 경로, NAT 요금 없음
    외부 서드파티 API NAT 필요 해당 없음
    패키지 저장소 NAT 또는 내부 미러 내부 미러 두면 NAT 안 탐

    NAT 요금 청구서가 이상하게 크면 제일 먼저 "인터넷 밖으로 안 나가도 될 트래픽이 NAT를 타고 있지 않은가"를 본다.

    4. East-West 트래픽과 서비스 디스커버리¶

    4.1 North-South와 East-West¶

    트래픽을 방향으로 나눠 부른다. 사용자→서비스처럼 경계를 넘는 세로 방향이 north-south, 서비스↔서비스처럼 내부에서 오가는 가로 방향이 east-west다. 모놀리식일 때는 east-west가 거의 없다가, 마이크로서비스로 쪼개면 east-west가 폭발한다. 요청 하나가 내부에서 10~20번의 서비스 간 호출로 번지는 게 흔하다.

    east-west가 많아지면 두 가지가 문제된다. 하나는 서비스가 서로를 어떻게 찾느냐(디스커버리), 다른 하나는 그 트래픽이 AZ를 넘나들면서 비용을 만드느냐다.

    4.2 서비스를 어떻게 찾게 할 것인가¶

    IP를 코드나 설정에 하드코딩하는 방식은 서비스가 몇 개 없을 때만 버틴다. 인스턴스가 오토스케일링으로 뜨고 죽으면 IP가 계속 바뀌기 때문에, 이름으로 찾고 그 이름 뒤의 실제 엔드포인트는 동적으로 채워지는 구조가 필요하다.

    [하드코딩]
  order-service → 10.0.16.42:8080  (인스턴스 죽으면 끝)

[DNS 기반 디스커버리]
  order-service → order.svc.internal → {10.0.16.42, 10.0.32.17, ...}
                  (죽은 인스턴스는 레코드에서 빠짐)

    디스커버리는 크게 두 방식이다.

    • 클라이언트 사이드: 클라이언트가 레지스트리(Consul, Eureka 등)에서 목록을 받아 직접 부하 분산 대상 인스턴스를 고른다. 네트워크 홉이 하나 줄지만 클라이언트 라이브러리가 언어마다 필요하다.
    • 서버 사이드: 클라이언트는 안정적인 이름(가상 IP, DNS)만 알고, 그 뒤의 로드밸런서나 프록시가 실제 인스턴스로 분배한다. 쿠버네티스 Service가 이 방식이다.

    요즘은 서버 사이드에 서비스 메시를 얹는 구성이 많다. 디스커버리 자체보다 그 위의 재시도·타임아웃·mTLS를 한꺼번에 가져가려는 목적이 크다. 이건 7절에서 다룬다.

    DNS 기반 디스커버리에서 자주 밟는 지뢰가 DNS 캐싱이다. 인스턴스가 죽어서 DNS 레코드에서 빠졌는데, 클라이언트(특히 JVM)가 DNS를 오래 캐싱해서 죽은 IP로 계속 붙는 경우가 있다. JVM은 networkaddress.cache.ttl이 기본값으로 무한 캐싱인 버전이 있어서, 이걸 명시적으로 30초 정도로 낮춰줘야 한다.

    # java.security 또는 시스템 프로퍼티
networkaddress.cache.ttl=30
networkaddress.cache.negative.ttl=5

    4.3 AZ를 넘는 east-west는 돈이다¶

    멀티 AZ로 서비스를 분산하면 가용성은 올라가는데, 서비스 간 호출이 AZ를 넘나들면서 AZ 간 데이터 전송 요금이 붙는다. north-south는 원래 요금 구조에 들어있어 눈에 잘 안 띄는데, east-west가 AZ를 넘는 요금은 서비스가 잘게 쪼개질수록 커진다. 어떤 경우엔 컴퓨트 비용보다 AZ 간 트래픽 비용이 더 나온다.

    이걸 줄이는 방법은 "가능하면 같은 AZ 안의 인스턴스로 먼저 보낸다"는 토폴로지 인지 라우팅이다. 쿠버네티스라면 트래픽을 같은 존 안에서 우선 처리하도록 힌트를 준다.

    apiVersion: v1
kind: Service
metadata:
  name: order-service
  annotations:
    # 같은 존 안의 엔드포인트로 우선 라우팅
    service.kubernetes.io/topology-mode: Auto
spec:
  selector:
    app: order
  ports:
    - port: 8080

    주의할 점은, 같은 AZ 안에 받아줄 인스턴스가 없으면 어차피 다른 AZ로 넘어간다는 것이다. 그리고 특정 AZ에 트래픽이 쏠려서 그 AZ 인스턴스만 과부하되는 부작용이 생길 수 있다. 비용을 아끼려다 부하 불균형을 만들 수 있으니, 트래픽이 정말 클 때만 켜는 게 낫다.

    5. 로드밸런서 배치¶

    5.1 L4와 L7 중 무엇을 어디에¶

    로드밸런서는 어느 계층에서 트래픽을 보느냐로 나뉜다. L4는 TCP/UDP 레벨에서 IP와 포트만 보고 분배하고, L7은 HTTP까지 열어봐서 경로·헤더·호스트로 분배한다.

    항목 L4 L7
    보는 계층 TCP/UDP (IP·포트) HTTP (경로·헤더·호스트)
    라우팅 기준 5-tuple 해시, 커넥션 URL 경로, 호스트, 쿠키
    성능 빠름, 오버헤드 적음 L4보다 무거움
    TLS 종료 보통 안 함(패스스루) 종료 가능
    쓰는 곳 gRPC, DB 프록시, 대용량 TCP REST API, 경로 기반 라우팅

    실무에서는 계층을 겹쳐 쓴다. 바깥에 L7을 두고 경로별로 서비스를 갈라 보내고, 그 안쪽에서 gRPC나 TCP 스트림은 L4로 받는 식이다. gRPC를 L7 로드밸런서 뒤에 그냥 두면 문제가 생기는데, gRPC는 HTTP/2 커넥션 하나를 오래 유지하면서 그 안에서 여러 요청을 멀티플렉싱하기 때문에, 커넥션 단위로 분배하는 L4에서는 한 인스턴스에만 요청이 쏠린다. gRPC는 L7(HTTP/2 인지)이나 클라이언트 사이드 분배가 필요하다.

    5.2 cross-zone 로드 밸런싱¶

    로드밸런서를 멀티 AZ에 두면, 각 AZ의 LB 노드가 자기 AZ 안의 타깃만 볼지, 아니면 모든 AZ의 타깃을 볼지를 정해야 한다. 이게 cross-zone 밸런싱이다.

    [cross-zone 끔]                      [cross-zone 켬]
  AZ-a LB → AZ-a 타깃만               AZ-a LB → 전체 AZ 타깃
  AZ-b LB → AZ-b 타깃만               AZ-b LB → 전체 AZ 타깃

  타깃 수가 AZ마다 다르면              부하가 고르게 퍼짐
  부하 불균형 발생                    대신 AZ 간 트래픽 발생

    cross-zone을 끄면 AZ-a로 들어온 트래픽은 AZ-a 타깃으로만 간다. AZ마다 타깃 수가 같으면 괜찮은데, 오토스케일링으로 AZ별 인스턴스 수가 틀어지면 어떤 AZ 인스턴스는 놀고 어떤 AZ는 과부하가 된다. cross-zone을 켜면 부하가 고르게 퍼지는 대신, LB가 다른 AZ 타깃으로 보내면서 AZ 간 트래픽 요금이 붙는다.

    또 하나 걸리는 점은 클라이언트가 보는 소스 IP다. cross-zone으로 다른 AZ 타깃에 트래픽이 넘어가면 실제 클라이언트 IP가 가려지는 경우가 있어서, 애플리케이션에서 원본 IP가 필요하면 X-Forwarded-For(L7)나 Proxy Protocol(L4)을 반드시 켜서 원본 IP를 실어 보내야 한다.

    5.3 connection draining¶

    배포나 스케일인으로 인스턴스를 뺄 때, 그 인스턴스가 처리 중이던 요청을 끊어버리면 사용자는 에러를 본다. connection draining(deregistration delay)은 인스턴스를 타깃 목록에서 빼되, 이미 붙어있는 커넥션은 끝날 때까지 기다렸다가 죽이는 동작이다.

          [draining 없음]                    [draining 있음]
  인스턴스 제거 → 진행 중 요청 끊김     인스턴스 제거 신호
       → 사용자 5xx                        → 신규 요청은 안 받음
                                          → 진행 중 요청은 끝까지 처리
                                          → drain 타임아웃 후 종료

    draining 타임아웃을 얼마로 잡느냐가 중요하다. 너무 짧으면 긴 요청이 잘리고, 너무 길면 배포가 느려진다. 보통 애플리케이션의 최대 요청 처리 시간보다 약간 길게 잡는다. 파일 업로드나 리포트 생성처럼 오래 걸리는 요청이 있으면 그걸 기준으로 잡아야 한다.

    여기서 놓치기 쉬운 게, LB의 draining과 애플리케이션의 graceful shutdown이 같이 맞물려야 한다는 점이다. LB가 "이제 이 인스턴스로 안 보낼게" 하는 시점과 애플리케이션이 실제로 종료되는 시점 사이에 시차가 있어서, 애플리케이션이 종료 신호(SIGTERM)를 받자마자 바로 죽으면 그 짧은 사이에 LB가 보낸 요청이 허공에 뜬다. 그래서 애플리케이션은 SIGTERM을 받으면 즉시 죽지 말고, 헬스체크만 실패로 바꿔서 LB가 자기를 뺄 시간을 준 다음, 진행 중 요청을 마치고 종료해야 한다.

    SIGTERM 수신
   → 헬스체크 엔드포인트를 실패로 전환 (LB가 나를 빼기 시작)
   → 몇 초 대기 (LB의 헬스체크 주기 × 임계 횟수만큼)
   → 새 요청 수신 중단, 진행 중 요청만 마무리
   → 프로세스 종료

    5.4 로드밸런서가 SPOF가 되는 순간¶

    로드밸런서를 두는 이유가 뒤쪽 인스턴스의 SPOF를 없애기 위해서인데, 정작 로드밸런서 자체가 SPOF가 되는 경우가 있다. 관리형 로드밸런서는 대개 내부적으로 이중화돼 있어서 이건 덜한데, 직접 세운 로드밸런서(HAProxy, Nginx 한 대)라면 그게 죽으면 전체가 죽는다.

    직접 운영하는 로드밸런서는 최소 둘 이상 띄우고 그 앞에 가상 IP(VIP)를 두거나 DNS 라운드로빈으로 묶는다. 두 LB가 Keepalived로 VIP를 주고받게 하면 한쪽이 죽어도 VIP가 살아있는 쪽으로 넘어간다.

            DNS: api.example.com
              │
      ┌───────┴────────┐
      │   VIP (Keepalived)   │  ← 한쪽 LB 죽으면 VIP가 넘어감
      └───────┬────────┘
        ┌─────┴─────┐
     [LB-1]      [LB-2]        ← active / standby 또는 active/active
        └─────┬─────┘
      [App] [App] [App]

    관리형 LB를 쓰더라도 SPOF가 완전히 사라진 건 아니다. LB가 물려있는 리전이나 AZ가 통째로 죽으면 그 LB도 같이 죽는다. 그래서 여러 AZ에 걸쳐 배치하고, 리전 장애까지 대비하려면 DNS 레벨에서 다른 리전 LB로 넘기는 페일오버(헬스체크 기반 DNS 라우팅)를 얹는다. 이때 DNS 자체가 또 SPOF가 되지 않게 하는 건 6절과 7절에서 이어 본다.

    한 가지 더, 로드밸런서의 헬스체크 설정이 잘못되면 멀쩡한 인스턴스를 전부 빼버리는 사고가 난다. 헬스체크가 DB까지 확인하는 깊은 체크인데 DB가 잠깐 느려지면, 모든 인스턴스가 동시에 헬스체크에 실패해서 LB가 타깃을 전부 빼버리고, 결과적으로 서비스 전체가 죽는다. 헬스체크의 깊이와 임계값은 인프라 설계 원칙의 헬스체크 절에서 다룬 내용을 로드밸런서 설정에도 그대로 적용해야 한다.

    6. 네트워크 세분화와 보안 경계¶

    6.1 flat network의 문제¶

    서브넷 계층만 나눠놓고 그 안에서는 서로 다 통신되게 열어두는 구성을 flat network라고 부른다. private 서브넷 안의 모든 서비스가 서로 자유롭게 붙을 수 있는 상태다. 편하지만, 한 서비스가 뚫리면 거기서 옆의 모든 서비스로 옮겨가는(lateral movement) 경로가 다 열려 있다.

    세분화(segmentation)는 "이 서비스는 저 서비스한테만 붙을 수 있다"를 명시적으로 규정하는 것이다. 주문 서비스는 결제 서비스와 DB에만 붙으면 되지, 로그 수집기나 관리자 콘솔에 붙을 이유가 없다. 그런 불필요한 경로를 다 닫는다.

    [flat: 모두가 모두에게]         [segmented: 필요한 경로만]
  A ── B                         A → B (허용)
  │ ╳ │                         A → DB (허용)
  C ── D                         B ─╳ C (차단)
  (전부 연결됨)                   C → 로그 (허용)
                                (나머지 전부 기본 차단)

    6.2 규칙은 IP가 아니라 신원으로¶

    세분화 규칙을 IP 대역으로 짜면 관리가 안 된다. 인스턴스가 오토스케일링으로 뜨고 죽으면서 IP가 계속 바뀌기 때문이다. 그래서 규칙을 IP가 아니라 신원(레이블, 보안 그룹, 서비스 계정)으로 건다.

    쿠버네티스의 NetworkPolicy가 이 방식이다. "결제 레이블이 붙은 Pod에서 온 트래픽만 주문 서비스의 8080으로 허용" 같은 규칙을 레이블로 표현한다.

    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: order-service-policy
  namespace: commerce
spec:
  podSelector:
    matchLabels:
      app: order
  policyTypes:
    - Ingress
    - Egress
  ingress:
    # payment 레이블이 붙은 Pod에서만 8080으로 들어올 수 있음
    - from:
        - podSelector:
            matchLabels:
              app: payment
      ports:
        - protocol: TCP
          port: 8080
  egress:
    # order-db 로만 나갈 수 있음
    - to:
        - podSelector:
            matchLabels:
              app: order-db
      ports:
        - protocol: TCP
          port: 5432

    여기서 중요한 건 기본 정책을 "전부 차단"으로 깔고 시작하는 것이다. 기본이 허용이면 규칙 하나 빠뜨렸을 때 뚫린 채로 도는데, 기본이 차단이면 규칙 하나 빠뜨렸을 때 통신이 안 돼서 바로 알아차린다. 운영이 조금 번거로워도 default-deny로 가야 한다.

    # 네임스페이스 전체에 default-deny를 먼저 깐다
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: commerce
spec:
  podSelector: {}         # 모든 Pod에 적용
  policyTypes:
    - Ingress
    - Egress
  # ingress/egress 규칙을 비워두면 전부 차단

    6.3 내부망 zero-trust¶

    전통적인 네트워크 보안은 경계(perimeter) 모델이다. 방화벽 안쪽은 믿고 바깥쪽은 안 믿는다. 문제는 공격자가 일단 경계를 넘어 안으로 들어오면, 안쪽은 다 믿는 구조라 마음대로 움직일 수 있다는 것이다. VPN 계정 하나만 털려도 내부 전체가 노출된다.

    zero-trust는 "내부망이라고 믿지 않는다"는 전제로 간다. 같은 VPC 안의 서비스 간 호출이라도 서로 신원을 증명하고 암호화한다. 네트워크 위치(어느 서브넷에 있느냐)가 아니라 신원(누구냐)으로 접근을 판단한다.

    구체적으로는 두 가지가 붙는다.

    • 서비스 간 통신에 상호 TLS(mTLS)를 강제한다. 양쪽이 인증서로 서로를 증명하므로, 내부망에 침입해도 유효한 인증서 없이는 어떤 서비스와도 대화할 수 없다.
    • 접근 결정을 매 요청마다 내린다. 한 번 인증했다고 계속 통과시키지 않고, 요청마다 "이 신원이 이 리소스에 접근할 권한이 있는가"를 정책 엔진에 묻는다.

    내부망 전체에 mTLS를 손으로 붙이는 건 현실적으로 어렵다. 인증서 발급·회전·검증을 서비스마다 코드로 짜야 하기 때문이다. 그래서 이 부분을 서비스 메시로 넘긴다.

    7. DNS와 서비스 메시 트래픽 흐름¶

    7.1 DNS는 조용한 SPOF¶

    내부 서비스 디스커버리가 DNS에 의존하는데, 그 DNS가 죽으면 서비스는 살아있어도 서로를 못 찾아서 전체가 마비된다. DNS는 평소에 너무 잘 돌아가서 SPOF라는 인식이 약한데, 실제 대형 장애의 상당수가 DNS에서 시작한다.

    쿠버네티스라면 CoreDNS가 클러스터 안 모든 이름 해석을 처리한다. CoreDNS Pod가 몇 개뿐인데 클러스터 전체 DNS 질의가 거기로 몰리면, CoreDNS가 병목이거나 SPOF가 된다. CoreDNS를 충분히 복제하고, 노드 로컬 DNS 캐시(NodeLocal DNSCache)를 깔아서 각 노드가 로컬에서 캐싱하게 하면 CoreDNS로 가는 질의 자체가 크게 준다.

    [NodeLocal DNS 캐시 없음]           [있음]
  Pod → CoreDNS (매번 원격)         Pod → 노드 로컬 캐시 → (미스 시) CoreDNS
       CoreDNS에 질의 집중              대부분 로컬에서 처리, CoreDNS 부하 급감

    DNS 관련해서 자주 겪는 또 다른 문제가 negative 캐싱과 짧은 TTL의 충돌이다. 서비스가 아직 안 떠서 DNS가 NXDOMAIN을 돌려주면, 그 "없음" 응답이 캐싱돼서 서비스가 실제로 뜬 뒤에도 한동안 못 찾는 경우가 있다. negative TTL을 짧게 잡아야 한다.

    7.2 서비스 메시가 트래픽을 어떻게 가로채는가¶

    서비스 메시는 각 서비스 옆에 사이드카 프록시(주로 Envoy)를 붙여서, 서비스가 주고받는 모든 트래픽을 그 프록시가 대신 처리하게 하는 구조다. 애플리케이션 코드는 그냥 localhost로 요청을 보내는데, 실제로는 사이드카가 그걸 가로채서 상대 서비스의 사이드카로 mTLS로 실어 나른다.

       [서비스 A Pod]                        [서비스 B Pod]
  ┌──────────────┐                     ┌──────────────┐
  │  App          │                     │  App          │
  │   │ localhost  │                     │   ↑ localhost  │
  │   ▼           │                     │   │           │
  │ [Envoy 사이드카]│─── mTLS ───────────▶│ [Envoy 사이드카]│
  └──────────────┘   (암호화·인증·재시도)  └──────────────┘

    앱은 자기가 평문으로 http://order-service/를 부른다고 생각하는데, 사이드카가 그걸 낚아채서 상대 사이드카까지 암호화된 채로 보낸다. 이 구조 덕분에 애플리케이션 코드를 한 줄도 안 고치고 mTLS, 재시도, 타임아웃, 서킷 브레이커, 트래픽 분할(카나리) 같은 걸 네트워크 계층에서 건다.

    트래픽이 실제로 어떻게 흐르는지 순서로 보면 이렇다.

    1. App이 localhost:포트로 요청 (평문)
2. iptables 규칙이 outbound를 사이드카로 리디렉션
3. 사이드카가 목적지 서비스를 디스커버리에서 조회
4. 사이드카가 상대 사이드카로 mTLS 커넥션 수립
5. 정책 확인 (이 신원이 저 서비스에 접근 가능한가)
6. 상대 사이드카가 받아서 복호화 → 상대 App의 localhost로 전달

    7.3 사이드카의 대가¶

    서비스 메시가 공짜는 아니다. 사이드카가 붙는 순간 몇 가지 비용이 생긴다.

    • 지연(latency): 요청마다 프록시를 두 번(나갈 때·들어올 때) 더 거치므로 홉이 늘고, 보통 요청당 밀리초 단위 지연이 추가된다. 지연에 민감한 서비스라면 이게 문제된다.
    • 리소스: Pod마다 사이드카 컨테이너가 하나씩 더 붙으니 메모리·CPU가 서비스 수만큼 곱해서 든다. Pod가 수천 개면 사이드카 오버헤드만으로 노드가 꽤 든다.
    • 운영 복잡도: 트래픽 흐름이 사이드카를 거치게 되면서, 문제가 생겼을 때 앱 문제인지 사이드카 설정 문제인지 구분하는 디버깅이 어려워진다.

    그래서 서비스 메시는 서비스가 충분히 많고 east-west가 복잡해진 다음에 넣는 게 맞다. 서비스가 몇 개 안 되는데 처음부터 메시를 깔면, 얻는 것보다 운영 부담이 크다. mTLS만 필요하면 메시 없이 라이브러리로도 되고, 재시도·타임아웃도 클라이언트 설정으로 충분한 경우가 많다.

    8. 네트워크 장애의 blast radius와 격리 설계¶

    8.1 네트워크 장애가 번지는 경로¶

    네트워크 장애는 한 곳에서 시작해서 예상 밖의 경로로 번진다. 실제로 겪은 전파 경로 몇 가지를 정리하면 이렇다.

    공유 NAT 죽음
   → 그 NAT를 쓰던 모든 서브넷의 아웃바운드 끊김
   → 외부 API 호출하던 서비스 전부 타임아웃
   → 타임아웃 대기로 스레드 풀 소진
   → 관련 없던 요청까지 처리 못 함 (연쇄 마비)

DNS 장애
   → 서비스 디스커버리 실패
   → 서비스는 살아있는데 서로 못 찾음
   → 헬스체크도 이름 해석 실패로 오판
   → LB가 멀쩡한 인스턴스를 빼버림

라우팅 테이블 오변경
   → 특정 대역으로 가는 경로가 블랙홀
   → 그 대역에 있던 DB로 못 붙음
   → DB 커넥션 대기 → 커넥션 풀 소진 → 서비스 다운

    공통점은 네트워크 한 지점의 장애가 그 지점에서 끝나지 않고, 그걸 공유하는 모든 워크로드로 번진다는 것이다. 그리고 대부분 타임아웃·커넥션 풀·스레드 풀이 소진되는 경로로 증폭된다.

    8.2 blast radius를 좁히는 격리 설계¶

    핵심은 공유 자원을 줄이는 것이다. 여러 워크로드가 하나의 네트워크 컴포넌트(NAT, LB, DNS, 라우팅 테이블)를 공유할수록, 그게 죽었을 때 같이 죽는 범위가 넓어진다.

    [공유 구성: blast radius 넓음]
        전체 서비스
            │
      ┌─────┴─────┐
      │  공유 NAT   │  ← 죽으면 전부 아웃바운드 끊김
      └───────────┘

[격리 구성: blast radius 좁음]
   서비스군 A      서비스군 B      서비스군 C
      │              │              │
   [NAT-A]        [NAT-B]        [NAT-C]  ← 하나 죽어도 나머지는 산다

    구체적으로 적용하는 방법들.

    • NAT는 AZ마다 둔다. AZ-a 서비스는 AZ-a NAT를 쓰게 라우팅을 나눈다. 한 NAT가 죽어도 그 AZ만 영향받고, 애초에 그 AZ가 죽는 상황과 blast radius가 같아진다.
    • 중요도가 다른 워크로드는 네트워크 컴포넌트를 분리한다. 결제 같은 핵심 서비스와 배치 잡을 같은 NAT·LB로 묶지 않는다. 배치가 NAT 대역폭을 다 먹어서 결제가 나가는 트래픽까지 느려지는 사고가 난다.
    • 셀(cell) 단위로 네트워크까지 나눈다. 인프라 설계 원칙의 셀룰러 아키텍처를 네트워크 계층으로 확장해서, 셀마다 서브넷·NAT·LB를 독립시키면 한 셀의 네트워크 장애가 다른 셀로 못 넘어간다.

    8.3 타임아웃과 격벽으로 증폭을 끊는다¶

    네트워크 컴포넌트를 아무리 격리해도, 장애가 타임아웃을 통해 애플리케이션으로 증폭되는 경로는 남는다. 이걸 끊는 건 네트워크가 아니라 애플리케이션 쪽 설정이다.

    • 모든 외부·내부 호출에 타임아웃을 건다. 타임아웃 없는 호출은 상대가 응답을 안 줄 때 무한 대기하고, 그동안 스레드와 커넥션을 붙잡는다. 이게 연쇄 마비의 핵심 증폭 경로다.
    • 격벽(bulkhead)으로 커넥션 풀을 분리한다. 외부 API용 커넥션 풀과 DB용 커넥션 풀을 하나로 쓰면, 외부 API가 느려질 때 그 풀이 소진되면서 DB 호출까지 막힌다. 목적지별로 풀을 나눠서, 한쪽이 소진돼도 다른 쪽은 살게 한다.
    • 서킷 브레이커로 죽은 목적지를 빠르게 포기한다. 상대가 계속 실패하는데 매번 타임아웃까지 기다리면 그 대기 자체가 부하다. 일정 횟수 실패하면 잠시 호출을 아예 끊고 빠르게 실패시킨다.

    이 세 가지는 서비스 메시를 쓰면 사이드카에서 걸 수도 있고, 없으면 애플리케이션 라이브러리(Resilience4j 등)로 건다. 어디서 걸든 핵심은 "네트워크 한 곳의 느려짐이 애플리케이션의 자원 소진으로 번지지 않게 막는 것"이다. 재시도·서킷 브레이커의 구체적인 함정은 인프라 설계 원칙의 복원력 절에 정리돼 있다.

    9. 트레이드오프 표¶

    결정 한쪽 다른 쪽
    서브넷 2계층 vs 3계층 단순함, 관리 편함 DB까지 인터넷 경로 격리, 라우팅 테이블 하나 더
    egress NAT vs 프록시 NAT는 편하고 빠름, 목적지 통제 불가 프록시는 도메인 allow-list 가능, 운영 부담·지연 증가
    프라이빗 엔드포인트 vs NAT 엔드포인트는 NAT 데이터 요금 절감 엔드포인트마다 관리·비용, 서비스별 설정 필요
    클라이언트 사이드 vs 서버 사이드 디스커버리 클라이언트는 홉 하나 절약 서버 사이드는 언어 무관, 홉 하나 추가
    cross-zone 켬 vs 끔 켜면 부하 균등 끄면 AZ 간 트래픽 요금 없음, 대신 불균형 위험
    L4 vs L7 로드밸런서 L4는 빠르고 가벼움 L7은 경로 라우팅·TLS 종료, 더 무거움
    flat vs segmented 네트워크 flat은 규칙 없이 편함 segment는 lateral movement 차단, 규칙 관리 부담
    경계 보안 vs zero-trust 경계는 단순, 안쪽 침입에 취약 zero-trust는 내부 침입 방어, mTLS 운영 복잡
    서비스 메시 도입 vs 미도입 도입하면 mTLS·재시도 코드 없이 미도입은 사이드카 지연·리소스 없음, 기능은 직접 구현
    공유 NAT/LB vs 워크로드별 분리 공유는 비용 적음 분리는 blast radius 좁힘, 컴포넌트 수·비용 증가

    10. 정리하며¶

    네트워크 설계에서 운영 들어간 뒤 제일 자주 후회하는 것들을 꼽으면 대체로 겹친다.

    CIDR을 작게 잡아서 IP가 고갈되는 것. 이건 되돌리기가 제일 어렵다. 처음에 계층별·AZ별로 넉넉히 쪼개두는 것 말고는 답이 없다.

    egress를 열어둔 채로 운영하다가, 보안 사고가 났을 때 데이터가 이미 밖으로 다 나간 뒤에 egress 통제를 시작하는 것. 인바운드만 챙기고 아웃바운드를 방치한 대가다.

    공유 NAT·공유 LB·단일 DNS를 아무 생각 없이 쓰다가, 그게 죽는 날 전체가 같이 죽는 것. 편해서 공유했는데 그 공유 범위가 곧 blast radius였다.

    헬스체크를 깊게 짜놓고 임계값을 타이트하게 잡아서, DB가 잠깐 느려질 때 LB가 멀쩡한 인스턴스를 전부 빼버리는 것. 자기 보호 장치가 자기를 죽인 경우다.

    네트워크는 다시 그리기 어려운 계층이라, 이 후회들은 대부분 처음 설계 때 조금 더 넉넉하게, 조금 더 격리해서, 조금 더 명시적으로 그렸으면 피할 수 있었던 것들이다. 나머지 세부 구현은 AWS VPC와 인프라 설계 원칙 문서로 이어진다.
