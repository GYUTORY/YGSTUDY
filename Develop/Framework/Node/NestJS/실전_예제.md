# NestJS 실전 예제

NestJS로 실제 서비스를 만들 때 빠지기 쉬운 함정과 자주 쓰는 패턴을 정리한다. 기본 CRUD부터 N+1 쿼리, 트랜잭션, 테스트 DB 초기화까지 실무에서 반복적으로 마주치는 주제 위주다.

### Entity

```typescript
// products/entities/product.entity.ts
import {
  Entity,
  Column,
  PrimaryGeneratedColumn,
  ManyToOne,
  JoinColumn,
  CreateDateColumn,
  UpdateDateColumn,
} from 'typeorm';
import { Category } from '../../categories/entities/category.entity';

@Entity('products')
export class Product {
  @PrimaryGeneratedColumn()
  id: number;

  @Column({ length: 100 })
  name: string;

  @Column({ type: 'text', nullable: true })
  description: string;

  @Column({ type: 'decimal', precision: 10, scale: 2 })
  price: number;

  @Column({ type: 'int', default: 0 })
  stock: number;

  @ManyToOne(() => Category, (category) => category.products)
  @JoinColumn({ name: 'category_id' })
  category: Category;

  @Column({ name: 'category_id' })
  categoryId: number;

  @CreateDateColumn()
  createdAt: Date;

  @UpdateDateColumn()
  updatedAt: Date;
}
```

```typescript
export class CreateProductDto {

  @MaxLength(100)
  name: string;

  @IsString()
  @IsOptional()
  description?: string;

  @Min(0)
```

```typescript
// products/dto/update-product.dto.ts
import { PartialType } from '@nestjs/mapped-types';
import { CreateProductDto } from './create-product.dto';

export class UpdateProductDto extends PartialType(CreateProductDto) {}
```

`PartialType`은 `CreateProductDto`의 모든 필드를 `optional`로 바꿔준다. 직접 DTO를 하나 더 만드는 것보다 유지보수가 쉽다. 단, `@nestjs/mapped-types`와 `@nestjs/swagger`의 `PartialType`은 다른 패키지이므로 Swagger를 쓴다면 `@nestjs/swagger`에서 import해야 한다.

### Service

```typescript
// products/products.service.ts
import { Injectable, NotFoundException } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { Product } from './entities/product.entity';
import { CreateProductDto } from './dto/create-product.dto';
import { UpdateProductDto } from './dto/update-product.dto';

@Injectable()
export class ProductsService {
  constructor(
    @InjectRepository(Product)
    private readonly productRepo: Repository<Product>,
  ) {}

  async create(dto: CreateProductDto): Promise<Product> {
    const product = this.productRepo.create(dto);
    return this.productRepo.save(product);
  }

  async findAll(): Promise<Product[]> {
    return this.productRepo.find();
  }

  async findOne(id: number): Promise<Product> {
    const product = await this.productRepo.findOne({ where: { id } });
    if (!product) {
      throw new NotFoundException(`Product #${id} not found`);
    }
    return product;
  }

  async update(id: number, dto: UpdateProductDto): Promise<Product> {
    const product = await this.findOne(id);
    Object.assign(product, dto);
    return this.productRepo.save(product);
  }

  async remove(id: number): Promise<void> {
    const result = await this.productRepo.delete(id);
    if (result.affected === 0) {
      throw new NotFoundException(`Product #${id} not found`);
    }
  }
}
```

`update` 메서드에서 `productRepo.update()`가 아닌 `findOne` + `save`를 쓴 이유: `update()`는 Entity 훅(`@BeforeUpdate` 등)을 실행하지 않는다. 훅이 필요 없는 경우에만 `update()`를 직접 쓴다.

### Controller

```typescript
// products/products.controller.ts
import {
  Controller,
  Get,
  Post,
  Body,
  Patch,
  Param,
  Delete,
  ParseIntPipe,
  HttpCode,
  HttpStatus,
} from '@nestjs/common';
import { ProductsService } from './products.service';
import { CreateProductDto } from './dto/create-product.dto';
import { UpdateProductDto } from './dto/update-product.dto';

@Controller('products')
export class ProductsController {
  constructor(private readonly productsService: ProductsService) {}

  @Post()
  @HttpCode(HttpStatus.CREATED)
  create(@Body() dto: CreateProductDto) {
    return this.productsService.create(dto);
  }

  @Get()
  findAll() {
    return this.productsService.findAll();
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.productsService.findOne(id);
  }

  @Patch(':id')
  update(
    @Param('id', ParseIntPipe) id: number,
    @Body() dto: UpdateProductDto,
  ) {
    return this.productsService.update(id, dto);
  }

  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)
  remove(@Param('id', ParseIntPipe) id: number) {
    return this.productsService.remove(id);
  }
}
```

`ParseIntPipe`를 빠뜨리면 `id`가 string으로 넘어온다. TypeORM에서 `where: { id: "1" }`로 쿼리가 나가는데, DB에 따라 암묵적 캐스팅이 되기도 하고 안 되기도 한다. 명시적으로 파이프를 걸어두는 게 안전하다.

### AppModule 설정

```typescript
// app.module.ts
import { Module } from '@nestjs/common';
import { TypeOrmModule } from '@nestjs/typeorm';
import { ConfigModule, ConfigService } from '@nestjs/config';

@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true }),
    TypeOrmModule.forRootAsync({
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        type: 'postgres',
        host: config.get('DB_HOST'),
        port: config.get<number>('DB_PORT'),
        username: config.get('DB_USERNAME'),
        password: config.get('DB_PASSWORD'),
        database: config.get('DB_NAME'),
        autoLoadEntities: true,
        synchronize: config.get('NODE_ENV') !== 'production',
      }),
    }),
  ],
})
export class AppModule {}
```

`synchronize: true`는 Entity 변경을 자동으로 DB 스키마에 반영한다. 프로덕션에서 켜면 컬럼이 날아가는 사고가 생긴다. 프로덕션에서는 반드시 migration을 쓴다.

`autoLoadEntities: true`를 쓰면 `TypeOrmModule.forFeature()`로 등록한 Entity가 자동으로 잡힌다. `entities` 배열에 하나씩 추가하는 것보다 편하다.

## N+1 쿼리 문제

NestJS + TypeORM 조합에서 가장 흔하게 겪는 성능 문제다.

### 문제 상황

```typescript
// 유저 목록을 가져오면서 각 유저의 게시글도 필요한 경우
async findAll(): Promise<User[]> {
  const users = await this.userRepo.find(); // SELECT * FROM users

  // 이 시점에서 user.posts에 접근하면?
  // TypeORM은 lazy loading이 기본이 아니라 undefined가 나온다.
  // eager: true로 설정하면 유저마다 SELECT가 한 번씩 나간다 → N+1
  return users;
}
```

Entity에 `eager: true`를 설정하면 `find()` 호출 시 자동으로 join이 걸리지만, 모든 조회에서 join이 발생한다. 게시글이 필요 없는 조회에서도 join이 걸린다.

### 해결: 필요한 곳에서만 relations 지정

```typescript
// posts가 필요한 조회
async findAllWithPosts(): Promise<User[]> {
  return this.userRepo.find({
    relations: ['posts'],
  });
  // SELECT ... FROM users LEFT JOIN posts ON ...
  // 쿼리 한 방에 끝난다
}

// posts가 필요 없는 조회
async findAll(): Promise<User[]> {
  return this.userRepo.find();
  // SELECT * FROM users
}
```

### QueryBuilder로 세밀한 제어

```typescript
async findUsersWithRecentPosts(): Promise<User[]> {
  return this.userRepo
    .createQueryBuilder('user')
    .leftJoinAndSelect('user.posts', 'post', 'post.createdAt > :date', {
      date: new Date(Date.now() - 7 * 24 * 60 * 60 * 1000),
    })
    .getMany();
}
```

`find({ relations })` 방식은 단순 join만 되지만, `QueryBuilder`는 join 조건을 걸 수 있다. 최근 7일 게시글만 가져오는 식의 조건부 로딩이 필요하면 `QueryBuilder`를 쓴다.

### 주의할 점

`relations`에 중첩 관계를 넣으면 쿼리가 급격히 무거워진다.

```typescript
// 이렇게 쓰면 3단계 join이 발생
this.userRepo.find({
  relations: ['posts', 'posts.comments', 'posts.comments.author'],
});
```

중첩이 깊어지면 응답 JSON 크기도 커진다. 필요한 데이터만 `select`로 골라서 가져오는 게 낫다.

## 트랜잭션 처리

여러 테이블에 데이터를 동시에 넣어야 할 때, 중간에 하나라도 실패하면 전부 롤백해야 한다.

### QueryRunner 방식

```typescript
import { Injectable } from '@nestjs/common';
import { DataSource } from 'typeorm';
import { Order } from './entities/order.entity';
import { OrderItem } from './entities/order-item.entity';
import { Product } from '../products/entities/product.entity';

@Injectable()
export class OrdersService {
  constructor(private readonly dataSource: DataSource) {}

  async createOrder(userId: number, items: { productId: number; quantity: number }[]) {
    const queryRunner = this.dataSource.createQueryRunner();
    await queryRunner.connect();
    await queryRunner.startTransaction();

    try {
      // 1. 주문 생성
      const order = queryRunner.manager.create(Order, { userId });
      const savedOrder = await queryRunner.manager.save(order);

      // 2. 주문 항목 생성 + 재고 차감
      for (const item of items) {
        const product = await queryRunner.manager.findOne(Product, {
          where: { id: item.productId },
          lock: { mode: 'pessimistic_write' }, // 동시 주문 시 재고 꼬임 방지
        });

        if (!product || product.stock < item.quantity) {
          throw new Error(`재고 부족: ${item.productId}`);
        }

        product.stock -= item.quantity;
        await queryRunner.manager.save(product);

        const orderItem = queryRunner.manager.create(OrderItem, {
          orderId: savedOrder.id,
          productId: item.productId,
          quantity: item.quantity,
          price: product.price,
        });
        await queryRunner.manager.save(orderItem);
      }

      await queryRunner.commitTransaction();
      return savedOrder;
    } catch (err) {
      await queryRunner.rollbackTransaction();
      throw err;
    } finally {
      await queryRunner.release(); // 반드시 release 해야 한다. 안 하면 커넥션이 풀에 반환되지 않는다
    }
  }
}
```

`pessimistic_write` 락은 해당 row를 다른 트랜잭션이 읽지 못하게 잠근다. 동시에 같은 상품에 주문이 들어왔을 때 재고가 마이너스로 빠지는 걸 방지한다.

### transaction() 메서드 방식

QueryRunner를 직접 다루는 게 번거로우면 `DataSource.transaction()`을 쓸 수 있다. rollback/release를 자동으로 처리해준다.

```typescript
async createOrder(userId: number, items: { productId: number; quantity: number }[]) {
  return this.dataSource.transaction(async (manager) => {
    const order = manager.create(Order, { userId });
    const savedOrder = await manager.save(order);

    for (const item of items) {
      const product = await manager.findOne(Product, {
        where: { id: item.productId },
        lock: { mode: 'pessimistic_write' },
      });

      if (!product || product.stock < item.quantity) {
        throw new Error(`재고 부족: ${item.productId}`);
      }

      product.stock -= item.quantity;
      await manager.save(product);

      await manager.save(
        manager.create(OrderItem, {
          orderId: savedOrder.id,
          productId: item.productId,
          quantity: item.quantity,
          price: product.price,
        }),
      );
    }

    return savedOrder;
  });
}
```

콜백 안에서 throw하면 자동으로 rollback된다. 대부분의 경우 이 방식이 더 깔끔하다.

### 트랜잭션에서 흔한 실수

**트랜잭션 밖의 repository를 쓰는 경우:**

```typescript
// 잘못된 예
async createOrder(userId: number) {
  return this.dataSource.transaction(async (manager) => {
    const order = manager.create(Order, { userId });
    await manager.save(order);

    // this.productRepo는 트랜잭션 밖의 커넥션을 쓴다!
    // 트랜잭션 격리가 깨진다
    await this.productRepo.update(1, { stock: 10 });
  });
}
```

트랜잭션 안에서는 반드시 `manager`를 통해 쿼리해야 한다. DI로 주입받은 repository를 쓰면 별도의 커넥션으로 쿼리가 나가서 트랜잭션이 의미 없어진다.

### Auth Service

```typescript
// auth/auth.service.ts
import { Injectable, UnauthorizedException } from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';
import { UsersService } from '../users/users.service';
import * as bcrypt from 'bcrypt';

@Injectable()
export class AuthService {
  constructor(
    private readonly usersService: UsersService,
    private readonly jwtService: JwtService,
  ) {}

  async validateUser(email: string, password: string) {
    const user = await this.usersService.findByEmail(email);
    if (!user) {
      throw new UnauthorizedException('이메일 또는 비밀번호가 틀렸다');
    }

    const isMatch = await bcrypt.compare(password, user.password);
    if (!isMatch) {
      throw new UnauthorizedException('이메일 또는 비밀번호가 틀렸다');
    }

    const { password: _, ...result } = user;
    return result;
  }

  async login(email: string, password: string) {
    const user = await this.validateUser(email, password);
    const payload = { sub: user.id, email: user.email };
    return {
      accessToken: this.jwtService.sign(payload),
    };
  }

  async register(email: string, password: string, name: string) {
    const hashedPassword = await bcrypt.hash(password, 10);
    const user = await this.usersService.create({
      email,
      password: hashedPassword,
      name,
    });
    const { password: _, ...result } = user;
    return result;
  }
}
```

`validateUser`에서 "이메일이 없다" / "비밀번호가 틀렸다"를 구분해서 에러를 보내면 공격자에게 해당 이메일이 가입되어 있다는 정보를 준다. 둘 다 같은 메시지를 쓴다.

**그런데 메시지를 같게 해도 응답 시간이 다르다.** 가입되지 않은 이메일이면 `bcrypt.compare` 를 아예 부르지 않고 곧장 throw 하기 때문이다. 두 경로를 재보면:

```
가입 안 된 이메일 평균 (밀리초):        0.00
가입된 이메일 + 틀린 비번 평균 (밀리초): 56.99
```

(bcrypt 6.0.0, cost 10)

**차이가 두 자릿수 밀리초라 네트워크 지연에 묻히지 않는다.** 이메일 목록을 넣고 응답 시간만 재면 어떤 계정이 존재하는지 그대로 뽑아낼 수 있다. 메시지를 통일한 의미가 사라진다.

사용자를 못 찾았을 때도 **더미 해시로 `compare` 를 한 번 돌려** 두 경로의 비용을 맞춘다.

```typescript
// 모듈 로드 시 한 번만 만들어 둔다
const DUMMY_HASH = bcrypt.hashSync('dummy-password-for-timing', 10);

async validateUser(email: string, password: string) {
  const user = await this.usersService.findByEmail(email);
  const isMatch = await bcrypt.compare(password, user?.password ?? DUMMY_HASH);
  if (!user || !isMatch) {
    throw new UnauthorizedException('이메일 또는 비밀번호가 틀렸다');
  }
  const { password: _, ...result } = user;
  return result;
}
```

`user` 존재 여부와 무관하게 항상 `compare` 를 한 번 돈다. 매 로그인마다 해시 비용을 한 번 더 무는 게 아니라, **원래 물던 비용을 실패 경로에도 똑같이 물리는 것**이다.

같은 문제가 회원가입·비밀번호 찾기에도 있다. "이미 가입된 이메일입니다" 를 그대로 노출하면 응답 시간을 잴 것도 없이 알려주는 셈이다.

### JWT Strategy

```typescript
// auth/strategies/jwt.strategy.ts
import { Injectable, UnauthorizedException } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { PassportStrategy } from '@nestjs/passport';
import { ExtractJwt, Strategy } from 'passport-jwt';
import { UsersService } from '../../users/users.service';

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(
    private readonly usersService: UsersService,
    configService: ConfigService,
  ) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: configService.get('JWT_SECRET'),
    });
  }

  async validate(payload: { sub: number; email: string }) {
    const user = await this.usersService.findOne(payload.sub);
    if (!user) {
      throw new UnauthorizedException();
    }
    return { userId: user.id, email: user.email };
  }
}
```

```
clearAllMocks 후 반환값: {"id":1}

```

(Jest 30.4.1)

**앞 테스트가 심은 반환값이 다음 테스트로 새어 나온다.** 그래서 뒤 테스트가 자기 mock 설정을 빼먹어도 통과해 버리고, 테스트 순서를 바꾸거나 앞 테스트를 지우는 순간 무너진다. 원인이 "내가 건드리지도 않은 테스트"라 찾기 어렵다.

구현까지 비우려면 `jest.resetAllMocks()` 를 쓴다. 설정 파일에 한 줄 넣어두면 매번 신경 쓸 필요가 없다.

```javascript

```

`clearAllMocks` / `resetAllMocks` / `restoreAllMocks` 는 지우는 범위가 각각 다르다. **"초기화한다"고 뭉뚱그리면 어느 것이 필요한지 판단할 수 없다** — 호출 기록만인지, 구현까지인지, 원래 함수로 되돌릴 것인지를 정하고 고른다.

### E2E Test와 DB 초기화

E2E 테스트에서 가장 골치 아픈 부분이 DB 상태 관리다. 테스트마다 깨끗한 DB에서 시작해야 결과가 예측 가능하다.

```typescript
// test/helpers/db-cleanup.ts
import { DataSource } from 'typeorm';

export async function cleanupDatabase(dataSource: DataSource) {
  const entities = dataSource.entityMetadatas;

  for (const entity of entities) {
    const repository = dataSource.getRepository(entity.name);
    await repository.query(`TRUNCATE TABLE "${entity.tableName}" CASCADE`);
  }
}
```

```typescript
// test/users.e2e-spec.ts
import { Test, TestingModule } from '@nestjs/testing';
```

**주의사항:**

- `TRUNCATE CASCADE`는 FK 관계가 있는 테이블까지 같이 비운다. MySQL에서는 `SET FOREIGN_KEY_CHECKS = 0` 후 truncate하고 다시 `SET FOREIGN_KEY_CHECKS = 1`로 켜야 한다.
- `beforeAll`에서 앱을 초기화하고 `beforeEach`에서 DB를 비우는 패턴이 표준이다. `beforeEach`에서 앱을 매번 초기화하면 테스트가 느려진다.
- E2E 테스트는 테스트 전용 DB를 쓴다. 개발 DB에 돌리면 데이터가 날아간다. `.env.test` 파일을 분리하든, 환경변수로 테스트 DB를 지정하든 방법을 정해둔다.

### E2E 테스트에서 ValidationPipe

`main.ts`에서 `app.useGlobalPipes()`로 등록한 ValidationPipe는 E2E 테스트의 `app`에는 적용되지 않는다. 테스트에서도 별도로 등록해야 한다. 빠뜨리면 잘못된 DTO가 그대로 통과해서 테스트가 의미 없어진다.

```typescript

  new ValidationPipe({
    whitelist: true,    // DTO에 없는 필드 자동 제거
    forbidNonWhitelisted: true, // DTO에 없는 필드가 오면 400
    transform: true,    // 쿼리 파라미터 자동 타입 변환
  }),
);
```

### Controller

```typescript
// files/files.controller.ts
import {
  Controller,
  Post,
  UseInterceptors,
  UploadedFile,
  BadRequestException,
  ParseFilePipe,
  MaxFileSizeValidator,
  FileTypeValidator,
} from '@nestjs/common';
import { FileInterceptor } from '@nestjs/platform-express';
import { diskStorage } from 'multer';
import { extname } from 'path';
import { randomUUID } from 'crypto';

@Controller('files')
export class FilesController {
  @Post('upload')
  @UseInterceptors(
    FileInterceptor('file', {
      storage: diskStorage({
        destination: './uploads',
        filename: (req, file, cb) => {
          const name = `${randomUUID()}${extname(file.originalname)}`;
          cb(null, name);
        },
      }),
    }),
  )
  upload(
    @UploadedFile(
      new ParseFilePipe({
        validators: [
          new MaxFileSizeValidator({ maxSize: 5 * 1024 * 1024 }), // 5MB
          new FileTypeValidator({ fileType: /image\/(jpg|jpeg|png|gif)/ }),
        ],
      }),
    )
    file: Express.Multer.File,
  ) {
    return {
      filename: file.filename,
      size: file.size,
    };
  }
}
```

`ParseFilePipe`는 NestJS 9부터 추가됐다. 이전에는 `fileFilter` 콜백에서 직접 검증했는데, 파이프 방식이 더 선언적이다.

**`FileTypeValidator` 가 보는 `file.mimetype` 은 클라이언트가 적어 보낸 값이다.** multer 는 멀티파트 본문의 `Content-Type` 헤더를 그대로 옮겨 담는다. 요청을 직접 만들어 확인해 보면 그대로 통과한다.

```
--X
Content-Disposition: form-data; name="file"; filename="shell.php.jpg"
Content-Type: image/jpeg

<?php system($_GET["c"]); ?>
--X--
```

```
받은 originalname=shell.php.jpg mimetype=image/jpeg → 검증 통과
서버 응답: {"accepted":true,"head":"<?php system($_GET[\""}
```

(multer 2.2.0)

파일명을 UUID 로 바꾸는 이 예제의 처리 덕분에 확장자 위장 자체는 힘을 잃지만(`extname` 만 가져오므로 `.jpg` 로 저장된다), **내용이 이미지가 아닌 파일이 이미지로 등록되는 건 그대로다.** 이미지 처리 파이프라인이 그 파일을 열다 터지거나, 정적 경로에서 그대로 서빙되면 문제가 커진다.

`ParseFilePipe` 는 1차 필터로 두고, **내용 기반 판정을 한 단계 더** 넣는다. 커스텀 validator 로 매직 넘버를 보거나, 저장 직후 `sharp(buffer).metadata()` 처럼 실제로 열어보고 실패하면 지운다. 업로드 디렉터리(`./uploads`)를 웹 루트 밖에 두는 것도 함께 해야 한다.

파일명에 원본 이름을 그대로 쓰면 한글, 특수문자, 중복 등 문제가 생긴다. UUID로 저장하고 원본 이름은 DB에 따로 저장한다.

### Gateway

```typescript
// chat/chat.gateway.ts
import {
  WebSocketGateway,
  WebSocketServer,
  SubscribeMessage,
  OnGatewayConnection,
  OnGatewayDisconnect,
  ConnectedSocket,
  MessageBody,
} from '@nestjs/websockets';
import { Server, Socket } from 'socket.io';

@WebSocketGateway({ cors: { origin: '*' } })
export class ChatGateway implements OnGatewayConnection, OnGatewayDisconnect {
  @WebSocketServer()
  server: Server;

  private connectedClients = new Map<string, string>(); // socketId → userId

  handleConnection(client: Socket) {
    console.log(`connected: ${client.id}`);
  }

  handleDisconnect(client: Socket) {
    this.connectedClients.delete(client.id);
    console.log(`disconnected: ${client.id}`);
  }

  @SubscribeMessage('joinRoom')
  handleJoin(
    @ConnectedSocket() client: Socket,
    @MessageBody() room: string,
  ) {
    client.join(room);
    client.to(room).emit('userJoined', { socketId: client.id });
  }

  @SubscribeMessage('message')
  handleMessage(
    @ConnectedSocket() client: Socket,
    @MessageBody() data: { room: string; message: string },
  ) {
    // 본인을 제외한 방의 다른 사람에게 전송
    client.to(data.room).emit('message', {
      from: client.id,
      message: data.message,
    });
  }
}
```

`@WebSocketGateway()`에 CORS 설정을 안 하면 브라우저에서 연결이 안 된다. 프로덕션에서는 `origin: '*'` 대신 실제 도메인을 지정한다.

`this.server.emit()`은 모든 클라이언트에게, `client.to(room).emit()`은 방의 다른 클라이언트에게, `client.emit()`은 본인에게만 전송한다. 셋을 헷갈리면 메시지가 이상한 곳으로 간다.

`connectedClients` Map은 `handleDisconnect`에서 `delete`만 하고 어디에서도 `set`하지 않는다. 항상 비어 있는 상태로 남는다. socketId ↔ userId 매핑이 필요하면 `handleConnection`에서 토큰을 검증하고 넣어야 한다. 그리고 이 게이트웨이에는 인증이 전혀 없다 — `@WebSocketGateway({ cors: { origin: '*' } })`는 아무나 연결해서 아무 방에나 들어올 수 있다는 뜻이다. HTTP 라우트에 `JwtAuthGuard`를 걸어놨더라도 WebSocket 핸드셰이크는 그 가드를 거치지 않는다.

## 붙여넣기 전에 확인할 것들

아래는 Node v22.21.1에서 실제로 돌려 확인한 내용이다.

### bcrypt는 72바이트에서 잘린다

`bcrypt.hash(password, 10)`은 입력의 **앞 72바이트만** 본다. 그보다 긴 부분은 해싱에 참여하지 않는다.

```
p1 = "A"×72 + "첫번째사용자의고유한뒷부분"   (111 바이트)
p2 = "A"×72 + "완전히다른뒷부분입니다XYZ"    (108 바이트)

p1 로 만든 해시에 p1 검증: true
p1 로 만든 해시에 p2 검증: true   ← 뒷부분이 완전히 달라도 통과
전혀 다른 비밀번호 검증:    false
```

패스프레이즈를 권장하는 서비스나 비밀번호 관리자가 만든 긴 문자열에서 실제로 걸린다. 한글은 UTF-8에서 글자당 3바이트라 24자만 넘어도 한도에 닿는다. 사용자는 긴 비밀번호를 썼다고 믿는데 실제 강도는 72바이트분뿐이다.

두 가지 중 하나를 택한다.

```typescript
// 1) 길이를 막는다 — 가장 단순하다
if (Buffer.byteLength(password, 'utf8') > 72) {
  throw new BadRequestException('비밀번호는 72바이트를 넘을 수 없습니다');
}

// 2) 먼저 해시해서 고정 길이로 만든다
const pre = crypto.createHash('sha256').update(password).digest('base64');  // 44자
const hash = await bcrypt.hash(pre, 12);
```

2번을 쓸 거면 검증 경로에도 같은 전처리를 적용해야 하고, 기존 해시와 섞이지 않게 버전 표시를 남겨야 한다. 새로 만드는 서비스라면 argon2id 쪽이 이 제약이 없다.

`saltRounds: 10`은 요즘 기준으로 낮은 편이다. 로그인 응답 시간을 재보고 허용 범위 안에서 올린다.

### `FileTypeValidator`의 정규식이 앵커가 없다

```typescript
new FileTypeValidator({ fileType: /image\/(jpg|jpeg|png|gif)/ })
```

이 정규식은 문자열 **어딘가에** 패턴이 있으면 통과시킨다.

```
true   "image/png"
true   "image/jpeg"
true   "notimage/jpeg"                        ← 통과
true   "text/html;x=image/png"                ← 통과
true   "application/x-php; name=image/gif"    ← 통과
false  "image/webp"
false  "image/svg+xml"
```

게다가 `FileTypeValidator`가 보는 값은 **클라이언트가 보낸 `Content-Type`**이다. multipart 파트의 헤더라 요청을 직접 만들면 마음대로 정할 수 있다. 파일 내용과는 아무 관계가 없다.

```typescript
new FileTypeValidator({ fileType: /^image\/(jpeg|png|gif|webp)$/ })
```

앵커를 붙이면 위 세 우회가 전부 막힌다(확인함). 다만 이건 오타 방어일 뿐이고, 실제 방어는 **파일 앞부분의 매직 바이트를 읽어 판별**하는 것이다. `image/jpg`는 표준 MIME 타입이 아니므로 목록에서 빼고 `image/jpeg`만 둔다. `image/webp`는 이 목록에 없어서 지금은 거부된다.

저장 경로 `./uploads`는 프로세스의 작업 디렉토리 기준이다. `npm run start`를 어디서 실행하느냐에 따라 위치가 바뀌고, 프로젝트 루트 안이라 정적 서빙 설정이 조금만 겹쳐도 업로드한 파일이 URL로 노출된다. 절대 경로로 고정하고 document root 밖에 둔다.

### `decimal` 컬럼은 런타임에 문자열로 온다

```typescript
@Column({ type: 'decimal', precision: 10, scale: 2 })
price: number;      // 타입 선언은 number, 실제로 들어오는 값은 string
```

TypeORM은 정밀도 손실을 막으려고 `decimal`을 문자열로 돌려준다. 타입 선언이 `number`라 컴파일러가 잡아주지 못한다. 주문 예제의 `price: product.price`가 그대로 흘러가면 이런 일이 생긴다.

```
price * qty  = 31.5        곱하기는 숫자로 강제변환돼서 맞아 보인다
price + qty  = "10.503"    더하기는 문자열 연결
합계 누적    = "010.5020.255.00"   reduce 로 더하면 이렇게 된다
JSON 응답   = {"price":"10.50"}    따옴표가 붙어서 나간다
```

곱셈이 우연히 맞기 때문에 단가 계산은 통과하고 **합계에서만 틀린다.** 프런트가 `price`를 숫자로 기대하면 응답 형식도 어긋난다. 같은 문제가 `bigint` 컬럼에도 있다.

```typescript
@Column({ type: 'decimal', precision: 10, scale: 2, transformer: {
  to: (v: number) => v,
  from: (v: string) => (v === null ? null : Number(v)),
}})
price: number;
```

금액을 다룬다면 `Number`로 바꾸는 것 자체가 부동소수점 문제를 들여온다. 정수 최소 단위(원)로 저장하거나 decimal 라이브러리를 쓰는 편이 안전하다. 어느 쪽이든 **지금 무엇이 오고 있는지 한 번 찍어보고 정하는 게 먼저다.**

```typescript
const p = await repo.findOne({ where: { id: 1 } });
console.log(typeof p.price, JSON.stringify(p.price));
```

### 테스트 DB 정리가 시퀀스를 되돌리지 않는다

```typescript
await repository.query(`TRUNCATE TABLE "${entity.tableName}" CASCADE`);
```

`TRUNCATE`만으로는 PostgreSQL의 시퀀스가 초기화되지 않는다. 테스트를 반복하면 `id`가 계속 커진다. `expect(res.body.id).toBe(1)` 같은 단언은 첫 실행에서만 통과한다.

```sql
TRUNCATE TABLE "users" RESTART IDENTITY CASCADE
```

테이블을 하나씩 도는 것도 느리다. 이름을 모아 한 번에 처리하면 왕복이 줄고, `CASCADE`가 서로를 다시 비우는 낭비도 없앨 수 있다.

```typescript
const tables = dataSource.entityMetadatas
  .map((e) => `"${e.tableName}"`)
  .join(', ');
await dataSource.query(`TRUNCATE TABLE ${tables} RESTART IDENTITY CASCADE`);
```

`beforeEach`에서 DB를 비우는데 테스트가 병렬로 돌면 서로의 데이터를 지운다. Jest는 파일 단위로 워커를 나눠 병렬 실행하는 게 기본이다. E2E는 `--runInBand`로 직렬 실행하거나 워커별로 DB를 분리한다. 이 설정을 빠뜨리면 **단독으로 돌리면 통과하는데 전체를 돌리면 깨지는** 테스트가 된다.
