# 블룸 필터 - 캐시 관통 방어와 용량 설계

캐시 앞에 블룸 필터를 두라는 조언은 흔하다. [캐시 쇄도·관통 방어](../../Architecture/MSA/분산_캐싱_패턴.md)에도 한 줄 나오고 [멀티 레벨 캐시](../../Framework/Node/캐싱/Multi_Level_Cache.md)에도 키워드로만 언급된다. 정작 실무에서 문제가 되는 것은 개념이 아니라 숫자다. 비트를 얼마나 잡아야 하는지, 키가 설계 용량을 넘으면 무슨 일이 생기는지, 필터를 파일로 저장했다가 다시 읽으면 왜 전부 틀리는지. 이 문서는 필터를 직접 만들어 돌려서 그 숫자와 함정을 확인한 기록이다.

[Cache Stampede](Cache_Stampede_Pattern.md)가 "같은 키에 요청이 몰리는" 문제라면 캐시 관통(penetration)은 **DB에 없는 키**를 계속 조회해서 캐시도 못 쓰고 매번 DB까지 가는 문제다. 없는 키는 캐시에 넣을 값이 없다. "없음"을 짧은 TTL로 캐시에 박는 방법(negative cache)은 키 공간이 크면 메모리를 터뜨린다. 블룸 필터는 이 자리를 아주 작은 메모리로 막는다.

## 무엇을 보장하고 무엇을 안 하나

블룸 필터는 비트 배열 하나와 해시 함수 k개로 이루어진다. 원소를 넣으면 k개 해시가 가리키는 비트를 1로 켠다. 조회할 때 k개 비트가 모두 1이면 "있을 수도 있다", 하나라도 0이면 "확실히 없다"고 답한다.

| 응답 | 의미 |
|---|---|
| 없음 | **틀리는 일이 없다.** 넣은 적이 없다 |
| 있음 | 넣었을 수도 있고, 다른 키들이 우연히 비트를 다 켠 것일 수도 있다 (false positive) |

그래서 관통 방어에 쓸 수 있다. 필터가 "없음"이라고 하면 DB를 안 가도 되고, "있음"이면 평소대로 캐시와 DB를 거친다. 틀려도 헛걸음 한 번일 뿐 틀린 데이터를 돌려주지는 않는다.

## 구현

외부 패키지 없이 쓴 구현이다. 해시 k개를 따로 계산하는 대신 해시 두 개로 `h1 + i*h2`를 만들어 k개로 쓰는 이중 해싱을 쓴다(Kirsch와 Mitzenmacher가 정리한 기법이고 FP율에는 거의 영향이 없다).

```python
import hashlib, math

class Bloom:
    def __init__(self, m_bits: int, k: int):
        self.m, self.k = m_bits, k
        self.bits = bytearray((m_bits + 7) // 8)

    @classmethod
    def for_capacity(cls, n: int, p: float):
        m = math.ceil(-n * math.log(p) / (math.log(2) ** 2))     # 필요한 비트 수
        k = max(1, round(m / n * math.log(2)))                    # 최적 해시 개수
        return cls(m, k)

    def _idx(self, key: str):
        d = hashlib.blake2b(key.encode(), digest_size=16).digest()
        h1 = int.from_bytes(d[:8], "big")
        h2 = int.from_bytes(d[8:], "big") | 1                     # 홀수로 만들어 m 과 겹침을 줄인다
        return ((h1 + i * h2) % self.m for i in range(self.k))

    def add(self, key):
        for i in self._idx(key):
            self.bits[i >> 3] |= 1 << (i & 7)

    def __contains__(self, key):
        return all(self.bits[i >> 3] & (1 << (i & 7)) for i in self._idx(key))
```

용량 n과 목표 오탐률 p를 주면 `m = -n·ln(p) / (ln 2)²`, `k = (m/n)·ln 2`로 크기가 정해진다. 이 식이 실제와 맞는지 키 20만 개를 넣고, 안 넣은 키 20만 개를 조회해서 확인했다.

| 설계 p | 키당 비트 | k | 크기 | 이론 FP | 실측 FP |
|---|---|---|---|---|---|
| 10% | 4.79 | 3 | 117KiB | 10.07% | 10.24% |
| 1% | 9.59 | 7 | 234KiB | 1.00% | 1.01% |
| 0.1% | 14.38 | 10 | 351KiB | 0.100% | 0.104% |

식은 맞는다. 눈여겨볼 것은 **1%를 주는 데 키당 9.6비트면 된다**는 점이다. 키 100만 개 규모에서 `set`과 비교했다.

```text
set  : 88.2 MiB   Bloom(1%): 1.14 MiB   (키 길이 평균 7자)
```

`tracemalloc`으로 잰 `set`의 크기다. 문자열 객체 오버헤드가 커서 짧은 키일수록 격차가 크게 나온다. 키가 UUID처럼 길면 `set`은 더 커지고 필터는 그대로다. 필터의 크기는 키 길이와 무관하게 개수와 p로만 정해진다.

## 관통 방어에서 DB 호출이 얼마나 줄어드나

ID 10만 개가 DB에 있고, 요청의 10%만 존재하는 ID를, 90%는 존재하지 않는 ID(스캔·오타·공격)를 조회한다고 가정했다. 필터는 1%로 설계했다.

```text
전체 조회 200000  실제 존재하는 키 조회 19883 (9.9%)
필터 없음: DB 조회 200000   필터 있음: DB 조회 21649 (10.8%), 이 중 헛걸음 1766
```

DB 호출이 20만에서 2.2만으로 내려갔고 남은 것 중 헛걸음은 1,766건이다. 존재하지 않는 요청 약 18만 건 중 1,766건이니 오탐률 0.98%로 설계값과 같다. **존재하지 않는 키를 조회하는 요청 비중이 높을수록 효과가 커진다.** 반대로 대부분의 요청이 존재하는 키라면 필터는 아무것도 막지 못하고 해시 계산 비용만 더한다.

## 조용히 깨지는 지점

### 설계 용량을 넘기면 FP율이 급격히 오른다

n=10만, p=1%로 설계한 필터에 설계보다 많은 키를 넣어 보았다.

| 넣은 키 | 실측 FP |
|---|---|
| 1배(10만) | 1.03% |
| 2배 | 15.94% |
| 5배 | 83.29% |
| 10배 | 99.54% |

2배만 넘겨도 오탐률이 약 15배가 된다. 오탐은 "DB를 한 번 더 간다"일 뿐이라 장애로 안 보이고, 필터를 두고도 관통이 슬그머니 되살아난다. 가입자가 늘어 ID 수가 설계 용량을 넘었는데도 필터를 키우지 않는 일이 흔하다. **필터에 들어간 키 수를 지표로 내보내고 설계 용량의 70~80%에서 알림을 건다.** 용량이 정해지지 않은 데이터에는 이 구조가 맞지 않는다. 확장형 필터가 있지만 이 문서에서는 다루지 않는다.

### 삭제하면 false negative가 생긴다

"없음"은 절대 틀리지 않는다는 보장이 이 구조의 근간이다. 키를 지우려고 해당 비트를 0으로 끄면 그 비트를 공유하던 다른 키가 사라진다.

```python
bf = Bloom.for_capacity(1000, 0.01)
for i in range(1000): bf.add(f"key:{i}")
for i in bf._idx("key:0"):                       # key:0 을 지우려고 비트를 끈다
    bf.bits[i >> 3] &= ~(1 << (i & 7))
sum(f"key:{i}" not in bf for i in range(1, 1000))   # -> 4
```

`key:0`만 지웠는데 다른 키 4개가 "확실히 없음"이 됐다. 관통 방어에서 이건 **존재하는 데이터를 DB에 있는데도 없다고 응답하는 버그**다. 삭제가 필요하면 카운터 배열을 쓰는 변형을 쓰거나, 정기적으로 전체를 다시 만들어 교체한다. 소프트 삭제된 행이 있는 서비스라면 필터에는 "한 번이라도 존재했던 ID"를 넣고 삭제 여부는 DB에서 확인하게 두는 편이 단순하다.

### 필터를 저장하고 다시 읽으면 전부 틀린다

비트 배열을 파일이나 Redis에 저장했다가 다른 프로세스에서 읽는 구조가 흔한데, 이때 해시 함수가 프로세스마다 달라지면 모든 키가 "없음"이 된다. Python의 내장 `hash()`는 문자열에 대해 프로세스마다 다른 값을 낸다(해시 무작위화).

```python
# bloom_persist.py - 내장 hash() 로 만든 필터를 저장하고, 다른 프로세스에서 읽어 조회
import sys
m, k, N = 100_000, 7, 10_000
def idx(key):                      # 이렇게 하면 안 된다
    h = hash(key); h1 = h & 0xFFFFFFFF; h2 = (h >> 32) | 1
    return [(h1 + i*h2) % m for i in range(k)]

if sys.argv[1] == "save":
    bits = bytearray(m//8 + 1)
    for n in range(N):
        for i in idx(f"key:{n}"): bits[i>>3] |= 1 << (i&7)
    open("bf.bin", "wb").write(bits)
else:
    bits = open("bf.bin", "rb").read()
    miss = sum(not all(bits[i>>3] & (1<<(i&7)) for i in idx(f"key:{n}")) for n in range(N))
    print(f"저장한 키 {N}개 중 필터가 '없다'고 답한 것: {miss}개 ({miss/N:.1%})")
```

```text
$ python3 bloom_persist.py save; python3 bloom_persist.py load
저장한 키 10000개 중 필터가 '없다'고 답한 것: 9914개 (99.1%)

$ PYTHONHASHSEED=0 python3 bloom_persist.py save; PYTHONHASHSEED=0 python3 bloom_persist.py load
저장한 키 10000개 중 필터가 '없다'고 답한 것: 0개 (0.0%)
```

`PYTHONHASHSEED`를 고정하면 멀쩡해 보이지만 그건 우연히 동작하는 것이다. 필터를 만드는 서비스(예: Python 배치)와 읽는 서비스(Java, Node)가 다르면 해시 구현부터 다르다. **저장하거나 공유하는 필터는 언어와 프로세스에 상관없이 같은 값을 내는 해시(위 코드의 blake2b, MurmurHash 등)를 쓰고, 해시 종류와 시드, m, k를 필터와 함께 저장한다.** 이 값들이 어긋나면 에러 없이 조회 결과만 틀린다.

### 필터를 만들기 전의 키를 놓친다

필터는 키가 DB에 들어갈 때 같이 채운다. 이미 있는 데이터는 배치로 한 번 채워야 한다. 그 사이(채우는 중, 또는 새 키 생성 후 필터 반영 전) 조회하면 존재하는 키에 "없음"이 나온다. 채우는 동안에는 필터를 켜지 않거나, 새 키는 DB 쓰기와 필터 쓰기를 같은 흐름에 둔다. 필터 쓰기가 실패하면 그 키는 조회할 수 없게 되므로 재시도·보정 경로가 필요하다.

## Redis에서 쓰기

RedisBloom 모듈은 `BF.RESERVE`로 오탐률과 용량을 주고 `BF.ADD`, `BF.EXISTS`로 쓴다. 이 문서의 실험은 Redis 없이 돌렸고 RedisBloom 명령은 직접 실행해 확인하지 않았다. 모듈 없이 `SETBIT`/`GETBIT`로 직접 구현할 때는 위의 해시 이식성 문제를 그대로 안고 간다. 해시 계산을 클라이언트가 하므로 서비스마다 같은 구현을 써야 한다.

## 쓰지 않는 편이 나은 경우

- 존재하지 않는 키 조회가 드물다. 필터가 거를 것이 없다.
- 키 수가 어디까지 늘지 예측이 안 된다. 용량 초과 시 FP율이 급상승한다.
- 삭제가 잦고 정확한 멤버십이 필요하다.
- 오탐 한 번의 비용이 크다. 필터를 통과한 요청은 결국 DB를 간다.

관통 공격이 의심되면 필터 이전에 [Rate Limiting](../../Security/Rate_Limiting.md)과 입력 형식 검증으로 존재할 수 없는 ID(형식이 틀린 값, 범위 밖 값)를 먼저 걸러내는 편이 싸다. 필터는 "형식은 맞지만 존재하지 않는" 키를 막는 마지막 층이다. 캐시 전략 전체는 [캐싱 전략](Caching_Strategies.md)을 본다.
