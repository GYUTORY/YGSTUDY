# 문서 최신화

문서를 작성해 두면 관리는 된다고 착각하기 쉽다. 팀에서 "문서가 없다"는 불만이 나올 때 들여다보면, 파일이 없는 게 아니라 파일은 있는데 내용을 믿을 수 없는 상태인 경우가 많다.

코드는 실행하면 동작이 드러나지만 문서는 틀려도 조용히 넘어간다. 관리가 안 된 문서는 없는 문서보다 나쁘다 — 읽은 사람이 잘못된 방향으로 구현하거나, 이미 바뀐 API를 그대로 쓰다가 뒤늦게 실패한다. 문서가 있다는 사실이 신뢰의 근거가 되기 때문에 더 위험하다.

## 부실 문서는 길이로 안 잡힌다

처음에는 짧은 문서가 부실하다고 생각했다. 길이를 기준으로 정비 대상을 추렸더니 1,000자짜리 간결한 정리 문서들이 걸리고, 5,000자짜리 코드 덩어리 문서들이 빠졌다. 길이는 신호가 아니었다.

실제 신호는 **코드 대비 설명 비율**이다. 코드 블록, 표, HTML, 헤딩을 제외한 순수 산문 길이와 코드 블록 길이를 비교한다. 코드가 설명의 5배 이상이고 코드 자체가 2,000자를 넘으면 "틀만 잡고 코드만 채운 뒤 설명을 안 쓴 문서"다.

```python
import re, pathlib

def measure_prose_code(text: str) -> tuple[int, int]:
    code_len = sum(len(m.group()) for m in re.finditer(r'```.*?```', text, re.DOTALL))
    stripped = re.sub(r'```.*?```', '', text, flags=re.DOTALL)
    stripped = re.sub(r'^#{1,6} .+$', '', stripped, flags=re.MULTILINE)
    stripped = re.sub(r'^[|<].+$', '', stripped, flags=re.MULTILINE)
    prose_len = len(stripped.strip())
    return prose_len, code_len

for path in pathlib.Path('Develop').rglob('*.md'):
    if path.name == 'index.md':
        continue
    text = path.read_text()
    prose, code = measure_prose_code(text)
    if code > 2000 and prose > 0 and code / prose > 5:
        print(f"{code/prose:.1f}x  {path}")
```

이 비율은 찾기 위한 지표지 목표가 아니다. 코드가 4만 자인 API 레퍼런스는 설명을 1,000자 넣어도 비율이 40:1이다. 그게 실패가 아니다. 비율이 높게 나온 문서를 열어서 "코드 없이 이 문서를 읽고 동작을 이해할 수 있나"를 직접 확인하는 것이 마지막 판단이다.

같은 템플릿을 쓰는 문서 유형이 있다면 그 중 어느 비율이 이 기준에 걸리는지 먼저 봐야 한다. 같은 구조에서 생긴 문서는 같은 패턴으로 부실해지는 경향이 있다.

## Outdated를 알아채는 신호들

문서가 오래됐다는 사실은 날짜를 보면 알 수 있지만, 실제로 틀렸는지는 날짜로 모른다. 작성 후 3년이 지났어도 변하지 않은 내용이 있고, 6개월 만에 완전히 달라진 것도 있다.

실무에서 outdated를 먼저 알아채는 건 독자다. "문서대로 했는데 안 됩니다"는 이슈가 올라오거나, 신입이 온보딩하다가 막히는 구간이 생긴다. 이걸 기다리지 않고 먼저 찾으려면 아래 신호를 본다.

**코드 참조가 깨진 것.** 문서에서 특정 함수명, 클래스명, 설정 키를 언급하면 그 이름이 코드베이스에 있는지 확인한다.

```bash
# 문서에서 언급한 함수명이 소스에 실제로 있는지 대조
grep -r "getUserById" Develop/ --include="*.md" -l | while read doc; do
    if ! grep -rq "getUserById" src/; then
        echo "MISSING IN CODE: $doc"
    fi
done
```

이 방식은 함수명이 바뀌거나 삭제됐을 때만 잡힌다. 함수가 있어도 동작이 바뀐 것은 못 잡는다.

**외부 링크 404.** 서드파티 라이브러리 문서, 클라우드 콘솔 URL, 릴리즈 노트 링크는 외부 사이트가 재편되면 죽는다. 링크 검사기가 주기적으로 돌면 여기서 걸린다.

**버전이 명시된 문서.** "Node.js 14에서 확인함", "Spring Boot 2.6 기준" 같은 문서는 마이그레이션 이후 stale이 될 가능성이 높다. 버전이 박힌 문서만 추려서 현재 사용 버전과 대조하는 것이 시간 대비 효과가 크다.

```bash
# 버전 명시 문서 목록
grep -rn --include="*.md" \
  -E "(v[0-9]+\.[0-9]|Java [0-9]+|Node[. ][0-9]+|Spring Boot [0-9]+)" \
  Develop/ | grep -v "index.md" | cut -d: -f1 | sort -u
```

**최근 코드 변경과 관련 문서 대조.** 코드가 바뀌었을 때 관련 문서도 같이 갱신됐는지 확인하는 것이 가장 직접적이다.

```bash
# 최근 30일간 변경된 소스 파일
git log --since="30 days ago" --name-only --pretty=format: -- src/ \
  | grep -v '^$' | sort -u
```

여기서 나온 파일이 담당하는 기능과 연관된 문서를 찾는 것은 수작업이다. 파일명과 디렉터리 구조를 보고 판단하는 수밖에 없다.

## PR 흐름에서 갱신 누락을 막는 법

캘린더 기반 점검보다 **트리거 기반 갱신**이 현실적이다. 그 트리거를 가장 자연스럽게 심을 수 있는 곳이 PR 리뷰 단계다. PR 템플릿에 "연관 문서" 섹션을 추가해 두면, 작성자가 제출 전에 한 번 확인하게 된다.

```markdown
<!-- .github/pull_request_template.md -->

## 변경 내용

## 연관 문서

API 응답 구조, 설정 키, 배포 절차가 바뀐 경우 관련 문서도 수정한다.

- 해당 없음 (내부 구현만 변경, 외부 동작 변화 없음)
- 수정 완료: `docs/api/payment.md`
- 별도 이슈로 추적: #이슈번호

## 테스트
```

"해당 없음"에 이유를 쓰게 만드는 것이 핵심이다. 이유 없이 체크만 하면 사실상 건너뛰는 것과 다르지 않다. 리뷰어도 "API 바뀌었는데 문서 링크가 없네요"라고 코멘트를 달기 훨씬 쉬워진다.

버그 리포트나 지원 질문이 같은 구간에서 두 번 이상 들어오면 문서 문제인 경우가 많다. 그 자리에서 바로 문서를 고치는 것이 별도 일정을 잡는 것보다 빠르고, 다음 질문을 줄인다.

배포 직후에 문서를 갱신하러 가는 것은 대부분 안 된다. 배포 체크리스트에 "연관 문서 확인" 항목이 있어도 배포 후 피로도가 쌓인 상태에서는 건너뛰게 된다. 배포 PR 안에서 같이 처리하는 것이 실질적인 방법이다.

캘린더 점검을 완전히 없애는 것은 아니다. 6개월 이상 변경이 없는 문서 중 코드 변경이 잦은 모듈을 다루는 것만 추려서 보면, 전체를 훑는 것보다 효율이 높다.

## 코드 변경이 있을 때 문서 변경을 확인하는 훅

PR 단계에서 사람이 확인하는 것 외에, 코드 변경이 있을 때 문서 변경이 없으면 경고하는 훅을 pre-commit에 두는 방법이 있다.

```bash
#!/bin/bash
# .git/hooks/pre-commit

SRC_CHANGED=$(git diff --cached --name-only | grep -E '^src/')
DOC_CHANGED=$(git diff --cached --name-only | grep -E '^(docs|Develop)/')

if [ -n "$SRC_CHANGED" ] && [ -z "$DOC_CHANGED" ]; then
    echo ""
    echo "[docs] src/ 변경이 감지됐는데 docs/ 변경이 없습니다."
    echo "       API나 설정이 바뀐 경우 관련 문서를 같이 수정하거나"
    echo "       커밋 메시지에 'docs: skip — 내부 구현만 변경'을 명시하세요."
    echo ""
    # 강제 차단 원하면 아래 주석 해제
    # exit 1
fi
```

`exit 1`을 주석 해제하면 차단 훅이 된다. 처음 도입할 때는 경고만 내보내는 게 낫다. 팀이 패턴에 익숙해진 다음에 차단으로 올리는 것을 권한다. 한 번에 차단으로 시작하면 우회 방법(--no-verify)부터 공유된다.

훅은 `git clone` 이후 자동으로 설치되지 않는다. 저장소에 `.githooks/` 디렉터리를 두고 README나 `Makefile`에 `git config core.hooksPath .githooks`를 온보딩 단계에 포함시키는 방식으로 팀 전체에 배포한다.

## CI에서 변경분만 검사하기

전체 문서를 매번 검사하면 규모가 커질수록 느려진다. 문서가 1,000개를 넘어가면 PR마다 전체를 돌리는 게 부담이 된다. 변경된 파일만 추려서 검사하는 방식이 현실적이다.

```yaml
# .github/workflows/docs-check.yml
- name: 변경된 문서만 frontmatter 검사
  run: |
    BASE=${{ github.event.pull_request.base.sha }}
    HEAD=${{ github.event.pull_request.head.sha }}

    CHANGED=$(git diff --name-only "$BASE" "$HEAD" -- '*.md')

    if [ -z "$CHANGED" ]; then
      echo "문서 변경 없음, 검사 생략"
      exit 0
    fi

    echo "$CHANGED" | python3 tools/check_frontmatter.py --files-from-stdin
```

`check_frontmatter.py`가 파일 목록을 stdin으로 받는 `--files-from-stdin` 옵션을 지원해야 한다. 기존 스크립트가 전체 디렉터리를 스캔하는 방식이면, 파일 목록을 받아서 그것만 처리하도록 수정하는 게 선행된다.

```python
# tools/check_frontmatter.py 일부 — stdin 지원 추가
import sys

if '--files-from-stdin' in sys.argv:
    files = [pathlib.Path(line.strip()) for line in sys.stdin if line.strip()]
else:
    files = list(pathlib.Path('Develop').rglob('*.md'))
```

변경분 기반 검사의 단점은 누적 오류를 잡지 못한다는 것이다. 이전 커밋에서 이미 깨진 파일이 이번 PR에서 건드려지지 않으면 계속 통과된다. 주간 혹은 월간 전체 검사를 별도 워크플로로 두고, PR 검사와 역할을 분리하는 방식이 실용적이다.

## 문서 부채를 수치로 추적하기

"문서가 낡았다"는 느낌은 있는데 얼마나 낡았는지 수치가 없으면 개선됐는지 알 수 없다. 세 가지 지표를 주기적으로 기록해두면 추이를 볼 수 있다.

**장기 방치 비율.** 6개월 이상 변경이 없는 문서가 전체의 몇 퍼센트인지 측정한다.

```python
#!/usr/bin/env python3
# tools/doc_debt_report.py
import subprocess, pathlib

def staleness_report(days: int = 180):
    result = subprocess.run(
        ['git', 'log', f'--since={days} days ago',
         '--name-only', '--pretty=format:', '--', 'Develop/'],
        capture_output=True, text=True
    )
    recently_changed = {
        line.strip() for line in result.stdout.splitlines() if line.strip()
    }

    all_docs = [
        p for p in pathlib.Path('Develop').rglob('*.md')
        if p.name != 'index.md'
    ]
    stale = [p for p in all_docs if str(p) not in recently_changed]

    print(f"전체 문서: {len(all_docs)}")
    print(f"6개월 이상 방치: {len(stale)} ({len(stale)/len(all_docs)*100:.1f}%)")
    print()
    for p in sorted(stale):
        last = subprocess.run(
            ['git', 'log', '-1', '--format=%ar', '--', str(p)],
            capture_output=True, text=True
        ).stdout.strip()
        print(f"  {last:20s}  {p}")

if __name__ == '__main__':
    staleness_report()
```

**버전 명시 문서 수.** 특정 버전을 언급한 문서가 얼마나 있는지 수를 낸다. 마이그레이션이 있었는데 버전 명시 문서 수가 줄지 않았다면 대부분 갱신이 안 된 것이다.

**설명 비율 미달 문서 수.** 위의 `measure_prose_code` 스크립트가 잡는 문서 수를 주기적으로 기록한다.

세 지표를 각각 절대 수치로 보는 것보다 이전 측정 대비 증감을 보는 게 실용적이다. 수치가 개선됐다고 문서 품질이 좋아진 것은 아니지만, 악화되고 있는지 멈춰 있는지는 알 수 있다.

이 리포트를 매주 Slack으로 자동 전송하거나, CI에서 지표가 일정 임계치를 넘으면 PR을 차단하는 방식은 오탐이 많아지면 아무도 안 보게 된다는 경험이 있다. 월간 리뷰 회의 자료로 쓰거나, 분기에 한 번 팀이 함께 보는 용도로 쓰는 게 지속된다.

## 온보딩 피드백 루프

신입 온보딩 후 막힌 구간 피드백을 받는 구조가 있으면 정비 대상이 자동으로 나온다. 1주일간 온보딩 하나에서 문서 6건이 정비된 경험이 있다. 이론적으로 정기 점검 두 번 치량이다.

온보딩 피드백을 체계적으로 받으려면 "막힌 구간을 기록하는 문서"가 먼저 있어야 한다. 구글 독이나 노션에 온보딩 일지를 두고, "이 단계에서 막혔는데 문서에서 찾지 못했다"는 항목을 남기는 관행을 만드는 것이 간단하다. 일지 링크를 온보딩 PR에 달게 하면 잊지 않는다.

온보딩 담당자가 일지를 받아서 지적된 문서를 직접 수정해도 되고, 이슈로 등록해서 나중에 처리해도 된다. 중요한 건 피드백이 어딘가에 남아야 한다는 것이다. 구두 대화로만 끝나면 다음 신입이 같은 곳에서 다시 막힌다.

## 자동화로 할 수 있는 것과 없는 것

자동화가 커버하는 건 **형식적 오류**다.

- 깨진 링크 — 빌드 단계에서 `check_links`
- 빠진 frontmatter 키 — `check_frontmatter`
- 코드 대비 설명 비율 — 위의 스크립트
- 버전 명시 문서 목록 생성 — grep
- 6개월 이상 방치 문서 목록 — `doc_debt_report.py`
- PR에서 변경된 문서만 선별 검사 — diff 기반

내용이 맞는지는 자동화가 못 한다. "Redis TTL을 5분으로 설정하라"는 문서가 이제 10분이 맞는 상황이 됐는지, "3단계로 설정한다"가 이제 4단계가 됐는지는 코드를 읽는 사람이 판단해야 한다.

문서 상태를 추적하는 도구를 만들어도 결국 병목은 사람이 결과를 가지고 무엇을 할지 결정하는 부분이다. 도구가 하는 건 그 결정에 필요한 정보를 빠르게 모아주는 것까지다. 도구 점수를 올리는 것과 문서 품질을 올리는 것은 같은 일이 아니다.

코드베이스가 바뀌는 한 문서는 계속 stale이 된다. 한 번 전체를 정비하고 "이제 됐다"는 상태는 없다. 한 번에 몰아서 하는 방식보다, 코드 변경과 문서 갱신을 같은 흐름 안에 두는 것이 지속 가능하다. 자동화는 형식적 오류를 빠르게 찾는 데 쓰고, 내용 판단은 코드를 가장 잘 아는 사람이 코드를 고칠 때 같이 하는 것이 현실적이다.
