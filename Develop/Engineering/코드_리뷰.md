# 코드 리뷰

리뷰는 **버그를 잡는 자리가 아니다.** 버그는 테스트와 정적 분석이 더 잘 잡는다. 사람이 봐야만 하는 게 따로 있고, 그걸 못 보면 리뷰가 "LGTM 누르는 절차" 가 된다.

## 도구가 못 보는 것만 본다

리뷰 시간은 유한하다. 기계가 잡는 걸 사람이 또 보면 정작 봐야 할 걸 못 본다.

| 이건 기계에게 | 사람이 봐야 하는 것 |
|---|---|
| 포맷·스타일 | **설계 판단** — 이 구조가 다음 요구사항을 받을 수 있나 |
| 문법 오류·타입 | **의도** — 코드가 하는 일이 하려던 일인가 |
| 미사용 변수 | **누락** — 처리 안 된 케이스가 있나 |
| 테스트 통과 여부 | **테스트가 진짜 검증하나** |
| 커버리지 숫자 | **이해 가능성** — 6개월 뒤 남이 읽을 수 있나 |

포맷 지적이 리뷰에 올라온다면 그건 리뷰 문제가 아니라 **린터가 없는 문제**다. 설정으로 고친다.

## 리뷰할 수 있는 크기인가

이 저장소의 커밋 294개를 재 봤다.

```
중앙값    84줄 추가
상위 25%  302줄
상위 10%  601줄
최대     6,316줄
400줄 넘는 커밋 49개 (17%)
```

**400줄이 넘어가면 사람이 제대로 못 읽는다.** 스크롤하면서 앞을 잊고, 후반부로 갈수록 대충 본다. 큰 PR 일수록 지적이 적게 나오는데, 그건 문제가 없어서가 아니라 **집중력이 떨어져서**다.

리뷰어 입장에서 큰 PR 을 받으면 할 수 있는 말이 하나 있다.

```
"이거 나눠 주실 수 있나요? 지금 크기로는 제가 제대로 못 봅니다.
 스키마 변경 / API 추가 / 리팩터링 세 덩어리로 보이는데,
 앞의 둘만 먼저 주시면 오늘 보겠습니다."
```

**"제대로 못 본다" 를 말하는 게 리뷰어의 책임이다.** 대충 보고 승인하면 리뷰가 없었던 것보다 나쁘다 — 통과했다는 기록만 남는다.

## 실제로 잡는 패턴

프로세스 얘기는 여기까지다. 리뷰어 눈에 실제로 걸려야 하는 것들을 본다.

### N+1 쿼리

JPA 쓰는 코드에서 가장 흔하다. 루프 안에서 연관 엔티티를 건드리면 항상 의심한다.

```java
// before
public List<OrderDto> getOrders() {
    List<Order> orders = orderRepository.findAll();
    return orders.stream()
        .map(order -> new OrderDto(
            order.getId(),
            order.getUser().getName()  // 주문마다 쿼리가 1개씩 더 나간다
        ))
        .collect(Collectors.toList());
}
```

주문 50건이면 쿼리가 51번 나간다. 개발 환경에서는 데이터가 적어 안 보이다가 운영에서 터진다.

```java
// after
@Query("SELECT o FROM Order o JOIN FETCH o.user")
List<Order> findAllWithUser();

public List<OrderDto> getOrders() {
    return orderRepository.findAllWithUser().stream()
        .map(order -> new OrderDto(order.getId(), order.getUser().getName()))
        .collect(Collectors.toList());
}
```

`JOIN FETCH` 를 걸면 단일 쿼리로 처리된다. Querydsl 쓰면 `fetchJoin()` 이다.

페이징과 `JOIN FETCH` 를 같이 쓰면 Hibernate 가 경고를 낸다. 전체를 메모리에 올려 페이징하기 때문이다. 이 경우 `@BatchSize` 나 `IN` 쿼리로 분리한다.

### 트랜잭션 경계 누락

여러 테이블을 건드리는 메서드에 `@Transactional` 이 없으면 중간 실패 시 일부만 반영된다.

```java
// before
public void placeOrder(PlaceOrderCommand cmd) {
    Order order = new Order(cmd.getUserId(), cmd.getProductId(), cmd.getQuantity());
    orderRepository.save(order);

    // 여기서 예외 나면 주문은 생겼는데 재고는 안 줄어든다
    inventoryService.decreaseStock(cmd.getProductId(), cmd.getQuantity());

    paymentService.charge(cmd.getUserId(), order.getTotalPrice());
}
```

```java
// after
@Transactional
public void placeOrder(PlaceOrderCommand cmd) {
    Order order = new Order(cmd.getUserId(), cmd.getProductId(), cmd.getQuantity());
    orderRepository.save(order);
    inventoryService.decreaseStock(cmd.getProductId(), cmd.getQuantity());
    paymentService.charge(cmd.getUserId(), order.getTotalPrice());
}
```

한 가지 주의할 점: `paymentService.charge` 가 외부 API 를 호출한다면 `@Transactional` 로 감싸도 롤백이 안 된다. 외부 연동이 섞인 경우에는 보상 트랜잭션이 필요하다. 이 코드를 보면 "외부 결제 API 실패 시 어떻게 처리하나" 를 물어봐야 한다.

### 동시성 문제

카운터, 재고, 포인트처럼 여러 요청이 동시에 읽고 쓰는 값에는 경쟁 조건이 생긴다.

```java
// before
@Transactional
public void usePoint(Long userId, int amount) {
    User user = userRepository.findById(userId).orElseThrow();
    if (user.getPoint() < amount) throw new IllegalStateException("포인트 부족");
    user.setPoint(user.getPoint() - amount);  // read-modify-write
}
```

두 요청이 동시에 들어오면 둘 다 같은 값을 읽어 둘 다 차감한다. 포인트가 100인데 두 요청이 동시에 50씩 쓰면 결과가 0 이 되거나 50 이 될 수 있다.

```java
// after — 비관적 락
@Transactional
public void usePoint(Long userId, int amount) {
    User user = userRepository.findByIdWithLock(userId).orElseThrow();
    if (user.getPoint() < amount) throw new IllegalStateException("포인트 부족");
    user.setPoint(user.getPoint() - amount);
}

// Repository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT u FROM User u WHERE u.id = :id")
Optional<User> findByIdWithLock(@Param("id") Long id);
```

낙관적 락(`@Version`)도 있다. 충돌이 드물면 낙관적, 잦으면 비관적 락이 맞다. 코드만 봐서는 판단이 안 될 때가 있어서 "동시 요청이 얼마나 예상되나" 를 물어봐야 한다.

### Omit 으로 민감정보를 빼는 패턴 (TypeScript)

`Omit` 은 존재하지 않는 키도 조용히 통과시킨다. 민감정보 필터링에 쓰면 구멍이 생긴다.

```typescript
// before
type PublicUser = Omit<User, 'password'>;

// User 타입에 나중에 passwordHash 필드가 추가됐을 때
// Omit<User, 'password'>는 오류 없이 passwordHash를 포함해 내보낸다
function toPublicUser(user: User): PublicUser {
    const { password, ...rest } = user;
    return rest; // passwordHash가 그대로 나간다
}
```

```typescript
// after — 노출할 필드를 명시적으로 고른다
type PublicUser = Pick<User, 'id' | 'email' | 'name' | 'createdAt'>;

function toPublicUser(user: User): PublicUser {
    return {
        id: user.id,
        email: user.email,
        name: user.name,
        createdAt: user.createdAt,
    };
}
```

뭘 **빼는지** 보다 뭘 **넣는지를 명시**하는 게 안전하다. 필드가 추가될 때 실수가 날 여지가 없어진다.

### null 미처리 (TypeScript)

`tsconfig.json` 에 `"strictNullChecks": true` 가 없으면 컴파일러가 못 잡는다. 이 경우 리뷰에서 봐야 한다.

```typescript
// before
function sendWelcomeEmail(userId: string): void {
    const user = userRepository.findById(userId); // User | undefined
    mailer.send(user.email, 'welcome');            // user가 없으면 런타임 에러
}
```

```typescript
// after
function sendWelcomeEmail(userId: string): void {
    const user = userRepository.findById(userId);
    if (!user) {
        logger.warn(`User not found: ${userId}`);
        return;
    }
    mailer.send(user.email, 'welcome');
}
```

반환 타입에 `undefined` 가 포함돼 있는데 분기가 없다면 잡아야 한다. `user?.email` 로 넘어가는 경우도 있는데, 그러면 `mailer.send` 가 `undefined` 를 받아 다른 곳에서 터진다. 잡는 게 맞는 위치를 먼저 정한다.

## GitHub suggestion 으로 코드를 바로 제안한다

코멘트로 "이렇게 바꾸면 어떨까요" 를 텍스트로 쓰면 올린 사람이 직접 타이핑해야 한다. GitHub 의 suggestion 기능을 쓰면 버튼 하나로 적용할 수 있다.

리뷰 화면에서 줄을 선택하고 "Add a suggestion" (±) 버튼을 누르면 아래 형식이 자동으로 들어간다.

````markdown
```suggestion
    user = userRepository.findByIdWithLock(userId).orElseThrow();
```
````

올린 사람은 코멘트 안의 "Commit suggestion" 버튼을 누르면 그 줄이 바로 바뀐다. 여러 줄을 묶어 suggestion 할 수도 있다. 드래그로 범위를 선택하면 된다.

suggestion 은 사소한 수정일 때 쓰는 게 맞다. 설계를 바꾸는 제안은 코멘트로 이유와 함께 써야 한다.

## 올리는 쪽이 할 일

리뷰 품질의 절반은 올리는 쪽에서 정해진다.

### 설명을 코드 밖에 쓴다

diff 만 던지면 리뷰어가 맥락을 복원하는 데 시간을 다 쓴다. **왜 이렇게 했는지는 코드에 안 적혀 있다.**

```markdown
## 무엇을
주문 조회를 배치 쿼리로 바꿨습니다.

## 왜
카드 20개면 쿼리가 21번 나갔습니다. p99 가 800ms 였고 이제 120ms 입니다.

## 봐 주셨으면 하는 곳
- `OrderRepository.findByIds` 의 IN 절 크기 제한 — 1000개로 잡았는데
  적절한지 모르겠습니다
- 트랜잭션 경계를 서비스 레이어로 올렸습니다. 기존과 다른 패턴이라
  이게 맞는지 봐 주세요

## 안 한 것
캐싱은 이번에 안 넣었습니다. 무효화 시점이 안 정해져서 별도 티켓(PROJ-1234)
으로 뺐습니다.
```

**"봐 주셨으면 하는 곳" 과 "안 한 것" 이 특히 값을 한다.** 앞의 것은 리뷰어의 시간을 중요한 데 쓰게 하고, 뒤의 것은 "이건 왜 안 했지" 를 미리 막는다.

### 스스로 먼저 읽는다

올리기 전에 자기 diff 를 한 번 읽으면 절반은 자기가 잡는다. 디버깅용 로그, 주석 처리한 코드, 실험하다 만 변수 같은 것들이다.

**남이 그걸 지적하게 두는 건 리뷰어 시간을 낭비하는 것이다.**

## 어떻게 말하나

같은 지적도 어떻게 말하느냐로 결과가 달라진다. 요점은 예의가 아니라 **작업 가능성**이다.

### 코드를 말하고 사람을 말하지 않는다

```
✗ "왜 이렇게 짰어요?"
✓ "여기서 예외가 나면 트랜잭션이 안 닫힐 것 같은데 확인 부탁드립니다"
```

앞 문장은 답할 게 없다. 뒤 문장은 확인하고 고치거나 "이래서 괜찮습니다" 라고 답할 수 있다.

### 근거를 붙인다

```
✗ "이건 이렇게 하는 게 낫습니다"
✓ "이렇게 하면 재시도가 들어왔을 때 중복 처리됩니다.
   같은 문제가 결제 모듈에서 났었고 PROJ-891 에 정리돼 있습니다"
```

근거 없는 취향은 논쟁이 되고, 근거 있는 지적은 결정이 된다.

### 무게를 표시한다

전부 같은 톤으로 말하면 뭐가 중요한지 안 보인다. **접두어로 무게를 나눈다.**

```
[막음]   재시도 시 중복 결제가 납니다. 멱등 키가 필요합니다.
[제안]   이 로직은 별도 함수로 빼면 테스트하기 쉬울 것 같습니다.
[질문]   여기서 null 이 올 수 있나요? 못 찾겠어서 묻습니다.
[사소]   오타입니다: recieve → receive
```

이러면 올린 사람이 **무엇을 반드시 고쳐야 하는지** 안다. `[사소]` 와 `[제안]` 은 안 고치고 넘어가도 되고, 그게 명시돼 있으면 서로 편하다.

### 물어볼 때는 진짜 물어본다

지적을 질문 형태로 포장하는 건 오히려 나쁘다.

```
✗ "이거 트랜잭션 안 걸어도 될까요?" (사실은 걸어야 한다고 생각함)
✓ "[막음] 여기 트랜잭션이 필요해 보입니다. 중간에 실패하면 재고만 줄고
   주문은 안 생깁니다."
```

돌려 말하면 상대가 "네 괜찮습니다" 하고 넘어간다. **말할 거면 말한다.**

## 승인 기준

"완벽해야 승인" 은 아무것도 못 내보낸다. **기준은 "지금보다 나아졌는가" 다.**

```
승인한다      — 남은 것이 [제안]·[사소] 뿐이다
조건부 승인   — [막음] 이 있지만 고치면 다시 안 봐도 된다
승인 안 한다  — [막음] 이 있고, 고친 걸 다시 봐야 한다
```

두 번째를 쓰면 왕복이 줄어든다. 오타나 명백한 누락은 "고치고 머지하세요" 로 끝내는 게 서로 낫다.

## 리뷰가 오래 걸리는 문제

리뷰 대기가 길어지면 두 가지가 생긴다 — 브랜치가 낡아서 충돌이 나고, 올린 사람이 맥락을 잊는다.

**하루 안에 첫 반응을 주는 걸 목표로 삼는다.** 다 못 보겠으면 부분이라도 준다.

```
"앞부분만 봤습니다. 스키마 쪽은 문제없어 보이고,
 서비스 레이어는 내일 오전에 보겠습니다."
```

아무 말 없이 이틀 두는 것보다 훨씬 낫다.

## 받는 쪽

지적을 방어하고 싶어지는 건 자연스럽다. 다만 몇 가지를 정해 두면 덜 소모된다.

- **동의하면 그냥 고친다.** "네 고쳤습니다" 면 충분하고 변명은 안 붙인다
- **동의 안 하면 근거를 댄다.** "이래서 이렇게 했습니다" 는 정당한 답이다. 리뷰는 명령이 아니다
- **두 번 오가면 대화로 옮긴다.** 코멘트로 세 번 이상 왕복하면 글로 풀 문제가 아니다
- **[제안] 은 안 받아도 된다.** 다만 왜 안 받는지는 한 줄 적는다

리뷰를 잘한다는 건 결함을 많이 찾는 게 아니라, **올린 사람이 다음에 더 나은 코드를 쓰게 만드는 것**이다.
