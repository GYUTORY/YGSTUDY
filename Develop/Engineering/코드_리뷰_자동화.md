# 코드 리뷰 자동화

코드 리뷰에서 "줄 끝 공백 제거해주세요", "이 변수 명이 컨벤션에 안 맞네요" 같은 코멘트가 달리기 시작하면 리뷰어도 피로하고 작성자도 지친다. 이 종류의 피드백은 전부 도구가 잡을 수 있다. 사람 시간을 아끼려면 자동화 레이어를 먼저 깔아야 한다.

## 자동화 레이어를 어디에 넣을 것인가

파이프라인은 세 단계로 나뉜다.

```
로컬 커밋 전 → PR 열릴 때 → 병합 전 게이트
(pre-commit)   (GitHub Actions)  (Danger.js + 상태 체크)
```

각 단계를 언제 어떤 이유로 쓰는지가 중요하다. 전부 CI에 몰아두면 피드백이 늦고, 전부 로컬에 깔면 팀원 환경이 달라져 재현이 안 된다.

**로컬 pre-commit 훅**: 포맷·문법·단순 린트. 커밋 단위로 즉시 피드백. 푸시 전에 잡으면 CI를 돌릴 필요 없다.

**CI 게이트 (PR 오픈 시)**: 전체 테스트 + 정적 분석 + 커버리지. 로컬마다 설치 환경이 다르니 여기서 단일 기준으로 돌린다.

**Danger.js**: 위 두 레이어가 통과해도 "이 PR은 테스트 파일이 없다", "변경 파일이 50개를 넘는다" 같은 메타 수준 규칙을 잡는다. 사람이 매번 확인하던 체크리스트를 코드로 옮기는 것이다.

## pre-commit 훅 설정

`pre-commit` 패키지를 쓰면 훅을 `.pre-commit-config.yaml` 한 파일로 관리한다. 팀원 모두 `pre-commit install` 한 번으로 동일한 훅을 쓴다.

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-merge-conflict

  - repo: https://github.com/eslint/eslint
    rev: v9.0.0
    hooks:
      - id: eslint
        files: \.(js|ts|tsx)$
        args: [--fix]
        additional_dependencies:
          - eslint@9.0.0
          - "@typescript-eslint/eslint-plugin@7.0.0"
          - "@typescript-eslint/parser@7.0.0"
```

Java 프로젝트라면 Checkstyle을 직접 걸 수도 있는데, pre-commit에서 Java 도구를 돌리는 건 JVM 시작 비용 때문에 느리다. Checkstyle은 CI에만 두고 로컬 훅은 가볍게 유지하는 편이 낫다.

```bash
# 팀원 온보딩 시 한 번
pip install pre-commit
pre-commit install

# 전체 파일에 한 번 돌리고 싶을 때
pre-commit run --all-files
```

`.pre-commit-config.yaml`을 저장소에 커밋해두면 `pre-commit install`만 하면 된다. 다만 각자 환경에 `pre-commit` 패키지가 없으면 훅이 실행 자체가 안 된다. 팀 개발 환경 스크립트에 설치 명령을 포함시켜 두는 게 좋다.

## GitHub Actions PR 게이트

PR이 열리거나 커밋이 추가될 때 자동으로 분석이 돌게 한다. 게이트가 실패하면 병합이 막힌다.

### ESLint + TypeScript 타입 체크

```yaml
# .github/workflows/lint.yml
name: Lint

on:
  pull_request:
    branches: [main, develop]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci

      - name: ESLint
        run: npx eslint . --ext .ts,.tsx --max-warnings 0

      - name: TypeScript
        run: npx tsc --noEmit
```

`--max-warnings 0`으로 경고도 실패로 처리한다. 경고를 허용하면 경고가 300개가 쌓이고 아무도 안 본다.

### Checkstyle (Java)

```yaml
# .github/workflows/checkstyle.yml
name: Checkstyle

on:
  pull_request:
    branches: [main, develop]

jobs:
  checkstyle:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Java
        uses: actions/setup-java@v4
        with:
          java-version: 21
          distribution: temurin

      - name: Run Checkstyle
        run: ./gradlew checkstyleMain checkstyleTest

      - name: Upload Checkstyle Report
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: checkstyle-report
          path: build/reports/checkstyle/
```

Checkstyle 규칙 파일(`checkstyle.xml`)은 프로젝트 루트나 `config/` 아래에 두고 `build.gradle`에서 참조한다.

```groovy
// build.gradle
checkstyle {
    toolVersion = '10.17.0'
    configFile = file("${rootDir}/config/checkstyle/checkstyle.xml")
    maxWarnings = 0
}
```

### SonarQube

SonarQube는 로컬에서 한 번 연동하면 PR마다 분석 결과가 달린다. 무료 플랜은 public 저장소에 한해 SonarCloud를 쓸 수 있다.

```yaml
# .github/workflows/sonar.yml
name: SonarQube Analysis

on:
  pull_request:
    branches: [main]

jobs:
  sonar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # SonarQube는 전체 히스토리 필요

      - name: Setup Java
        uses: actions/setup-java@v4
        with:
          java-version: 21
          distribution: temurin

      - name: Cache SonarQube packages
        uses: actions/cache@v4
        with:
          path: ~/.sonar/cache
          key: ${{ runner.os }}-sonar

      - name: Build and Analyze
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
        run: |
          ./gradlew build sonar \
            -Dsonar.projectKey=my-project \
            -Dsonar.organization=my-org \
            -Dsonar.host.url=https://sonarcloud.io
```

SonarQube의 Quality Gate를 PR 게이트로 연결하면 커버리지 80% 미만, 버그 등급 C 이하는 병합이 안 된다. 처음 연동할 때 기존 코드베이스의 이슈가 수천 개 터지는 경우가 있는데, "New Code" 기준으로만 게이트를 걸면 기존 빚을 건드리지 않고 새 코드에만 적용할 수 있다.

## Danger.js로 메타 규칙 자동화

Danger.js는 "PR에 테스트가 없다", "PR이 너무 크다", "CHANGELOG를 업데이트하지 않았다" 같은 팀 규칙을 코드로 표현한다.

```bash
npm install --save-dev danger
```

```typescript
// dangerfile.ts
import { danger, warn, fail, message } from "danger";

// PR 크기 경고
const changedFiles = danger.git.modified_files.length + danger.git.created_files.length;
if (changedFiles > 50) {
  warn(`이 PR은 변경 파일이 ${changedFiles}개입니다. 분리를 고려해 주세요.`);
}

// 테스트 파일 없이 소스만 변경
const hasSourceChanges = danger.git.modified_files.some(f => f.startsWith("src/") && !f.includes(".test."));
const hasTestChanges = danger.git.modified_files.some(f => f.includes(".test.") || f.includes(".spec."));

if (hasSourceChanges && !hasTestChanges) {
  warn("소스 변경이 있는데 테스트 파일 변경이 없습니다.");
}

// PR 설명 없음
if (!danger.github.pr.body || danger.github.pr.body.length < 10) {
  fail("PR 설명을 작성해 주세요.");
}

// 특정 파일 변경 시 알림
const touchedSecurityFiles = danger.git.modified_files.some(
  f => f.includes("security") || f.includes("auth") || f.includes("jwt")
);
if (touchedSecurityFiles) {
  message("보안 관련 파일이 변경되었습니다. 보안 담당자 리뷰를 추가하는 것을 권장합니다.");
}
```

```yaml
# .github/workflows/danger.yml
name: Danger

on:
  pull_request:
    branches: [main, develop]

jobs:
  danger:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci

      - name: Run Danger
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: npx danger ci
```

`GITHUB_TOKEN`은 별도 설정 없이 Actions에서 자동으로 주어진다.

`warn`은 PR에 경고 코멘트를 달지만 병합을 막지 않는다. `fail`은 Danger 자체를 실패로 처리해서 게이트를 막는다. 처음 도입할 때는 전부 `warn`으로 시작하고, 팀이 익숙해지면 필요한 것만 `fail`로 올리는 게 부작용이 적다.

## 흔한 실수

**린트 자동 수정을 CI에서 돌리고 커밋 푸시하기**

CI가 `--fix` 옵션으로 자동 수정하고 커밋을 만들어 올리는 구성을 쓰는 팀이 있다. 처음엔 편해 보이는데 PR 히스토리가 지저분해지고, 작성자가 변경된 내용을 인지하지 못한 채 병합하는 상황이 생긴다. CI에서는 수정하지 말고 "이 파일에 문제가 있다"고 알리는 것으로 충분하다. 수정은 작성자가 로컬에서 한다.

**모든 규칙을 하드 실패로**

처음에 모든 Danger 규칙을 `fail`로 설정하면 팀원들이 Danger 자체를 우회하거나 무시하게 된다. `warn`으로 시작해서 충분히 검토 후 `fail`로 올린다.

**Checkstyle 규칙을 Google Java Style 그대로 가져다 쓰기**

Google Style은 들여쓰기 2칸이다. 대부분의 Java 팀은 4칸을 쓴다. 기본 설정 그대로 가져오면 기존 파일 전체가 위반으로 잡혀서 팀원들이 포기하게 된다. 팀 코드베이스에서 실제로 쓰는 스타일로 규칙 파일을 조정한 다음 도입한다.

**SonarQube를 처음 연동하면서 전체 코드베이스에 게이트 적용**

새 코드에만 Quality Gate를 걸고 기존 이슈는 별도 티켓으로 관리한다. `sonar.newCode.period`를 PR 기준으로 설정하면 PR에서 추가된 코드에만 분석을 적용한다.

## 사람 리뷰에 넘기기 전 체크 흐름

결국 자동화 레이어의 목적은 사람 리뷰어가 진짜 봐야 하는 것에 집중하게 만드는 것이다. 사람이 매번 확인하던 것들을 도구로 옮기면 리뷰 코멘트의 밀도가 달라진다. "세미콜론 빠짐", "줄 길이 초과" 같은 코멘트가 사라지고 "이 트랜잭션 경계가 적절한가", "여기서 예외를 삼키면 운영에서 추적이 안 된다" 같은 코멘트만 남는다.

파이프라인을 처음 구성할 때는 작은 것부터 올린다. pre-commit 훅 하나 + ESLint CI 게이트 정도로 시작해서 팀이 거부감 없이 적응하면 Checkstyle, SonarQube, Danger.js 순으로 추가한다. 한 번에 전부 붙이면 기존 코드가 다 걸려서 팀이 지쳐 포기한다.
