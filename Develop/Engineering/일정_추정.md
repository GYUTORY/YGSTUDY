# 일정 추정

"이거 얼마나 걸려요?" 에 답하는 게 업무의 일부가 되는 시점이 온다. 그런데 이 질문에 잘 답하는 법은 어디서도 안 가르친다. 대충 부르고 못 지키거나, 크게 불러서 신뢰를 잃거나 둘 중 하나가 된다.

이 문서는 추정을 정확하게 만드는 법이 아니다. **정확해질 수 없다는 걸 전제로, 그래도 쓸모 있게 답하는 법**이다.

## 먼저 — 추정은 실제로 얼마나 틀리나

남의 통계를 가져오는 대신 이 저장소의 git 히스토리를 셌다. 개인 블로그 문서 작업이라 요구사항이 바뀔 일도, 협업 마찰도 없다. **가장 유리한 조건**이다.

```bash
# 문서별로 며칠에 걸쳐 커밋됐는지
git log --name-only --pretty='%H %ad' --date=short -- 'Develop/**/*.md'
```

```
문서 1,202개 중 이틀 이상에 걸쳐 고친 것 979개 (81%)

  1일에 걸침: 223개   ← 한 번에 끝난 것
  2일에 걸침: 429개
  3일에 걸침: 293개
  4일에 걸침: 170개
  5일 이상  :  84개
```

**한 번에 끝난 게 19% 다.** 나머지 81% 는 "다 썼다" 고 생각한 뒤에 또 손댔다.

커밋 메시지로도 같은 게 보인다.

```bash
git log --oneline | grep -icE 'fix|정정|고친다|수정|버그|오류|틀린|잘못'
# 444개 중 160개 = 36%
```

**커밋 세 개 중 하나가 앞서 한 걸 고치는 것**이다. 혼자 하는 문서 작업이 이렇다. 요구사항이 있고 리뷰가 있고 QA 가 있는 실무는 이보다 나을 리 없다.

여기서 나오는 결론은 "추정을 더 잘하자" 가 아니다. **"한 번에 끝난다" 를 전제한 추정은 19% 확률에 거는 것**이라는 사실이다.

## 왜 틀리나 — 세 가지 구조적 이유

### 1. 안 보이는 일이 절반이다

"API 하나 만들기" 를 추정할 때 머릿속에 그리는 건 핸들러 작성이다. 실제로 하는 일은 이렇다.

| 떠올리는 것 | 실제로 하는 것 |
|---|---|
| 핸들러 작성 | 핸들러 작성 |
| | 기존 코드 읽고 패턴 파악 |
| | DTO·스키마·타입 정의 |
| | 에러 케이스 처리 |
| | 테스트 작성 |
| | 로컬에서 안 돌아서 디버깅 |
| | 리뷰 받고 고치기 |
| | 배포하고 확인 |
| | 다른 사람이 쓰다 나온 문제 대응 |

추정할 때는 첫 줄만 세고, 실제로는 아홉 줄을 한다. **"코딩 시간" 을 추정하고 "일이 끝나는 시간" 으로 말하는 게 어긋남의 뿌리다.**

### 2. 모르는 걸 모른다

추정 시점에 가진 정보가 가장 적다. 착수하고 나서야 알게 되는 것들이 있다.

- 이 API 가 참조하는 테이블에 인덱스가 없다
- 기존 코드가 이 케이스를 전제하지 않고 짜여 있다
- 붙여야 하는 외부 API 문서가 실제 동작과 다르다
- 요구사항에 안 적힌 예외 케이스를 기획자가 당연하게 생각하고 있었다

이건 실력으로 줄일 수 있는 부분이 아니다. **모르는 것의 크기는 착수 전에 알 수 없다.** 그래서 추정은 진행하면서 좁아지는 것이지, 처음부터 정확할 수 없다.

### 3. 낙관이 기본값이다

같은 일을 시켜도 대부분 "잘 풀렸을 때" 를 기준으로 답한다. 막히는 상황이 떠오르지 않아서가 아니라, 떠올려도 그게 나한테 일어날 거라고 생각하지 않기 때문이다.

**과거의 나는 항상 막혔는데, 미래의 나는 안 막힐 것 같다.** 이걸 인정하는 게 출발점이다.

## 추정 전에 — 요구사항이 불분명하면 거부한다

추정을 요구받는 상황에서 답하기 가장 어려운 건 "뭘 만들지 모를 때" 다. 이때 숫자를 부르면 무조건 틀린다. 요구사항이 바뀌면 추정이 의미를 잃기 때문이 아니라, **애초에 같은 일을 두고 이야기하고 있지 않기 때문**이다.

실제로 이런 상황이 온다:

- "회원 관련 기능인데 아직 기획 중이에요. 대략 얼마나요?"
- "이 페이지 디자인이 나왔는데 DB 구조는 아직입니다. 한 번 봐줄 수 있어요?"
- "A 방식이랑 B 방식 중에 아직 결정 못 했는데, 일정은 어떻게 될까요?"

이런 질문에 숫자를 내놓으면 상대는 그 숫자를 들고 계획을 세운다. 나중에 요구사항이 확정되면 처음 말한 숫자와 달라지고, "왜 말이 바뀌냐" 는 상황이 된다.

거부는 이렇게 한다:

```
"지금은 답드리기 어렵습니다. DB 구조가 확정되면 그날 안에 추정 내드릴 수 있습니다.
 그 전에 숫자를 드리면 어차피 바뀔 가능성이 높아서요."
```

부분적으로라도 확정된 게 있으면 그 범위 안에서만 답한다:

```
"인증 부분은 기존과 같은 방식이라 3일 잡으면 됩니다.
 나머지는 A/B 방식에 따라 1~2주가 더 붙거나 안 붙거나 합니다.
 결정되면 이어서 말씀드리겠습니다."
```

이렇게 하면 답을 안 준 게 아니라, 확정된 부분과 불확정 부분을 분리해서 준 게 된다. 상대가 결정을 서두르게 되는 효과도 있다.

## 그래서 어떻게 답하나

### 하나의 숫자로 답하지 않는다

"3일이요" 는 정보가 없는 답이다. 듣는 사람은 그걸 확정으로 받아들이고, 말한 사람은 "잘 되면" 을 뜻했다. 어긋날 수밖에 없다.

**범위로 답한다.**

```
✗ "3일이면 됩니다"
✓ "막히는 게 없으면 2일, 보통은 3~4일, 지금 안 보이는 문제가 나오면 일주일까지 봅니다"
```

이렇게 말하면 세 가지가 전달된다 — 최선, 현실, 최악. 듣는 쪽이 어느 숫자로 계획을 세울지 스스로 고를 수 있다. 그리고 **일주일이 걸렸을 때 "말했던 범위 안" 이 된다.**

### 불확실한 지점을 이름으로 말한다

범위만 주면 "왜 그렇게 넓냐" 는 말이 돌아온다. **넓은 이유를 구체적으로 대면 대화가 달라진다.**

```
"2~5일입니다. 폭이 넓은 이유는 결제사 API 문서를 아직 못 봐서입니다.
 문서가 정확하면 2일, 실제 응답이 다르면 붙이는 데만 3일 더 걸립니다.
 오늘 문서 받아 보면 내일 다시 좁혀 드리겠습니다."
```

이러면 상대가 할 수 있는 게 생긴다 — 문서를 빨리 구해 오거나, 리스크를 감수하고 시작하라고 하거나. **추정을 좁히는 것보다 불확실성의 정체를 알려주는 게 더 도움이 된다.**

### 쪼개서 세면 낙관이 줄어든다

큰 덩어리는 낙관적으로 세게 된다. "회원 가입 기능 = 3일" 같은 식이다. 쪼개면 잊고 있던 일이 드러난다.

```
회원 가입
├─ 스키마 설계·마이그레이션      0.5일
├─ 가입 API                  1일
├─ 이메일 인증 (외부 연동)      1~3일  ← 여기가 불확실하다
├─ 중복 가입 처리              0.5일
├─ 테스트                     1일
└─ 리뷰 반영                  0.5일
                            4.5 ~ 6.5일
```

3일이라고 하려다 4.5~6.5일이 나온다. **덩어리로 셀 때 사라지는 게 테스트·리뷰·연동이고, 그게 대개 절반이다.**

쪼갤 때 항목이 안 떠오르면 그건 잘 아는 일이 아니라 **모르는 일**이다. 그때는 추정 대신 "반나절 보고 다시 말씀드리겠습니다" 가 정직하다.

### 버퍼는 숨기지 않는다

곱하기 2 를 해서 부르는 건 흔한 방법인데, 두 가지가 나쁘다. 들킨다는 것, 그리고 **일찍 끝나면 버퍼가 그냥 사라진다**는 것.

버퍼는 드러내 놓고 붙인다.

```
"작업 자체는 3일입니다. 여기에 리뷰 반영과 예상 못 한 문제용으로
 2일을 더 잡아서 5일로 보고 있습니다."
```

이러면 3일 만에 끝났을 때 "2일 벌었다" 가 되고, 5일이 걸려도 약속을 지킨 게 된다. 숨긴 버퍼는 둘 다 안 된다.

## 팀이 함께 추정할 때

혼자 추정하는 것과 팀이 함께 추정하는 건 다른 문제다. 팀 추정에서 자주 나오는 실수는 **가장 경험 많은 사람의 숫자가 바로 팀 추정치가 되는 것**이다. 낙관적인 사람이거나, 자기가 할 거라 가정하고 세거나, 발언 압력이 있거나 — 이유가 뭐든 합의가 아니라 복종이 된다.

### 플래닝 포커로 독립 추정

플래닝 포커는 이 문제를 해결하려고 만든 방법이다. 팀원이 동시에 숫자를 공개해서 먼저 발언한 사람의 영향을 차단한다.

```
태스크: 결제 API 연동

김개발 →  2
이개발 →  8
박개발 →  3
```

8을 부른 사람과 2를 부른 사람의 생각이 왜 다른지 확인하는 게 핵심이다. "저는 결제사 쪽 인증서 갱신이랑 테스트 계정 세팅까지 포함해서 셌습니다" — 이게 나오면 팀이 같은 작업을 다르게 이해하고 있었다는 걸 그 자리에서 잡는다. 차이가 크게 나면 그 태스크는 이미 정의가 안 된 것이다.

숫자는 시간 대신 포인트(스토리 포인트)를 쓰는 경우가 많다. 시간으로 추정하면 개인마다 생산성이 달라서 합산이 어렵다. 포인트는 상대적 복잡도라서 팀 전체 단위로 다루기 편하다.

### 속도(velocity) 기반 계획

포인트를 쌓아서 한 스프린트에 팀이 처리하는 포인트 수가 나오면 그게 팀의 속도다. 이게 쌓이면 계획이 달라진다.

```
팀 velocity: 스프린트당 40포인트 (최근 4스프린트 평균)

남은 백로그: 160포인트
→ 4스프린트, 약 8주
```

velocity 를 최근 3~4스프린트 평균으로 잡아야 쓸 만하다. 처음 1~2번은 팀이 과대 추정을 하거나 외부 방해를 과소평가해서 실제 처리량이 낮게 나온다.

velocity 기반 추정이 개인 추정보다 나은 점은 **"이 사람이 하면 3일, 저 사람이 하면 1주일" 을 계획에서 제거한다**는 것이다. 팀 단위 데이터라서 누가 맡든 같은 숫자를 쓴다.

한계도 있다. 팀 구성이 바뀌거나, 기술 스택이 달라지거나, 레거시 구역에 처음 들어가는 경우에는 과거 velocity 가 의미 없다. 그때는 스프린트 하나를 탐색에 쓰고 다음부터 추정한다.

## 진행 중에 해야 하는 일

### 재추정 시점을 미리 정한다

추정이 크게 달라질 만한 시점은 대개 세 곳이다:

**착수 직후 (1~2일 내)** — 기존 코드를 뜯어보고 나서 안 보이던 복잡도가 드러난다. 외부 API 문서를 받아 보거나, 스키마를 보고 나서다. 여기서 처음 추정이 3배 이상 차이 나는 경우가 많다.

**중반부 (전체 기간의 30~50% 지점)** — 큰 기술적 선택이 끝나고 남은 작업이 구체적으로 보인다. "이 페이스면 언제 끝난다" 가 처음으로 실측에서 나온다.

**막히는 시점** — 예상보다 오래 걸리는 게 생겼을 때. 막힌 지 반나절이 넘으면 "이 문제가 전체 일정에 얼마나 영향 주는지" 를 바로 올린다.

재추정은 이전 추정을 부정하는 게 아니다. 정보가 늘어난 시점에 다시 정밀하게 재는 것이다. **"처음 말한 것과 달라지면 신뢰를 잃는다" 는 생각이 오히려 나쁜 소식을 늦게 전달하게 만든다.**

### 재추정을 말하는 방법

재추정을 말할 때 "생각보다 복잡하네요" 로 끝내면 안 된다. 구체적으로 세 가지를 담는다.

```
1. 당초 추정: 5일
2. 현재 실측: 2일 지남, 남은 작업 예상 6일
3. 원인과 선택지:
   - 결제사 Webhook 형식이 문서와 달라 재설계 필요 (+2일)
   - 범위를 줄이면 (Webhook 제외, 폴링으로 임시 처리) 원래 일정 안에 됩니다
   - 아니면 7일로 늘려야 합니다
```

원인이 외부 요인이면 그냥 말한다. 내 실력 부족이었으면 그것도 말한다. 이유를 감추면 다음에도 같은 일이 반복된다.

### 어긋나는 순간 바로 말한다

가장 나쁜 건 마감 당일에 "못 끝냈습니다" 다. 그 시점엔 상대가 할 수 있는 게 없다.

**어긋날 것 같다는 신호가 오는 즉시 말한다.** 3일짜리를 1일 하고 나서 "생각보다 큽니다" 라고 하면 상대는 범위를 줄이거나 사람을 붙이거나 일정을 옮길 수 있다.

늦게 말할수록 선택지가 없어진다. **나쁜 소식은 빨리 갈수록 덜 나쁘다.**

### 왜 늘어났는지 기록한다

"이번에도 늦었네" 로 끝내면 다음에도 같다. 늘어난 이유를 적어 두면 패턴이 보인다.

```
회원가입 API: 3일 예상 → 6일
  +1일  기존 인증 코드가 이 케이스를 전제 안 함 (착수 후 발견)
  +1일  이메일 인증 외부 API 응답이 문서와 다름
  +1일  리뷰에서 트랜잭션 경계 지적 → 재작업
```

몇 번 쌓이면 자기 편향이 드러난다. 어떤 사람은 항상 외부 연동에서 터지고, 어떤 사람은 항상 리뷰 재작업을 안 센다. **자기 편향을 알면 다음 추정에 그 항목을 미리 넣을 수 있다.**

## 자주 나오는 질문 둘

### "정확히 언제 끝나요?"

정확한 답을 요구받을 때가 있다. 이때 지어내면 안 된다. 대신 **무엇을 확정하면 정확해지는지**를 말한다.

```
"지금은 못 드립니다. 결제사 응답 형식을 확인하면 그때 하루 단위로
 말씀드릴 수 있습니다. 그 전까지는 2~5일 범위로만 잡아 주세요.
 확인은 오늘 중에 하겠습니다."
```

### "왜 저번보다 오래 걸려요?"

비슷해 보이는 일이 다른 시간이 걸리는 건 정상이다. 다른 점을 구체적으로 대면 된다.

```
"저번 건은 단일 테이블이라 트랜잭션이 단순했습니다. 이번엔 재고랑
 주문을 같이 건드려서 실패 시 되돌리는 처리가 붙습니다. 그 부분이 이틀입니다."
```

## 정리

추정을 잘한다는 건 숫자를 잘 맞추는 게 아니다. 틀릴 걸 알고도 상대가 쓸 수 있는 정보를 주는 것이다.

이 저장소 실측에서 한 번에 끝난 작업은 19% 였다. 실무는 이보다 낮다. 그걸 전제하면 하나의 숫자 대신 범위로 답해야 한다는 결론이 자연스럽게 나온다. 범위가 넓으면 그 이유를 이름으로 말한다. 그래야 상대가 무언가를 손쓸 수 있다. 쪼개서 세면 테스트·리뷰·연동이 드러나고, 그게 보통 전체 시간의 절반이다. 버퍼는 드러내 놓고 붙여야 일찍 끝났을 때 이득이 되고, 늦어도 약속을 지킨 게 된다.

요구사항이 확정되지 않으면 추정을 거부하는 것도 답이다. 모른다는 걸 알면서 숫자를 부르면, 나중에 바뀐 숫자를 설명할 때 더 어려운 상황이 된다.

진행 중에는 착수 직후, 중반부, 막히는 시점 셋을 재추정 기점으로 잡는다. 어긋날 것 같으면 그 즉시 원인과 선택지를 붙여서 말한다. 늦게 말할수록 상대의 선택지가 줄어든다.
