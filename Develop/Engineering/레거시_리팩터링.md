# 돌아가는 코드를 안 멈추고 바꾸기

아키텍처 전환(모놀리스에서 MSA 로) 은 커리어에 몇 번 없다. 반면 **돌아가는 코드를 조금씩 고치는 일은 매주 한다.** 이 문서는 후자를 다룬다.

전자는 [모놀리스 to MSA 마이그레이션](../Architecture/MSA/모놀리스_to_MSA_마이그레이션.md) 의 Strangler Fig 절에 있다.

## 먼저 — 리팩터링을 하면 안 되는 때

"코드가 더러우니까" 는 이유가 아니다. 더러운 채로 5년째 잘 도는 코드가 많다. 손대는 순간 그건 **안 건드렸으면 없었을 위험**이 된다.

리팩터링이 정당한 건 이 셋 중 하나일 때다.

1. **지금 그 코드를 고쳐야 하는데** 구조 때문에 못 고친다
2. **같은 버그가 반복**된다. 구조가 그 버그를 부른다
3. **읽는 데 드는 시간**이 팀 전체로 쌓여 무시할 수 없다

셋 다 아니면 미뤄도 된다. 특히 "언젠가 필요할 것 같아서" 하는 리팩터링은 대개 그 언젠가가 안 온다.

## 기능 변경과 섞지 않는다

이게 가장 중요한 규칙이고, 가장 자주 깨진다.

리팩터링 커밋에 기능 변경이 섞이면 **문제가 났을 때 어느 쪽 탓인지 알 수 없다.** 되돌리려 해도 기능까지 같이 되돌아간다. 리뷰어도 "구조가 바뀐 건지 동작이 바뀐 건지" 를 diff 로 구분 못 해서 제대로 못 본다.

```
✗ 커밋 하나: "결제 로직 리팩터링 + 부분 환불 지원"
✓ 커밋 둘:   "결제 로직에서 금액 계산 분리 (동작 동일)"
             "부분 환불 지원"
```

앞 커밋의 메시지에 **"동작 동일"** 을 적어 두면 나중에 이력을 볼 때 도움이 된다. 그 커밋에서 난 문제는 리팩터링이 동작을 바꿨다는 뜻이므로, 범위가 좁혀진다.

## 테스트가 없으면 테스트부터

리팩터링의 정의가 "동작을 안 바꾸고 구조를 바꾸는 것" 인데, **동작이 안 바뀌었다는 걸 무엇으로 아는가.** 테스트가 없으면 알 수 없고, 그러면 그건 리팩터링이 아니라 그냥 다시 짜는 것이다.

문제는 리팩터링이 필요한 코드일수록 테스트가 없다는 것이다. 순서가 이렇게 된다.

### 1) 특성화 테스트 — 옳은 동작이 아니라 현재 동작을 박는다

레거시 코드의 "올바른 동작" 을 모를 때가 많다. 명세가 없거나, 있어도 코드가 다르게 돌고 있다. 이때는 **옳은지 따지지 말고 지금 나오는 값을 그대로 테스트로 박는다.**

```javascript
// 이 함수가 맞게 도는지는 모른다. 다만 지금 이렇게 돈다.
test('현재 동작 고정 — 리팩터링 전후 비교용', () => {
  expect(calcFee(10000, 'VIP')).toBe(850);      // 왜 850 인지는 나중에
  expect(calcFee(10000, 'NORMAL')).toBe(1000);
  expect(calcFee(0, 'VIP')).toBe(0);
  expect(calcFee(-1, 'VIP')).toBe(0);           // 음수인데 0? 일단 박는다
});
```

이 테스트는 **버그까지 같이 고정한다.** 그게 목적이다. 리팩터링 중에 버그가 사라지면 그것도 동작 변경이고, 지금은 그걸 원하는 게 아니다.

이상해 보이는 케이스(`-1` 이 `0` 을 내는 것)는 주석으로 표시해 두고 **리팩터링이 끝난 뒤에 따로 다룬다.**

### 2) 입력을 모르면 로그에서 캔다

테스트에 넣을 입력이 안 떠오르면 프로덕션 로그가 답이다. 실제로 들어온 입력을 모아 그대로 돌린다.

```bash
# 지난 하루 실제 호출을 뽑아 케이스로
grep 'calcFee' app.log | jq -r '.args' | sort -u | head -50
```

머리로 짜낸 케이스보다 이쪽이 낫다. **실제로 오는 입력에는 예상 못 한 게 섞여 있고, 그게 리팩터링에서 깨지는 자리다.**

### 3) 의존성을 끊어야 테스트를 붙일 수 있다

의존성이 얽혀서 테스트 자체가 안 만들어지는 경우가 있다. 방법은 세 가지다.

**파라미터 주입.** 가장 안전하다. 의존 객체를 함수 밖에서 받도록 바꾸고, 기본값을 두면 호출부는 안 바뀐다.

```javascript
// 전: 함수 안에서 직접 만든다. 테스트에서 갈아끼울 수 없다
function process() { const db = new Database(config); ... }

// 후: 밖에서 받는다. 기본값을 두면 호출부는 안 바뀐다
function process(db = new Database(config)) { ... }
```

호출부가 하나도 안 바뀌므로 위험이 거의 없고, 이제 테스트에서 가짜 `db` 를 넣을 수 있다.

**서브클래스-오버라이드.** 파라미터를 건드릴 수 없을 때 쓴다. 외부 호출을 메서드로 분리하고 테스트에서 그 메서드만 덮어쓴다.

```javascript
class OrderService {
  process(order) {
    const fee = this.charge(order.amount);
    return { orderId: order.id, fee };
  }
  charge(amount) {
    return externalGateway.charge(amount); // 프로덕션에서는 실제 호출
  }
}

// 테스트에서만 charge를 가짜로
class TestOrderService extends OrderService {
  charge(amount) { return 100; }
}
```

상속은 숨겨진 결합을 만들고 테스트 클래스가 프로덕션 클래스 내부 구조를 알아야 한다. 파라미터 주입이 불가능할 때만 선택한다.

**인터페이스 추출.** 구현체가 여럿이거나 나중에 교체할 가능성이 있으면 이쪽이 낫다. 클래스가 아니라 계약을 단위로 가른다.

```typescript
interface PaymentGateway {
  charge(amount: number): Promise<number>;
}

// 기존 구현체는 인터페이스를 구현하도록만 수정
class StripeGateway implements PaymentGateway {
  async charge(amount) { return externalStripe.charge(amount); }
}

// OrderService는 인터페이스에만 의존. 구현체를 모른다
class OrderService {
  constructor(private gateway: PaymentGateway) {}
  async process(order) {
    const fee = await this.gateway.charge(order.amount);
    return { orderId: order.id, fee };
  }
}

// 테스트에서는 가짜 구현체
class FakeGateway implements PaymentGateway {
  async charge(amount) { return amount * 0.1; }
}
```

인터페이스 추출은 테스트를 위한 변경이지만, 결과적으로 의존성이 역전되므로 Branch by Abstraction 으로 이어지기 좋다.

## 큰 리팩터링은 작은 커밋으로

한 번에 큰 걸 바꾸고 "잘 되네" 로 끝내는 게 제일 위험하다. 문제가 나면 어디서 났는지 못 찾고, 되돌리면 전부 되돌아간다.

이 저장소에 실제 예가 있다. 대비 검사기(`check_contrast.py`) 를 고칠 때 이렇게 나뉘었다.

```
test(css): 전경·배경 대비 검사를 게이트에 넣는다 (현재 미달 0건)
fix(css): 다크에서 인용문이 2.19:1 — 그리고 그걸 못 잡던 대비 게이트를 고친다
fix(css): 라이트에서 한 번도 칠해진 적 없는 색 3건 — 특이도로 지고 있었다
fix(css): 라이트에만 면이 없던 코드블록·표·인용문 — 다크에는 있었다
대비 검사의 미판정 28쌍을 3쌍으로 줄이고, 그 사이에 숨어 있던 결함을 고친다
대비 검사가 조용히 건너뛰던 규칙 6개를 되찾고, 아는 척하던 색을 미판정으로 뺀다
```

**검사기를 고칠 때마다 새 결함이 드러났다.** 한 번에 다 고치려 했으면 어느 수정이 어느 결함을 잡았는지 몰랐을 것이고, 중간에 뭔가 깨졌을 때 6개 변경을 통째로 되돌려야 했을 것이다.

쪼개는 기준은 **"각 커밋이 그 자체로 배포 가능한가"** 다. 중간 상태가 깨져 있으면 아직 덜 쪼갠 것이다.

## Branch by Abstraction — 실행 중인 구현체를 교체하기

구현체를 새것으로 바꾸고 싶은데 한 번에 교체하기에 범위가 크다. 전체를 한 브랜치에서 다시 짜면 merge 충돌이 나고, 테스트 없이 큰 변경을 넣으면 위험하다.

Branch by Abstraction 은 이렇게 한다. 인터페이스를 먼저 뽑고, 구 구현체가 그걸 구현하도록 바꾸고, 새 구현체를 같은 인터페이스로 만들어 점진적으로 교체한다. 브랜치를 딴 것처럼 보이지만 **코드베이스 안에서 구 코드와 새 코드가 동시에 산다.**

```typescript
// 1단계: 인터페이스를 추출한다. 구 로직은 그대로고 타입만 붙인다
interface FeeCalculator {
  calc(order: Order): number;
}

class LegacyFeeCalc implements FeeCalculator {
  calc(order: Order): number {
    // 수백 줄짜리 기존 로직 그대로
    return order.amount * 0.1;
  }
}

// 2단계: 새 구현체를 만든다. 아직 어디서도 안 쓴다
class NewFeeCalc implements FeeCalculator {
  calc(order: Order): number {
    return Math.max(order.amount * 0.09, 100);
  }
}

// 3단계: 주입 지점을 하나 만들고 플래그로 가른다
const calculator: FeeCalculator = featureFlags.useNewFeeCalc
  ? new NewFeeCalc()
  : new LegacyFeeCalc();
```

3단계에서 플래그를 올리면 새 구현체가 실제 트래픽을 받는다. 문제가 나면 플래그를 내리면 되고, 안 나면 구 구현체를 지우고 플래그도 지운다. **교체가 완료된 뒤에도 구 코드가 남아 있으면 이행이 덜 된 것이다.**

코드 리뷰에서 "같은 일을 하는 클래스가 왜 둘이냐"는 질문이 온다. PR에 이행 계획을 적어 두고, 구 구현체를 지우는 티켓을 같이 만들어 두는 게 낫다.

## 병렬 실행 — 새 로직을 검증하면서 배포하기

Branch by Abstraction 으로 구현체를 준비했는데 "새 로직이 구 로직과 정말 같은 결과를 내는가"를 테스트만으로 확신하기 어려울 때가 있다. 엣지 케이스가 많거나 데이터 조건이 복잡한 경우다. 그때 두 로직을 모두 돌리되 결과는 구 로직에서만 반환하고, 결과가 다르면 로그를 남긴다.

```typescript
async function calcFee(order: Order): Promise<number> {
  const legacyResult = legacyCalc(order); // 구 로직을 먼저, 반드시 반환할 것

  try {
    const newResult = await newCalc(order);
    if (legacyResult !== newResult) {
      logger.warn('fee_calc_mismatch', {
        orderId: order.id,
        legacy: legacyResult,
        new: newResult,
        diff: newResult - legacyResult,
      });
    }
  } catch (err) {
    // 새 로직이 죽어도 구 로직 결과로 응답한다
    logger.error('fee_calc_new_failed', { orderId: order.id, err });
  }

  return legacyResult;
}
```

불일치 로그가 쌓이면 케이스를 분석해서 새 로직을 고친다. 불일치가 0에 수렴하면 `return newResult` 로 바꾼 뒤 다음 배포에서 구 로직을 지운다.

두 가지는 반드시 지킨다.

새 로직이 **부수 효과를 내면 안 된다.** DB 쓰기, 외부 API 호출, 메일 발송이 섞인 코드를 그냥 병렬 실행에 넣으면 실제로 데이터가 두 번 써진다. 부수 효과가 있는 경로는 읽기와 쓰기를 먼저 분리하고, 쓰기 교체는 따로 이행한다.

새 로직 실행 시간이 응답 시간에 더해진다. 연산이 무거우면 전체 트래픽의 일부에만 돌린다. 10% 샘플링만 해도 불일치는 충분히 잡힌다.

## 데이터가 얽히면 확장-수축

코드는 배포하면 한 번에 바뀌지만 **데이터는 그렇지 않다.** 컬럼 이름 하나 바꾸는 것도 배포 중간에 구 코드와 신 코드가 동시에 돌기 때문에 한 번에 못 한다.

세 단계로 나눈다.

```
1. 확장 (expand)   새 컬럼을 추가한다. 구 컬럼은 그대로
                   → 이 시점에 구 코드도 신 코드도 다 돈다
2. 이행 (migrate)  양쪽에 다 쓰고, 읽기를 새 컬럼으로 옮긴다
                   → 기존 데이터는 배치로 채운다
3. 수축 (contract) 구 컬럼을 지운다
                   → 구 코드가 완전히 사라진 것을 확인한 뒤에
```

각 단계 사이에 **배포가 한 번씩 들어간다.** 1번과 3번 사이는 며칠에서 몇 주가 걸릴 수 있고, 그동안 컬럼이 둘인 어색한 상태로 산다. 그게 정상이다.

3번을 잊는 게 흔한 일이다. 구 컬럼이 몇 년째 남아 있는 테이블이 그렇게 생긴다. **1번 할 때 3번 티켓을 같이 만들어 두는 게 유일하게 통하는 방법이다.**

### NOT NULL 컬럼 추가 — 락이 걸리는 순서

신규 컬럼을 NOT NULL 로 바로 추가하면 테이블 전체에 락을 잡고 기존 행에 기본값을 채운다. 수백만 행 테이블에서는 배포 중 수 분간 쓰기가 막힌다. PostgreSQL 12 이전과 MySQL 에서 실제로 겪는 문제다.

순서를 나눠야 한다.

```sql
-- 1단계: DEFAULT 포함해 nullable 로 추가
-- 대부분 메타데이터 변경만 일어나서 빠르다
ALTER TABLE orders ADD COLUMN merchant_id BIGINT DEFAULT 0;

-- 2단계: 기존 행을 배치로 채운다. 한 번에 다 하면 락이 오래 잡힌다
-- 1,000~5,000행 단위로 쪼개서 반복
UPDATE orders
SET merchant_id = (SELECT id FROM merchants WHERE merchants.name = 'default')
WHERE merchant_id = 0 AND id BETWEEN :start AND :end;

-- 3단계: 값이 다 채워진 걸 확인한 뒤 NOT NULL 제약 추가
-- PostgreSQL 12+ 는 validate check 없이 메타데이터만 바꾸므로 빠름
ALTER TABLE orders ALTER COLUMN merchant_id SET NOT NULL;

-- 4단계(선택): DEFAULT 제거. 앞으로 이 컬럼은 명시적으로 넣는다
ALTER TABLE orders ALTER COLUMN merchant_id DROP DEFAULT;
```

인덱스도 마찬가지다. `CREATE INDEX` 는 테이블 락을 잡는다. 쓰기 트래픽이 있는 테이블에서는 `CONCURRENTLY` 를 써야 한다.

```sql
-- 락 없이 인덱스 추가 (PostgreSQL)
CREATE INDEX CONCURRENTLY idx_orders_merchant_id ON orders(merchant_id);

-- 실패하면 인덱스가 invalid 상태로 남는다. 완료 후 반드시 확인한다
SELECT indexname, indisvalid
FROM pg_stat_user_indexes
WHERE relname = 'orders';
-- indisvalid 가 false 이면 DROP 하고 다시 만들어야 한다
```

`CONCURRENTLY` 는 트랜잭션 안에서 쓸 수 없고, 실패 시 자동 롤백이 안 된다. 인덱스가 invalid 로 남아 있으면 쿼리가 그걸 타지 않아서 배포 후 조용히 느려지는 경우가 있다. 배포 직후 위 쿼리로 확인하는 걸 습관으로 만들어야 한다.

## 언제 멈추나

리팩터링은 끝이 없다. 더 나은 구조가 항상 보인다. 멈추는 기준을 미리 정해 두지 않으면 예정에 없던 일주일이 사라진다.

**착수할 때 목표를 한 문장으로 적는다.**

```
"결제 금액 계산을 함수로 분리해서 테스트를 붙일 수 있게 한다"
```

그 문장이 달성되면 멈춘다. 그 과정에서 발견한 다른 문제들은 **고치지 말고 적어 둔다.** 눈에 보이는데 안 고치는 게 답답하지만, 범위가 번지기 시작하면 리뷰도 못 받고 롤백도 못 하는 덩어리가 된다.

## 되돌릴 수 있게 해 둔다

아무리 조심해도 문제는 난다. 그때 **되돌리는 데 걸리는 시간**이 피해 크기를 정한다.

이 저장소에 실제 사례가 있다.

```
revert(build): enable_git_follow 를 기본값으로 되돌림

  앞 커밋에서 mkdocs.yml 을 스테이징할 때 enable_git_follow: false 가
  함께 들어갔다. 성능 측정용으로 잠시 켠 값인데 내가 검토 없이 커밋했다.
```

되돌리기가 쉬웠던 이유는 그 변경이 **한 줄이었고 다른 것과 안 섞여 있었기 때문**이다. 앞의 "기능과 섞지 않는다", "작은 커밋으로" 가 여기서 값을 한다.

큰 리팩터링이라면 피처 플래그로 감싸는 것도 방법이다. 새 경로와 구 경로를 둘 다 두고 플래그로 가른다. 문제가 나면 배포 없이 플래그만 내린다. 다만 **플래그를 지우는 일정을 같이 잡아야 한다** — 안 그러면 두 경로가 영원히 남아서 오히려 복잡해진다.

## 정리

- **하면 안 되는 때가 있다.** 지금 고쳐야 하는데 막힐 때 / 같은 버그가 반복될 때 / 읽는 비용이 쌓일 때, 셋 중 하나가 아니면 미룬다
- **기능 변경과 섞지 않는다.** 섞이면 문제가 났을 때 원인을 못 가리고 되돌리지도 못한다
- **테스트가 없으면 특성화 테스트부터.** 옳은 동작이 아니라 현재 동작을 박는다. 버그까지 같이 고정하는 게 맞다
- 입력이 안 떠오르면 **프로덕션 로그**에서 캔다
- 의존성을 끊을 때는 파라미터 주입 → 서브클래스-오버라이드 → 인터페이스 추출 순서로 시도한다. 앞쪽이 더 안전하다
- **Branch by Abstraction.** 인터페이스를 먼저 뽑고 구현체를 점진적으로 교체한다. 교체가 끝나면 구 구현체와 플래그를 같이 지운다
- **병렬 실행.** 새 로직을 검증할 자신이 없으면 구 로직과 나란히 돌리고 불일치를 로그로 쌓는다. 부수 효과가 없는 경로에서만 쓴다
- **작은 커밋으로 쪼갠다.** 기준은 "각 커밋이 그 자체로 배포 가능한가"
- 데이터가 얽히면 **확장-수축.** 3번(수축) 티켓을 1번 할 때 같이 만든다. NOT NULL 컬럼은 DEFAULT 추가 → 배치 backfill → 제약 추가 순서로 한다
- **멈출 지점을 먼저 정한다.** 한 문장으로 적고, 그게 되면 멈춘다
- **되돌리는 시간이 피해 크기를 정한다.** 작고 안 섞인 커밋이 그래서 값을 한다

리팩터링을 잘한다는 건 더 좋은 구조를 아는 게 아니라, **바꾸는 동안 서비스가 안 멈추게 하는 것**이다.
