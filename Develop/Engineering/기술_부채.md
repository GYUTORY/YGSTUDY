# 기술 부채

"나중에 고치자" 는 말은 대부분 안 지켜진다. 안 지켜지는 이유가 게을러서가 아니라 **기록이 남지 않는 구조**라서다.

이 문서는 부채를 안 만드는 법이 아니다. 부채는 필연이고, **그걸 잊지 않고 갚는 방법**이다.

## 부채와 그냥 나쁜 코드는 다르다

둘을 섞으면 대화가 안 된다.

| | 기술 부채 | 그냥 나쁜 코드 |
|---|---|---|
| 왜 생겼나 | **알고** 택했다 — 일정·정보 부족 때문에 | 몰랐거나 대충 했다 |
| 대안이 있었나 | 있었는데 지금은 못 한다 | 처음부터 그게 최선인 줄 알았다 |
| 갚을 계획 | 있어야 한다 | 그냥 고치면 된다 |

**"알고 택했다" 가 부채의 정의다.** 시간이 없어서 인덱스 없이 배포한 건 부채다. 인덱스가 필요한 줄 몰라서 안 넣은 건 그냥 실수다.

이걸 구분해야 하는 이유는 대화 상대가 다르기 때문이다. 실수는 조용히 고치면 된다. **부채는 그걸 택한 근거가 있으므로, 갚는 것도 근거를 대고 협상해야 한다.**

## 기록 — TODO 주석은 도구가 아니다

이 저장소를 세어 봤다.

```bash
grep -rn 'TODO\|FIXME\|HACK\|XXX' tools/ overrides/ Develop/javascripts/
# 0건
```

TODO 가 0건인 게 부채가 없다는 뜻은 아니다. **TODO 주석이 부채 관리 도구로 안 쓰인다**는 뜻이다. 그게 맞다. 주석은 세 가지가 안 된다.

- **검색이 안 된다** — 코드베이스 전체를 grep 해야 보이고, 여러 저장소면 그마저 안 된다
- **우선순위가 없다** — 5분짜리와 2주짜리가 같은 `// TODO` 다
- **아무도 안 본다** — 그 파일을 여는 사람만 본다. 그 파일을 안 여는 게 문제인데

부채는 **티켓으로 남긴다.** 이슈 트래커든 뭐든, 코드 밖에 있고 검색되고 우선순위가 붙는 곳이면 된다.

### 티켓에 뭘 적나

"리팩터링 필요" 만 적힌 티켓은 6개월 뒤에 아무도 못 읽는다. 네 가지가 필요하다.

```markdown
## 무엇을 미뤘나
주문 조회에서 상품 정보를 건별로 가져온다 (N+1).
카드 20개면 쿼리가 21번 나간다.

## 왜 미뤘나
2026-08-15 오픈 일정. 배치 조회로 바꾸려면 응답 DTO 구조가 바뀌고
프론트도 같이 고쳐야 해서 그 주에 못 했다.

## 지금 무슨 문제가 있나
주문 목록 p99 가 800ms. 현재 트래픽에서는 견딘다.
상품이 카드당 5개를 넘으면 타임아웃 구간에 들어간다.

## 언제 터지나 (이게 제일 중요하다)
- 주문 건수가 지금의 3배가 되면
- 또는 카드당 상품이 5개를 넘는 기획이 들어오면
```

**"언제 터지나" 를 적는 게 핵심이다.** 이게 있으면 티켓이 스스로 우선순위를 말한다. 없으면 "언젠가 해야 하는 일" 더미에 섞여서 영영 안 올라온다.

### 코드에는 티켓 번호만 남긴다

주석이 쓸모없는 건 아니다. **그 코드를 읽는 사람에게 "이건 의도된 것" 을 알리는 역할**은 한다. 다만 내용은 티켓에 두고 링크만 남긴다.

```javascript
// 건별 조회 — 배치로 바꿔야 한다. 근거와 조건은 PROJ-1234.
// 그냥 고치지 말 것: 응답 DTO 가 바뀌어서 프론트와 같이 배포해야 한다.
for (const item of items) { ... }
```

```java
// 건별 조회 — 배치로 바꿔야 한다. 근거와 조건은 PROJ-1234.
// 그냥 고치지 말 것: 응답 DTO 가 바뀌어서 프론트와 같이 배포해야 한다.
for (Item item : items) { ... }
```

```python
# 건별 조회 — 배치로 바꿔야 한다. 근거와 조건은 PROJ-1234.
# 그냥 고치지 말 것: 응답 DTO가 바뀌어서 프론트와 같이 배포해야 한다.
for item in items:
    ...
```

두 번째 줄이 중요하다. **"왜 아직 안 고쳤는지" 를 적어야** 다음 사람이 좋은 뜻으로 고치다 사고를 안 낸다.

## 측정 — 도구가 보여주지 않는 것

SonarQube나 CodeClimate을 처음 도입하면 "기술 부채 X일" 같은 수치가 나온다. 그게 실제 상환 비용이라고 믿으면 안 된다.

SonarQube는 중복, 인지 복잡도(cognitive complexity), 코드 스멜을 측정해서 "이만큼 고치면 된다"는 수치를 뱉는다. CodeClimate은 파일 단위로 A~F 등급을 매긴다. 둘 다 **정적 분석** 기준이라 코드가 그 자리에 있는 한 측정값이 바뀌지 않는다.

문제는 실제로 비싼 부채들이 여기서 안 잡힌다는 점이다.

- 서비스 간 스키마 계약이 암묵적으로 어긋난 것
- 캐시와 DB 동기화 로직이 빠진 채 배포된 것
- 분산 트랜잭션을 단순 REST 호출로 대체한 것

이것들은 중복도 없고 복잡도도 높지 않을 수 있다. 코드가 깔끔하게 버그를 내장하고 있는 상태다.

SonarQube를 유용하게 쓴 방식은 **추세 추적**이다. 절댓값보다 "이번 스프린트에 코드 스멜이 몇 개 늘었나"를 보면 어느 방향으로 가고 있는지는 알 수 있다. PR에서 critical 이슈가 새로 생기면 병합을 막는 것도 쓸 만하다.

단, "기술 부채 0일"을 목표로 삼으면 팀이 이상한 일을 한다. SonarQube를 통과하기 위해 코드를 쪼개거나 suppress 주석을 붙인다. **도구 점수를 올리는 것과 부채를 줄이는 것은 같은 일이 아니다.**

## 부채 속도를 추적하는 지표

코드 분석 도구와 별개로, DORA 지표를 보면 부채 누적 속도가 간접적으로 보인다.

**cycle time**: PR이 열린 시점부터 배포까지 걸리는 시간. 같은 팀, 같은 규모의 작업인데 cycle time이 늘어나고 있다면 무언가가 느려지고 있다는 신호다. 대개는 테스트가 자주 깨지거나, 코드를 읽는 데 시간이 오래 걸리거나, 의존성이 복잡해진 것이다.

**change failure rate**: 배포 후 롤백하거나 긴급 패치를 낸 비율. 이게 올라가면 안 건드린 곳이 건드린 것에 영향을 받고 있다는 뜻이다. 격리가 안 된 것이고 대개 부채가 원인이다.

**파일 변경 빈도 × 복잡도**: 자주 바뀌는데 복잡도가 높은 파일이 가장 위험하다. git log로 파일별 커밋 수를 뽑고, SonarQube에서 복잡도를 교차하면 "지금 당장 갚아야 할 것"이 보인다.

```bash
# 최근 6개월간 파일별 변경 횟수
git log --after="6 months ago" --name-only --pretty=format: \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -20
```

cycle time이나 change failure rate를 측정하려면 배포 기록이 있어야 한다. GitHub Actions 로그나 Jira 이슈 상태 변경 이력에서 뽑을 수 있다. 팀에 대시보드가 없으면 처음에는 직접 세서라도 한 달에 한 번 공유하는 것이 먼저다.

이 수치들은 부채의 **존재**를 말해주지 않는다. 부채가 **쌓이는 속도**를 말한다. 한 달 전보다 cycle time이 30% 늘었으면 그 사이에 뭔가가 쌓인 것이다.

## 실제로 터진 것들

N+1은 비교적 눈에 잘 띈다. 로그에서 쿼리가 많이 나오는 게 보이고, 원인도 명확하다. 눈에 안 보이다가 터지는 유형이 더 까다롭다.

**캐시·DB 동기화 누락**: 상품 서비스에서 재고 정보를 Redis에 5분 TTL로 캐싱했다. 주문 서비스가 재고를 확인할 때 캐시만 보고 DB를 안 봤다. 재고가 0으로 업데이트된 지 4분 뒤, 캐시가 아직 살아있는 사이에 주문이 5건 들어왔다. 재고보다 많은 주문이 접수됐고 환불 처리가 수동으로 됐다.

이 상태는 처음 배포할 때부터 있었다. 부하가 적을 때는 TTL 안에 주문이 들어오지 않아서 안 걸렸다. 부채 티켓은 없었다. "캐시 써도 되냐"는 논의가 Slack 스레드에 있었고 "일단 이렇게 가자"는 답이 달렸다. 그 스레드는 아무도 못 찾았다.

**스키마 불일치**: 사용자 서비스와 알림 서비스가 `user_id` 타입을 각자 정의했다. 사용자 서비스는 `bigint`, 알림 서비스는 `varchar(36)`. 초기에는 UUID를 쓰다가 사용자 서비스가 숫자형으로 바꿨는데 알림 서비스가 안 따라갔다. 숫자가 작을 때는 varchar가 그냥 저장했다. `user_id`가 10자리를 넘어가면서 알림 서비스 DB에 저장이 안 됐고, 6주 동안 몰랐다.

이 부류의 공통점은 **처음엔 동작하는데 나중에 조용히 깨진다**는 것이다. 부채를 기록하지 않으면 이렇게 된다. 당시에는 괜찮아서 잊고, 조건이 바뀌면서 터진다.

## 갚기 — 몰아서는 안 된다

"다음 스프린트는 부채 정리" 는 대개 실패한다. 기능 개발을 멈춰야 하는데 그걸 승인받기 어렵고, 승인받아도 한 번 하고 끝나면 다시 쌓인다.

현실적으로 통하는 건 둘이다.

### 1) 그 코드를 만질 때 같이

가장 자연스럽다. 어차피 그 파일을 열었고, 맥락이 머리에 있고, 테스트도 그때 돌린다.

**규칙은 "만진 만큼만"** 이다. 주문 조회를 고치러 갔으면 주문 조회의 부채만 갚는다. 옆에 보이는 다른 것까지 손대면 그건 범위가 번진 것이고, [리팩터링 문서](레거시_리팩터링.md) 의 "멈출 지점" 문제가 된다.

### 2) 정기적으로 조금씩

만질 일이 없는 코드는 1번으로 안 갚힌다. 스프린트마다 일정 비율을 부채에 배정한다.

비율은 팀마다 다르지만 **10~20% 가 흔한 출발점**이다. 중요한 건 숫자가 아니라 **그게 계획에 들어가 있다는 것**이다. "여유 있으면 하자" 는 여유가 안 생겨서 안 된다.

### 3) 팀 회고에서 부채를 다루는 방법

스프린트 리뷰에서 부채를 이야기하면 대개 묻힌다. 기능 데모가 끝나고 시간이 남으면 "아, 이것도 있는데요" 하고 나오는데, 그 자리에서 결론이 나기 어렵다.

별도 부채 세션을 운영하는 팀들이 있다. 월 1회 30분, 열린 부채 티켓을 훑고 우선순위를 재조정한다. 집중해서 볼 수 있다는 장점은 있는데, 그 사이에 생긴 부채는 한 달을 기다린다.

두 방식을 같이 쓰는 것이 현실적이다.

- 스프린트마다: 새로 생긴 부채 티켓을 백로그에 추가하고 대략적인 크기를 붙인다. 5분이면 된다.
- 월 1회: 전체 부채 목록을 훑고, "언제 터지나"가 바뀐 것을 다시 적고, 다음 스프린트에 넣을 것을 고른다.

논쟁이 생기는 지점은 별도 세션의 필요성이다. "굳이 따로 해야 하나, 스프린트 플래닝 때 같이 보면 안 되냐"는 의견이 나온다. 플래닝에 넣으면 기능 개발 항목과 경쟁하게 되고 대부분 진다. 부채 전용 시간이 없으면 매번 밀린다는 것이 반복되는 패턴이다.

별도 세션에서 무엇을 먼저 다룰지 막막할 때 가장 빠른 방법은 **"지금 이게 문제가 됐냐"** 를 먼저 묻는 것이다. 문제가 된 것은 이번 스프린트에 넣고, 안 된 것은 조건이 바뀌었는지 확인해서 우선순위를 조정한다.

## 설득 — "코드가 더러워요" 는 안 통한다

부채를 갚으려면 시간을 받아야 하고, 그건 기능 개발을 미룬다는 뜻이다. 이걸 승인하는 사람은 대개 코드를 안 본다.

**코드 품질로 설명하면 안 통한다.** 통하는 건 셋이다.

### 1) 지금 드는 비용

```
✗ "이 부분 코드가 너무 복잡해요"
✓ "이 모듈을 고칠 때마다 평균 이틀이 걸립니다. 비슷한 다른 모듈은 반나절입니다.
   지난 분기에 여기를 여섯 번 고쳤으니 아흐레를 더 쓴 셈입니다."
```

숫자가 없으면 만들어서라도 대야 한다. **"몇 번 고쳤고 매번 얼마나 걸렸나" 는 티켓 이력에서 뽑을 수 있다.**

### 2) 언제 터지는지

앞의 티켓 템플릿이 여기서 값을 한다.

```
"지금은 견딥니다. 다만 주문이 3배가 되면 타임아웃이 납니다.
 성장 계획대로면 4개월 뒤입니다. 지금 고치면 3일, 터진 뒤에 고치면
 장애 대응까지 붙습니다."
```

**"언젠가 문제가 됩니다" 와 "4개월 뒤입니다" 는 완전히 다른 말이다.**

### 3) 다음 기능의 발목을 잡는다

가장 강력한 논거다. 부채 자체가 아니라 **하고 싶은 일이 막힌다**는 걸 보여준다.

```
"다음 분기에 하기로 한 상품 추천 기능이 이 조회 로직을 씁니다.
 지금 구조로는 추천 후보를 50개씩 가져와야 해서 쿼리가 51번 나갑니다.
 이걸 먼저 고치면 추천 기능이 3일 짧아집니다."
```

이러면 부채 상환이 아니라 **다음 기능의 선행 작업**이 된다. 승인 난이도가 다르다.

## 부채를 일부러 지는 법

부채가 항상 나쁜 건 아니다. **먼저 내보내는 게 더 중요한 상황**이 있다. 다만 지는 방식이 중요하다.

의식적으로 지려면 세 가지를 같이 한다.

1. **티켓을 그 자리에서 만든다** — 나중에 만들면 안 만든다
2. **터지는 조건을 적는다** — 그게 감시 지점이 된다
3. **가능하면 알림을 건다** — 조건이 숫자면 대시보드에 올린다

```
부채: 주문 조회 N+1
조건: 주문 목록 p99 > 500ms
알림: 그 임계값으로 경고를 걸어 둔다
```

이러면 부채가 **스스로 만기를 알린다.** 사람 기억에 안 맡기는 게 요점이다.

## 갚지 않기로 하는 것도 결정이다

모든 부채를 갚을 필요는 없다. **없어질 코드에 든 부채는 그냥 두는 게 맞다.**

- 6개월 뒤 걷어낼 레거시
- 실험용으로 만든 기능 (아직 살아남을지 모른다)
- 트래픽이 안 늘 것이 확실한 내부 도구

이때도 **티켓은 닫는다.** "안 갚기로 함, 이유: 2027 Q1 폐기 예정" 을 적고 닫는 게, 열린 채로 계속 쌓이게 두는 것보다 낫다. **열린 티켓이 100개면 아무도 목록을 안 본다.**

## 정리

- **부채와 실수는 다르다.** "알고 택했다" 가 부채. 실수는 조용히 고치고, 부채는 협상한다
- **TODO 주석은 도구가 아니다.** 검색 안 되고 우선순위 없고 아무도 안 본다. 티켓으로
- 티켓에 **"언제 터지나"** 를 적는다. 이게 있으면 티켓이 스스로 우선순위를 말한다
- 코드에는 **티켓 번호와 "왜 아직 안 고쳤는지"** 만. 다음 사람이 좋은 뜻으로 고치다 사고 내는 걸 막는다
- **SonarQube·CodeClimate 수치는 추세 추적에 쓴다.** 절댓값으로 부채 규모를 재면 가장 비싼 것들이 안 잡힌다
- **cycle time·change failure rate** 가 늘어나면 부채가 쌓이고 있다는 신호다
- 조용히 터지는 부채는 **동기화 누락·스키마 불일치** 같은 유형이다. 처음엔 동작하다 조건이 바뀌면서 깨진다
- **몰아서 갚지 않는다.** 만질 때 같이 + 정기적으로 조금씩. 팀 회고에서는 월 1회 별도 세션이 현실적이다
- 설득은 **비용·시점·다음 기능**으로. 코드 품질로는 안 통한다
- 일부러 질 때는 **티켓·조건·알림**을 같이 건다. 부채가 스스로 만기를 알리게
- **안 갚기로 하는 것도 결정이다.** 이유를 적고 닫는다

부채 관리를 잘한다는 건 부채가 없는 게 아니라, **어떤 부채가 있고 언제 터지는지 아는 상태**다.
