# 술어 누락

술어(predicate)는 WHERE, ON, HAVING 절에 들어가는 조건식이다. 이 조건이 빠지거나 불완전하면 옵티마이저는 해당 조건이 없는 것으로 실행 계획을 짠다. 결과는 두 가지 중 하나다. 전체 테이블을 읽거나, 전체 행을 수정한다.

성능 문제는 서비스 속도 저하로 드러나지만 데이터 손실은 조용하다. UPDATE나 DELETE에서 WHERE를 빠뜨리면 배포 직후엔 아무 에러 없이 정상 종료되고, 수십 분 뒤 데이터를 보고 나서야 문제를 인지한다.

---

## UPDATE / DELETE without WHERE

가장 파괴력이 큰 패턴이다.

```sql
-- 특정 사용자의 등급만 바꾸려고 했는데
UPDATE users SET grade = 'PREMIUM';
-- WHERE id = 1234 가 빠졌다
-- 전체 테이블의 grade가 PREMIUM으로 덮어씌워진다
```

```sql
-- 특정 토큰 하나를 무효화하려고 했는데
DELETE FROM refresh_tokens;
-- WHERE token = '...' 가 빠졌다
-- 전체 로그인 세션이 날아간다
```

실수는 보통 두 가지 상황에서 일어난다.

첫째, 빠르게 핫픽스를 치다가 WHERE 절을 작성하기 전에 엔터를 누르는 경우다. MySQL CLI에서 멀티라인 쿼리를 치다 보면 의도치 않게 세미콜론이 먼저 찍히는 일이 생긴다.

둘째, 조건을 변수로 넘기는 코드에서 변수가 NULL이나 빈 값이 되는 경우다.

```python
# user_ids가 비어 있으면 WHERE IN () 구문이 실패하거나 아예 조건이 생략된다
user_ids = []  # 의도치 않게 빈 리스트

# 잘못된 패턴: 빈 리스트를 그냥 넘기면
query = f"DELETE FROM sessions WHERE user_id IN ({','.join(map(str, user_ids))})"
# → WHERE user_id IN ()  → 문법 오류 또는 전체 삭제
```

```typescript
// TypeORM에서 조건 없이 delete() 호출하면 전체 삭제
await sessionRepo.delete({});  // 전체 삭제
await sessionRepo.delete(undefined);  // 전체 삭제
```

TypeORM의 `delete()`, `update()` 메서드는 빈 객체나 undefined를 받으면 WHERE 절 없이 쿼리를 실행한다.

## JOIN 조건 누락 — 카테시안 곱

ON 절 조건이 빠지면 두 테이블의 모든 행 조합이 만들어진다. 테이블 A가 1,000행, 테이블 B가 500행이면 결과는 500,000행이다.

```sql
-- 주문과 상품을 조인하려 했는데
SELECT o.id, p.name
FROM orders o
JOIN products p;
-- ON o.product_id = p.id 가 빠졌다
-- orders 10만 건 × products 5천 건 = 5억 행
```

카테시안 곱은 실행 즉시 DB 서버 CPU와 메모리를 폭발적으로 소비하면서 다른 쿼리에도 영향을 준다. 운영 DB에서 이 쿼리가 나가는 순간 서비스 전체가 느려진다.

세 테이블 이상 조인에서 조건 한 쌍만 빠져도 같은 일이 생긴다.

```sql
SELECT u.name, o.id, p.name
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN products p;  -- orders와 products 사이 ON 조건 누락
-- users × orders는 정상인데 products가 카테시안으로 곱해진다
```

ON 조건이 완전히 빠지는 경우만 문제가 아니다. 조건이 있어도 선택도(selectivity)가 너무 낮으면 비슷한 결과가 나온다.

```sql
-- created_at이 NULL인 행이 대부분인 컬럼으로 조인
SELECT * FROM orders o
JOIN order_items oi ON o.created_at = oi.created_at;
-- 날짜가 같은 행끼리 전부 조인 → 같은 날 주문 수 × 같은 날 주문 항목 수
```

비즈니스 키 없이 시간이나 상태 같은 값으로 조인하면 의도하지 않은 곱집합이 생기기 쉽다.

## ORM에서 조건이 빠지는 패턴

ORM은 조건 없는 쿼리를 막아주지 않는다. 오히려 메서드 체이닝 구조에서 조건을 빠뜨리기 쉽다.

### TypeORM QueryBuilder

```typescript
// 의도: 특정 상태의 주문만 조회
const orders = await orderRepo
  .createQueryBuilder('order')
  .where('order.userId = :userId', { userId })
  // .andWhere('order.status = :status', { status: 'PENDING' })  // 주석 처리 후 배포됨
  .getMany();
// userId에 해당하는 모든 상태의 주문이 나온다
```

```typescript
// 의도: 비활성 계정만 삭제
await userRepo
  .createQueryBuilder()
  .delete()
  .from(User)
  // .where('lastLoginAt < :date', { date: cutoffDate })  // 로직 수정 중 누락
  .execute();
// 전체 users 삭제
```

### Prisma

```typescript
// Prisma updateMany에 where를 빈 객체로 넘기면 전체 업데이트
await prisma.user.updateMany({
  where: {},  // 의도치 않게 전체 대상
  data: { isActive: false },
});
```

```typescript
// 조건 변수가 undefined가 되는 경우
const userId = req.query.userId;  // 쿼리스트링 없으면 undefined

await prisma.session.deleteMany({
  where: { userId: userId as string },  // userId가 undefined면 조건이 무의미해지거나 오동작
});
```

### JPA / Spring Data

```kotlin
// @Modifying + @Query에서 실수
@Modifying
@Query("UPDATE User u SET u.grade = :grade WHERE u.id = :id")
fun updateGrade(@Param("id") id: Long?, @Param("grade") grade: String): Int
// id가 null로 넘어오면 WHERE u.id = null → 매칭 행 없음 (의도와 다름)
// null 체크 없이 서비스 레이어가 null을 그냥 넘기는 경우 발생
```

JPA의 `deleteAll()`, `save()` 같은 메서드는 안전하지만 `@Query`로 직접 쓴 JPQL은 보호 장치가 없다.

## EXPLAIN으로 술어 누락 탐지

실행 전 `EXPLAIN`으로 실행 계획을 보면 풀 스캔 여부를 알 수 있다.

### MySQL

```sql
EXPLAIN SELECT * FROM orders WHERE status = 'PENDING';
```

`type` 컬럼이 핵심이다.

| type | 의미 |
|------|------|
| `ALL` | 풀 테이블 스캔. 인덱스 미사용 |
| `index` | 인덱스 풀 스캔. 전체 인덱스를 순회 |
| `range` | 인덱스 범위 스캔. 조건이 있음 |
| `ref` | 인덱스로 특정 값 조회 |
| `eq_ref` | 조인에서 유니크/PK 매칭 |
| `const` | 상수로 최대 1행 매칭 |

`type: ALL`이 나오면 조건이 없거나 인덱스가 없는 컬럼에 조건이 걸린 것이다. `rows` 컬럼으로 예상 스캔 행 수를 확인한다.

```sql
EXPLAIN SELECT * FROM orders o JOIN products p ON o.product_id = p.id;
-- type: ALL, rows: 100000 → 조인 조건이 인덱스를 타지 않거나 카테시안 가능성
```

카테시안 곱이 발생하면 `rows`가 두 테이블 행 수의 곱 수준으로 나온다.

```sql
-- 카테시안 곱 탐지
EXPLAIN SELECT * FROM orders o JOIN products p;
-- id=1, table=o, type=ALL, rows=100000
-- id=1, table=p, type=ALL, rows=5000
-- 예상 행 수 = 100000 * 5000 = 5억
```

### PostgreSQL

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'PENDING';
```

`Seq Scan`이 나오면 풀 스캔이다. `ANALYZE` 옵션을 붙이면 실제 실행 시간과 실제 행 수도 같이 나온다. 예상 행 수(`rows=`)와 실제 행 수(`actual rows=`)의 차이가 크면 통계 정보가 오래됐거나 조건이 의도대로 동작하지 않는 신호다.

```sql
EXPLAIN (ANALYZE)
SELECT * FROM orders o
JOIN products p ON o.product_id = p.id
WHERE o.status = 'PENDING';

-- Seq Scan on orders (cost=...) (actual rows=50000 ...)
-- → orders에서 status 조건이 인덱스를 못 타고 있음
```

`BUFFERS` 옵션을 추가하면 블록 I/O도 함께 나온다. `shared hit`은 메모리에서 읽은 블록, `shared read`는 디스크에서 읽은 블록이다. 풀 스캔에서 `shared read`가 많으면 실제로 디스크 I/O가 발생하고 있다는 뜻이다.

### slow query log 활용

실시간으로 문제 쿼리를 잡으려면 slow query log를 켜두는 게 낫다.

MySQL에서 `long_query_time = 1`로 설정하면 1초 이상 걸리는 쿼리를 로그에 남긴다. `log_queries_not_using_indexes = ON`을 추가하면 인덱스를 타지 않는 쿼리도 잡힌다.

```sql
-- MySQL 동적 설정 (재시작 없이)
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = ON;
```

`pt-query-digest` 같은 툴로 slow query log를 분석하면 패턴 단위로 요약해서 보여준다.

## DB 레벨 방어

### MySQL: sql_safe_updates

MySQL에서 `sql_safe_updates = ON`을 설정하면 WHERE 절 없는 UPDATE/DELETE나 키 컬럼 없는 WHERE를 가진 UPDATE/DELETE를 거부한다.

```sql
SET SESSION sql_safe_updates = ON;

-- 이후 WHERE 없는 UPDATE/DELETE는 에러
UPDATE users SET grade = 'PREMIUM';
-- ERROR 1175: You are using safe update mode...

DELETE FROM sessions;
-- ERROR 1175: ...
```

세션 레벨로 설정하면 해당 연결에서만 적용된다. 운영 DB 접속 시 기본으로 이 모드를 켜두면 실수로 날리는 쿼리를 막을 수 있다.

단, 애플리케이션 서버에서 실행하는 쿼리에 전역 설정하면 의도적으로 전체 행을 수정하는 배치 쿼리가 막힌다. 운영 DB 직접 접속 세션에만 적용하는 게 현실적이다.

### PostgreSQL: 트랜잭션과 LIMIT으로 보호

PostgreSQL에는 `sql_safe_updates` 같은 내장 설정이 없다. 대신 트랜잭션 안에서 먼저 확인하는 패턴을 쓴다.

```sql
BEGIN;

-- 먼저 대상 행 수 확인
SELECT COUNT(*) FROM users WHERE grade = 'BASIC';
-- 예상 행 수가 맞으면 UPDATE 진행, 아니면 ROLLBACK

UPDATE users SET grade = 'PREMIUM' WHERE grade = 'BASIC';
-- 결과가 예상과 다르면 ROLLBACK

ROLLBACK;  -- 또는 COMMIT
```

대규모 UPDATE/DELETE는 `LIMIT`과 반복으로 처리하면 의도치 않은 전체 처리를 중간에 멈출 수 있다.

```sql
-- 한 번에 1000행씩 처리
DELETE FROM audit_logs
WHERE created_at < NOW() - INTERVAL '1 year'
LIMIT 1000;
-- 행 수를 확인하면서 반복
```

PostgreSQL은 `DELETE`에 `LIMIT`이 없지만 서브쿼리로 우회한다.

```sql
DELETE FROM audit_logs
WHERE id IN (
  SELECT id FROM audit_logs
  WHERE created_at < NOW() - INTERVAL '1 year'
  LIMIT 1000
);
```

### 테이블 레벨 방어: `BEFORE UPDATE` 트리거

UPDATE 대상 행 수가 임계값을 넘으면 트리거에서 에러를 낸다.

```sql
-- MySQL: UPDATE 전 영향 받는 행 수 제한
DELIMITER $$
CREATE TRIGGER prevent_mass_update
BEFORE UPDATE ON users
FOR EACH ROW
BEGIN
  -- 단일 행 트리거라 전체 행 수 카운트는 어렵지만
  -- 조건 없는 갱신을 막으려면 애플리케이션 레벨 제어가 더 실용적
  IF NEW.grade != OLD.grade AND OLD.id IS NULL THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Mass update not allowed';
  END IF;
END$$
DELIMITER ;
```

트리거로 전체 행 수를 제한하는 건 MySQL 단일 행 트리거 구조상 직접 구현이 어렵다. PostgreSQL statement-level 트리거로는 가능하다.

```sql
-- PostgreSQL: statement-level 트리거로 영향 받은 행 수 확인
CREATE OR REPLACE FUNCTION check_mass_update()
RETURNS TRIGGER AS $$
BEGIN
  IF (SELECT COUNT(*) FROM users) = (TG_OP = 'UPDATE' AND TG_TABLE_NAME = 'users')::int THEN
    RAISE EXCEPTION 'Mass update detected on users table';
  END IF;
  RETURN NULL;
END;
$$ LANGUAGE plpgsql;
```

현실에서 트리거보다 더 자주 쓰는 방법은 마이그레이션 툴이나 배포 파이프라인에서 위험한 쿼리 패턴을 정적 분석으로 잡는 것이다.

## 애플리케이션 레벨 방어

### 빈 조건 차단

ORM 레이어 상위에서 조건이 비어 있는 경우를 명시적으로 막는다.

```typescript
// 서비스 레이어에서 빈 조건 방어
async deleteUserSessions(userId: number | undefined): Promise<void> {
  if (!userId) {
    throw new Error('userId is required for deleteUserSessions');
  }
  await this.sessionRepo.delete({ userId });
}
```

```typescript
// 조건 배열이 비어 있으면 실행 자체를 건너뜀
async deactivateUsers(userIds: number[]): Promise<void> {
  if (userIds.length === 0) {
    return;  // 빈 배열이면 전체 처리 없이 종료
  }
  await this.userRepo.update(
    { id: In(userIds) },
    { isActive: false },
  );
}
```

### 영향 행 수 검증

UPDATE/DELETE 실행 후 실제로 영향받은 행 수를 확인해서 예상 범위를 벗어나면 롤백한다.

```typescript
const result = await dataSource.transaction(async (manager) => {
  const updateResult = await manager.update(
    User,
    { id: userId },
    { grade: 'PREMIUM' },
  );

  if (updateResult.affected !== 1) {
    throw new Error(`Expected 1 row affected, got ${updateResult.affected}`);
    // 트랜잭션이 롤백됨
  }
  return updateResult;
});
```

```python
# SQLAlchemy
with session.begin():
    result = session.execute(
        update(User).where(User.id == user_id).values(grade='PREMIUM')
    )
    if result.rowcount != 1:
        raise ValueError(f"Expected 1 row updated, got {result.rowcount}")
        # 예외 발생 → 트랜잭션 롤백
```

배치 처리에서 대량 업데이트가 예상되는 경우, 상한선을 두고 초과하면 알람을 보내는 패턴을 쓴다.

```typescript
const MAX_BATCH_DELETE = 10_000;

async cleanupExpiredTokens(before: Date): Promise<number> {
  const result = await this.tokenRepo.delete({
    expiresAt: LessThan(before),
  });

  if (result.affected && result.affected > MAX_BATCH_DELETE) {
    this.alertService.warn(
      `Large batch delete: ${result.affected} tokens deleted`,
    );
  }

  return result.affected ?? 0;
}
```

### 쿼리 리뷰 단계에서 잡기

CI 파이프라인에 쿼리 분석 단계를 넣으면 마이그레이션 파일의 위험한 패턴을 배포 전에 잡을 수 있다.

```bash
# 마이그레이션 파일에서 WHERE 없는 UPDATE/DELETE 패턴 탐지
grep -n "UPDATE\s\+\w\+\s\+SET\b" migrations/*.sql | grep -v "WHERE"
grep -n "DELETE\s\+FROM\b" migrations/*.sql | grep -v "WHERE"
```

`squitch`, `flyway`, `liquibase` 같은 마이그레이션 툴에서 체크섬과 실행 이력을 관리하지만 내용 분석은 하지 않는다. 정적 분석은 별도로 구성해야 한다.

## 술어가 있어도 무력화되는 경우

조건이 있어도 결과적으로 전체 행에 영향을 주는 패턴이 있다.

**항상 참인 조건**

```sql
UPDATE users SET grade = 'PREMIUM' WHERE 1 = 1;
-- 전체 업데이트
```

코드에서 조건을 동적으로 조립하다가 생기는 경우다.

```python
conditions = []
# 로직 오류로 conditions가 비어 있어서 fallback
where_clause = " AND ".join(conditions) if conditions else "1=1"
query = f"UPDATE users SET grade = 'PREMIUM' WHERE {where_clause}"
# "WHERE 1=1" → 전체 업데이트
```

**NULL 비교 실수**

```sql
-- NULL인 행을 제외하려고 했는데
SELECT * FROM users WHERE deleted_at != '2024-01-01';
-- NULL != '2024-01-01'은 NULL을 반환 → NULL인 행이 결과에서 제외됨
-- 의도와 반대 결과

-- 올바른 패턴
SELECT * FROM users WHERE deleted_at IS NULL OR deleted_at != '2024-01-01';
```

NULL 비교는 `=`, `!=` 연산자가 동작하지 않는다. `IS NULL`, `IS NOT NULL`을 써야 한다. ORM이 자동으로 처리해주지 않는 경우가 있어서 직접 쿼리를 확인해야 한다.

**타입 불일치로 인덱스 무력화**

```sql
-- user_id 컬럼이 INT인데 문자열로 비교
SELECT * FROM sessions WHERE user_id = '1234';
-- MySQL: 암묵적 형변환 → 인덱스 미사용 → 풀 스캔
```

컬럼 타입과 비교값 타입이 다르면 MySQL은 컬럼 값을 형변환해서 비교한다. 컬럼에 함수가 적용되면 인덱스를 사용할 수 없다. ORM에서 타입을 잘못 지정해두면 이 문제가 조용히 지속된다.

```typescript
// TypeORM: 컬럼 타입 불일치 예시
@Column({ type: 'bigint' })
userId: number;
// bigint 컬럼에 number를 쓰면 일부 환경에서 문자열로 바인딩됨
// → WHERE user_id = '1234' → 형변환 → 인덱스 무력화
```

`EXPLAIN` 결과에서 `Extra: Using where`만 있고 `type`이 `ALL`이면 이 패턴을 의심한다.
