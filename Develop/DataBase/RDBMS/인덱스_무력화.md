# 인덱스 무력화

인덱스를 걸어뒀는데 쿼리가 느린 경우, EXPLAIN을 찍어보면 `type: ALL` 또는 `Seq Scan`이 나온다. 인덱스가 무력화된 상태다. 원인은 몇 가지 패턴으로 좁혀진다.

대부분은 인덱스를 다시 만들 필요 없이 쿼리 작성 방식만 바꾸면 해결된다.

---

## 함수 적용

인덱스가 걸린 컬럼에 함수를 씌우면 인덱스를 탈 수 없다. B-Tree 인덱스는 컬럼 값 자체를 저장하는데, 함수 결과는 저장된 값과 다르기 때문이다. 옵티마이저는 탐색 시작점을 결정할 수 없어서 풀 스캔으로 빠진다.

```sql
-- created_at에 인덱스 있음
-- 인덱스 무력화
SELECT * FROM orders WHERE DATE(created_at) = '2026-07-15';
SELECT * FROM orders WHERE YEAR(created_at) = 2026;
SELECT * FROM orders WHERE DATE_FORMAT(created_at, '%Y-%m') = '2026-07';
SELECT * FROM orders WHERE UPPER(email) = 'USER@EXAMPLE.COM';
```

```
-- MySQL EXPLAIN (인덱스 무력화 상태)
+------+------+---------+-------------+
| type | key  | rows    | Extra       |
+------+------+---------+-------------+
| ALL  | NULL | 5823412 | Using where |
```

컬럼을 건드리지 않고 상수를 변환하면 된다.

```sql
-- DATE() 대신 범위 조건으로 변환
SELECT * FROM orders
WHERE created_at >= '2026-07-15 00:00:00'
  AND created_at < '2026-07-16 00:00:00';
```

```
-- 변환 후 EXPLAIN
+-------+----------------+------+-----------------------+
| type  | key            | rows | Extra                 |
+-------+----------------+------+-----------------------+
| range | idx_created_at | 3    | Using index condition |
```

ORM에서 날짜를 다룰 때 암묵적으로 `DATE()` 같은 함수가 들어가는 경우가 있다. 생성된 SQL을 직접 로그로 찍어서 확인해야 한다.

### MySQL 8.0+ 함수 기반 인덱스

쿼리를 바꿀 수 없는 상황이라면 인덱스 자체를 함수 결과로 만든다. MySQL 8.0.13부터 지원한다.

```sql
CREATE INDEX idx_year_month ON orders ((DATE_FORMAT(created_at, '%Y-%m')));

-- 이제 인덱스를 탐
SELECT * FROM orders WHERE DATE_FORMAT(created_at, '%Y-%m') = '2026-07';
```

함수 표현식이 쿼리와 정확히 일치해야 한다. `DATE_FORMAT(created_at, '%Y-%m')`으로 만들었으면 쿼리도 동일하게 써야 한다.

### PostgreSQL 표현식 인덱스

PostgreSQL은 표현식 인덱스(expression index)를 오래전부터 지원한다.

```sql
CREATE INDEX idx_email_lower ON users (LOWER(email));

SELECT * FROM users WHERE LOWER(email) = 'user@example.com';
```

대소문자 무시 검색이 잦다면 `citext` 타입도 방법이다. citext 컬럼에 일반 인덱스를 걸면 대소문자 구분 없이 인덱스가 동작한다.

## 묵시적 타입 변환

컬럼 타입과 비교 값의 타입이 다를 때 묵시적 변환이 발생한다. 변환 방향에 따라 인덱스가 무력화된다.

### 문자열 컬럼에 숫자 비교

```sql
-- phone VARCHAR(20) 컬럼에 인덱스 있음
-- 인덱스 무력화: 숫자 리터럴로 비교
SELECT * FROM users WHERE phone = 01012345678;

-- 인덱스 사용: 문자열 리터럴로 비교
SELECT * FROM users WHERE phone = '01012345678';
```

MySQL은 문자열 컬럼에 숫자가 들어오면 컬럼의 각 행을 숫자로 변환해서 비교한다. 인덱스가 아닌 테이블 전체를 스캔하면서 변환하므로 풀 스캔과 같다.

ORM에서 자주 발생한다. 파라미터를 Integer 타입으로 바인딩하면 따옴표 없이 쿼리가 나간다.

```java
// 잘못된 타입
@Query("SELECT u FROM User u WHERE u.phone = :phone")
User findByPhone(@Param("phone") Long phone);

// 반드시 String으로 받아야 함
User findByPhone(@Param("phone") String phone);
```

### 숫자 컬럼에 문자열 비교

반대 방향은 MySQL에서 인덱스가 유지되는 경우가 있다.

```sql
-- id INT 컬럼에 문자열 비교
SELECT * FROM orders WHERE id = '123';
-- MySQL: 문자열을 숫자로 변환, 인덱스 사용 가능
```

MySQL은 숫자 컬럼에 문자열이 오면 비교 값을 숫자로 변환한다. 컬럼이 아닌 상수 쪽이 변환되므로 인덱스를 탈 수 있다. 다만 `'123abc'` 같은 값은 0으로 변환되어 의도치 않은 결과가 나온다.

### PostgreSQL의 타입 변환

PostgreSQL은 타입 캐스팅이 훨씬 엄격하다. 타입이 맞지 않으면 오류가 난다.

```sql
-- PostgreSQL: 오류 발생
SELECT * FROM users WHERE phone = 01012345678;
-- ERROR: operator does not exist: character varying = integer
```

덕분에 묵시적 타입 변환으로 인한 인덱스 무력화는 MySQL보다 드물다. varchar와 text, int4와 int8 같은 같은 계열 타입 간에는 암묵적 변환이 일어나지만, 이 경우 인덱스는 대부분 유지된다.

## LIKE 앞 와일드카드

`LIKE` 패턴이 `%`로 시작하면 B-Tree 인덱스를 탈 수 없다. B-Tree는 왼쪽부터 정렬하기 때문에 앞이 고정되지 않으면 탐색 시작점을 정할 수 없다.

```sql
-- 풀 스캔
SELECT * FROM products WHERE name LIKE '%keyboard';
SELECT * FROM products WHERE name LIKE '%key%';

-- 인덱스 사용 (앞이 고정됨)
SELECT * FROM products WHERE name LIKE 'key%';
```

```
-- MySQL EXPLAIN
-- LIKE '%keyboard': type=ALL, key=NULL, rows=891234
-- LIKE 'key%':      type=range, key=idx_name, rows=12
```

쿼리 패턴 자체를 바꾸지 않는 한 B-Tree로는 해결이 안 된다. 전문 검색이 필요하면 MySQL FULLTEXT 인덱스나 Elasticsearch를 써야 한다.

```sql
-- MySQL FULLTEXT
ALTER TABLE products ADD FULLTEXT INDEX ft_name (name);
SELECT * FROM products WHERE MATCH(name) AGAINST ('keyboard');
```

FULLTEXT는 단어 단위로 색인한다. 중간 포함 검색이 가능하지만, 기본 최소 단어 길이(3~4자) 미만인 단어는 색인되지 않는다. `innodb_ft_min_token_size`(MySQL InnoDB 기준) 설정으로 조정한다.

PostgreSQL에서는 `pg_trgm` 확장을 쓰면 앞 와일드카드도 GIN 인덱스로 처리할 수 있다.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING GIN (name gin_trgm_ops);

-- 앞 와일드카드도 인덱스 사용
SELECT * FROM products WHERE name LIKE '%keyboard%';
SELECT * FROM products WHERE name ILIKE '%keyboard%';
```

```
-- PostgreSQL EXPLAIN
Bitmap Index Scan on idx_products_name_trgm
  Index Cond: ((name)::text ~~ '%keyboard%'::text)
```

trigram은 3글자 단위로 색인하므로 패턴이 3자 미만이면 인덱스를 타지 않는다.

## OR 조건

OR 조건은 옵티마이저가 각 인덱스를 병합(index merge)하거나, 비용 계산 결과에 따라 풀 스캔으로 빠진다.

```sql
-- email에는 인덱스 있음, name에는 인덱스 없음
SELECT * FROM users WHERE email = 'a@example.com' OR name = '홍길동';
-- type: ALL, key: NULL
```

name에 인덱스가 없으면 OR 전체를 인덱스로 처리할 수 없다. MySQL 옵티마이저는 풀 스캔을 선택한다.

두 컬럼 모두 인덱스가 있어도 OR는 각각의 인덱스를 합치는 Index Merge Union 방식으로 처리한다. 비용 계산에서 풀 스캔이 낫다고 판단하면 Index Merge를 포기하는 경우도 있다.

```sql
-- Index Merge Union 발생 시 EXPLAIN
SELECT * FROM orders WHERE status = 'PAID' OR user_id = 123;
-- type: index_merge, key: idx_status,idx_user_id
-- Extra: Using union(idx_status,idx_user_id); Using where
```

UNION으로 분리하면 각각 독립적으로 인덱스를 탄다.

```sql
SELECT * FROM users WHERE email = 'a@example.com'
UNION ALL
SELECT * FROM users WHERE name = '홍길동' AND email != 'a@example.com';
```

`UNION ALL`에서 중복 제거가 필요하면 두 번째 쿼리에 첫 번째 조건을 배제하는 조건을 추가한다. `UNION`(중복 제거)은 내부 정렬이 발생해서 데이터 양이 많으면 비용이 커진다.

같은 컬럼에 OR를 여러 값으로 쓰는 경우는 IN으로 바꾸면 가독성도 좋아지고 실행 계획도 명확해진다.

```sql
-- OR로 같은 컬럼 반복
SELECT * FROM orders WHERE status = 'PAID' OR status = 'SHIPPED' OR status = 'DELIVERED';

-- IN으로 대체
SELECT * FROM orders WHERE status IN ('PAID', 'SHIPPED', 'DELIVERED');
```

## NOT IN / != / <>

NOT 계열 조건은 인덱스를 타는 경우도 있지만 대부분 비효율적이다.

### != 와 <>

```sql
-- status에 인덱스 있음
SELECT * FROM orders WHERE status != 'PAID';
```

MySQL에서 `!=`는 인덱스를 타기도 한다(type: range). 하지만 `status != 'PAID'`가 전체 행의 90%를 반환하는 상황이라면 옵티마이저가 인덱스를 버리고 풀 스캔을 선택한다.

인덱스 선택 기준은 반환 행 비율이다. MySQL 기준으로 대략 20~30% 이상을 반환하면 풀 스캔이 더 싸다고 판단한다. `status != 'PAID'`가 전체의 5%만 반환한다면 인덱스를 탄다. EXPLAIN의 `rows`와 전체 행 수를 비교하면 판단할 수 있다.

### NOT IN과 NULL 문제

`NOT IN` 목록이나 서브쿼리에 NULL이 포함되면 결과가 0건이 된다.

```sql
-- 의도: 삭제된 유저의 주문 제외
SELECT * FROM orders WHERE user_id NOT IN (
    SELECT id FROM users WHERE deleted_at IS NOT NULL
);
-- deleted_at이 NULL인 users 행이 있으면 NOT IN 전체가 0건 반환
```

SQL의 3값 논리(TRUE/FALSE/UNKNOWN) 때문이다. `1 NOT IN (2, NULL)`은 `1 != 2 AND 1 != NULL`이고, `1 != NULL`은 UNKNOWN이다. UNKNOWN이 하나라도 있으면 전체 AND가 UNKNOWN이 되어 행이 반환되지 않는다.

`NOT EXISTS`로 바꾸면 NULL 문제 없이 처리된다.

```sql
SELECT * FROM orders o
WHERE NOT EXISTS (
    SELECT 1 FROM blacklist b WHERE b.user_id = o.user_id
);
```

`NOT EXISTS`는 서브쿼리 행이 존재하지 않으면 TRUE다. NULL 행 때문에 결과가 왜곡되지 않는다.

### PostgreSQL에서 NOT IN 성능

PostgreSQL에서 `NOT IN (서브쿼리)`는 Hash Anti Join으로 처리된다. 서브쿼리 결과가 크면 메모리를 많이 쓴다. `NOT EXISTS`는 Nested Loop Anti Join으로 처리되는 경우가 많아서 서브쿼리에 인덱스가 있으면 더 빠르다.

## 컬럼 직접 연산

WHERE 절에서 컬럼에 직접 연산을 하면 인덱스를 탈 수 없다. 함수 적용과 같은 이유다.

```sql
-- 인덱스 무력화: 컬럼을 변형
SELECT * FROM orders WHERE amount * 1.1 > 10000;
SELECT * FROM products WHERE quantity - reserved > 0;
SELECT * FROM logs WHERE CAST(response_time AS UNSIGNED) > 5000;
```

컬럼 값을 식 안에 넣으면 B-Tree가 그 결과를 저장하지 않으므로 인덱스 탐색 시작점을 정할 수 없다.

상수 쪽을 이동하면 해결된다.

```sql
-- 상수를 이동
SELECT * FROM orders WHERE amount > 10000 / 1.1;
SELECT * FROM orders WHERE amount > 9090.9;
```

`quantity - reserved > 0`처럼 컬럼끼리 연산하는 경우는 상수 이동이 불가능하다. 가상 컬럼(generated column)을 만들어 인덱스를 거는 방식으로 해결한다.

```sql
-- MySQL: STORED 가상 컬럼 + 인덱스
ALTER TABLE products
    ADD COLUMN available_qty INT GENERATED ALWAYS AS (quantity - reserved) STORED;

CREATE INDEX idx_available ON products (available_qty);

SELECT * FROM products WHERE available_qty > 0;
```

```sql
-- PostgreSQL: 표현식 인덱스 (가상 컬럼 불필요)
CREATE INDEX idx_available ON products ((quantity - reserved));

-- 괄호를 반드시 써야 인덱스 조건과 매칭됨
SELECT * FROM products WHERE (quantity - reserved) > 0;
```

PostgreSQL은 가상 컬럼 없이 표현식 인덱스로 바로 해결된다. 쿼리에서도 동일한 표현식을 괄호로 감싸야 옵티마이저가 인덱스와 매칭한다.

## NULL 비교

### IS NULL / IS NOT NULL

MySQL에서 `IS NULL`과 `IS NOT NULL`은 인덱스를 탄다. B-Tree에 NULL도 저장되기 때문이다.

```sql
-- deleted_at에 인덱스 있음
SELECT * FROM users WHERE deleted_at IS NULL;     -- 인덱스 사용
SELECT * FROM users WHERE deleted_at IS NOT NULL; -- 인덱스 사용
```

`IS NOT NULL`이 전체 행의 대부분을 반환하는 상황(소프트 삭제 비율이 낮을 때)이라면 옵티마이저가 풀 스캔을 선택한다.

PostgreSQL도 `IS NULL`/`IS NOT NULL`에서 인덱스를 사용한다. B-Tree 인덱스는 NULL을 가장 크거나 작은 값으로 취급하며(`NULLS FIRST`/`NULLS LAST`), `IS NULL` 조건은 NULL 구간을 범위 스캔한다.

### != NULL 실수

```sql
-- 항상 0건 반환
SELECT * FROM users WHERE deleted_at != NULL;
SELECT * FROM users WHERE deleted_at <> NULL;
```

NULL과의 비교 결과는 항상 UNKNOWN이다. WHERE 절에서 UNKNOWN은 FALSE와 같으므로 행이 하나도 반환되지 않는다. 인덱스 문제가 아니라 쿼리 자체가 잘못된 것이다.

```sql
SELECT * FROM users WHERE deleted_at IS NOT NULL;
```

쿼리 결과가 예상보다 훨씬 적거나 0건이 나올 때 먼저 확인해봐야 할 항목이다.

## 복합 인덱스 컬럼 순서 위반

복합 인덱스에서 선두 컬럼을 건너뛰면 인덱스를 탈 수 없다.

```sql
CREATE INDEX idx_orders ON orders (status, user_id, created_at);

-- 인덱스 사용 안 됨: 선두 컬럼(status) 없음
SELECT * FROM orders WHERE user_id = 123;
SELECT * FROM orders WHERE user_id = 123 AND created_at > '2026-01-01';

-- 인덱스 사용됨: 선두 컬럼 포함
SELECT * FROM orders WHERE status = 'PAID' AND user_id = 123;
```

범위 조건(`>`, `<`, `BETWEEN`) 이후 컬럼도 인덱스 범위 좁히기에서 빠진다.

```sql
-- created_at 범위 이후 user_id는 인덱스 탐색에 기여 못 함
CREATE INDEX idx_wrong ON orders (created_at, status, user_id);

SELECT * FROM orders
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31'
  AND status = 'PAID'
  AND user_id = 456;
-- type: range, rows: 500000 (created_at 범위 전체 스캔)

-- 올바른 순서: 등치 조건 먼저, 범위 조건 마지막
CREATE INDEX idx_correct ON orders (status, user_id, created_at);
-- type: range, rows: 12 (status + user_id로 좁힌 후 날짜 범위)
```

`key_len`으로 어디까지 인덱스가 쓰이는지 확인할 수 있다.

```sql
EXPLAIN SELECT * FROM orders
WHERE status = 'PAID' AND user_id = 456 AND created_at > '2026-01-01';

-- key: idx_correct
-- key_len: 87 → status(83바이트) + user_id(4바이트) 두 컬럼까지 인덱스 사용
```

복합 인덱스 컬럼 순서 설계 원칙은 [복합 인덱스 선두 컬럼](복합_인덱스_선두.md)에서 자세히 다룬다.

## EXPLAIN 빠르게 읽는 법

### MySQL

```sql
EXPLAIN SELECT * FROM orders WHERE DATE(created_at) = '2026-07-15';
```

| 필드 | 확인할 값 |
|---|---|
| `type` | `ALL`이면 풀 스캔. `ref`, `range`, `eq_ref`이면 인덱스 사용 |
| `key` | `NULL`이면 인덱스 미사용 |
| `rows` | 예상 스캔 행 수. 전체 행 수에 가까우면 풀 스캔 의심 |
| `Extra` | `Using where`이면 인덱스 이후 행 단위 필터. `Using filesort`이면 인덱스로 정렬 못 함 |

### PostgreSQL

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE DATE(created_at) = '2026-07-15';
```

- `Seq Scan`: 풀 스캔
- `Index Scan` / `Bitmap Index Scan`: 인덱스 사용
- `Index Cond`: 인덱스로 처리된 조건
- `Filter`: 인덱스 이후 행 단위 필터
- `Rows Removed by Filter`: 필터에서 버려진 행 수. 이 수치가 크면 인덱스가 충분히 좁혀주지 못하는 것

