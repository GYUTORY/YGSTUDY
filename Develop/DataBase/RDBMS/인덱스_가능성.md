# 인덱스 가능성

인덱스가 있는 컬럼을 WHERE 절에 썼는데 EXPLAIN을 찍어보면 `type: ALL` 또는 `Seq Scan`이 나오는 경우가 있다. 인덱스를 탈 수 있는 조건 형태가 아니기 때문이다. 이 차이를 SARGable(Search ARGument ABLE) 이라는 개념으로 구분한다.

SARGable 조건은 B-Tree 인덱스가 탐색 시작점과 끝점을 결정할 수 있는 형태다. 비SARGable 조건은 컬럼 값을 행마다 직접 계산하거나 변환해야 해서, 인덱스가 존재해도 풀 스캔으로 빠진다.

---

## 판단 기준

가장 빠른 판단 방법은 하나다: WHERE 절에서 인덱스가 걸린 컬럼이 단독으로 나타나는가.

컬럼에 함수, 연산자, 형변환이 씌워지면 비SARGable이다.

```sql
-- 비SARGable: 컬럼을 변형
WHERE DATE(created_at) = '2026-07-15'
WHERE YEAR(order_date) = 2026
WHERE UPPER(email) = 'TEST@EXAMPLE.COM'
WHERE amount * 1.1 > 10000
WHERE CAST(phone AS UNSIGNED) = 1012345678

-- SARGable: 컬럼이 단독
WHERE created_at >= '2026-07-15' AND created_at < '2026-07-16'
WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01'
WHERE email = 'test@example.com'
WHERE amount > 9090.9
WHERE phone = '01012345678'
```

이유는 B-Tree 구조에 있다. 인덱스는 컬럼 값 자체를 정렬된 순서로 저장한다. `DATE(created_at) = '2026-07-15'`처럼 컬럼에 함수가 씌워지면, 저장된 값(`2026-07-15 09:23:11`, `2026-07-15 14:55:03`)과 비교 대상(`'2026-07-15'`) 사이의 탐색 시작점을 결정할 수 없다. 옵티마이저는 인덱스 전체 또는 테이블을 스캔한다.

`created_at >= '2026-07-15 00:00:00' AND created_at < '2026-07-16 00:00:00'`는 다르다. 정렬된 인덱스에서 시작점(`'2026-07-15 00:00:00'`)과 끝점(`'2026-07-16 00:00:00'`)을 바로 찾아서 그 사이만 읽는다.

## 비SARGable → SARGable 재작성

### 날짜 범위

날짜 함수가 가장 자주 나오는 패턴이다. 해결 방법은 범위 조건으로 바꾸는 것이다. 컬럼을 건드리지 않고 비교 값을 변환한다.

```sql
-- 비SARGable → SARGable
SELECT * FROM orders WHERE DATE(created_at) = '2026-07-15';
-- →
SELECT * FROM orders
WHERE created_at >= '2026-07-15 00:00:00'
  AND created_at < '2026-07-16 00:00:00';

SELECT * FROM orders WHERE YEAR(created_at) = 2026;
-- →
SELECT * FROM orders
WHERE created_at >= '2026-01-01 00:00:00'
  AND created_at < '2027-01-01 00:00:00';

SELECT * FROM orders WHERE DATE_FORMAT(created_at, '%Y-%m') = '2026-07';
-- →
SELECT * FROM orders
WHERE created_at >= '2026-07-01 00:00:00'
  AND created_at < '2026-08-01 00:00:00';
```

타임존이 섞이는 서비스는 범위 경계 계산을 주의해야 한다. DB 서버가 UTC+9로 설정되어 있고 애플리케이션이 UTC 기준으로 범위를 넘기면 실제 조회 구간이 의도와 9시간 어긋난다. 세션 타임존을 명시하거나 애플리케이션에서 DB 타임존 기준으로 범위를 변환해서 넘기는 게 안전하다.

ORM에서 날짜 조건을 다룰 때도 주의가 필요하다. `LocalDate` 타입 파라미터를 받아서 `DATE(created_at) = :date` 형태로 SQL이 나가는 경우가 있다. 쿼리 로그를 찍어서 실제 SQL을 확인해야 한다.

### 타입 캐스팅

```sql
-- 비SARGable: 컬럼을 캐스팅
WHERE CAST(order_no AS UNSIGNED) = 20260715001
WHERE CAST(score AS DECIMAL) > 4.5
WHERE price::text = '10000'  -- PostgreSQL

-- SARGable: 비교 값 쪽을 맞춤
WHERE order_no = '20260715001'   -- VARCHAR 컬럼에 문자열 리터럴
WHERE score > 4.5               -- DECIMAL 컬럼에 소수 리터럴
WHERE price = 10000             -- NUMERIC 컬럼에 숫자 리터럴
```

컬럼에 CAST를 쓰게 되는 원인은 대부분 두 가지다. 컬럼 타입과 파라미터 타입이 맞지 않거나, 컬럼 타입 자체가 잘못 설계된 경우다. 전자는 파라미터 타입을 컬럼에 맞게 변환해서 해결한다. 후자라면 파라미터 캐스팅으로 임시 처리할 수 있지만, 근본적으로 컬럼 타입을 바꾸는 게 낫다.

MySQL에서 VARCHAR 컬럼에 숫자 리터럴로 비교할 때는 반드시 따옴표를 써야 한다. 따옴표 없이 숫자로 비교하면 MySQL이 컬럼 전체를 숫자로 변환해서 비교하므로 인덱스가 무력화된다.

### 함수 제거

```sql
-- 비SARGable
WHERE UPPER(email) = 'USER@EXAMPLE.COM'
WHERE LOWER(name) LIKE '홍%'
WHERE TRIM(code) = 'ABC123'

-- SARGable: 저장 시 정규화, 조회 시 함수 불필요
WHERE email = 'user@example.com'   -- 소문자로 저장
WHERE name LIKE '홍%'
WHERE code = 'ABC123'              -- 저장 시 trim 처리
```

`UPPER`, `LOWER` 같은 대소문자 정규화 함수는 데이터를 저장할 때 정규화해두면 쿼리에서 제거할 수 있다. 소문자로 정규화해서 저장하는 방식이 일반적이다.

PostgreSQL에서 대소문자 무시 검색이 잦다면 `citext` 타입을 쓰는 방법도 있다. `citext` 컬럼에 일반 인덱스를 걸면 `ILIKE`, `=` 비교에서 대소문자 구분 없이 인덱스가 동작한다. 애플리케이션 코드에서 정규화를 강제하기 어려운 경우에 쓸 만하다.

## 표현식 인덱스로 비SARGable 커버

쿼리를 바꿀 수 없는 상황이 있다. 외부 시스템에서 넘어오는 쿼리거나, ORM이 생성하는 SQL을 제어하기 어려운 경우다. 이때는 쿼리에 맞게 인덱스를 만든다.

### PostgreSQL 표현식 인덱스

```sql
-- 기존 비SARGable 쿼리에 맞는 표현식 인덱스
CREATE INDEX idx_users_email_lower ON users (LOWER(email));
CREATE INDEX idx_logs_date ON logs (DATE(created_at));
CREATE INDEX idx_products_avail ON products ((quantity - reserved));

-- 쿼리는 그대로 사용
SELECT * FROM users WHERE LOWER(email) = 'user@example.com';
SELECT * FROM logs WHERE DATE(created_at) = '2026-07-15';
SELECT * FROM products WHERE (quantity - reserved) > 0;
```

쿼리의 표현식과 인덱스 정의가 정확히 일치해야 한다. `LOWER(email)`로 인덱스를 만들었으면 쿼리도 `LOWER(email)`을 써야 한다. PostgreSQL은 함수와 연산자 표현식을 parse tree 수준에서 매칭하므로 괄호도 맞춰야 한다. `(quantity - reserved)`처럼 이항 연산자 표현식은 쿼리에서도 괄호를 써야 인덱스와 매칭된다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE LOWER(email) = 'user@example.com';

-- 인덱스 사용 확인
Index Scan using idx_users_email_lower on users
  Index Cond: (lower((email)::text) = 'user@example.com'::text)
```

표현식 인덱스는 INSERT, UPDATE 시 해당 표현식을 계산해서 인덱스를 갱신하므로 쓰기 비용이 늘어난다. 자주 조회하고 드물게 쓰는 컬럼에 쓰는 게 적합하다.

### MySQL 함수 기반 인덱스 (8.0.13+)

```sql
-- 함수 기반 인덱스 생성
CREATE INDEX idx_email_upper ON users ((UPPER(email)));
CREATE INDEX idx_year_month ON orders ((DATE_FORMAT(created_at, '%Y-%m')));
```

MySQL에서 함수 기반 인덱스는 내부적으로 숨겨진 가상 컬럼(generated column)을 만들고 거기에 인덱스를 생성한다. 표현식이 쿼리와 정확히 일치해야 한다는 제약은 PostgreSQL과 동일하다. `DATE_FORMAT(created_at, '%Y-%m')`으로 인덱스를 만들었으면 `DATE(created_at)`, `YEAR(created_at)` 함수를 따로 쓰는 쿼리는 타지 않는다.

## 연산자별 인덱스 가능성

### IN 리스트

IN 리스트는 SARGable이다. 옵티마이저가 IN 목록의 각 값을 등치 비교 묶음이나 정렬된 범위로 처리한다.

```sql
-- 인덱스 사용
SELECT * FROM orders WHERE status IN ('PAID', 'SHIPPED', 'DELIVERED');
SELECT * FROM users WHERE id IN (1, 2, 3, 100, 200);
```

```
-- MySQL EXPLAIN
type: range, key: idx_status, rows: 12345
```

IN 목록이 너무 길어지면 문제가 생긴다. 수백~수천 개를 넘어가면 MySQL 옵티마이저가 실행 계획 생성에 시간을 쓰거나 풀 스캔을 선택한다. 수천 개의 ID를 IN으로 넘기는 패턴이 있다면 임시 테이블을 만들어서 조인하는 방식으로 바꾸는 게 낫다.

IN 서브쿼리는 별개로 봐야 한다. `WHERE id IN (SELECT user_id FROM ...)`는 옵티마이저가 서브쿼리를 어떻게 처리하느냐에 따라 결과가 달라진다. MySQL 8.0에서 대부분 세미조인으로 최적화되지만, EXPLAIN으로 확인하는 게 확실하다.

### BETWEEN

BETWEEN은 범위 조건이다. 컬럼이 단독으로 나타나면 SARGable이다.

```sql
SELECT * FROM orders WHERE created_at BETWEEN '2026-07-01' AND '2026-07-31';
SELECT * FROM products WHERE price BETWEEN 10000 AND 50000;
```

`BETWEEN a AND b`는 `>= a AND <= b`와 동일하다. MySQL, PostgreSQL 모두 range 스캔으로 처리한다.

문자열 컬럼에 BETWEEN을 쓸 때는 콜레이션(문자열 정렬 순서)으로 범위가 결정된다. 날짜를 문자열로 저장한 컬럼에 `BETWEEN '2026-07-01' AND '2026-07-31'`을 쓰면 사전순 비교가 되어 의도와 다른 범위가 나올 수 있다. 날짜는 DATE, DATETIME 컬럼에 저장해야 한다.

복합 인덱스에서 BETWEEN이 나오면 이후 컬럼은 인덱스 탐색 범위를 좁히지 못한다. 범위 조건 다음에 다른 컬럼이 있어도 인덱스 레벨에서 필터링되지 않는다.

```sql
CREATE INDEX idx_orders ON orders (user_id, created_at, status);

SELECT * FROM orders
WHERE user_id = 123
  AND created_at BETWEEN '2026-07-01' AND '2026-07-31'
  AND status = 'PAID';

-- MySQL EXPLAIN
-- type: range, key: idx_orders
-- Extra: Using index condition
-- status 조건은 ICP로 스토리지 레벨에서 필터링, 인덱스 탐색 범위를 좁히진 않음
```

MySQL 5.6+ ICP(Index Condition Pushdown)가 활성화된 경우 `Extra: Using index condition`이 나온다. 인덱스 범위를 넘어선 컬럼 조건을 스토리지 엔진 레벨에서 필터링해서 가져오는 행 수를 줄인다. 인덱스가 완전히 활용된다는 뜻이 아니므로 혼동하지 않는다.

### LIKE

LIKE의 인덱스 가능성은 패턴 위치에 달려 있다.

```sql
-- SARGable: 접두사 고정
WHERE name LIKE 'kim%'
WHERE email LIKE 'admin@%'

-- 비SARGable: 접두사 미고정
WHERE name LIKE '%kim'
WHERE name LIKE '%kim%'
```

B-Tree는 왼쪽부터 정렬한다. 앞이 고정되지 않으면 인덱스에서 탐색 시작점을 정할 수 없어서 풀 스캔이 된다.

```
-- MySQL EXPLAIN
LIKE 'kim%':  type=range, key=idx_name, rows=23
LIKE '%kim':  type=ALL,   key=NULL,     rows=891234
```

후방 일치나 중간 포함 검색은 B-Tree 인덱스로 해결이 안 된다.

MySQL에서는 FULLTEXT 인덱스를 쓴다. 한국어 검색이라면 ngram 파서를 함께 설정해야 한다.

```sql
ALTER TABLE users ADD FULLTEXT INDEX ft_name (name) WITH PARSER ngram;

SELECT * FROM users WHERE MATCH(name) AGAINST ('길동' IN BOOLEAN MODE);
```

기본 ngram 토큰 크기(`ngram_token_size`)는 2다. `innodb_ft_min_token_size`는 InnoDB FULLTEXT에 영향을 주지 않으므로 혼동하지 않는다. ngram 토큰 크기보다 짧은 검색어는 인덱스를 타지 않는다.

PostgreSQL에서는 `pg_trgm` 확장과 GIN 인덱스를 조합한다.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_name_trgm ON users USING GIN (name gin_trgm_ops);

-- 앞 와일드카드도 인덱스 탐
SELECT * FROM users WHERE name LIKE '%길동%';
SELECT * FROM users WHERE name ILIKE '%GILDONG%';
```

trigram은 3글자 단위로 색인한다. 패턴이 3자 미만이면 인덱스를 타지 않는다. `LIKE '%길%'`처럼 1~2글자 패턴은 Seq Scan으로 빠진다.

## EXPLAIN 분석

### MySQL

```sql
-- 비SARGable
EXPLAIN SELECT * FROM orders WHERE DATE(created_at) = '2026-07-15'\G

*************************** 1. row ***************************
         type: ALL
possible_keys: NULL
          key: NULL
      key_len: NULL
         rows: 5823412
        Extra: Using where
```

`type: ALL`, `key: NULL` — 풀 스캔이다.

```sql
-- SARGable 재작성 후
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2026-07-15' AND created_at < '2026-07-16'\G

         type: range
possible_keys: idx_created_at
          key: idx_created_at
      key_len: 5
         rows: 347
        Extra: Using index condition
```

`type: range`, `key: idx_created_at` — 범위 스캔이다. `rows`가 전체 행 수(5,823,412)에서 347로 줄었다.

MySQL EXPLAIN에서 확인할 필드는 `type`, `key`, `rows`, `Extra`다. `type: ALL`이면 풀 스캔, `key: NULL`이면 인덱스 미사용, `rows`는 예상 스캔 행 수다. 전체 행 수 대비 비율로 인덱스 선택성을 판단한다.

### PostgreSQL

```sql
-- 비SARGable
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE DATE(created_at) = '2026-07-15';

Seq Scan on orders  (cost=0.00..142388.12 rows=58234 width=124)
                    (actual time=0.042..1834.231 rows=347 loops=1)
  Filter: (date(created_at) = '2026-07-15'::date)
  Rows Removed by Filter: 5823065
Buffers: shared hit=32412 read=45678
```

`Seq Scan`, `Rows Removed by Filter: 5823065` — 전체를 읽고 대부분 버렸다.

```sql
-- SARGable 재작성 후
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE created_at >= '2026-07-15' AND created_at < '2026-07-16';

Index Scan using idx_created_at on orders
  (cost=0.56..28.12 rows=347 width=124) (actual time=0.018..0.891 rows=347 loops=1)
  Index Cond: ((created_at >= '2026-07-15 00:00:00') AND (created_at < '2026-07-16 00:00:00'))
Buffers: shared hit=12
```

`Index Scan`, `Buffers: shared hit=12` — 필요한 블록만 읽었다.

PostgreSQL EXPLAIN에서 핵심 항목은 세 가지다. 노드 타입(`Seq Scan` vs `Index Scan`), `Rows Removed by Filter`(인덱스 이후 버려진 행 수), `Buffers`(실제 I/O 블록 수)다. `Rows Removed by Filter`가 크면 인덱스가 범위를 충분히 좁혀주지 못하는 것이다. 인덱스가 있어도 실제로 얼마나 유효한지는 이 수치로 판단한다.
