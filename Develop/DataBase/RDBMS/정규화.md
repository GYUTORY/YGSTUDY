# 정규화

정규화는 함수 종속 관계를 기준으로 테이블을 분리해서 데이터 중복과 이상 현상을 제거하는 과정이다. 이론 기반은 [함수_종속.md](함수_종속.md)에서 다루며, 여기서는 이상 현상이 실제로 어떻게 나타나는지, 각 정규형 위반을 어떻게 식별하고 분해하는지에 집중한다.

## 이상 현상

이상 현상(Anomaly)이 왜 생기는지는 나쁜 테이블을 하나 보면 금방 이해된다.

주문, 고객, 상품 정보를 하나의 테이블에 담으면 어떻게 되는지 보자.

| 주문ID | 고객ID | 고객명 | 고객등급 | 상품ID | 상품명 | 상품단가 | 주문수량 |
|--------|--------|--------|----------|--------|--------|----------|----------|
| 1001   | C01    | 홍길동 | GOLD     | P01    | 노트북 | 1200000  | 1        |
| 1001   | C01    | 홍길동 | GOLD     | P02    | 마우스 | 35000    | 2        |
| 1002   | C02    | 김철수 | SILVER   | P01    | 노트북 | 1200000  | 1        |

기본키는 (주문ID, 상품ID)다.

### 삽입 이상

새 상품 "키보드"를 등록하고 싶다. 그런데 이 테이블에 키보드를 INSERT하려면 반드시 어떤 주문에 포함시켜야 한다. 주문이 없는 상품은 테이블에 넣을 수가 없다.

```sql
-- 불가능: 주문ID와 고객 정보 없이는 INSERT할 방법이 없다
INSERT INTO order_data (상품ID, 상품명, 상품단가) VALUES ('P03', '키보드', 89000);
```

신규 고객을 등록할 때도 마찬가지다. 주문이 없는 고객은 이 테이블에 존재할 수 없다.

### 삭제 이상

주문 1002번이 취소됐다. 이 행을 DELETE하면 C02 고객인 "김철수"의 정보가 함께 사라진다. 김철수의 주문이 이것뿐이었다면 고객 자체에 대한 기록이 DB에서 완전히 없어진다.

삭제 이상은 실무에서 가장 늦게 발견된다. 주문 취소나 수강 취소, 계약 해지처럼 특정 이벤트를 삭제할 때 의도치 않은 정보가 사라지는 게 운영 중에 문제로 터진다.

### 갱신 이상

노트북 단가가 1,200,000원에서 1,300,000원으로 올랐다. 현재 테이블에서 노트북이 포함된 모든 행을 찾아서 업데이트해야 한다.

```sql
UPDATE order_data SET 상품단가 = 1300000 WHERE 상품ID = 'P01';
```

업데이트 중에 일부 행만 변경되면 같은 상품ID가 두 가지 단가를 동시에 갖는 상태가 된다. 트랜잭션 중간에 실패하거나, 병렬로 실행되는 다른 쿼리가 끼어들면 데이터 불일치가 생긴다.

세 가지 이상 현상의 공통 원인은 서로 다른 엔티티(주문, 고객, 상품)가 한 테이블에 섞인 것이다.

## 1NF

1NF는 각 컬럼이 원자값(Atomic Value)만 가져야 한다는 조건이다. 하나의 셀에 여러 값이 들어가면 위반이다.

```sql
-- 위반: 한 컬럼에 여러 값
CREATE TABLE orders (
    order_id    BIGINT PRIMARY KEY,
    customer_id BIGINT,
    product_ids VARCHAR(500)  -- '101,102,103' 형태로 저장
);
```

이 구조에서 특정 상품이 포함된 주문을 찾으려면 LIKE나 FIND_IN_SET 같은 우회 방법을 써야 한다. 인덱스를 제대로 쓸 수 없고 집계도 어렵다.

```sql
-- 준수: 별도 행으로 분리
CREATE TABLE order_items (
    order_id   BIGINT,
    product_id BIGINT,
    quantity   INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);
```

실무에서 1NF 위반이 자주 나타나는 패턴:

- 권한 목록, 태그, 카테고리를 콤마로 구분해서 VARCHAR에 저장
- 전화번호 컬럼을 phone1, phone2, phone3로 반복
- JSON 배열로 연관 ID 목록을 저장

JSON 컬럼은 상황에 따라 다르다. WHERE 절이나 JOIN 조건에 쓸 데이터라면 정규화된 테이블로 분리해야 한다. 검색이나 집계가 필요 없는 부가 정보(사용자별 UI 설정값, 외부 연동 메타데이터 등)는 JSON으로 넣어도 괜찮다.

## 2NF

2NF는 1NF를 만족하면서 기본키의 일부에만 종속된 컬럼이 없어야 한다. 부분 함수 종속을 제거하는 단계다.

단일 컬럼 기본키를 쓰는 테이블은 2NF를 자동으로 만족한다. 부분 함수 종속은 복합키에서만 생긴다.

```sql
-- 위반: (order_id, product_id)가 기본키
-- product_name은 product_id만 알면 결정된다. order_id는 무관하다.
CREATE TABLE order_items (
    order_id     BIGINT,
    product_id   BIGINT,
    product_name VARCHAR(100),   -- product_id → product_name (부분 종속)
    category     VARCHAR(50),    -- product_id → category (부분 종속)
    quantity     INT,
    PRIMARY KEY (order_id, product_id)
);
```

C01이 주문했든 C02가 주문했든 product_id가 'P01'이면 product_name은 '노트북'이다. order_id와 무관하게 product_id 하나로 결정된다. 이게 부분 함수 종속이다.

결과는 갱신 이상이다. 노트북 이름을 바꾸려면 이 상품이 포함된 모든 주문 행을 찾아서 업데이트해야 한다.

```sql
-- 분리 후
CREATE TABLE products (
    product_id   BIGINT PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL,
    category     VARCHAR(50),
    base_price   DECIMAL(10,2) NOT NULL
);

CREATE TABLE order_items (
    order_id   BIGINT,
    product_id BIGINT REFERENCES products(product_id),
    unit_price DECIMAL(10,2) NOT NULL,
    quantity   INT NOT NULL,
    PRIMARY KEY (order_id, product_id)
);
```

unit_price는 products 테이블의 base_price와 별개로 order_items에 남겨뒀다. 나중에 상품 가격이 변경돼도 주문 당시 단가를 보존해야 하는 요구사항이 있기 때문이다. 겉보기에 부분 종속처럼 보여도 비즈니스 규칙이 이 중복을 요구하는 경우는 많다. 정규화 규칙을 적용하기 전에 "이 컬럼이 왜 여기 있어야 하는가"를 먼저 따져야 한다.

## 3NF

3NF는 2NF를 만족하면서 기본키가 아닌 컬럼이 다른 기본키 아닌 컬럼을 결정하는 이행 함수 종속이 없어야 한다.

```sql
-- 위반: emp_id → dept_id → dept_name
-- dept_name은 기본키(emp_id)가 아니라 dept_id에 종속된다
CREATE TABLE employees (
    emp_id     BIGINT PRIMARY KEY,
    emp_name   VARCHAR(50),
    dept_id    INT,
    dept_name  VARCHAR(50),  -- 이행 종속
    dept_city  VARCHAR(50),  -- dept_id → dept_city (이행 종속)
    salary     DECIMAL(10,2)
);
```

개발팀 소속 직원이 100명이면 dept_name '개발팀'이 100개 행에 중복 저장된다. 부서명을 '서버팀'으로 바꾸려면 100개 행을 모두 업데이트해야 한다. 업데이트 중 일부만 반영되면 같은 dept_id를 가진 행이 서로 다른 dept_name을 갖는 상태가 된다.

```sql
-- 분리 후
CREATE TABLE departments (
    dept_id   INT PRIMARY KEY,
    dept_name VARCHAR(50) NOT NULL,
    dept_city VARCHAR(50)
);

CREATE TABLE employees (
    emp_id   BIGINT PRIMARY KEY,
    emp_name VARCHAR(50) NOT NULL,
    dept_id  INT REFERENCES departments(dept_id),
    salary   DECIMAL(10,2)
);
```

직원 목록에 부서명을 보여줄 때 JOIN이 필요해진다. dept_id에 인덱스가 걸려 있으면 조인 비용은 크지 않다. 부서명을 바꿀 때 departments 한 행만 수정하면 된다는 이점이 더 크다.

이행 종속이 잘 안 보이는 패턴들이 있다.

- `order_id → customer_id → customer_grade`: 주문이 고객을 결정하고, 고객이 등급을 결정한다. customer_grade를 orders 테이블에 넣으면 이행 종속이다.
- `product_id → category_id → category_name`: 상품이 카테고리를 결정하고, 카테고리가 카테고리명을 결정한다.
- `zip_code → city → province`: 우편번호가 도시를 결정하고, 도시가 도/광역시를 결정한다.

세 경우 모두 마지막 속성이 기본키가 아닌 컬럼에 종속된다. 이 속성들을 현재 테이블에 두면 3NF 위반이다.

## BCNF

BCNF(Boyce-Codd Normal Form)는 3NF보다 한 단계 엄격하다. 모든 결정자(함수 종속 `X → Y`에서 X)가 후보키여야 한다는 조건이다.

3NF를 만족하면서 BCNF를 위반하는 상황은 후보키가 여러 개이고, 그 후보키들이 서로 겹치는 속성을 가질 때 나온다.

```
수강지도 릴레이션: {학번, 과목명, 담당교수}

비즈니스 규칙:
  - 학생은 한 과목에서 한 명의 교수에게만 지도받는다
  - 교수는 한 과목만 담당한다

함수 종속:
  {학번, 과목명} → 담당교수    (후보키 1)
  {학번, 담당교수} → 과목명   (후보키 2, 교수가 한 과목만 담당하므로)
  담당교수 → 과목명            (교수가 한 과목만 담당)
```

후보키는 {학번, 과목명}과 {학번, 담당교수} 두 가지다. 3NF 기준으로는 비기본키 속성 담당교수, 과목명이 기본키에 종속되므로 통과한다. 그런데 `담당교수 → 과목명`의 결정자 '담당교수'가 후보키가 아니다. BCNF 위반이다.

이 상태에서 신규 교수가 부임했는데 아직 수강 학생이 없으면 이 테이블에 교수 정보를 넣을 수 없다(삽입 이상). 마지막 학생이 수강 취소하면 그 교수의 담당 과목 정보도 사라진다(삭제 이상).

```sql
-- BCNF 분리
CREATE TABLE professor_course (
    professor_id BIGINT PRIMARY KEY,  -- 교수는 한 과목만 담당
    course_id    BIGINT NOT NULL
);

CREATE TABLE enrollment (
    student_id   BIGINT,
    professor_id BIGINT REFERENCES professor_course(professor_id),
    PRIMARY KEY (student_id, professor_id)
);
```

BCNF 분리의 단점이 있다. 원래 릴레이션에 있던 `{학번, 과목명} → 담당교수` 종속을 단일 테이블로 표현할 수 없게 된다. "학생 A가 과목 B를 수강한다"는 사실을 알려면 두 테이블을 조인해야 한다. 의존성 보존(Dependency Preservation)이 깨진다.

BCNF는 3NF와 달리 의존성 보존을 항상 보장하지 않는다. 실무에서 3NF 이상으로 가지 않는 경우가 많은 이유다. 3NF까지만 해도 대부분의 이상 현상은 제거된다. BCNF 분리를 결정했다면 의존성이 깨진 부분을 어떻게 무결성으로 보완할지 설계해야 한다.

## 4NF

4NF는 BCNF를 만족하면서 다치 종속(Multi-valued Dependency)을 제거한다. 다치 종속은 `X →→ Y`로 표기하며, X가 결정되면 Y의 집합이 독립적으로 대응될 때 나타난다.

```
교수_과목_교재 릴레이션: {교수ID, 과목ID, 교재ID}

비즈니스 규칙:
  - 교수는 여러 과목을 담당한다
  - 교수는 여러 교재를 선택한다
  - 교재 선택은 과목과 무관하다 (어떤 과목이든 같은 교재를 쓴다)

교수ID →→ 과목ID
교수ID →→ 교재ID
```

| 교수ID | 과목ID | 교재ID |
|--------|--------|--------|
| P1     | C1     | B1     |
| P1     | C1     | B2     |
| P1     | C2     | B1     |
| P1     | C2     | B2     |

P1 교수가 교재 B3을 추가하면 담당 과목 수만큼 행을 INSERT해야 한다. 과목이 10개면 10행이 필요하다. 교재가 과목과 독립적인데 테이블 구조상 과목마다 교재를 반복해야 하는 상황이다.

```sql
-- 4NF 분리
CREATE TABLE professor_course (
    professor_id BIGINT,
    course_id    BIGINT,
    PRIMARY KEY (professor_id, course_id)
);

CREATE TABLE professor_textbook (
    professor_id BIGINT,
    textbook_id  BIGINT,
    PRIMARY KEY (professor_id, textbook_id)
);
```

4NF 위반 상황 자체가 실무에서 자주 나오지 않는다. 이런 구조가 나왔다면 초기 설계 단계에서 관계를 잘못 잡은 경우가 많다. 교재와 과목 사이에 관계가 없다면 처음부터 분리된 테이블로 설계하는 게 맞다.

## 정규형 요약

| 정규형 | 제거 대상 | 핵심 조건 |
|--------|-----------|-----------|
| 1NF    | 비원자값 | 셀에 단일 값만 |
| 2NF    | 부분 함수 종속 | 복합키 일부에 종속 없음 |
| 3NF    | 이행 함수 종속 | 비기본키 → 비기본키 종속 없음 |
| BCNF   | 비후보키 결정자 | 모든 결정자는 후보키 |
| 4NF    | 다치 종속 | 독립적인 다치 종속 없음 |

각 단계는 이전 단계를 포함한다. 3NF면 2NF도 만족한다.

## 과도한 정규화의 JOIN 비용

정규화를 하면 테이블이 늘어나고 JOIN이 늘어난다. JOIN 자체는 문제가 아닌데, 특정 상황에서는 병목이 된다.

주문 내역 조회 쿼리가 전형적인 예다.

```sql
SELECT
    o.order_id,
    c.customer_name,
    c.customer_grade,
    p.product_name,
    cat.category_name,
    oi.quantity,
    oi.unit_price
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN order_items oi ON o.order_id = oi.order_id
JOIN products p ON oi.product_id = p.product_id
JOIN categories cat ON p.category_id = cat.category_id;
```

5개 테이블 JOIN이다. 각 JOIN 컬럼에 인덱스가 있고 데이터가 수십만 건 수준이면 문제없다. 수천만 건이 넘고 이 쿼리가 초당 수백 번 실행된다면 다르다.

JOIN 성능이 실제로 문제가 되는 상황:

- 수백만 건의 주문을 한 번에 집계해서 정산하는 배치
- 복잡한 JOIN 쿼리가 반복 실행되는 실시간 대시보드
- GROUP BY와 함께 여러 테이블을 JOIN하는 집계 쿼리

단건 조회나 소량 리스트 조회는 JOIN이 5개여도 인덱스만 제대로 걸려 있으면 문제없다.

### 인덱스와 JOIN 성능

정규화된 테이블에서 JOIN 성능은 외래키 컬럼의 인덱스에 달려 있다.

```sql
CREATE INDEX idx_order_items_order_id ON order_items(order_id);
CREATE INDEX idx_order_items_product_id ON order_items(product_id);
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
```

MySQL InnoDB는 외래키를 걸면 자동으로 인덱스를 생성한다. PostgreSQL은 외래키 인덱스를 자동 생성하지 않는다. PostgreSQL에서 FK를 많이 쓰면서 인덱스를 빠뜨리면 JOIN 쿼리가 느려진다. 이걸 모르고 "PostgreSQL이 느리다"는 결론을 내리는 경우가 있다.

JOIN이 느리다고 판단하기 전에 EXPLAIN으로 실행 계획을 확인해야 한다. Seq Scan이 나오면 인덱스가 없거나 제대로 쓰이지 않는 것이다.

## 비정규화 선택 기준

비정규화(Denormalization)는 정규화를 되돌리는 게 아니다. 정규화된 구조를 바탕으로, 조회 성능을 위해 의도적으로 중복을 허용하는 것이다.

### 비정규화를 선택하는 시점

**읽기 쿼리가 압도적으로 많고 JOIN이 실제 병목으로 확인됐을 때**

주문 목록 페이지에서 매번 고객명과 고객 등급을 JOIN해서 조회한다. 슬로우 쿼리 로그에서 이 쿼리가 자주 잡힌다. 고객명이 바뀌는 빈도는 낮고 주문 조회 빈도는 높다. 이 경우 customer_name과 customer_grade를 orders 테이블에 복사해두는 선택을 할 수 있다.

```sql
ALTER TABLE orders ADD COLUMN customer_name VARCHAR(50);
ALTER TABLE orders ADD COLUMN customer_grade VARCHAR(20);
```

고객명이 바뀔 때 orders 테이블도 함께 업데이트해야 한다는 부담이 생기지만, 변경 빈도가 낮고 조회 빈도가 높다면 감수할 수 있다.

**집계 컬럼을 미리 계산해서 저장할 때**

상품 목록에서 리뷰 수와 평균 별점을 보여줘야 한다. 요청마다 reviews 테이블을 집계하면 느리다.

```sql
ALTER TABLE products ADD COLUMN review_count INT DEFAULT 0;
ALTER TABLE products ADD COLUMN average_rating DECIMAL(3,2);
```

리뷰가 등록될 때마다 이 컬럼을 업데이트하는 로직이 필요하다. 또는 배치로 주기적으로 동기화한다. 어느 정도의 지연을 허용할 수 있는 집계값에 적합하다.

**이력 데이터에서 당시 상태를 보존해야 할 때**

주문 내역에서 주문 당시 고객 등급을 보여줘야 한다. 고객 등급이 나중에 바뀌어도 주문 당시 등급을 유지해야 한다. customer_grade를 orders 테이블에 컬럼으로 두는 게 맞다. 2NF 위반처럼 보이지만 이건 비즈니스 요구사항이다.

### 비정규화를 하지 말아야 할 때

쓰기가 빈번한 테이블에 중복 컬럼을 추가하면 쓰기 비용이 증가하고 데이터 불일치 위험이 생긴다. 재고수량처럼 자주 바뀌는 데이터를 여러 테이블에 복사해두면 동기화 문제가 생긴다.

가장 자주 보이는 실수는 "JOIN이 많아서 느릴 것 같다"는 추측으로 비정규화하는 것이다. EXPLAIN으로 실행 계획을 확인하고, 슬로우 쿼리 로그에서 실제 병목을 확인한 뒤에 결정해야 한다. 추측으로 비정규화하면 쓰기 비용과 동기화 문제만 늘어난다.

### 비정규화 후 데이터 정합성 관리

비정규화를 하면 중복된 데이터의 동기화를 직접 관리해야 한다.

**애플리케이션 레벨**: 서비스 레이어에서 원본 데이터를 업데이트할 때 복사본도 함께 업데이트한다. 구현이 단순하지만 업데이트 로직이 여러 곳에 흩어지면 누락 위험이 있다.

**DB 트리거**: 원본 테이블에 트리거를 걸어 자동으로 복사본을 업데이트한다. 누락 위험은 없지만 트리거가 숨겨진 동작을 하므로 디버깅이 어렵다. 대용량 배치 업데이트 시 트리거가 건당 실행되면 성능 문제가 생긴다.

**배치 동기화**: 주기적으로 복사본을 원본과 재집계해서 덮어쓴다. 리뷰 수, 평균 별점처럼 실시간성이 필요 없는 집계 컬럼에 적합하다.

---

정규화는 3NF까지 적용하고, 실제 성능 문제가 확인되면 인덱스 조정과 쿼리 최적화를 먼저 시도한다. 그래도 해결이 안 되면 비정규화를 검토하되, 어떤 컬럼을 어디에 복사할지, 동기화 방법은 무엇인지 설계를 명확히 해야 한다.
