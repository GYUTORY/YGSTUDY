# 롤백 불가 변경

스키마 변경 중 일부는 실행 즉시 데이터가 사라지거나 구조가 파괴된다. 트랜잭션 롤백도, 마이그레이션 도구의 undo도 작동하지 않는다. 프로덕션에서 이 유형의 변경이 잘못되면 binlog 복구나 스냅샷 복원 외에 선택지가 없다.

---

## 유형 분류

### DROP TABLE / DROP COLUMN / DROP INDEX

테이블을 DROP하면 데이터 파일(`.ibd`)과 딕셔너리 정보가 즉시 삭제된다. MySQL 8.0의 Atomic DDL 덕분에 DDL 자체는 원자적으로 처리되지만, 커밋 이후에는 되돌릴 수 없다. DROP INDEX는 데이터 손실은 없지만 인덱스 재생성에 걸리는 시간을 감수해야 한다.

DROP COLUMN은 더 위험하다. 컬럼을 지우면 해당 컬럼의 데이터가 전부 날아가고, 원본 값을 알 방법이 없다. 심지어 binlog에도 컬럼 제거 이후의 DML부터만 기록된다.

```sql
-- 이 두 줄 중 하나라도 프로덕션에서 잘못 실행하면 복구 불가
DROP TABLE orders;
ALTER TABLE users DROP COLUMN ssn;
```

### TRUNCATE

DELETE와 달리 TRUNCATE는 DDL이다. 행 단위 로그를 남기지 않고 데이터 파일을 통째로 초기화한다. MySQL InnoDB에서 TRUNCATE는 트랜잭션 내에 있어도 자동 커밋된다.

```sql
BEGIN;
TRUNCATE TABLE sessions;
ROLLBACK; -- 아무 효과 없음. sessions는 이미 비워짐
```

TRUNCATE 직후 `SHOW ENGINE INNODB STATUS`를 봐도 롤백 세그먼트에 아무것도 없다.

### 컬럼 타입 축소

VARCHAR(255)를 VARCHAR(50)으로 줄이거나, BIGINT를 INT로 바꾸는 변경이다. 기존 데이터가 새 타입 범위를 벗어나면 MySQL은 변경 자체를 거부하거나(strict 모드), 데이터를 잘라버린다(non-strict 모드).

```sql
-- strict 모드: 에러 발생
ALTER TABLE products MODIFY COLUMN description VARCHAR(10);
-- ERROR 1406 (22001): Data too long for column 'description'

-- non-strict 모드(sql_mode에 STRICT_TRANS_TABLES 없음)
-- 에러 없이 실행되고 데이터가 조용히 잘린다
```

non-strict 환경은 `SELECT @@sql_mode`로 확인한다. STRICT_TRANS_TABLES 없으면 데이터 손실이 에러 없이 일어난다.

### ENUM 값 삭제

ENUM 타입에서 값을 제거하면 해당 값이 들어있는 행이 빈 문자열로 변환되거나 에러가 난다. 추가는 Online DDL로 무중단 처리가 가능하지만, 제거는 테이블 리빌드가 강제된다.

```sql
-- 기존: ENUM('active', 'inactive', 'suspended')
-- suspended를 제거하려는 경우
ALTER TABLE users MODIFY COLUMN status ENUM('active', 'inactive');
-- status = 'suspended'인 행 수천 건이 '' 또는 에러로 변환됨
```

ENUM 값을 지우기 전에 반드시 해당 값이 실제로 사용 중인지 확인해야 한다.

```sql
SELECT COUNT(*) FROM users WHERE status = 'suspended';
```

### CHARACTER SET 변환

`latin1`에서 `utf8mb4`로 변환하는 경우가 많다. 기존 latin1 데이터에 한글이나 이모지가 없으면 변환이 깔끔하게 된다. 문제는 latin1로 저장된 문자열 중 실제로는 utf8 바이트가 섞여있는 경우다.

이 상태에서 CHARACTER SET 변환을 하면 이중 인코딩이 발생한다. 변환 후 데이터가 깨지고, 원복도 어렵다.

```sql
-- 변환 전 데이터 확인
SELECT HEX(column_name), column_name FROM table WHERE id = 1;
-- latin1 컬럼에 0xEAB080 같은 3바이트 한글 바이트가 있으면 이중인코딩 위험
```

변환 후 문제가 생기면 `CONVERT(column USING binary)` 우회를 써야 하는데, 이미 커밋된 상태에서는 binlog 기반으로 복구해야 한다.

### 파티션 구조 변경

파티션을 삭제하면 해당 파티션의 데이터가 전부 날아간다. `ALTER TABLE ... DROP PARTITION`은 DDL이므로 롤백 불가다.

```sql
-- 2022년 데이터 파티션 삭제
ALTER TABLE logs DROP PARTITION p2022;
-- p2022에 속한 수억 건의 로그가 즉시 삭제됨
```

파티션 교체(EXCHANGE PARTITION)는 데이터 손실 없이 파티션과 일반 테이블을 교환하지만, 교환 후 원본 파티션을 DROP하면 동일한 상황이 된다.

## 변경 전 검증

실행 전에 세 가지를 확인한다.

**1. 실제 참조 여부 확인**

DROP COLUMN 전에 애플리케이션 코드, 뷰, 저장 프로시저, 트리거가 해당 컬럼을 참조하는지 검색한다. 코드 검색뿐 아니라 DB 내부 오브젝트도 확인해야 한다.

```sql
-- 컬럼을 참조하는 뷰 확인
SELECT TABLE_NAME, VIEW_DEFINITION
FROM INFORMATION_SCHEMA.VIEWS
WHERE VIEW_DEFINITION LIKE '%column_name%';

-- 저장 프로시저/트리거 확인
SELECT ROUTINE_NAME, ROUTINE_DEFINITION
FROM INFORMATION_SCHEMA.ROUTINES
WHERE ROUTINE_DEFINITION LIKE '%column_name%';
```

**2. 데이터 분포 확인**

삭제하려는 컬럼이나 파티션에 실제로 데이터가 있는지, 있다면 얼마나 있는지 확인한다.

```sql
-- 컬럼에 NULL이 아닌 값이 있는 행 수
SELECT COUNT(*) FROM table WHERE column_name IS NOT NULL;

-- 파티션별 행 수
SELECT PARTITION_NAME, TABLE_ROWS
FROM INFORMATION_SCHEMA.PARTITIONS
WHERE TABLE_SCHEMA = 'db_name' AND TABLE_NAME = 'table_name';
```

**3. 의존 서비스 파악**

다른 서비스가 해당 테이블을 직접 조회하는지 확인한다. MSA 환경에서는 공유 DB를 여러 서비스가 읽는 경우가 있다. 슬로우 쿼리 로그나 general log로 최근 쿼리를 분석하면 참조 여부를 파악할 수 있다.

```sql
-- general log 임시 활성화 후 해당 테이블 참조 쿼리 확인
SET GLOBAL general_log = 'ON';
SET GLOBAL general_log_file = '/tmp/mysql-general.log';
-- 일정 시간 후 로그 분석
SET GLOBAL general_log = 'OFF';
```

## 스냅샷 타이밍 전략

롤백 불가 변경을 실행하기 전에 스냅샷을 찍어두는 것이 기본이지만, 타이밍이 중요하다.

**RDS / Aurora의 경우**

변경 직전에 수동 스냅샷을 생성한다. 자동 스냅샷은 일 단위로 찍히기 때문에, 자동 스냅샷만 믿고 있다가 당일 변경이 실패하면 최대 하루치 데이터를 잃을 수 있다.

```bash
# AWS CLI로 수동 스냅샷 생성
aws rds create-db-snapshot \
  --db-instance-identifier prod-mysql \
  --db-snapshot-identifier pre-drop-column-users-ssn-20260806
```

스냅샷 생성에는 시간이 걸린다. 변경 작업 30분 전에 시작해서 완료 확인 후 변경하는 것이 안전하다.

**온프레미스의 경우**

mysqldump로 해당 테이블만 덤프를 뜨거나, xtrabackup으로 전체 물리 백업을 찍는다. 테이블 단위 덤프가 훨씬 빠르다.

```bash
# 특정 테이블만 덤프
mysqldump -h host -u user -p \
  --single-transaction \
  --set-gtid-purged=OFF \
  db_name table_name > /backup/table_name_20260806.sql

# 덤프 파일 크기와 row count 교차 확인
wc -l /backup/table_name_20260806.sql
mysql -u user -p -e "SELECT COUNT(*) FROM db_name.table_name"
```

**shadow table 방식 (변경 전 데이터 보존)**

변경 전에 대상 테이블을 복사해두는 방법이다.

```sql
-- 변경 전 테이블 전체 복사 (스냅샷 역할)
CREATE TABLE users_backup_20260806 AS SELECT * FROM users;

-- 인덱스도 복사하려면
CREATE TABLE users_backup_20260806 LIKE users;
INSERT INTO users_backup_20260806 SELECT * FROM users;

-- 변경 성공 후 일정 기간(보통 2주~1달) 유지 후 삭제
DROP TABLE users_backup_20260806;
```

대용량 테이블은 이 방식이 디스크를 많이 쓴다. 삭제 대상 컬럼만 따로 보존하는 방법이 현실적이다.

```sql
-- ssn 컬럼만 id와 함께 보존
CREATE TABLE users_ssn_backup_20260806 AS
  SELECT id, ssn FROM users WHERE ssn IS NOT NULL;
```

## binlog 기반 복구 절차

스냅샷이 없거나 오래된 경우, binlog를 사용해 특정 시점까지 복구할 수 있다. binlog_format=ROW일 때 가장 정확하다.

**binlog 위치 확인**

```sql
-- 현재 binlog 파일과 포지션
SHOW MASTER STATUS;

-- binlog 파일 목록
SHOW BINARY LOGS;
```

**특정 시점 이전으로 복구**

```bash
# binlog에서 특정 시간대 이벤트 확인
mysqlbinlog \
  --start-datetime="2026-08-06 14:00:00" \
  --stop-datetime="2026-08-06 14:30:00" \
  /var/lib/mysql/binlog.000123 | head -200

# 특정 테이블에 대한 이벤트만 필터링
mysqlbinlog \
  --database=mydb \
  --start-datetime="2026-08-06 14:00:00" \
  --stop-datetime="2026-08-06 14:29:00" \
  /var/lib/mysql/binlog.000123 | grep -A5 "users"
```

**Point-in-Time Recovery (PITR) 절차**

```bash
# 1. 마지막 전체 백업에서 복원 (스테이징 환경 권장)
mysql -u root -p < full_backup.sql

# 2. 장애 발생 직전 시각까지 binlog 적용
mysqlbinlog \
  --start-datetime="2026-08-05 00:00:00" \
  --stop-datetime="2026-08-06 14:28:00" \
  binlog.000100 binlog.000101 binlog.000123 | mysql -u root -p

# 3. 복구된 환경에서 필요한 데이터 추출
mysqldump -u root -p mydb users > recovered_users.sql

# 4. 프로덕션에서 손실된 컬럼 데이터만 복원
mysql -u root -p mydb << 'EOF'
UPDATE users u
JOIN recovered_users_tmp r ON u.id = r.id
SET u.ssn = r.ssn
WHERE u.ssn IS NULL AND r.ssn IS NOT NULL;
EOF
```

RDS/Aurora는 콘솔에서 특정 시각으로 인스턴스를 복원하는 기능을 제공한다. 백업 보존 기간 내라면 분 단위 복원이 가능하다.

## 데이터 손실 없이 동등한 변경을 달성하는 우회 패턴

### shadow table 패턴 (테이블 삭제 대신)

테이블을 바로 DROP하지 않고, 먼저 이름을 바꿔서 격리한다.

```sql
-- 1단계: 테이블 이름 변경 (데이터 보존)
RENAME TABLE orders TO orders_deprecated_20260806;

-- 2단계: 애플리케이션이 새 테이블을 사용하도록 배포

-- 3단계: 일정 기간 경과 후 참조 없음 확인 후 삭제
-- (general log, 슬로우 쿼리 등으로 참조 여부 확인)
DROP TABLE orders_deprecated_20260806;
```

테이블 이름 변경은 메타데이터 변경이라 거의 즉각적이고 데이터를 건드리지 않는다.

### 단계적 Contract (컬럼 삭제 시)

컬럼을 바로 DROP하면 위험하다. 애플리케이션 배포와 스키마 변경을 분리해서 단계를 나누어야 한다.

```
[배포 1단계] 애플리케이션이 해당 컬럼을 읽지 않도록 코드 변경 배포
  - SELECT * 쿼리를 컬럼 명시 쿼리로 교체
  - 해당 컬럼 참조 코드 모두 제거

[대기] 1~2주간 문제 없음을 확인

[배포 2단계] 컬럼 DROP
  ALTER TABLE users DROP COLUMN ssn;
```

이 절차를 지키지 않으면, 컬럼을 DROP한 직후 이전 버전 배포가 살아있는 인스턴스가 해당 컬럼을 SELECT하다가 에러가 난다.

### ENUM 값 삭제 우회

ENUM 값을 바로 제거하는 대신, VARCHAR 또는 별도 상태 테이블로 마이그레이션한다.

```sql
-- 1단계: ENUM → VARCHAR로 타입 변경
ALTER TABLE users MODIFY COLUMN status VARCHAR(20) NOT NULL DEFAULT 'active';

-- 2단계: 제거하려는 값을 가진 행을 다른 값으로 업데이트
UPDATE users SET status = 'inactive' WHERE status = 'suspended';

-- 3단계: 애플리케이션에서 'suspended' 값을 더 이상 사용하지 않음을 확인
-- 4단계: 필요하면 CHECK constraint로 허용 값 제한
ALTER TABLE users ADD CONSTRAINT chk_status
  CHECK (status IN ('active', 'inactive'));
```

### 파티션 삭제 우회 (아카이빙)

파티션을 DROP하기 전에 EXCHANGE PARTITION으로 일반 테이블로 꺼낸다.

```sql
-- 1단계: 빈 아카이브 테이블 생성 (파티션 테이블과 동일 구조)
CREATE TABLE logs_archive_2022 LIKE logs;
ALTER TABLE logs_archive_2022 REMOVE PARTITIONING;

-- 2단계: 파티션 데이터를 아카이브 테이블로 교환
ALTER TABLE logs EXCHANGE PARTITION p2022 WITH TABLE logs_archive_2022;

-- 3단계: 파티션 삭제 (이제 p2022는 비어있으므로 데이터 손실 없음)
ALTER TABLE logs DROP PARTITION p2022;

-- 4단계: 아카이브 테이블은 저비용 스토리지로 이전하거나 덤프 후 삭제
```

## 실행 후 문제 발생 시 DBA 협업 절차

변경 직후 문제가 발견됐을 때 DBA와 협업해서 복구를 진행하는 순서다.

**즉시 해야 할 일**

변경을 실행한 사람이 혼자 복구를 시도하기 전에 DBA에게 상황을 알린다. DBA는 binlog 위치, 현재 복제 지연 상태, 백업 타이밍을 즉시 파악할 수 있다. 잘못된 복구 시도가 상황을 더 악화시키는 경우가 많다.

DBA에게 전달해야 하는 정보:

- 실행한 SQL 구문 정확히
- 실행 시각 (가능하면 초 단위)
- 영향받은 테이블명과 데이터베이스명
- 마지막으로 정상 확인된 시각

**DBA가 수행하는 초기 진단**

```sql
-- binlog에서 문제의 DDL이 기록된 위치 확인
mysqlbinlog --base64-output=decode-rows -v binlog.000123 | \
  grep -B5 -A10 "DROP TABLE\|ALTER TABLE.*DROP"

-- GTID 환경에서 특정 트랜잭션 식별
mysqlbinlog --base64-output=decode-rows -v binlog.000123 | \
  grep "SET @@SESSION.GTID"
```

**복구 환경 분리**

프로덕션에서 직접 복구를 시도하지 않는다. 별도 인스턴스(스테이징, 복제 슬레이브, 스냅샷 복원 인스턴스)에서 복구를 먼저 수행하고, 데이터가 정상임을 확인한 후 프로덕션에 반영한다.

복구된 데이터를 프로덕션에 반영할 때는, 복구 중 프로덕션에서 발생한 새 트랜잭션과의 충돌을 확인해야 한다. 복구 대상 테이블에 대한 쓰기를 일시적으로 막거나, 복구 데이터와 신규 트랜잭션 데이터를 신중하게 병합해야 한다.

**서비스 영향 최소화**

복구 중 해당 기능의 쓰기를 차단하거나, 기능 플래그로 비활성화하는 것을 먼저 처리한다. 불완전한 데이터 상태에서 계속 쓰기가 발생하면 복구 후 데이터 정합성이 더 복잡해진다.
