# TypeScript 타입 정의 파일

## 배경

타입 정의 파일(type definition file)은 타입이 없는 JavaScript 라이브러리의 타입 정보를 TypeScript 컴파일러에 넘겨 컴파일을 돕는다.

### 타입 정의 파일의 필요성
- **타입 안전성 확보**: JavaScript 라이브러리의 타입 정보 제공
- **개발자 경험 향상**: IDE에서 자동완성과 타입 검사 지원
- **컴파일 에러 방지**: 런타임 오류를 컴파일 타임에 감지
- **코드 가독성**: 명확한 API 문서화

### 기본 개념
- **파일 확장자**: `.d.ts` (d는 definition을 의미)
- **앰비언트 선언**: `declare` 키워드를 사용한 타입만 선언
- **고스트 모듈**: 실제 구현 없이 타입 정보만 제공

## 핵심

### 1. 기본 앰비언트 선언

#### 변수 선언
```typescript
declare var hello: any;
declare const API_BASE_URL: string;
declare let globalConfig: {
    debug: boolean;
    timeout: number;
};
```

#### 함수 선언
```typescript
declare function area(shape: string, width: number, height: number): number;
declare function fetchData(url: string): Promise<any>;
declare function formatDate(date: Date, format: string): string;
```

#### 클래스 선언
```typescript
declare class Calculator {
    constructor(initialValue?: number);
    add(value: number): Calculator;
    subtract(value: number): Calculator;
    getResult(): number;
}
```

`declare` 를 읽을 때 반드시 붙잡고 있어야 할 사실이 하나 있다. **선언은 검사가 아니라 약속이다.** "이런 게 어딘가에 있다"고 컴파일러에게 통보하는 것이고, 컴파일러는 그 말을 그대로 믿는다. 진짜로 있는지는 **아무도 확인하지 않는다.**

`.d.ts` 파일은 자바스크립트를 한 줄도 만들어 내지 않는다. 위 `Calculator` 는 타입 세계에만 존재하므로 런타임에 `new Calculator()` 를 하면 `ReferenceError` 가 난다. 마찬가지로 `declare var hello: any` 를 써 두면 `hello.foo()` 가 컴파일을 통과하고 실행에서 죽는다.

그래서 타입 정의 파일에서 나는 사고는 **전부 같은 형태**다. 컴파일은 초록불인데 런타임에서 터지고, 타입 에러가 아니라 `undefined is not a function` 이나 `ReferenceError` 로 나타나 원인을 찾기 어렵다.

이 위험을 줄이는 방법은 정해져 있다.

- **`@types/*` 가 이미 있으면 직접 쓰지 않는다.** `npm i -D @types/<패키지명>` 을 먼저 확인한다. DefinitelyTyped 의 정의는 여러 사람이 실제 라이브러리와 대조한 것이라 손으로 쓴 것보다 훨씬 정확하다.
- **직접 쓴다면 라이브러리 실제 소스나 문서를 열어 두고 대조한다.** 기억이나 짐작으로 쓰면 그대로 거짓말이 된다.
- **라이브러리 버전이 오르면 정의도 함께 검토한다.** 라이브러리가 API 를 바꿔도 `.d.ts` 는 조용히 예전 모양을 유지한다. 컴파일러는 여전히 통과시킨다.
- **가능하면 `declare` 대신 실제 타입 검사를 거치게 만든다.** 값이 외부에서 들어오는 자리라면 정의를 믿지 말고 런타임 검증을 둔다.

### 2. 모듈 선언

#### 기본 모듈 선언
```typescript
declare module 'my-library' {
    export interface User {
        id: number;
        name: string;
        email: string;
    }

    export class UserService {
        getUser(id: number): Promise<User>;
        createUser(user: Omit<User, 'id'>): Promise<User>;
        updateUser(id: number, user: Partial<User>): Promise<User>;
        deleteUser(id: number): Promise<void>;
    }

    export function formatUserName(user: User): string;
}
```

**같은 `declare module` 이 파일 사정에 따라 다른 뜻이 된다.** 이게 `.d.ts` 에서 가장 자주 사람을 잡는 지점이다.

```typescript
// ambient.d.ts — 파일에 import/export 가 하나도 없다
declare module 'my-library' {
  export function hello(): string;
}
```

```typescript
// augment.d.ts — 파일에 export 가 하나 있다
export {};
declare module 'my-library-2' {
  export function hello(): string;
}
```

둘을 함께 컴파일하면 아래만 실패한다.

```
error TS2307: Cannot find module 'my-library-2' or its corresponding type declarations.
```

앞은 **앰비언트 모듈 선언**(없는 모듈에 타입을 새로 만들어 준다)이고, 뒤는 **모듈 보강**(이미 존재하는 모듈에 타입을 덧붙인다)이다. 보강은 원본 모듈이 실제로 있어야 성립하는데 `my-library-2` 는 없으므로 못 찾는다고 나온다.

바로 앞 절의 `declare global` 은 정반대였다는 점이 헷갈림의 원인이다.

| 쓰려는 것 | 파일이 모듈이어야 하나 |
|---|---|
| `declare global { ... }` | **모듈이어야 한다** — `export {};` 필요 |
| 없는 패키지에 타입 만들기 | **모듈이면 안 된다** — `export {};` 를 지운다 |
| 기존 패키지에 타입 덧붙이기 | 모듈이어야 한다 — 원본 모듈도 실제로 있어야 한다 |

한 파일에서 두 가지를 같이 하려다 이 규칙이 충돌한다. 그럴 때는 파일을 나누는 것이 답이다. 오류 메시지가 원인을 가리키지 않으므로(`Cannot find module` 은 경로 문제처럼 읽힌다) **"export 를 넣거나 뺐더니 갑자기 안 된다"** 면 이걸 먼저 의심한다.

와일드카드 선언도 같은 문법을 쓴다. 번들러가 처리하는 비 JS 자산에 타입을 붙일 때 쓰고, 이쪽도 파일이 모듈이 아니어야 한다.

```typescript
declare module '*.svg' {
  const src: string;
  export default src;
}
```

#### 네임스페이스 사용
```typescript
declare namespace MyLibrary {
    interface Config {
        apiUrl: string;
        timeout: number;
    }

    class HttpClient {
        constructor(config: Config);
        get<T>(url: string): Promise<T>;
        post<T>(url: string, data: any): Promise<T>;
    }

    function createClient(config: Config): HttpClient;
}
```

### 3. 전역 선언

#### 전역 변수와 함수
```typescript
declare global {
    var globalConfig: {
        apiUrl: string;
        debug: boolean;
    };

    function showNotification(message: string, type?: 'info' | 'warning' | 'error'): void;
}

export {};
```

#### 전역 인터페이스 확장
```typescript
declare global {
    interface Window {
        myApp: {
            version: string;
            config: any;
        };
    }

    interface Array<T> {
        customFilter(predicate: (value: T) => boolean): T[];
    }
}

export {};
```

두 블록 끝의 `export {};` 는 장식이 아니라 **없으면 컴파일이 안 된다.**

```
error TS2669: Augmentations for the global scope can only be directly nested in
              external modules or ambient module declarations.
```

`declare global` 은 **모듈 안에서만** 쓸 수 있는데, `import` 도 `export` 도 없는 `.ts` 파일은 모듈이 아니라 전역 스크립트로 취급된다. `export {};` 는 내보낼 게 없으면서 파일을 모듈로 만드는 관용구다. `import` 나 `export` 가 이미 하나라도 있으면 필요 없다.

`Array<T>` 확장은 특히 조심해야 한다. **선언은 구현을 만들어 주지 않는다.**

```typescript
const nums = [1, 2, 3];
nums.customFilter(n => n > 1);
// 컴파일 통과 → TypeError: nums.customFilter is not a function
```

타입만 선언하고 `Array.prototype.customFilter = ...` 를 어딘가에서 실제로 실행하지 않으면 이렇게 된다. 그리고 **그 실행은 사용하는 코드보다 먼저 일어나야 한다.** 폴리필 모듈을 import 하는 위치가 하나만 틀려도 같은 에러가 난다.

내장 프로토타입 확장 자체를 피하는 편이 낫다. 전역에 영향을 주므로 다른 라이브러리와 이름이 충돌할 수 있고, `for...in` 으로 배열을 순회하는 코드가 있으면 확장한 속성까지 딸려 나온다. 같은 기능을 **일반 함수로 만들어 import 해서 쓰면** 이 부류가 전부 사라진다.

```typescript
export function customFilter<T>(arr: T[], predicate: (v: T) => boolean): T[] {
    return arr.filter(predicate);
}
```

`interface Window` 확장은 사정이 다르다. 실제로 `window.myApp` 에 값을 넣는 스크립트가 있는 상황을 타입에 반영하는 것이므로 정당한 용법이다. 다만 이때도 **값을 넣는 코드가 실제로 실행됐는지는 타입이 보장하지 않으니**, 읽는 쪽에서 `window.myApp?.version` 처럼 방어하거나 타입을 `myApp?: {...}` 로 선택적으로 선언하는 편이 사실에 가깝다.

## 예시

### 1. 실제 사용 사례

#### 외부 라이브러리 타입 정의
```typescript
// chart-library.d.ts
declare module 'chart-library' {
    export interface ChartOptions {
        width: number;
        height: number;
        data: Array<{ x: number; y: number }>;
        color?: string;
        showLegend?: boolean;
    }

    export interface ChartInstance {
        render(): void;
        update(data: Array<{ x: number; y: number }>): void;
        destroy(): void;
    }

    export function createChart(container: HTMLElement, options: ChartOptions): ChartInstance;
    export function createLineChart(container: HTMLElement, options: ChartOptions): ChartInstance;
    export function createBarChart(container: HTMLElement, options: ChartOptions): ChartInstance;
}
```

#### 사용 예시
```typescript
import { createChart, ChartOptions } from 'chart-library';

const options: ChartOptions = {
    width: 800,
    height: 600,
    data: [
        { x: 1, y: 10 },
        { x: 2, y: 20 },
        { x: 3, y: 15 }
    ],
    color: '#ff0000',
    showLegend: true
};

const chart = createChart(document.getElementById('chart'), options);
chart.render();
```

**이 사용 예시는 `strict` 에서 컴파일되지 않는다.**

```
error TS2345: Argument of type 'HTMLElement | null' is not assignable to
              parameter of type 'HTMLElement'.
```

`getElementById` 는 요소를 못 찾으면 `null` 을 돌려주는데 `createChart` 는 `HTMLElement` 를 요구한다. 타입 정의를 제대로 써 놓았기 때문에 **컴파일러가 정확히 짚어 준 것**이고, 좋은 정의가 하는 일이 바로 이거다.

여기서 `as HTMLElement` 로 눌러 버리면 정의를 쓴 의미가 없어진다. 확인하고 넘긴다.

```typescript
const container = document.getElementById('chart');
if (!container) throw new Error('#chart 요소가 없습니다');
const chart = createChart(container, options);
```

타입 정의를 직접 작성할 때도 **null 가능성을 시그니처에 반영해야** 이런 검사가 작동한다. 라이브러리가 `null` 을 받아 준다면 `container: HTMLElement | null` 로, 안 받아 준다면 지금처럼 `HTMLElement` 로 적는다. 실제 동작보다 느슨하게 적으면 컴파일러가 잡아 줄 기회 자체가 사라진다.

#### API 클라이언트 타입 정의

```typescript
// api-client.d.ts
declare module 'api-client' {
    export interface ApiResponse<T> {
        data: T;
        status: number;
        message: string;
    }

    export interface ApiError {
        code: string;
        message: string;
        details?: any;
    }

    export interface RequestConfig {
        baseURL?: string;
        timeout?: number;
        headers?: Record<string, string>;
    }

    export class ApiClient {
        constructor(config?: RequestConfig);
        
        get<T>(url: string, config?: RequestConfig): Promise<ApiResponse<T>>;
        post<T>(url: string, data: any, config?: RequestConfig): Promise<ApiResponse<T>>;
        put<T>(url: string, data: any, config?: RequestConfig): Promise<ApiResponse<T>>;
        delete<T>(url: string, config?: RequestConfig): Promise<ApiResponse<T>>;
    }

    export function createApiClient(config?: RequestConfig): ApiClient;
}
```

### 2. 고급 활용 패턴

#### 조건부 타입과 제네릭

조건부 타입을 타입 정의 파일에 쓰면 API 응답의 여러 상태를 타입 레벨에서 안전하게 표현할 수 있다. 성공/실패 같은 유니온 타입을 다룰 때 특히 쓸모가 있다.

```typescript
// advanced-types.d.ts
declare module 'advanced-types' {
    // 성공과 실패를 구분하는 조건부 타입
    // success 필드로 타입 가드를 할 수 있어서 런타임에서도 안전
    export type ApiResult<T> = 
        | { success: true; data: T }
        | { success: false; error: string };

    export type AsyncApiResult<T> = Promise<ApiResult<T>>;

    export interface ApiHandler<T> {
        execute(): AsyncApiResult<T>;
    }

    // 엔드포인트별로 다른 타입을 반환하는 API 클라이언트
    // T는 { '/users': User[], '/posts': Post[] } 같은 맵 타입
    export class TypedApiClient<T> {
        constructor(baseUrl: string);
        
        // K는 T의 키만 허용 (자동완성으로 엔드포인트 목록이 뜸)
        get<K extends keyof T>(endpoint: K): AsyncApiResult<T[K]>;
        post<K extends keyof T>(endpoint: K, data: Partial<T[K]>): AsyncApiResult<T[K]>;
    }
}
```

**실제 사용 예시**
```typescript
import { TypedApiClient, ApiResult } from 'advanced-types';

// API 엔드포인트와 반환 타입을 맵으로 정의
interface ApiEndpoints {
    '/users': User[];
    '/posts': Post[];
    '/profile': UserProfile;
}

const client = new TypedApiClient<ApiEndpoints>('https://api.example.com');

// 엔드포인트를 잘못 입력하면 컴파일 에러
const result = await client.get('/users'); // OK
// const wrong = await client.get('/wrong'); // 에러: '/wrong'은 ApiEndpoints의 키가 아님

// success 필드로 타입 가드
if (result.success) {
    // result.data는 User[] 타입
    console.log(result.data[0].name);
} else {
    // result.error는 string 타입
    console.error(result.error);
}
```

**조건부 타입으로 유연한 반환 타입 만들기**
```typescript
declare module 'flexible-api' {
    // 옵션에 따라 반환 타입이 바뀌는 함수
    export type FetchOptions = {
        raw?: boolean;
        parsed?: boolean;
    };

    // raw가 true면 Response, 아니면 parsed된 데이터
    export type FetchResult<T, O extends FetchOptions> = 
        O['raw'] extends true 
            ? Response 
            : T;

    export function fetchData<T, O extends FetchOptions>(
        url: string, 
        options?: O
    ): Promise<FetchResult<T, O>>;
}
```

이 조건부 타입은 **의도대로 동작하지 않는다.** `raw: true` 를 넘겨도 `Response` 가 아니라 `T` 가 나온다.

```typescript
const opts = { raw: true };
const c = await fetchData<string, typeof opts>('u', opts);
const check: Response = c;
// error TS2322: Type 'string' is not assignable to type 'Response'
```

원인은 **리터럴 타입 넓히기(widening)** 다. `{ raw: true }` 를 변수에 담거나 인자로 넘기면 `raw` 의 타입이 `true` 가 아니라 `boolean` 으로 넓어진다. 그러면 `boolean extends true` 는 거짓이라 항상 `T` 가지로 간다. `O` 를 `FetchOptions` 로 명시해도 `raw` 가 `boolean | undefined` 라 같은 결과다.

타입 인자를 직접 리터럴로 써 줄 때만 통과한다.

```typescript
const a = await fetchData<string, { raw: true }>('u', { raw: true });  // Response ✅
```

호출할 때마다 타입 인자를 손으로 적어야 한다면 조건부 타입을 쓴 이유가 없다. `as const` 로 리터럴을 유지하는 방법도 있지만, **함수 오버로드로 푸는 쪽이 훨씬 명확하다.**

```typescript
export function fetchData(url: string, options: { raw: true }): Promise<Response>;
export function fetchData<T>(url: string, options?: { raw?: false }): Promise<T>;
```

오버로드는 호출부에서 어느 시그니처가 선택됐는지 에디터에 그대로 보이고, 실패해도 원인이 명확하다. 조건부 타입은 틀렸을 때 **에러가 아니라 조용히 다른 가지로 가기 때문에** 이런 부류를 알아채기 어렵다. 반환 타입을 인자에 따라 바꾸고 싶다면 오버로드를 먼저 검토한다.

**제네릭 제약으로 타입 안전성 높이기**
```typescript
declare module 'type-safe-store' {
    // 특정 구조를 가진 객체만 저장할 수 있는 스토어
    export interface Identifiable {
        id: string | number;
    }

    // T는 반드시 id 필드를 가져야 함
    export class DataStore<T extends Identifiable> {
        constructor();
        
        add(item: T): void;
        get(id: T['id']): T | undefined;
        update(id: T['id'], updates: Partial<T>): void;
        delete(id: T['id']): boolean;
        
        // T의 특정 필드로 필터링
        findBy<K extends keyof T>(key: K, value: T[K]): T[];
    }

    // 배열 타입에서 요소 타입 추출
    export type ExtractArrayType<T> = T extends (infer U)[] ? U : never;
}
```

이런 패턴은 외부 라이브러리의 복잡한 타입 관계를 표현할 때 쓸모가 있다. API 클라이언트, 상태 관리 라이브러리, 데이터 변환 유틸리티 쪽에서 특히 자주 쓴다.

#### 이벤트 시스템 타입 정의
```typescript
// event-system.d.ts
declare module 'event-system' {
    export interface EventMap {
        'user:created': { userId: string; name: string };
        'user:updated': { userId: string; changes: Record<string, any> };
        'user:deleted': { userId: string };
        'order:placed': { orderId: string; amount: number };
    }

    export type EventHandler<T extends keyof EventMap> = (data: EventMap[T]) => void;

    export class EventEmitter {
        on<T extends keyof EventMap>(event: T, handler: EventHandler<T>): void;
        off<T extends keyof EventMap>(event: T, handler: EventHandler<T>): void;
        emit<T extends keyof EventMap>(event: T, data: EventMap[T]): void;
        once<T extends keyof EventMap>(event: T, handler: EventHandler<T>): void;
    }
}
```

## 운영 팁

### 성능 최적화

#### 타입 정의 파일 구조화
```typescript
// types/index.d.ts
export * from './api';
export * from './models';
export * from './utils';

// types/api.d.ts
export interface ApiResponse<T> {
    data: T;
    status: number;
}

// types/models.d.ts
export interface User {
    id: number;
    name: string;
}

// types/utils.d.ts
export type DeepPartial<T> = {
    [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};
```

이 구조에는 앞 절의 규칙이 그대로 걸린다. **`export * from` 을 쓴 순간 이 파일들은 전부 모듈이다.** 그래서 여기에 `declare module 'some-lib'` 를 앰비언트 선언으로 넣으려 하면 보강으로 해석돼 실패한다. 앰비언트 선언용 파일은 배럴에 묶지 말고 따로 두고, `tsconfig` 의 `include` 에만 들어가게 한다.

**`skipLibCheck` 를 켜면 `.d.ts` 안의 오류는 아예 안 본다.**

```typescript
// broken.d.ts
declare module 'broken-lib' {
  export const x: NonExistentType;   // 존재하지 않는 타입
}
```

```
skipLibCheck 끔 → error TS2304: Cannot find name 'NonExistentType'
skipLibCheck 켬 → 오류 0건
```

이 옵션은 남의 `@types` 패키지끼리 충돌해서 빌드가 막힐 때 쓰라고 있는 것인데, 켜 두면 **내가 쓴 `.d.ts` 도 함께 검사에서 빠진다.** 손으로 쓴 정의가 많은 프로젝트에서는 이 옵션이 정의의 오류를 통째로 가린다. 대부분의 스타터 템플릿이 기본으로 켜 두므로 `tsconfig.json` 을 한 번 확인해 볼 만하다.

내가 쓴 정의만 검사받고 싶으면 방법이 몇 가지 있다.

- **정의를 `.d.ts` 대신 `.ts` 에 둔다.** 타입만 export 하는 일반 모듈이면 `skipLibCheck` 의 영향을 안 받는다. 앰비언트 선언이 필요한 경우가 아니라면 대부분 이쪽으로 해결된다.
- **정의를 쓰는 예제 코드를 함께 둔다.** 정의만 있으면 아무도 안 쓰는 타입이라 틀려도 모른다. 실제 호출 형태를 적은 파일을 하나 두면 그게 곧 검사다.
- **타입 테스트를 넣는다.** `expectType` 류 도구나 아래 형태면 충분하다.

```typescript
// 컴파일되면 통과, 안 되면 실패
const _check: (url: string) => Promise<ApiResponse<User>> = apiClient.get;
```

`.d.ts` 는 **테스트가 없으면 썩는 코드**다. 실행되지 않으니 CI 가 잡아 주지 않고, 라이브러리가 바뀌어도 조용히 예전 모양을 유지한다.

## 참고

### 타입 정의 파일 작성 가이드라인

1. **명확한 인터페이스 정의**: API의 모든 매개변수와 반환값을 명확히 정의
2. **제네릭 활용**: 재사용 가능한 타입 정의를 만들 때 제네릭 적극 활용
3. **문서화**: JSDoc 주석으로 API 문서화
4. **테스트**: 실제 사용 사례로 타입 정의 검증

### 자주 사용되는 패턴

```typescript
// 기본 모듈 선언
declare module 'module-name' {
    export interface Config {
        // 설정 인터페이스
    }

    export class MainClass {
        constructor(config: Config);
        // 메서드들
    }

    export function utilityFunction(): void;
}

// 전역 확장
declare global {
    interface Window {
        // 전역 객체 확장
    }
}

// 네임스페이스
declare namespace MyNamespace {
    // 네임스페이스 내 타입들
}
```

### 결론
TypeScript 타입 정의 파일은 JavaScript 라이브러리의 타입 안전성을 확보하는 핵심 도구다.
정의를 제대로 써 두면 개발자 경험이 크게 좋아진다.
모듈 선언, 전역 확장, 네임스페이스 같은 걸 써서 타입 정의를 체계적으로 짠다.
실제 사용 사례로 타입 정의를 검증하고 계속 다듬는다.
타입 정의 파일은 라이브러리의 API 문서 노릇도 하니 이름은 명확하고 일관되게 붙인다.
