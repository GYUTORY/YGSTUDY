# 관측성 허브

## 이 주제를 언제 찾게 되는가

- 분산 시스템에서 어느 서비스에서 지연이 발생하는지 Trace로 추적해야 할 때
- Prometheus·Grafana 대시보드를 설계하는데 어떤 메트릭을 수집해야 할지 모를 때
- 로그가 여러 서버에 분산되어 있어서 장애 원인 파악에 시간이 걸릴 때
- NestJS 애플리케이션에 OpenTelemetry를 적용해서 분산 추적을 구성해야 할 때
- SLI/SLO를 정의하고 알림 임계값을 설정해야 할 때

## 관측성이란

실행 중인 시스템의 내부 상태를 외부 출력만 보고 파악할 수 있는 능력이다. 로그·메트릭·트레이스 세 축이 이 능력을 구성한다.

모니터링(monitoring)과 혼용되는 경우가 있는데, 모니터링은 미리 정해진 지표를 보는 것이고 관측성은 예상하지 못한 문제를 질문하고 답을 찾을 수 있는 것이다. CPU 사용률 그래프가 모니터링이라면, "3시간 전 특정 사용자 요청이 왜 5초 걸렸는가"를 답할 수 있는 게 관측성이다.

## 세 축의 역할과 차이

### 로그

이벤트의 기록이다. "언제, 무슨 일이 있었는가"를 남긴다.

디버깅할 때 가장 먼저 열어보는 것이 로그다. 그런데 로그만으로는 한계가 있다. 요청 하나가 서비스 A → B → C를 거쳤을 때, 각 서비스의 로그를 열어서 타임스탬프와 요청 ID를 손으로 맞춰봐야 한다. 서비스가 10개 이상이면 이 과정이 수십 분씩 걸린다.

구조화 로그(JSON 형태)를 쓰지 않으면 Loki·ELK 같은 로그 집계 시스템에서 쿼리하기가 어렵다. 평문 로그는 개발 로컬에서는 읽기 편하지만, 프로덕션에서 수백만 건 중 특정 조건을 필터링하려면 정규식 파싱이 필요해지고 이게 느리다.

### 메트릭

시스템 상태를 수치로 집계한 시계열 데이터다. "지금 이 순간 시스템이 어떤 상태인가"를 보여준다.

CPU, 메모리, 요청 수, 응답 시간 분포, 에러율 등이 메트릭이다. 개별 이벤트가 아니라 집계값이기 때문에 저장 공간이 작고, 그래프로 표현하기 쉽다. 알림(alert)은 거의 메트릭 기반으로 설정한다.

메트릭의 약점은 "왜"를 설명하지 못한다는 점이다. 에러율이 5%로 올랐다는 건 알 수 있어도, 어떤 요청이 에러를 냈는지는 로그나 트레이스를 봐야 한다.

### 트레이스

요청 하나가 시스템을 관통하는 경로를 기록한다. "이 요청이 어디를 거쳐서 얼마나 걸렸는가"를 보여준다.

Span이라는 단위로 각 작업을 기록하고, Trace ID로 하나의 요청을 추적한다. 서비스 A가 B를 호출하고, B가 DB를 조회하는 흐름이 Waterfall 차트로 시각화된다. 응답이 왜 느린지를 찾을 때, 트레이스가 없으면 각 서비스 로그를 직접 비교하는 수밖에 없다.

분산 트레이스가 동작하려면 서비스 간에 Trace ID를 HTTP 헤더나 메시지 헤더로 전파해야 한다. 이걸 빠뜨린 서비스가 하나라도 있으면 Trace가 끊긴다.

## 관측성이 없을 때 실제로 겪는 문제

장애가 나면 먼저 어느 서버의 로그를 봐야 할지부터 결정해야 한다. 서비스가 여러 대의 인스턴스로 뜨고 있으면, 어느 인스턴스가 문제인지 모르니까 전부 SSH로 접속해서 `grep`을 돌린다.

"응답이 간헐적으로 느리다"는 신고를 받아도 재현이 안 되는 경우가 많다. 느린 요청 로그가 없고, 메트릭도 없으면 "지금은 정상인데요"로 끝나고 원인을 못 찾는다. 이런 상황이 반복되면 특정 시간대에만 느린 배치 쿼리나 GC 이슈를 놓치게 된다.

서비스가 3개 이상으로 나뉜 환경에서는 트레이스 없이 장애 원인을 찾는 데 평균 30분 이상 걸리는 게 일반적이다. 각 팀이 "우리 서비스는 정상"이라고 하면 서로 미루다가 시간이 간다.

알림이 없으면 장애를 사용자 신고로 알게 된다. 메트릭 기반 알림이 있으면 사용자가 체감하기 전에 이상 징후를 잡을 수 있다.

## 도입 우선순위

서비스 규모와 구조에 따라 필요한 게 다르다.

단일 서비스 모놀리스이고 인스턴스가 1~2대라면 구조화 로그와 기본 메트릭(CPU·메모리·에러율)만 있어도 장애 대응이 된다. 트레이스는 이 단계에서 굳이 없어도 된다.

서비스가 3개 이상으로 나뉘거나 MSA 구조라면 트레이스 도입이 급해진다. 로그를 아무리 잘 남겨도 서비스 경계를 넘는 요청 추적은 트레이스 없이는 힘들다.

알림을 설정하고 싶다면 메트릭이 필수다. Prometheus 같은 시스템이 없으면 임계값 기반 알림을 만들 수 없다.

로그 집계 파이프라인(Loki, ELK)은 인스턴스가 여러 대로 늘어날 때 도입한다. 서버 한 대면 직접 로그를 봐도 되지만, 인스턴스가 오토스케일링으로 늘어나면 중앙 집계 없이는 관리가 안 된다.

## 툴 선택 기준

### 로그 집계

Loki와 ELK(Elasticsearch·Logstash·Kibana) 중 하나를 쓰는 경우가 많다.

Loki는 레이블 기반 인덱싱을 쓰기 때문에 저장 비용이 낮고, Grafana와 통합이 자연스럽다. 로그 내용 전체를 인덱싱하지 않아서 풀텍스트 검색 속도는 ELK보다 느리다.

ELK는 풀텍스트 검색이 필요하거나, 로그를 복잡한 조건으로 쿼리해야 할 때 쓴다. 운영 복잡도와 인프라 비용이 Loki보다 높다.

Grafana 스택을 이미 쓰고 있다면 Loki가 붙이기 쉽다. 그 외에는 팀에 ELK 경험자가 있는지가 선택 기준이 되는 경우가 많다.

### 메트릭

Prometheus가 사실상 표준이다. Pull 방식으로 수집하고, PromQL로 쿼리한다. 쿠버네티스 환경에서는 kube-state-metrics, node-exporter 조합으로 인프라 메트릭을 바로 수집할 수 있다.

AWS CloudWatch를 이미 쓰고 있고, 팀이 AWS 중심이라면 CloudWatch Metrics를 그대로 쓰는 게 셋업 비용이 낮다. 단, PromQL 생태계와 단절되기 때문에 Grafana로 시각화하려면 CloudWatch datasource를 별도로 설정해야 한다.

### 트레이스 백엔드

Jaeger, Grafana Tempo, Zipkin 중 선택하는 경우가 많다.

Jaeger는 단독으로 설치하기 쉽고, UI가 직관적이다. 소규모 팀에서 빠르게 도입할 때 쓴다.

Tempo는 Grafana 스택과 통합이 잘 돼 있다. 로그(Loki)·메트릭(Prometheus)·트레이스(Tempo)를 Grafana 하나로 보고 싶을 때 선택한다. 단, Loki처럼 전체 인덱싱 없이 Trace ID로만 조회하는 구조라 복잡한 쿼리가 제한된다.

Zipkin은 레거시 프로젝트에서 남아있는 경우가 있다. 신규 프로젝트라면 Jaeger나 Tempo가 낫다.

### 시각화

Grafana가 표준이다. Prometheus·Loki·Tempo·CloudWatch 등 대부분의 데이터 소스를 붙일 수 있다.

### 계측 표준

OpenTelemetry(OTel)로 계측 코드를 작성하면 백엔드(Jaeger, Tempo 등)를 나중에 교체할 때 애플리케이션 코드를 건드리지 않아도 된다. Vendor 종속 SDK로 계측하면 백엔드를 바꿀 때 코드를 다 고쳐야 한다. 신규 프로젝트라면 OTel부터 시작하는 게 낫다.

## 읽는 순서

1. **분산 시스템 관측성** — 여기까지 읽으면 메트릭·로그·트레이스 각 축의 역할과 세 축을 연결하는 방법을 이해한다
2. **Logging and Monitoring** — 구조화 로그와 로그 레벨 설계 기초를 다진다
3. **OpenTelemetry (DevOps)** — OTel SDK를 설치하고 Exporter를 연결하는 실습을 진행한다
4. **NestJS OpenTelemetry / Observability 전략** — 사용 프레임워크에 맞게 계측을 적용한다
5. **인프라 관측성 설계** — SLI/SLO 정의와 on-call이 실제로 쓸 수 있는 대시보드 설계로 마무리한다
