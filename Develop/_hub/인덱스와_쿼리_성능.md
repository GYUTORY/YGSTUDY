# 인덱스와 쿼리 성능 허브

## 이 주제를 언제 찾게 되는가

- 쿼리가 갑자기 느려졌는데 EXPLAIN 결과를 어떻게 읽어야 할지 모를 때
- 인덱스를 추가했는데 옵티마이저가 사용하지 않거나 잘못된 인덱스를 선택할 때
- 인덱스를 타고 있는데도 I/O가 많고 응답이 느릴 때
- 대용량 테이블에서 페이지네이션이 뒤로 갈수록 급격히 느려질 때
- Slow Query Log를 분석해서 튜닝 우선순위를 정해야 할 때
- DB 통계 정보가 오래되어 실행 계획이 엉뚱하게 나올 때
- 소프트 삭제나 상태 기반 조건에서 인덱스 크기를 줄이고 싶을 때

## 읽는 순서

1. **RDBMS 인덱스** — 여기까지 읽으면 B-Tree 구조와 인덱스 설계의 기본 판단 기준이 생긴다
2. **복합 인덱스 선두 컬럼** — 좌측 선두 접두사 규칙과 등치·범위 조건 순서 원칙을 이해하면 인덱스를 만들기 전에 컬럼 순서를 잘못 잡는 실수를 줄인다
3. **인덱스 지역성** — B+Tree 물리 저장 구조와 랜덤/순차 I/O 차이를 이해하면 인덱스가 있는데도 느린 이유가 보인다
4. **부분 인덱스** — PostgreSQL을 쓴다면 소프트 삭제·상태 기반 필터에서 인덱스 크기와 쓰기 비용을 줄이는 방법을 여기서 잡는다
5. **데이터베이스 옵티마이저** — 옵티마이저가 비용을 어떻게 추정하고 플랜을 선택하는지 원리를 이해한다
6. **쿼리 옵티마이저 (RDBMS)** — EXPLAIN 결과를 실제로 읽고 느린 쿼리를 진단하는 방법을 익힌다
7. **데이터베이스 성능 튜닝** — Slow Query Log부터 시작해 체계적 튜닝 절차를 적용한다
8. **API 페이지네이션 패턴** — 대용량 목록 API에서 Keyset 방식으로 전환하는 시점과 방법을 결정한다

## 빠르게 확인할 때

쿼리가 느린데 원인을 모르는 경우, EXPLAIN 한 줄로 출발점을 잡는다.

```sql
EXPLAIN SELECT * FROM orders WHERE status = 'PENDING' ORDER BY created_at DESC LIMIT 100;
```

`type` 컬럼이 `ALL`이면 풀 테이블 스캔이다. `ref` 또는 `range`면 인덱스를 타고 있다. 인덱스를 타는데도 느리면 `Extra` 컬럼의 `Using index condition`을 확인한다. 세컨더리 인덱스에서 PK를 가져온 뒤 클러스터드 인덱스를 다시 읽는 랜덤 I/O가 발생 중이다. 조회 컬럼을 인덱스에 포함하거나(커버링 인덱스), 결과 건수를 줄이는 쪽으로 개선한다.

### 복합 인덱스가 선두 컬럼부터 제대로 쓰이는지 확인할 때

MySQL에서는 `key_len`으로 인덱스 몇 번째 컬럼까지 실제로 사용됐는지 파악할 수 있다.

```sql
-- (status VARCHAR(20), user_id INT, created_at DATETIME) 복합 인덱스
EXPLAIN SELECT * FROM orders WHERE status = 'PAID';
-- key_len: 83 → status 컬럼만 사용 (utf8mb4 기준 20*4 + 3바이트 길이 접두사)

EXPLAIN SELECT * FROM orders WHERE status = 'PAID' AND user_id = 123;
-- key_len: 87 → status + user_id 사용 (83 + 4바이트 INT)

EXPLAIN SELECT * FROM orders WHERE user_id = 123;
-- key: NULL → 선두 컬럼 없으면 인덱스 자체를 타지 않음
```

PostgreSQL에서는 `EXPLAIN (ANALYZE, BUFFERS)` 출력의 `Index Cond`와 `Filter`를 구분해서 본다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'PAID' AND user_id = 123 AND created_at > '2026-01-01';
```

`Index Cond`에 나오는 컬럼은 인덱스 범위 탐색에 실제로 쓰인 것이고, `Filter`에 나오는 컬럼은 행을 꺼낸 후 추가 필터링한 것이다. `Rows Removed by Filter` 수치가 크면 인덱스 컬럼 순서를 다시 검토한다.

### 인덱스를 만들었는데 안 탈 때

인덱스가 있는데 EXPLAIN에서 `Seq Scan`이 나오는 원인은 대략 세 가지다.

**카디널리티가 낮다.** status 컬럼에 `ACTIVE`, `INACTIVE` 두 값만 있고 분포가 반반이면, 옵티마이저는 인덱스보다 풀 스캔이 더 싸다고 판단한다. 인덱스 자체 문제가 아니라 컬럼 특성 문제다.

**함수로 컬럼을 감쌌다.** `WHERE LOWER(email) = 'test@example.com'`은 `email` 인덱스를 타지 않는다. 인덱스는 원본 값 기준이라 함수 결과값으로 검색이 불가하다. `LOWER(email)` 기준으로 인덱스를 따로 만들거나 쿼리에서 변환을 제거한다.

```sql
-- 안 탄다
SELECT * FROM users WHERE LOWER(email) = 'test@example.com';

-- 탄다: 함수 인덱스 생성
CREATE INDEX idx_users_email_lower ON users (LOWER(email));
SELECT * FROM users WHERE LOWER(email) = 'test@example.com';
```

**통계가 오래됐다.** 대량 INSERT 후나 데이터가 급격히 늘어난 직후에 옵티마이저가 오래된 통계로 잘못된 플랜을 잡는 경우가 있다. `ANALYZE` 또는 `VACUUM ANALYZE`로 통계를 갱신하면 플랜이 다시 잡힌다.

```sql
VACUUM ANALYZE orders;
```

### 부분 인덱스가 안 탈 때

PostgreSQL 부분 인덱스는 쿼리 WHERE 절에 인덱스 조건이 리터럴로 일치해야 탄다. 파라미터 바인딩 쿼리에서는 타지 않는다.

```sql
CREATE INDEX idx_jobs_waiting ON background_jobs (scheduled_at) WHERE status = 'WAITING';

-- 탄다: 리터럴 값 일치
SELECT * FROM background_jobs WHERE status = 'WAITING' AND scheduled_at < now();

-- 안 탄다: $1에 'WAITING'을 바인딩해도 플래닝 시점에 옵티마이저가 값을 모른다
SELECT * FROM background_jobs WHERE status = $1 AND scheduled_at < now();
```

ORM이 prepared statement를 기본으로 쓰는 환경에서 이 문제가 발생한다. 부분 인덱스를 만들기 전에 애플리케이션이 해당 조건을 리터럴로 쿼리에 포함하는지 확인한다. 소프트 삭제 패턴(`deleted_at IS NULL`)은 표현식 자체가 고정이라 파라미터 바인딩 문제가 없다.

```sql
-- 탄다: IS NULL 조건은 리터럴과 동일하게 처리됨
CREATE INDEX idx_users_active ON users (email) WHERE deleted_at IS NULL;
SELECT * FROM users WHERE deleted_at IS NULL AND email = 'test@example.com';
```
