# Claude Code Memory 시스템

Claude Code는 대화가 끝나면 컨텍스트가 사라진다. 다음 대화에서 같은 설명을 반복하지 않으려면 메모리 시스템을 써야 한다.

세션 간 컨텍스트를 유지하는 수단은 두 가지다. **CLAUDE.md**는 프로젝트 규칙과 컨벤션을 담는다. **메모리 파일**은 사용자 정보, 피드백, 프로젝트 상태를 담는다. 두 가지는 역할이 다르고, 같은 내용을 양쪽에 적으면 나중에 불일치가 생긴다.

---

## CLAUDE.md 계층 구조

CLAUDE.md는 세 위치에 둘 수 있고 범위가 각각 다르다.

```
~/.claude/CLAUDE.md               # 글로벌 — 모든 프로젝트에 적용
<project>/CLAUDE.md               # 프로젝트 — 해당 프로젝트에만 적용
<project>/Develop/AI/CLAUDE.md    # 로컬 — 그 디렉토리에서 작업할 때만 적용
```

세 파일이 모두 있으면 전부 로드된다. 우선순위가 있다기보다는, 상위 파일이 기본값을 제공하고 하위 파일이 그 위에 덮어쓰는 구조다.

**글로벌 CLAUDE.md**에는 모든 프로젝트에 공통으로 적용할 규칙을 적는다. 사용 언어, 커밋 메시지 형식, 개인 스타일 같은 것들이다.

```markdown
# ~/.claude/CLAUDE.md

응답은 한국어로 한다.
커밋 메시지는 `feat(범위): 제목` 형식으로 쓴다.
코드 설명 없이 수정만 할 때는 이유를 먼저 말하지 않는다.
```

**프로젝트 CLAUDE.md**에는 이 프로젝트에서만 적용되는 규칙을 적는다. 아키텍처 결정, 테스트 정책, 실수 이력 같은 것들이다. 이 저장소의 CLAUDE.md가 그 예다 — 실제로 사이트를 망가뜨렸던 사고를 정리해뒀다.

```markdown
# <project>/CLAUDE.md

통합 테스트는 testcontainers를 사용한다. DB 모킹 금지.
.pages 파일에서 콜론이 포함된 제목은 반드시 따옴표로 감싼다.
푸시 전에 bash tools/verify.sh 를 실행한다.
```

**로컬 CLAUDE.md**는 특정 서브디렉토리에서 집중적으로 작업할 때 쓴다. 마이크로서비스 구조에서 서비스마다 다른 규칙이 있을 때 유용하다.

```markdown
# <project>/services/auth/CLAUDE.md

이 서비스는 JWT를 사용하지 않는다. 세션 기반이다.
refresh token은 Redis에 저장한다 — `auth:refresh:{userId}` 키.
```

CLAUDE.md는 Git으로 추적된다. 팀 전체에 적용되는 규칙은 여기에 적는다. 개인적인 맥락은 메모리에 저장한다.

---

## 메모리 파일 구조

메모리는 `~/.claude/projects/<프로젝트경로>/memory/` 디렉토리에 마크다운 파일로 저장된다.

```
~/.claude/projects/-Users-dev-myproject/memory/
├── MEMORY.md              # 인덱스 파일 — 매 대화 시작 시 자동 로드
├── user_role.md           # 사용자 정보
├── feedback_testing.md    # 작업 방식 피드백
├── project_auth.md        # 프로젝트 상태
└── reference_linear.md    # 외부 리소스 참조
```

메모리 저장은 두 단계다.

**1단계 — 메모리 파일 생성:**

```markdown
---
name: 기술 수준
description: 사용자의 기술 스택과 수준 — 답변 깊이 조절용
type: user
---

백엔드 5년차. Spring Boot, Kotlin 주력.
React는 이 프로젝트에서 처음 만졌다.
프론트 설명할 때 백엔드 개념에 비유하면 잘 받아들인다.
```

**2단계 — MEMORY.md에 포인터 추가:**

```markdown
- [기술 수준](user_role.md) — 백엔드 5년차, Spring/Kotlin 주력
```

MEMORY.md에는 내용을 직접 쓰지 않는다. 개별 파일을 만들고, 인덱스에는 링크 한 줄만 남긴다. 200줄을 넘으면 잘리니까 한 항목을 한 줄로 제한한다.

---

## 네 가지 타입

### user — 사용자 정보

사용자의 기술 수준, 역할, 작업 방식을 기록한다. 이 정보가 있어야 설명 수준을 맞출 수 있다. 시니어한테 기초부터 설명하거나, 주니어한테 내부 구현을 전제한 설명을 하는 걸 막아준다.

```markdown
---
name: 기술 배경
description: 사용자의 주력 스택과 약점 영역 — 설명 깊이와 비유 선택에 사용
type: user
---

Go 10년차. React는 이 프로젝트에서 처음 만졌다.
프론트 설명할 때 Go의 인터페이스, 채널 같은 개념에 비유하면 잘 받아들인다.
```

**저장 시점**: 사용자가 자기 역할, 기술 수준, 선호도를 언급할 때.

### feedback — 작업 방식 피드백

"이렇게 하지 마"와 "이게 맞아" 둘 다 저장한다. 수정 피드백만 쌓으면 점점 소극적인 응답이 나온다. 잘 된 것도 같이 저장해야 같은 방식을 반복할 수 있다.

```markdown
---
name: 테스트 방식
description: 통합 테스트에서 DB 모킹 금지 — 실DB 연결 필수
type: feedback
---

통합 테스트에서 DB를 모킹하지 않는다.

**Why:** 지난 분기에 모킹한 테스트가 통과했는데 프로덕션 마이그레이션이 깨진 적이 있다.
**How to apply:** 테스트 코드 작성 시 항상 testcontainers로 실제 DB를 띄운다.
```

구조는 "규칙 → Why → How to apply"로 고정한다. Why가 없으면 엣지 케이스에서 판단이 안 된다. "DB 모킹 금지"라고만 적으면, 유닛 테스트의 레포지토리 목도 금지인지 헷갈린다.

**저장 시점**: 사용자가 작업 방식을 교정하거나 특정 방식을 확인할 때.

### project — 프로젝트 상태

코드나 Git에서 알 수 없는 맥락을 기록한다. 담당자, 마감일, 진행 이유 같은 것들이다.

```markdown
---
name: 머지 프리즈
description: 모바일 릴리스 커트로 인한 머지 제한 — 비핵심 PR 일정 주의
type: project
---

2026-03-05부터 비핵심 머지 프리즈.
모바일 팀이 릴리스 브랜치를 자른다.

**Why:** 릴리스 브랜치 안정성 확보
**How to apply:** 비핵심 PR 작업을 해당 일자 이후로 잡지 않는다.
```

상대 날짜는 반드시 절대 날짜로 변환해서 저장한다. "목요일까지"는 나중에 읽으면 언제인지 알 수 없다.

프로젝트 메모리는 빨리 낡는다. Why가 있어야 "이 메모리가 아직 유효한가?"를 판단할 수 있다.

**저장 시점**: 담당자, 일정, 결정 배경, 이슈 등 코드에 안 나타나는 정보를 언급할 때.

### reference — 외부 리소스

외부 시스템의 위치와 용도를 기록한다. 다음에 찾아볼 때 어디를 봐야 하는지 알 수 있게.

```markdown
---
name: 파이프라인 버그 트래커
description: Linear INGEST 프로젝트 — 파이프라인 버그 추적 위치
type: reference
---

파이프라인 관련 버그는 Linear의 "INGEST" 프로젝트에서 관리한다.
파이프라인 이슈를 언급하거나 확인할 때 이 프로젝트를 참조한다.
```

**저장 시점**: "~는 여기서 확인해", "~는 이 채널에 있어" 같이 외부 리소스 위치를 알려줄 때.

---

## 세션 간 컨텍스트 유지 패턴

메모리 파일만 있으면 되는 게 아니다. Claude가 메모리를 어떻게 읽고 쓰는지, 그 패턴이 중요하다.

### 기본 패턴 — 메모리 파일 생성

메모리를 저장할 때 Claude가 실행하는 패턴이다:

```bash
# 1. 메모리 파일 작성
cat > ~/.claude/projects/-root-myproject/memory/feedback_testing.md << 'EOF'
---
name: 테스트 방식
description: 통합 테스트 DB 모킹 금지
type: feedback
---

통합 테스트에서 DB를 모킹하지 않는다.

**Why:** 프로덕션 마이그레이션 실패 경험
**How to apply:** testcontainers 사용
EOF

# 2. MEMORY.md에 포인터 추가
echo "- [테스트 방식](feedback_testing.md) — 통합 테스트 DB 모킹 금지" >> ~/.claude/projects/-root-myproject/memory/MEMORY.md
```

### 세션 시작 시 컨텍스트 복원 패턴

새 대화가 시작되면 Claude는 자동으로 MEMORY.md를 읽는다. 여기서 관련 메모리 파일들을 파악하고 필요할 때 읽어온다. 사용자가 "지난번에 얘기했던 거 기억해?"라고 할 필요 없이, 대화 맥락에서 관련 메모리를 자동으로 참조한다.

MEMORY.md가 이 패턴의 핵심이다:

```markdown
# MEMORY.md 예시 — 컨텍스트 복원용 인덱스

- [기술 수준](user_role.md) — Go 10년차, React 처음, 백엔드 비유 선호
- [테스트 방식](feedback_testing.md) — 통합 테스트 DB 모킹 금지
- [릴리스 일정](project_release.md) — 2026-03-10 v2.0, 인증 모듈 포함
- [버그 트래커](reference_linear.md) — 파이프라인 버그는 Linear INGEST
```

항목 하나가 한 줄이어야 한다. 나중에 이 인덱스를 읽을 때 전체 내용이 한눈에 들어와야 어떤 메모리를 열어볼지 판단할 수 있다.

### 메모리 검증 패턴

메모리에 파일 경로, 함수명, URL 같은 것이 기록돼 있다면, 사용자에게 안내하기 전에 먼저 확인한다.

```bash
# 메모리에 "src/auth/validateToken 함수가 있다"고 적혀 있을 때
# 바로 안내하지 않고 먼저 확인

grep -r "validateToken" src/auth/
# 파일이 이동했거나 함수명이 바뀌었을 수 있다
```

"메모리에 X가 있다"와 "X가 지금 존재한다"는 다른 말이다. 메모리는 작성 시점의 사실이다.

### 메모리 갱신 패턴

기존 메모리와 현재 상태가 다를 때:

```python
# 메모리 파일을 직접 덮어쓴다
# 기존 내용을 Read → 수정된 내용으로 Write

# user_role.md 갱신 예시
new_content = """---
name: 기술 수준
description: 사용자의 기술 스택 — 2026-09 업데이트
type: user
---

백엔드 5년차에서 테크리드로 전환.
아키텍처 결정과 코드 리뷰 중심으로 작업한다.
세부 구현보다 설계와 트레이드오프 논의를 선호한다.
"""
```

MEMORY.md의 해당 포인터도 같이 갱신한다. 파일만 바꾸고 인덱스를 안 바꾸면 설명이 틀린 채로 남는다.

## 메모리 vs CLAUDE.md vs 태스크 / 플랜

세 가지 수단이 있고 용도가 다르다.

| 구분 | 메모리 | CLAUDE.md | 태스크 / 플랜 |
|------|--------|-----------|--------------|
| **범위** | 대화를 넘어 유지 | 대화를 넘어 유지 | 현재 대화 내 |
| **공유** | 개인 전용 | 팀 공유 (Git 추적) | 해당 대화만 |
| **용도** | 사용자/프로젝트 맥락 | 프로젝트 규칙/컨벤션 | 작업 진행 추적/방향 합의 |
| **저장 위치** | `~/.claude/projects/.../memory/` | 프로젝트 루트 또는 서브디렉토리 | 대화 내 |

구분 기준은 단순하다. **다음 대화에서도 알아야 하는가?** 그리고 **팀 전체가 알아야 하는가?**

"이 사용자는 한국어 문서를 선호한다" → 메모리 (개인 맥락)  
"통합 테스트는 testcontainers를 쓴다" → CLAUDE.md (팀 규칙)  
"3번 파일까지 수정 완료" → 태스크 (현재 작업 진행)  
"인증 모듈 리팩토링 순서" → 플랜 (현재 대화에서 합의)  

흔한 실수:
- 작업 단계를 메모리에 저장 → 다음 대화에서 이미 끝난 단계를 본다. 태스크를 써야 한다.
- 코드 구조를 메모리에 저장 → 리팩토링하면 틀린 정보가 된다. 코드를 직접 읽는 게 정확하다.
- CLAUDE.md에 적혀 있는 내용을 메모리에도 저장 → 불일치가 생기면 어느 쪽이 맞는지 판단하기 어렵다.

## Stale 메모리

메모리는 작성 시점의 사실이다. 시간이 지나면 틀릴 수 있다.

**타입별 부패 속도:**

- **feedback**: 거의 안 변한다. "DB 모킹하지 마"는 조직의 결정이 바뀌지 않는 한 유효하다.
- **user**: 느리게 변한다. 기술 수준이나 선호도는 수개월 단위로 바뀐다.
- **reference**: 중간 수준. 외부 시스템의 URL이나 구조가 바뀔 수 있다.
- **project**: 가장 빨리 변한다. 마감일, 담당자, 진행 상태는 매주 바뀔 수 있다.

충돌이 발생하면 현재 상태를 신뢰한다. 메모리가 아니라 지금 보이는 게 맞다. 틀린 메모리는 갱신하거나 삭제한다. 방치하면 다음 대화에서 또 혼란이 생긴다.

---

## 인덱스 관리

MEMORY.md는 200줄 제한이 있다. 메모리가 쌓이면 정리가 필요하다.

**정리 시점:**
- 같은 주제의 메모리가 여러 개 생겼을 때 → 최신 정보 기준으로 하나로 합치고 나머지 삭제
- 프로젝트 메모리의 마감일이 지났을 때 → 아직 유효한지 확인 후 삭제 또는 갱신
- 200줄에 근접했을 때 → 더 이상 관련 없는 항목부터 정리 (보통 오래된 project 타입)

MEMORY.md에 직접 내용을 쓰지 않는다:

```markdown
# 잘못된 예
- 사용자는 백엔드 5년차이고 Spring Boot를 주로 사용하며 React는 잘 모른다

# 올바른 예
- [기술 수준](user_role.md) — 백엔드 5년차, Spring/Kotlin 주력
```

전자는 MEMORY.md가 커지고, 인덱스가 아니라 내용 파일이 된다.

## 저장하지 않는 것

메모리에 저장해도 의미가 없는 정보가 있다:

- **코드 패턴, 아키텍처, 파일 경로**: 코드를 직접 읽으면 정확하다. 메모리에 복제해봤자 금방 낡는다.
- **Git 히스토리, 변경 이력**: `git log`, `git blame`이 정확하다.
- **디버깅 해결법**: 수정 내역은 코드와 커밋 메시지에 있다.
- **CLAUDE.md에 이미 적힌 내용**: 중복이고, 나중에 불일치가 생긴다.
