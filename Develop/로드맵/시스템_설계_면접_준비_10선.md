# 시스템 설계 면접 준비 10선

"URL 단축기를 설계하세요"로 시작해서 45분 안에 아키텍처를 그려야 한다. 외운 것을 쏟아내는 자리가 아니다. 면접관은 트레이드오프를 알고 있는 사람인지 보고 싶어한다.

첫 면접에서 ElastiCache 레이어를 추가했더니 면접관이 "왜 캐시가 필요하다고 판단했냐"고 물었다. "일반적으로 캐시는..."이라고 대답했다가 바로 다음 질문으로 넘어갔다. 이 리스트는 그때부터 정리한 것이다.

---

## 면접 첫 5분 — 수치 추정

면접관이 "하루 100만 명이 쓰는 서비스를 설계하라"고 하면 수를 먼저 잡아야 한다. 이 단계를 건너뛰고 바로 아키텍처를 그리면 후반부에 번복이 생긴다.

### QPS 추정 공식

```
일간 요청 수 = DAU × 1인당 일평균 요청
QPS (평균) = 일간 요청 수 / 86,400
QPS (피크) = 평균 QPS × 피크 배율 (보통 2~5배)
```

**URL 단축기 예시**

- DAU 1,000만, 1인당 쓰기 1회 + 읽기 10회
- 쓰기 QPS: 10,000,000 / 86,400 ≈ **116 QPS**, 피크 ≈ 580 QPS
- 읽기 QPS: 100,000,000 / 86,400 ≈ **1,157 QPS**, 피크 ≈ 5,785 QPS

읽기 : 쓰기 비율이 10:1이 나온다. 이 순간 "읽기 최적화가 필요하다"는 결론이 자연스럽게 나온다.

**Instagram 피드 예시**

- DAU 5억, 1인당 읽기 20회
- 읽기 QPS: 500,000,000 × 20 / 86,400 ≈ **115,741 QPS**

이 수치가 나오면 단일 DB에 모든 읽기를 때리는 구조는 불가능하다는 게 명백해진다. Fan-out write 또는 Fan-out read 선택이 필요하고, 이게 면접 본론이 된다.

### 스토리지 추정 공식

```
5년치 저장량 = 일간 쓰기 건수 × 365 × 5 × 1건당 용량
```

**URL 단축기 예시**

- 1건당 레코드 크기: short_code(7B) + original_url(평균 200B) + metadata(100B) ≈ 310B
- 5년: 10,000,000 × 365 × 5 × 310B = **5.67TB**

이 정도면 단일 DB로 감당 가능하다. 읽기 QPS가 높으니 캐시 레이어가 병목을 잡는다.

## URL 단축기 설계

가장 자주 나오는 문제다. 표면은 단순해 보이지만 파고들면 해시 충돌, 리다이렉트 성능, DB 병목이 전부 나온다.

### short_code 생성 방법

두 가지가 충돌한다.

- Base62 인코딩 (auto-increment ID → 62진수 변환): 충돌 없음, 순차적이라 예측 가능
- 랜덤 6~7자리 해시: 예측 불가, 하지만 충돌 재시도 로직 필요

실무에서는 Snowflake 형태의 분산 ID 생성기를 쓰고 Base62로 변환한다. 충돌 재시도 로직을 없애는 게 안정성 측면에서 낫다.

```python
BASE62 = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def to_base62(num: int) -> str:
    result = []
    while num > 0:
        result.append(BASE62[num % 62])
        num //= 62
    return ''.join(reversed(result))

# auto_increment id 1234567 → "5ban"
# id가 단조 증가하므로 충돌 없음, short_code 길이는 id 크기에 따라 자동 조정
```

### 리다이렉트 경로의 병목

읽기 QPS가 피크 5,785 QPS일 때 모든 요청을 DB에 때리면 일반 RDS 인스턴스는 버티지 못한다. 연결 수 자체가 문제가 된다.

해결 경로: Redis를 앞에 세운다.

```
클라이언트 → CloudFront → Lambda → Redis
                                    ↓ cache miss
                                   RDS
```

- Cache hit: Redis에서 original_url 반환, DB 접근 없음
- Cache miss: DB 조회 후 Redis에 TTL 설정해서 적재
- 히트율 90% 이상이면 DB 부하가 1/10로 줄어든다

면접에서 "캐시를 쓴다"고 하면 바로 나오는 질문이 "캐시 무효화는 어떻게 하냐"다. URL 단축기는 URL이 변경되는 경우가 드물어서 TTL 기반으로 관리하면 충분하다. TTL을 얼마로 잡느냐는 비즈니스 요구사항 (URL 삭제 반영 속도)에 따라 달라진다.

## 피드 시스템 설계

면접 난이도 기준 상위 문제다. Fan-out write와 Fan-out read 사이 선택이 핵심이고, 이걸 DAU와 팔로워 분포로 설명해야 한다.

### Fan-out Write vs Fan-out Read

**Fan-out Write (Push model)**

유저가 게시물을 올리는 순간, 모든 팔로워의 피드 테이블에 미리 써넣는다.

```
POST /posts
  → SQS → Lambda (fanout worker)
  → 팔로워 수만큼 feed_table insert
```

장점: 읽기가 단순하다. 본인 feed_table만 읽으면 된다.
단점: 팔로워 1,000만 명인 인플루언서가 게시물을 올리면 1,000만 건 insert가 발생한다. 쓰기 폭풍이 일어나고 SQS 지연이 수 분이 될 수 있다.

**Fan-out Read (Pull model)**

읽기 시점에 팔로잉 목록을 조회해서 각자 최신 게시물을 수집한다.

장점: 쓰기가 단순하다. 게시물 1건만 저장하면 끝.
단점: 읽기 QPS가 높을 때 팔로잉 50명의 게시물을 실시간 조합하면 읽기 부하가 심각해진다.

**실제 선택: 혼합**

인플루언서 계정 (팔로워 100만+)은 Fan-out read, 일반 계정은 Fan-out write. Instagram과 Twitter 모두 이 방식을 쓴다.

```
게시물 작성 시:
  팔로워 수 <= 10,000 → Fan-out write (피드 캐시에 미리 적재)
  팔로워 수 >  10,000 → Fan-out read 대상으로 마킹만

피드 읽기 시:
  1. 본인의 feed_cache 읽기 (일반 계정 게시물)
  2. 팔로잉 중 인플루언서의 최신 게시물 실시간 조회
  3. merge & sort (created_at 기준)
```

Redis Sorted Set으로 피드 캐시를 구현하면 `ZADD feed:{user_id} {timestamp} {post_id}`로 최신순 정렬을 O(log N)에 유지한다. `ZREVRANGE feed:{user_id} 0 99`로 최신 100건 조회.

면접에서 "피드 캐시가 없는 사용자는?"이라고 물으면 Cold start 처리를 설명해야 한다. 처음 로그인한 사용자는 캐시가 비어있으니 Fan-out read로 채운 뒤 캐시에 적재한다.

[SNS SQS Lambda 통합 메시지 파이프라인](../Cloud/AWS/Application_Integration/SNS_SQS_Lambda_통합_메시지_파이프라인.md) — 팬아웃 이벤트 구현

## 알림 시스템 설계

유저 A가 B의 게시물에 좋아요를 눌렀다는 알림을 이메일, 푸시, SMS로 보내는 시스템이다.

### 채널 분기와 재시도

```
이벤트 발생 → SNS Topic → 각 채널 SQS

SNS Topic "notification-events"
  ├── SQS "email-queue" → Lambda (SES 이메일 발송)
  ├── SQS "push-queue"  → Lambda (APNs/FCM 푸시 발송)
  └── SQS "sms-queue"   → Lambda (Twilio SMS 발송)
```

채널을 SQS로 분리하는 이유는 장애 격리다. 이메일 발송 실패가 푸시 발송을 막지 않는다. 각 채널의 처리량과 재시도 정책도 독립적으로 조정한다.

**재시도 설계**

Lambda가 SES 호출에서 일시적 오류를 받으면 예외를 던지고 SQS가 재시도한다. maxReceiveCount=3 초과 시 DLQ(Dead Letter Queue)로 이동한다.

```
SQS 재시도 정책:
  visibilityTimeout: 30초 (Lambda 처리 시간의 6배)
  maxReceiveCount: 3
  DLQ retentionPeriod: 7일
```

면접에서 "같은 알림이 두 번 가면 어떻게 되냐"는 질문이 꼭 나온다. 멱등성 처리를 설명해야 한다. notification_log 테이블에 (user_id, event_id, channel)를 저장하고 중복 발송 전에 체크한다.

[SNS SQS Lambda 통합 메시지 파이프라인](../Cloud/AWS/Application_Integration/SNS_SQS_Lambda_통합_메시지_파이프라인.md)

## 채팅 시스템 설계

WebSocket 연결 관리와 메시지 전달 보장이 핵심이다.

### 연결 유지와 메시지 라우팅

HTTP는 요청-응답 모델이라 서버가 클라이언트에 먼저 데이터를 보낼 수 없다. 채팅은 서버 → 클라이언트 푸시가 필요하니 WebSocket이 기본이 된다.

```
[유저 A] <--WebSocket--> [Chat Server 1]
[유저 B] <--WebSocket--> [Chat Server 2]

유저 A → 유저 B 메시지 흐름:
1. Chat Server 1이 메시지 수신
2. 메시지를 DB에 저장 (내구성 확보)
3. 유저 B가 어느 서버에 연결됐는지 조회 → Chat Server 2
4. Chat Server 1 → Redis Pub/Sub → Chat Server 2 → 유저 B
```

Chat Server 2가 `user:{B}` 채널을 구독하고 있으면, Chat Server 1이 해당 채널에 publish해서 전달한다.

**오프라인 유저 처리**

유저 B가 오프라인이면 WebSocket 연결이 없다. 메시지를 DB에만 저장하고, 유저가 온라인이 되면 미읽음 메시지를 가져오는 구조다. 푸시 알림은 별도 알림 시스템을 탄다.

면접에서 "메시지 순서 보장을 어떻게 하냐"는 질문이 따라온다. 클라이언트 타임스탬프는 신뢰하면 안 된다. 서버 수신 시간 + 단조 증가 sequence number를 메시지에 붙여서 클라이언트가 정렬하게 한다.

## 검색 자동완성 설계

"goo"를 치면 "google", "good morning" 같은 후보를 보여주는 기능이다.

### 응답 속도 요구사항

키를 누를 때마다 요청이 간다. 100ms 이내 응답이 없으면 UX가 깨진다. 검색 자동완성은 성능이 기능 자체다.

**Trie vs DB 쿼리**

처음 떠올리는 방법은 검색 키워드 테이블에 `LIKE 'goo%'` 쿼리다. 인덱스를 타지만 키워드가 수십억 건이면 느려진다. Trie 자료구조를 메모리에 올려두고 prefix 탐색을 O(prefix 길이)에 처리하는 방법이 현실적이다.

```
Trie 노드 구조:
{
  char: 'g',
  children: { 'o': ... },
  is_end: false,
  top_k: ['google', 'good morning', 'go'],  # 이 prefix에서 가장 많이 검색된 K개
  score: 검색 빈도
}

탐색: "goo" prefix 노드 도달 → top_k 꺼내기 → 끝
```

top_k를 각 노드에 pre-compute해서 저장하면 탐색이 단순해진다.

**업데이트 주기**

실시간으로 Trie를 업데이트하면 lock 경쟁이 생긴다. 검색 로그를 Kafka로 쌓고, 1시간마다 batch job이 Trie를 재빌드해서 교체하는 방식이 일반적이다. 트렌드 반영에 1시간 지연이 생기지만 허용 가능한 수준이다.

## 데이터 레이어 선택 판단

면접관이 "어떤 DB를 쓰겠냐"고 물으면 "요구사항에 따라 다르다"는 말로 시작하면 안 된다. 판단 기준을 구체적으로 제시해야 한다.

### RDB vs NoSQL

**RDB (PostgreSQL, Aurora)를 선택하는 경우**

- 트랜잭션이 필요한 경우 (결제, 재고 차감)
- 데이터 관계가 복잡하고 JOIN이 필수인 경우
- 데이터 모델이 확정되어 있고 스키마 변경이 드문 경우

**NoSQL (DynamoDB)을 선택하는 경우**

- 단순 key-value 또는 document 조회가 전부인 경우
- 쓰기 처리량이 수만 QPS 이상이고 수평 확장이 필수인 경우
- 읽기 패턴이 고정되어 있어 쿼리 유연성이 필요 없는 경우

DynamoDB에서 파티션 키 선택은 치명적이다. user_id를 파티션 키로 쓰면 인기 유저의 파티션에 트래픽이 몰린다 (핫 파티션). 이를 피하려면 파티션 키에 suffix를 붙여서 분산시키거나 (user_id#shard_0 ~ user_id#shard_9) Access Pattern을 재설계해야 한다.

## Kafka vs SQS 선택

둘 다 메시지 큐인데 면접에서 혼용하면 감점이다.

**SQS를 쓰는 경우**

- 메시지를 소비하면 삭제되어도 되는 경우 (알림 발송)
- 소비자가 하나이거나 간단한 fan-out (SNS + SQS)
- 메시지 재처리가 DLQ 기반으로 충분한 경우

**Kafka (MSK)를 쓰는 경우**

- 메시지를 여러 소비자 그룹이 독립적으로 처리해야 하는 경우
- 메시지를 시간 순서로 offset 기반 재처리해야 하는 경우 (이벤트 소싱, 감사 로그)
- 처리량이 초당 수십만 건 이상인 경우

Kafka는 retention period 동안 메시지를 디스크에 보관한다. 소비자 버그로 메시지를 잘못 처리했을 때 offset을 되돌려서 재처리한다. SQS는 한 번 소비된 메시지는 삭제되므로 이 패턴이 불가능하다.

[MSK (Managed Kafka)](../Cloud/AWS/Application_Integration/MSK.md) — Kafka vs SQS 세부 비교

## 글로벌 서비스 설계

"한국에 서버를 두면 미국 유저는 어떻게 하냐"는 질문의 답이다.

### 레이턴시 문제의 근본

물리적 거리는 어쩔 수 없다. 한국-미국 간 RTT는 약 150ms다. API 응답 시간을 50ms 이내로 맞추려면 미국 리전에 서버를 둬야 한다.

**CDN으로 해결되는 것과 안 되는 것**

CDN(CloudFront)은 정적 자산 (이미지, JS, CSS)과 캐시 가능한 API 응답을 엣지에서 제공한다. 사용자 프로필 조회처럼 캐시 가능한 데이터는 CDN으로 레이턴시를 줄인다.

캐시 불가능한 읽기 (실시간 피드, 결제)와 모든 쓰기는 CDN이 해결하지 못한다. 미국 유저의 쓰기 요청이 한국 서버까지 150ms를 써야 한다면 글로벌 서비스로 볼 수 없다.

**멀티 리전 설계**

```
[미국 유저] → [US ALB] → [US App Server] ↔ [US DB (Primary)]
                                                     ↓ 비동기 복제
[한국 유저] → [KR ALB] → [KR App Server] ↔ [KR DB (Replica)]
```

쓰기는 Global Primary (미국)로 라우팅하거나, 각 리전이 독립 Primary를 갖고 충돌 해소 정책을 두는 방식 중 선택한다. 충돌 해소가 필요 없도록 데이터를 지역 단위로 분리하는 게 가장 단순하다 (미국 유저 데이터는 US DB에만).

## 장애 발생 시 면접관이 원하는 답

"DB가 죽으면 어떻게 되냐"는 질문은 설계에 장애 대응이 포함됐는지 확인하는 것이다.

### SPOF 제거 우선순위

면접에서 그린 아키텍처에 단일 컴포넌트가 있으면 "저게 죽으면?"이라는 질문이 들어온다. 모든 레이어를 이중화하는 것이 원칙이지만 비용이 따른다. 어떤 컴포넌트를 이중화할지 우선순위를 설명해야 한다.

```
장애 영향도 높은 순:
1. DB           → 데이터 접근 불가, 서비스 전체 중단
2. 로드밸런서   → 단일 진입점, 전체 트래픽 차단
3. 캐시 서버    → Cache miss 폭증, DB 부하로 서비스 느려짐
4. 앱 서버 1대  → 일부 요청 실패, 다른 서버가 처리
```

RDS Multi-AZ는 Primary가 죽으면 Standby가 수 분 내 자동으로 Primary가 된다. Aurora는 이 전환이 30초 이내다. 면접에서 Aurora를 선택하면 이 수치를 근거로 들어야 한다.

**장애 대응 절차**

Metrics, Logs, Traces 세 가지를 동시에 본다. 에러율이 올라갔다면 (Metrics) → 어느 서비스인지 (Traces) → 구체적인 에러 내용 (Logs) 순서로 좁혀나간다.

## 45분 면접의 흐름

**0~5분: 요구사항 확인**

DAU, 예상 QPS, 읽기/쓰기 비율, 레이턴시 요구사항을 먼저 잡는다. 수치 없이 설계를 시작하면 후반부에 번복이 생긴다.

**5~15분: 상위 레벨 설계**

컴포넌트를 나열하고 데이터 흐름을 그린다. 세부 구현보다 전체 그림을 먼저 완성한다.

**15~35분: 세부 설계**

면접관이 관심 있는 컴포넌트를 깊게 판다. DB 스키마, API 명세, 알고리즘. 면접관의 질문 방향을 보면서 어디를 깊게 팔지 조정한다.

**35~45분: 트레이드오프 토론**

"다른 방법은?"이라는 질문에 대비한다. 선택한 방법의 단점과 대안을 미리 준비해둔다.
