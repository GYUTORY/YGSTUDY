    Amazon SageMaker 실무 활용¶

    들어가며¶

    SageMaker를 처음 접했을 때 가장 혼란스러웠던 건 "이게 하나의 서비스인가, 플랫폼인가"라는 점이다. 실제로는 데이터 준비부터 학습, 배포, 모니터링까지 ML 전체 수명주기를 덮는 여러 하위 서비스의 집합이다. 이름 뒤에 붙는 접미사(Studio, Notebook, Training Job, Endpoint, Pipelines, Feature Store 등)가 각각 독립된 리소스다.

    현실에서 SageMaker를 도입하면 단순히 "모델 학습 돌리는 환경" 수준으로만 쓰다가 비용이 예상보다 몇 배 나오거나, 엔드포인트를 띄워놓고 방치해서 월말에 청구서를 보고 놀라는 경우가 많다. 실무 관점에서 어떤 구성요소가 어떤 역할을 하고, 어디에서 돈이 새고, 어떤 함정에 빠지기 쉬운지를 정리했다.

    SageMaker 구성요소 개요¶

    Studio와 Notebook Instance의 차이¶

    Studio는 웹 기반 IDE로 JupyterLab 기반에 SageMaker 기능을 통합한 것이다. Notebook Instance는 EC2 인스턴스 위에 Jupyter Server를 띄운 옛날 방식이다. 신규 프로젝트라면 Studio를 써야 한다. Notebook Instance는 인스턴스를 켜놓으면 요금이 계속 나가고, 커널 따로 컴퓨팅 따로 분리가 안 되어 리소스 낭비가 심하다.

    Studio에서도 한 가지 주의점이 있는데, Jupyter Server 앱과 Kernel Gateway 앱이 별도로 과금된다. 노트북을 닫아도 커널이 살아 있으면 요금이 계속 나간다. Studio UI 좌측에서 "Running Instances and Kernels" 패널을 열어서 불필요한 커널을 직접 Shut down 해야 한다. 이걸 모르고 팀 전체가 Studio를 쓰다가 월 수백 달러씩 새는 경우를 자주 본다.

    Idle shutdown을 강제하려면 lifecycle configuration script를 도메인에 붙여서 일정 시간 이상 유휴 상태인 앱을 자동 종료하게 설정해야 한다.

    Studio Spaces와 앱 종류¶

    Studio가 한 차례 개편되면서 사용자별 작업 공간이 Spaces 개념으로 정리됐다. Space 하나가 EBS 볼륨과 앱들을 묶는 단위다. 한 사용자가 여러 Space를 만들어서 프로젝트별로 나누거나, 팀이 공유 Space(Shared Space)를 만들어 같은 코드와 노트북을 함께 보는 식으로 쓴다.

    Space 안에서 띄울 수 있는 앱은 크게 세 가지다.

    • JupyterLab 앱: 가장 흔한 노트북 환경. 인스턴스 타입을 바꿔가며 띄울 수 있다.
    • Code Editor 앱: VS Code(Code-OSS) 기반 IDE. 모델 코드를 좀 더 IDE스럽게 짜고 싶을 때 쓴다.
    • RStudio 앱: 라이선스가 별도라 잘 안 쓴다.

    각 앱은 띄울 때 인스턴스 타입을 고르고, 그 인스턴스가 살아있는 동안 시간당 과금된다. JupyterLab으로 GPU 인스턴스를 띄워놓고 점심 먹으러 가면 그동안 GPU 요금이 그대로 나간다. 개발은 ml.t3.medium이나 ml.m5.large 같은 저렴한 인스턴스에서 하고, 무거운 작업은 Training Job이나 Processing Job으로 분리해서 돌려야 한다.

    EBS 볼륨은 Space별로 따로 잡혀서, 앱을 내려도 EBS 비용은 계속 나간다. 안 쓰는 Space는 삭제해야 한다.

    노트북 일상 작업 흐름¶

    Studio JupyterLab을 처음 열면 좌측에 SageMaker 리소스 패널, 가운데에 파일 브라우저와 에디터가 뜬다. 실무에서 노트북을 다룰 때 자주 쓰는 흐름은 이렇다.

    먼저 인스턴스 타입을 고른다. 우상단의 인스턴스 칩을 클릭하면 변경 가능한 타입 목록이 나오는데, 변경 시점에 현재 커널이 종료되고 새 인스턴스로 옮겨진다. 메모리에 올려둔 변수는 다 날아간다. 큰 데이터프레임을 계속 들고 있어야 한다면 변경 전에 df.to_parquet("/home/sagemaker-user/cache.parquet")처럼 EBS에 직렬화해두고 다시 읽는 게 안전하다.

    커널 선택은 좌측 위 커널 표시를 누르면 이미지 + Python 버전 조합으로 뜬다. 이미지가 PyTorch 2.x를 포함하면 별도 설치 없이 바로 임포트 가능하다. 추가 패키지가 필요하면 노트북 첫 셀에 %pip install -q transformers==4.40.0 식으로 박아두는 게 표준이다. !pip install은 셸 스코프라 패키지 위치가 꼬이는 경우가 가끔 있어서 매직 명령(%pip)을 권장한다.

    S3 데이터 접근은 sagemaker.Session().default_bucket()으로 기본 버킷을 잡거나, AWS CLI를 그대로 쓴다. 노트북 인스턴스에는 SageMaker Execution Role이 자동으로 붙어 있어서 별도 자격 증명 없이 boto3가 동작한다. 단, 회사 정책으로 별도 KMS 키가 걸린 버킷이라면 Role에 KMS Decrypt 권한이 빠져 있을 가능성이 높다.

    import sagemaker, boto3, pandas as pd

session = sagemaker.Session()
bucket = session.default_bucket()
role = sagemaker.get_execution_role()
print(bucket, role)

s3 = boto3.client("s3")
s3.download_file(bucket, "datasets/users.parquet", "/tmp/users.parquet")
df = pd.read_parquet("/tmp/users.parquet")

    터미널이 필요하면 File → New → Terminal로 띄운다. 컨테이너 안에서 apt-get은 보통 막혀 있고, 추가 OS 패키지가 필요하면 커스텀 이미지를 만들어서 도메인에 등록해야 한다. 임시로 Python 라이브러리만 설치하면 충분한 경우가 대부분이다.

    JupyterLab은 자동 저장이 켜져 있지만, 인스턴스 강제 종료가 일어나면 저장되지 않은 셀 출력은 사라진다. Git 연동을 권장한다. Studio는 jupyterlab-git 확장이 기본 탑재돼서 좌측 패널에서 commit/push가 가능하다. 사내 GitHub Enterprise라면 PAT를 ~/.netrc에 박아두거나 SSH 키를 EBS에 한번 만들어놓으면 된다.

    Studio 노트북에서 Training Job을 띄울 때 자주 쓰는 패턴은 같은 코드를 그대로 컨테이너에 보내는 방식이다.

    from sagemaker.pytorch import PyTorch

estimator = PyTorch(
    entry_point="train.py",
    source_dir="./src",
    role=role,
    framework_version="2.1",
    py_version="py310",
    instance_type="ml.g5.xlarge",
    instance_count=1,
    hyperparameters={"epochs": 5, "lr": 1e-4},
)

estimator.fit({"train": f"s3://{bucket}/datasets/train/"}, wait=False)

    wait=False로 띄우면 노트북은 바로 셀이 끝나고 학습은 백그라운드에서 돈다. 진행 상황은 SageMaker 콘솔의 Training Jobs 탭이나 CloudWatch Logs /aws/sagemaker/TrainingJobs에서 본다. 학습이 끝나기를 기다리는 동안 노트북 인스턴스는 작은 CPU 타입으로 충분하다는 게 핵심이다.

    Training Job¶

    모델 학습을 실행하는 단위다. 학습 코드를 컨테이너 이미지로 만들거나 SageMaker가 제공하는 빌트인 이미지(PyTorch, TensorFlow, Hugging Face 등)를 쓴다. 학습이 시작되면 지정한 인스턴스가 프로비저닝되고, 학습이 끝나면 자동으로 종료되며 모델 아티팩트가 S3에 업로드된다.

    핵심은 "학습 시간만큼만 돈을 낸다"는 점이다. 학습이 10분 걸리면 10분치만 과금된다. 그래서 비싼 GPU 인스턴스를 Notebook에 띄워놓고 학습하는 것보다, 개발은 저렴한 CPU 인스턴스에서 하고 학습만 Training Job으로 돌리는 게 훨씬 싸다.

    Training Job은 시작될 때마다 새 인스턴스를 프로비저닝해서 컨테이너 이미지를 내려받는다. 코드 한 줄 바꾸고 다시 돌리면 매번 수 분의 부팅 오버헤드가 발생한다. 반복 실험이 잦으면 keep_alive_period_in_seconds를 줘서 Warm Pool을 활성화하면 같은 인스턴스를 재사용해 부팅 시간을 거의 0으로 줄일 수 있다. 단, Warm Pool 동안에도 인스턴스 시간 요금이 그대로 나가므로 짧게(예: 600초) 잡아야 한다.

    estimator = PyTorch(
    entry_point="train.py",
    role=role,
    framework_version="2.1",
    py_version="py310",
    instance_type="ml.g5.xlarge",
    instance_count=1,
    keep_alive_period_in_seconds=600,
    use_spot_instances=True,
    max_run=3600,
    max_wait=7200,
    checkpoint_s3_uri="s3://my-bucket/checkpoints/",
)

    학습은 대부분 중단돼도 재개 가능한 구조라서 Spot 인스턴스가 잘 맞는다. use_spot_instances=True로 설정하면 같은 GPU를 50~90% 싸게 쓴다. 단, Spot은 언제든 회수당할 수 있으니 체크포인트를 S3에 주기적으로 저장하고 재개 로직을 코드에 넣어야 한다. max_wait는 Spot 인스턴스를 기다리는 최대 시간이며, 이 안에 못 받으면 실패 처리된다.

    여러 노드에 걸친 분산 학습이 필요하면 instance_count를 2 이상으로 주고 distribution 파라미터로 백엔드(smdistributed, pytorchddp, mpi 등)를 지정한다. 노드 간 통신이 EFA 지원 인스턴스(p4d, p5)에서 훨씬 빠르므로 큰 모델은 EFA 가능 인스턴스로 골라야 한다.

    Endpoint (추론 엔드포인트)¶

    학습된 모델을 HTTP API로 서빙하는 리소스다. 한번 만들면 인스턴스가 24시간 켜져 있어서 요청이 없어도 요금이 계속 나간다. 개발 중에 여러 모델을 실험한다고 엔드포인트를 여러 개 띄워놓고 잊어버리면 월말에 폭탄을 맞는다. 실험용 엔드포인트는 반드시 삭제 스크립트를 만들거나 태그 기반 자동 정리 람다를 돌려야 한다.

    Pipelines¶

    SageMaker Pipelines는 학습·평가·등록·배포를 DAG로 정의하는 MLOps 도구다. Step Functions와 비슷하지만 ML에 특화된 스텝(ProcessingStep, TrainingStep, ModelStep 등)을 제공한다.

    모델 배포 방식 4가지¶

    SageMaker 엔드포인트는 용도에 따라 네 가지 모드가 있다. 각각 과금 방식이 달라서 이걸 잘못 고르면 비용이 2~10배 차이난다.

    Real-time Inference¶

    가장 기본 형태. 인스턴스가 상시 떠 있고 HTTP 요청에 밀리초 단위로 응답한다. 레이턴시가 중요하고 트래픽이 꾸준한 경우에 쓴다. 인스턴스 시간당 과금이라 트래픽이 없어도 돈이 나간다.

    from sagemaker.pytorch import PyTorchModel

model = PyTorchModel(
    model_data="s3://my-bucket/model.tar.gz",
    role=role,
    framework_version="2.1",
    py_version="py310",
    entry_point="inference.py",
)

predictor = model.deploy(
    initial_instance_count=2,
    instance_type="ml.g5.xlarge",
    endpoint_name="my-model-endpoint",
)

    Serverless Inference¶

    요청이 올 때만 컨테이너가 뜨고, 유휴 시 내려간다. Lambda와 비슷한 과금 모델로, 추론 요청 수와 컴퓨팅 시간만큼만 돈을 낸다. 트래픽이 간헐적이거나 예측 불가능할 때 좋다.

    다만 콜드 스타트가 있다. 모델 크기가 크면 첫 요청이 수 초~수십 초 걸릴 수 있다. 큰 LLM을 Serverless로 올리면 거의 쓸 수 없는 수준이다. 현실적으로 모델 크기 수백 MB 이하의 경량 모델에만 쓴다.

    from sagemaker.serverless import ServerlessInferenceConfig

serverless_config = ServerlessInferenceConfig(
    memory_size_in_mb=4096,
    max_concurrency=20,
)

predictor = model.deploy(
    serverless_inference_config=serverless_config,
    endpoint_name="my-serverless-endpoint",
)

    Serverless는 GPU를 지원하지 않는다. CPU 기반 모델(전통적인 ML, 작은 임베딩 모델 등)에만 쓸 수 있다.

    Asynchronous Inference¶

    요청을 받아서 S3에 저장하고, 큐에 쌓아서 백그라운드로 처리한다. 처리 결과는 S3에 쓰고 SNS로 알림이 온다. 하나의 추론이 오래 걸리는 경우(수십 초~분 단위)에 쓴다. 타임아웃 없이 최대 1시간까지 처리 가능하다.

    트래픽이 없을 때 인스턴스를 0으로 내릴 수 있다(Auto Scaling 최소값 0 설정 가능). 이게 Real-time과의 큰 차이다. Real-time은 최소 1 이상을 유지해야 한다.

    Batch Transform¶

    엔드포인트를 만들지 않고, S3에 있는 대량의 데이터를 한 번에 추론한다. 배치 작업이 끝나면 인스턴스가 자동 종료된다. 예를 들어 매일 밤 전체 사용자에 대한 추천을 미리 계산해두는 경우에 쓴다.

    Batch Transform은 엔드포인트 유지 비용이 없어서 대량 일괄 추론에서는 가장 저렴하다. "실시간이 필요한가?"를 팀이 진지하게 따져보면, 생각보다 많은 경우에 Batch Transform으로도 충분하다.

    선택 기준¶

    flowchart TD
    A[추론 요구사항] --> B{실시간 필요?}
    B -->|예| C{트래픽 패턴}
    B -->|아니오| D{처리 시간}
    C -->|꾸준함| E[Real-time]
    C -->|간헐적/CPU 모델| F[Serverless]
    C -->|요청당 수십초 이상| G[Async]
    D -->|주기적 일괄| H[Batch Transform]
    D -->|온디맨드 대량| G

    Multi-Model Endpoint¶

    모델이 수십 개 이상인데 각각 트래픽이 적은 경우, 엔드포인트를 모델마다 따로 만들면 비용이 감당이 안 된다. 모델 100개면 인스턴스 100개 이상을 상시 띄워야 한다.

    Multi-Model Endpoint(MME)는 하나의 엔드포인트에 여러 모델을 올려두고, 요청 시 지정한 모델을 동적으로 로드한다. 자주 안 쓰는 모델은 메모리에서 언로드되고, 요청이 오면 S3에서 다시 로드한다.

    from sagemaker.multidatamodel import MultiDataModel

mme = MultiDataModel(
    name="tenant-models-mme",
    model_data_prefix="s3://my-bucket/tenant-models/",
    image_uri=container_uri,
    role=role,
)

predictor = mme.deploy(
    initial_instance_count=2,
    instance_type="ml.m5.xlarge",
    endpoint_name="tenant-models-endpoint",
)

response = predictor.predict(
    data=payload,
    target_model="tenant_42/model.tar.gz",
)

    주의할 점이 있다. 첫 호출 시 S3에서 모델을 내려받아 메모리에 올리는 시간이 걸린다. 모델 크기가 수 GB면 이 콜드 로드가 수 초~수십 초 걸린다. 사용자가 기다릴 수 없는 레이턴시라면 자주 쓰이는 모델은 warming 요청을 주기적으로 보내서 메모리에 남겨야 한다.

    또 모든 모델이 같은 컨테이너 이미지를 공유한다. 모델마다 프레임워크나 의존성이 다르면 Multi-Container Endpoint나 Inference Components를 써야 한다.

    Multi-Model Endpoint는 B2B SaaS에서 테넌트별 모델을 서빙할 때 특히 잘 맞는다. 테넌트마다 모델이 다르지만 활성 테넌트는 전체의 일부라 대부분의 모델이 유휴 상태인 경우다.

    Inference Components¶

    Inference Components는 비교적 최근에 추가된 방식인데, 하나의 엔드포인트에 서로 다른 컨테이너 이미지를 가진 모델 여러 개를 올릴 수 있다. Multi-Model Endpoint가 같은 이미지에 모델만 다른 경우라면, Inference Components는 모델별로 컨테이너·프레임워크·CPU·GPU 메모리 할당량을 따로 지정한다.

    sm_client.create_inference_component(
    InferenceComponentName="ic-llm-7b",
    EndpointName="shared-gpu-endpoint",
    VariantName="AllTraffic",
    Specification={
        "ModelName": "llm-7b-model",
        "ComputeResourceRequirements": {
            "NumberOfAcceleratorDevicesRequired": 1,
            "MinMemoryRequiredInMb": 16000,
        },
        "StartupParameters": {
            "ModelDataDownloadTimeoutInSeconds": 1200,
            "ContainerStartupHealthCheckTimeoutInSeconds": 1200,
        },
    },
    RuntimeConfig={
        "CopyCount": 1,
    },
)

    쓸모가 가장 큰 시나리오는 LLM 여러 개를 한 인스턴스에 패킹하는 경우다. ml.g5.12xlarge는 GPU 4장, 192GB GPU 메모리인데, 7B 모델 두 개와 13B 모델 한 개를 각각 다른 컨테이너로 올려 GPU 메모리를 나눠 쓰면 인스턴스를 분리해서 띄우는 것보다 훨씬 싸다.

    Inference Component 단위로 Auto Scaling도 가능하다. 특정 모델만 트래픽이 늘면 그 컴포넌트의 CopyCount만 증가시켜 같은 인스턴스 풀에 복제본을 더 띄운다. 인스턴스 자체의 스케일링은 별도로 동작한다.

    주의할 건 컴포넌트별 시작 시간이 길다는 점이다. 큰 모델(LLM)은 S3에서 가중치를 내려받는 데만 수 분 걸리니 ModelDataDownloadTimeoutInSeconds와 헬스체크 타임아웃을 충분히 길게 잡아야 한다. 기본값으로는 시작이 실패하는 경우가 흔하다.

    Auto Scaling¶

    엔드포인트 뒤 인스턴스 수를 트래픽에 따라 자동으로 조정한다. Application Auto Scaling 서비스와 연동된다.

    스케일링 메트릭으로 제일 흔히 쓰는 건 SageMakerVariantInvocationsPerInstance다. 인스턴스당 초당 요청 수로 기준을 잡는다.

    import boto3

client = boto3.client("application-autoscaling")

client.register_scalable_target(
    ServiceNamespace="sagemaker",
    ResourceId=f"endpoint/my-endpoint/variant/AllTraffic",
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
    MinCapacity=2,
    MaxCapacity=10,
)

client.put_scaling_policy(
    PolicyName="invocations-target",
    ServiceNamespace="sagemaker",
    ResourceId=f"endpoint/my-endpoint/variant/AllTraffic",
    ScalableDimension="sagemaker:variant:DesiredInstanceCount",
    PolicyType="TargetTrackingScaling",
    TargetTrackingScalingPolicyConfiguration={
        "TargetValue": 50.0,
        "PredefinedMetricSpecification": {
            "PredefinedMetricType": "SageMakerVariantInvocationsPerInstance",
        },
        "ScaleInCooldown": 300,
        "ScaleOutCooldown": 60,
    },
)

    실무 주의사항 몇 가지가 있다.

    스케일 인 쿨다운을 짧게 잡으면 안 된다. 트래픽이 잠깐 줄었다고 인스턴스를 빠르게 내리면, 다시 트래픽이 오를 때 콜드 스타트(새 인스턴스에 모델 로드)로 응답이 느려진다. 최소 5분 이상 둬야 한다.

    MinCapacity를 0으로 설정할 수 없다 (Real-time 엔드포인트의 경우). 트래픽이 0이어도 최소 1개 인스턴스는 떠 있어야 한다. 완전히 내리고 싶으면 Serverless나 Async를 쓰거나, Lambda로 야간에 엔드포인트 자체를 삭제하고 아침에 재생성하는 식으로 우회한다.

    GPU 인스턴스 스케일 아웃은 느리다. GPU 인스턴스(ml.g5, ml.p4 등)는 풀이 제한적이라 스케일 아웃 요청이 들어와도 인스턴스를 얻기까지 수 분이 걸릴 수 있다. 피크 예측이 가능하면 Scheduled Scaling으로 미리 띄워놓는 게 낫다.

    인스턴스 비용 감각¶

    비용 최적화 이야기를 하기 전에, 어떤 인스턴스가 얼마쯤 하는지 감을 잡아야 의사결정이 빨라진다. 정확한 가격은 리전과 시기에 따라 변하지만, us-east-1 기준 대략적인 시간당 단가는 다음 정도다(2026년 초 기준, 온디맨드 가격). 작업 전에 SageMaker Pricing 페이지에서 최신 단가를 확인하는 습관을 들여야 한다.

    카테고리 인스턴스 대략 단가($/h) 주 용도
    CPU 소형 ml.t3.medium 0.05 Studio 개발용
    CPU 일반 ml.m5.large 0.12 노트북, 작은 추론
    CPU 일반 ml.m5.xlarge 0.24 일반 추론
    CPU Graviton ml.m7g.xlarge 0.20 CPU 추론 비용 절감
    CPU 컴퓨팅 ml.c6i.2xlarge 0.43 CPU 헤비 추론
    GPU 소형 ml.g5.xlarge 1.41 7B 미만 LLM, 임베딩
    GPU 중형 ml.g5.2xlarge 1.69 7B~13B 모델
    GPU 멀티 ml.g5.12xlarge 7.09 LLM 호스팅
    GPU Inferentia ml.inf2.xlarge 0.99 Neuron 컴파일된 추론
    GPU 학습 ml.p4d.24xlarge ~37 A100 8장 분산 학습
    GPU 학습 ml.p5.48xlarge ~98 H100 8장 대형 학습

    이 표를 처음 보면 ml.p5.48xlarge가 시간당 100달러 가까이라는 게 비현실적으로 느껴진다. 한 달 24시간 켜두면 7만 달러다. 그래서 큰 학습은 반드시 일회성 Training Job으로 돌리고, 끝나는 즉시 자동 종료되도록 설계한다.

    엔드포인트 비용을 빠르게 추산하는 공식은 단순하다. 시간당 단가 × 24 × 30 × 인스턴스 수. ml.g5.xlarge 1대를 24시간 띄워두면 한 달 약 1015달러다. initial_instance_count=2로 시작하면 2030달러부터 출발한다. Auto Scaling으로 평균 3대가 떠 있으면 3000달러를 넘는다. 추론 트래픽 자체는 무료라는 점도 자주 까먹는데, 비용 계산에서 핵심은 "인스턴스가 켜져 있는 시간"뿐이다.

    학습 비용은 다르게 계산한다. 시간당 단가 × 학습 시간 × 인스턴스 수만 내면 된다. ml.g5.xlarge로 4시간짜리 학습을 100번 돌리면 564달러 수준이고, Spot을 쓰면 같은 작업을 100~200달러로 줄일 수 있다.

    그 외 SageMaker에 부가되는 비용도 무시하면 안 된다.

    • EBS: Studio Space, 노트북, 학습 작업이 사용하는 디스크. 보통 GB·월 0.10달러. 큰 데이터셋을 EBS에 캐싱해두면 무시 못한다.
    • S3 저장 및 PUT/GET: 모델 아티팩트, Data Capture, 체크포인트. 학습이 자주 도는 경우 PUT 요청 수가 많아져 청구가 의외로 늘어난다.
    • CloudWatch Logs: 추론 로그 수집·저장 비용. 뒤에서 별도로 다룬다.
    • NAT Gateway: VPC 안에 SageMaker 자원을 두면 외부 모델 가중치 다운로드가 NAT를 타서 GB당 비용이 나간다. Hugging Face에서 큰 모델을 자주 받으면 이 비용이 학습 비용 못지않게 나오는 경우가 있다.

    추론 비용 최적화¶

    SageMaker 비용의 대부분은 엔드포인트 인스턴스 시간이다. 여기서 돈을 아끼는 방법을 순서대로 시도한다.

    인스턴스 타입을 다시 본다. 초보자들이 무조건 ml.g5.xlarge 같은 비싼 GPU 인스턴스를 쓰는데, 모델이 작거나 CPU에서도 충분한 지연시간으로 돈다면 ml.c6i, ml.m6i 같은 CPU 인스턴스가 훨씬 싸다. CPU/GPU 둘 다 벤치마크를 돌려보고 결정해야 한다.

    Inferentia/Graviton을 고려한다. AWS가 설계한 Inferentia 칩(ml.inf1, ml.inf2)은 GPU 대비 절반 이하 가격에 비슷한 추론 성능을 낸다. 단, 모델을 Neuron SDK로 컴파일해야 해서 초기 작업이 필요하다. Transformer 모델은 대부분 지원되지만, 커스텀 연산이 있으면 컴파일이 안 될 수 있다. Graviton 기반 ml.c7g, ml.m7g도 CPU 추론에서 비용 대비 성능이 좋다.

    Savings Plan을 건다. 엔드포인트가 24시간 떠 있다면 SageMaker Savings Plan으로 40~60% 할인된다. 1년/3년 약정이고 약정한 인스턴스 시간만큼 할인 요금이 적용된다. 유휴 시간이 많은 개발용 엔드포인트에는 맞지 않는다.

    트래픽이 적으면 Serverless나 Async로 바꾼다. 하루 수백 건 수준이면 Real-time을 유지할 이유가 없다.

    엔드포인트를 공유한다. 모델이 여러 개면 Multi-Model Endpoint나 Inference Components로 하나의 인스턴스에 여러 모델을 올린다.

    Batch로 전환 가능한 것은 전환한다. 일 1회 일괄 처리로 충분한 건 Batch Transform으로 돌린다.

    학습 비용은 Spot으로 줄인다. Training Job에 use_spot_instances=True를 주면 같은 인스턴스를 50~90% 싸게 쓴다. 체크포인트만 잘 저장하면 중단되도 재개되니 대부분의 학습 워크로드에 적용 가능하다. 다만 짧은 실험성 학습은 Warm Pool과 같이 쓰기 어렵고 시작 대기가 추가될 수 있으니 무거운 학습에 우선 적용한다.

    Pipelines로 MLOps 구성¶

    Pipelines는 학습·평가·모델 등록·배포를 DAG로 묶는 도구다. Python SDK로 정의하고 실행 시점에 SageMaker가 각 스텝에 맞는 리소스를 띄운다.

    from sagemaker.workflow.pipeline import Pipeline
from sagemaker.workflow.steps import ProcessingStep, TrainingStep
from sagemaker.workflow.model_step import ModelStep
from sagemaker.workflow.condition_step import ConditionStep
from sagemaker.workflow.conditions import ConditionGreaterThan

preprocess_step = ProcessingStep(
    name="Preprocess",
    processor=sklearn_processor,
    code="preprocess.py",
    inputs=[ProcessingInput(source=raw_data_s3, destination="/opt/ml/processing/input")],
    outputs=[ProcessingOutput(output_name="train", source="/opt/ml/processing/train")],
)

train_step = TrainingStep(
    name="Train",
    estimator=estimator,
    inputs={
        "train": TrainingInput(
            s3_data=preprocess_step.properties.ProcessingOutputConfig.Outputs["train"].S3Output.S3Uri
        )
    },
)

evaluate_step = ProcessingStep(
    name="Evaluate",
    processor=sklearn_processor,
    code="evaluate.py",
    inputs=[
        ProcessingInput(
            source=train_step.properties.ModelArtifacts.S3ModelArtifacts,
            destination="/opt/ml/processing/model",
        ),
    ],
    property_files=[evaluation_report],
)

register_step = ModelStep(
    name="RegisterModel",
    step_args=model.register(
        content_types=["application/json"],
        response_types=["application/json"],
        inference_instances=["ml.m5.large"],
        model_package_group_name="my-model-group",
        approval_status="PendingManualApproval",
    ),
)

cond = ConditionGreaterThan(
    left=JsonGet(step_name="Evaluate", property_file=evaluation_report, json_path="metrics.accuracy"),
    right=0.85,
)

condition_step = ConditionStep(
    name="AccuracyCheck",
    conditions=[cond],
    if_steps=[register_step],
    else_steps=[],
)

pipeline = Pipeline(
    name="my-training-pipeline",
    steps=[preprocess_step, train_step, evaluate_step, condition_step],
)

pipeline.upsert(role_arn=role)
pipeline.start()

    핵심은 Model Registry와의 연동이다. 학습된 모델을 Model Package로 등록하고 승인 상태를 PendingManualApproval로 두면, 자동 학습이 돌아도 사람이 승인하기 전까지는 프로덕션에 배포되지 않는다. 승인되면 EventBridge를 통해 배포 Lambda가 트리거되어 스테이징 엔드포인트 → 카나리 → 프로덕션 순으로 배포하는 식으로 구성한다.

    Pipelines를 쓰다가 자주 겪는 문제는 캐싱이다. cache_config를 enabled=True로 두면 동일한 입력과 코드의 스텝은 이전 결과를 재사용한다. 빠른 반복에는 좋은데, 코드가 바뀌어도 캐시가 히트되는 경우가 가끔 있어서 의심되면 캐시를 꺼서 확인해야 한다.

    프로덕션 모니터링: Data Capture와 Model Monitor¶

    엔드포인트를 띄우는 순간부터 운영이 시작된다. 입력 분포가 학습 시점과 달라지는 데이터 드리프트는 모델을 조용히 망가뜨린다. SageMaker는 엔드포인트의 요청·응답을 S3로 자동 저장하는 Data Capture 기능을 제공한다.

    from sagemaker.model_monitor import DataCaptureConfig

data_capture_config = DataCaptureConfig(
    enable_capture=True,
    sampling_percentage=20,
    destination_s3_uri="s3://my-bucket/data-capture/my-endpoint",
    capture_options=["REQUEST", "RESPONSE"],
)

predictor = model.deploy(
    initial_instance_count=2,
    instance_type="ml.m5.xlarge",
    endpoint_name="my-endpoint",
    data_capture_config=data_capture_config,
)

    샘플링 비율을 100%로 두면 트래픽이 클 때 S3 저장 비용과 IO 부담이 커진다. 처음에는 5~20% 정도로 시작하고 필요할 때 올리는 게 낫다.

    Model Monitor는 캡처된 데이터를 베이스라인(학습 데이터의 통계 프로파일)과 비교해서 데이터 품질·모델 품질·바이어스·피처 어트리뷰션 드리프트를 주기적으로 검사한다. 결과는 CloudWatch 메트릭과 보고서로 나오고, 임계값을 넘으면 알람을 걸 수 있다.

    현실적으로 Model Monitor 자체가 ProcessingJob을 주기적으로 돌리는 구조라 비용이 따로 든다. 트래픽이 많지 않은 모델에는 굳이 안 쓰고, 캡처된 데이터를 자체 분석 파이프라인에서 처리하는 팀도 많다. 핵심은 "운영 중 입출력을 어딘가에 남겨놓는다"는 점이다. 운영 시작 후에 드리프트 의심이 생겼을 때 자료가 없으면 원인을 못 찾는다.

    실무에서 자주 놓치는 함정¶

    인스턴스 타입 선택¶

    인스턴스 타입은 학습과 추론을 분리해서 골라야 한다. 학습 때는 배치가 크고 메모리가 중요해서 GPU가 필요하지만, 추론 때는 배치가 1~수십 건이라 CPU로도 충분한 경우가 많다. 실무에서는 학습과 추론 모두 같은 ml.g5.xlarge를 쓰다가, 추론만 ml.c6i.2xlarge로 바꿔서 비용을 60% 줄인 사례가 흔하다.

    메모리 기반 모델(큰 Transformer)은 ml.g5 시리즈의 GPU 메모리 크기를 잘 봐야 한다. ml.g5.xlarge는 A10G 24GB인데, 모델이 20GB면 KV 캐시까지 들어가면 OOM 난다. 그럴 땐 ml.g5.2xlarge (같은 A10G 24GB지만 CPU 메모리가 더 큼)로는 해결이 안 되고, ml.g5.12xlarge 이상(A10G 4장, 96GB)으로 가거나 모델을 양자화해야 한다.

    Training Job에서 자주 쓰는 ml.p3.2xlarge는 V100 16GB인데, 최근 큰 모델에는 부족해서 ml.p4d.24xlarge(A100 40GB×8) 또는 ml.p5.48xlarge(H100 80GB×8)를 쓴다. 문제는 이 인스턴스들이 엄청나게 비싸고 (p5는 시간당 수십 달러) 쿼터 승인이 까다롭다.

    GPU 쿼터 문제¶

    신규 계정이나 새 리전에서 GPU 인스턴스를 못 띄우는 경우가 많다. 기본 쿼터가 0인 경우도 있다. ml.g5 같은 흔한 인스턴스도 프로덕션용 여러 대를 한 번에 띄우려 하면 쿼터가 부족하다.

    Service Quotas 콘솔에서 Amazon SageMaker를 검색하고, 인스턴스 타입별 "for endpoint usage"와 "for training job usage"를 따로 찾아야 한다. 쿼터 승인은 평균 수 시간~1영업일 걸리고, 큰 수량은 며칠 걸리기도 한다. 프로덕션 배포 일정이 급하면 미리 여유 있게 올려놔야 한다.

    리전별로 쿼터가 독립이라는 점도 주의해야 한다. us-east-1에서 잘 돌던 게 ap-northeast-2에서는 쿼터 부족으로 안 돌아가는 경우가 많다.

    IAM 역할 혼란¶

    SageMaker는 실행 역할(execution role)이 필수고, 이 역할에 S3 접근·ECR 접근·CloudWatch Logs 쓰기 권한이 있어야 한다. 처음 쓰는 사람들은 Studio 로그인 계정의 권한과 실행 역할을 헷갈린다. 학습 Job이 S3에서 데이터를 못 읽는다고 나오면 대부분 실행 역할의 S3 권한 문제다.

    특히 KMS로 암호화된 S3 버킷을 쓰면 실행 역할에 해당 KMS 키의 Decrypt 권한도 줘야 한다. 이걸 놓쳐서 원인 파악에 시간을 쓰는 경우가 많다.

    학습 데이터 전송 비용과 시간¶

    S3에서 학습 인스턴스로 데이터를 가져오는 방식이 세 가지다.

    • File mode: 학습 시작 시 전체 데이터를 인스턴스로 내려받는다. 작은 데이터에 적합.
    • Pipe mode: 스트리밍으로 받으면서 학습한다. 대용량에 유리하지만 프레임워크가 지원해야 한다.
    • FastFile mode: POSIX 파일시스템처럼 마운트해서 필요한 부분만 읽는다. 대용량에 가장 쓰기 편하다.

    수십~수백 GB 데이터를 File mode로 쓰면 학습 시작 전에 데이터 다운로드만 수십 분 걸린다. 이 시간도 인스턴스 과금에 포함된다. FastFile mode나 FSx for Lustre를 고려해야 한다.

    CloudWatch Logs 비용¶

    학습 Job과 엔드포인트 모두 로그를 CloudWatch Logs로 보낸다. 추론 로그를 너무 상세하게 남기면(요청/응답 전체 dump 등) 로그 수집·저장 비용이 추론 비용만큼 나오는 경우가 있다. 실제로 만난 사례 중에 로그 비용이 엔드포인트 비용의 1.5배가 나온 경우도 있었다.

    로그 보존 기간을 필요한 만큼만 설정하고, 상세 로그는 조건부로 남기거나 샘플링해야 한다.

    엔드포인트 업데이트 시 다운타임¶

    UpdateEndpoint로 모델을 업데이트할 때 SageMaker가 새 인스턴스를 먼저 띄우고 트래픽을 옮긴 뒤 기존 인스턴스를 내린다. 이 과정이 보통 수 분~10분 이상 걸린다. 트래픽이 몰리는 시간대에 업데이트하면 일시적으로 인스턴스가 2배로 떠서 비용이 튄다.

    Blue/Green 배포, 카나리 배포를 위해 BlueGreenUpdatePolicy와 트래픽 시프팅 설정을 쓸 수 있다. 자동 롤백 조건(알람 발동 시 롤백)도 함께 설정해두면 사고를 줄인다.

    트러블슈팅 사례¶

    실제로 자주 만나는 에러 메시지와 원인을 모았다. 검색했을 때 여러 페이지를 돌아다니지 않고 바로 해결할 수 있도록 정리했다.

    ResourceLimitExceeded¶

    학습 Job이나 엔드포인트 생성 직후 이 에러가 나오면 99% 쿼터 부족이다. 메시지 안에 ml.g5.xlarge for endpoint usage 같은 식으로 인스턴스 타입과 용도가 박혀 나오니, Service Quotas 콘솔에서 정확히 그 항목을 찾아 증액 요청을 넣는다. 신규 계정에서 GPU 인스턴스 쿼터는 0인 경우가 많아 첫 학습부터 막히는 일이 흔하다.

    ClientError: Failed to download data from s3://...¶

    Training Job 시작 직후 로그에 이 메시지가 뜨면 실행 역할의 S3 권한 문제다. 정확히 어떤 권한이 빠졌는지 확인하려면 메시지에 같이 나오는 AccessDenied 본문을 본다. 단순히 s3:GetObject만 빠진 경우도 있고, 버킷 정책에서 특정 VPC Endpoint만 허용하는 경우도 있다. KMS 암호화 버킷이라면 kms:Decrypt를 빼먹은 경우가 많다.

    {
  "Effect": "Allow",
  "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
  "Resource": "arn:aws:kms:ap-northeast-2:123456789012:key/abc-..."
}

    CannotPullContainerError: pull access denied¶

    빌트인 컨테이너가 아닌 ECR의 사설 이미지를 쓸 때 자주 발생한다. SageMaker Execution Role에 ecr:GetAuthorizationToken, ecr:BatchGetImage, ecr:GetDownloadUrlForLayer 권한이 있어야 한다. 또 ECR 리포지터리 정책이 SageMaker 서비스에 풀 권한을 줘야 하는 경우도 있다. 같은 계정·같은 리전이면 보통 Role 권한만으로 되지만, 다른 계정의 ECR을 참조하면 리포지터리 정책 추가가 필수다.

    Endpoint InService 안 되고 Failed로 떨어짐¶

    CloudWatch Logs /aws/sagemaker/Endpoints/<endpoint-name>에서 model-server나 python 로그를 본다. 가장 흔한 원인은 inference.py의 model_fn이 모델 로드 중 예외를 던지는 경우다. 큰 모델을 메모리에 못 올려서 OOM이 나거나, model.tar.gz 안의 파일 경로 구조가 컨테이너가 기대하는 구조와 안 맞을 때다.

    model.tar.gz는 컨테이너 안 /opt/ml/model/에 풀린다. PyTorch의 경우 model.pth(또는 pytorch_model.bin)와 code/inference.py가 그 경로 바로 아래 있어야 한다. tar 안에 디렉토리 한 단계가 더 들어 있으면 못 찾는다. 만들 때 tar -czf model.tar.gz -C model_dir . 식으로 디렉토리 안에서 묶어야 한다.

    ContainerStartupHealthCheckTimeoutInSeconds로 시작 실패¶

    큰 LLM(7B 이상)을 엔드포인트에 올리면 모델 로드 자체가 5~10분 이상 걸린다. 기본 헬스체크 타임아웃이 짧아서 모델이 다 안 올라온 상태에서 컨테이너가 죽었다고 판단된다. ProductionVariants 또는 Inference Components의 ContainerStartupHealthCheckTimeoutInSeconds와 ModelDataDownloadTimeoutInSeconds를 1200~3600초로 늘려야 한다.

    추론 응답이 갑자기 502/504¶

    엔드포인트 자체는 살아 있는데 일부 요청이 게이트웨이 에러로 떨어지면 두 가지를 본다. 첫째, 요청 페이로드가 6MB를 넘는지. SageMaker Real-time 엔드포인트는 동기 요청 페이로드 한도가 6MB다. 이미지 일괄이나 긴 텍스트 일괄을 한 번에 보내면 자른다. 둘째, 추론 타임아웃이 60초를 넘는지. Real-time은 60초 제한이고, 그 이상은 Async나 큰 요청 분할로 돌려야 한다.

    Multi-Model Endpoint에서 첫 호출이 느림¶

    S3에서 모델을 콜드 로드하는 시간이다. 자주 쓰는 모델이 정해져 있다면 Lambda로 5분 주기 warming 요청을 보내서 메모리에 잡아둔다. 또는 ModelCacheSetting을 조정해서 캐시 크기를 늘리면 LRU에서 밀려나가는 빈도가 줄어든다.

    학습 Spot 인스턴스가 자꾸 회수당해서 학습이 안 끝남¶

    MaxWaitTimeInSeconds(max_wait)를 짧게 잡았거나, GPU 풀 자체가 빡빡한 시간대에 큰 인스턴스를 요청한 경우다. max_wait을 충분히 길게 잡고, 체크포인트 저장 주기를 짧게(에폭당 1회 → 스텝 100~500마다 1회) 가져가면 회수 후 재개 시 손실이 적다. 정말 안 되면 일부 작업만 온디맨드로 돌리는 게 결국 더 싸다.

    Studio JupyterLab 커널이 갑자기 죽음¶

    대부분 OOM이다. Top 셀에서 !free -h로 메모리 상태를 확인하거나, psutil로 사용량을 모니터링한다. pandas로 큰 parquet을 통째 로드하다 죽는 경우가 흔하다. PyArrow의 dataset.scanner API로 컬럼 단위로 읽거나, Dask로 분산 처리한다. 그래도 안 되면 인스턴스 타입을 한 단계 키운다(메모리 위주면 ml.r5 시리즈 고려).

    ValidationError: Endpoint configuration "..." is in use¶

    엔드포인트가 사용 중인 EndpointConfig는 삭제할 수 없다. 신규 EndpointConfig를 만들어서 UpdateEndpoint로 교체한 뒤, 기존 EndpointConfig를 지운다. 자동화 스크립트에서 이 순서를 헷갈리면 배포가 막힌다.

    비용이 갑자기 튀는데 원인을 모르겠음¶

    Cost Explorer에서 Service: SageMaker로 필터링하고, Usage Type 그룹핑을 켠다. <Region>-Hosting:ml.g5.xlarge 같은 항목이 평소보다 크면 엔드포인트가 자고 있어야 할 시간에 떠 있는 거고, Studio-JupyterLab:ml.g5.xlarge 같은 게 있으면 누군가 GPU 노트북을 켜놓고 퇴근한 거다. 태깅(Project, Owner)을 강제하면 누구 책임인지 추적이 쉽다.

    정리¶

    SageMaker는 편리한 만큼 비용이 쉽게 튀는 서비스다. 엔드포인트를 띄울 때는 트래픽 패턴과 레이턴시 요구사항을 먼저 확인해서 Real-time, Serverless, Async, Batch Transform 중 맞는 것을 골라야 한다. 모델이 여러 개라면 Multi-Model Endpoint나 Inference Components로 인스턴스를 공유하고, 학습 워크로드는 Spot 인스턴스와 Warm Pool로 비용을 줄인다. 인스턴스 타입은 학습용과 추론용을 분리해서 고르고, CPU로도 충분한지 반드시 검토한다. GPU 쿼터는 미리 신청해두고, 리전별로 별개라는 점을 잊지 말아야 한다.

    MLOps를 꾸리려면 Pipelines + Model Registry로 학습-승인-배포를 분리해야 한다. 수동 승인 게이트를 두면 자동 학습이 폭주해도 프로덕션에 잘못된 모델이 배포되는 사고를 막을 수 있다. 운영 단계에서는 Data Capture로 입출력을 S3에 남겨서 드리프트 분석에 대비한다. Studio Spaces의 유휴 커널 종료, 엔드포인트 태그 기반 정리, Savings Plan 적용은 운영 초기에 챙겨두면 매달 수백 달러 이상을 아낄 수 있는 기본기다.
