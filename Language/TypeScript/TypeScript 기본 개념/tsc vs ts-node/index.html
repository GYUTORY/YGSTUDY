    tsc와 ts-node의 차이¶

    배경¶

    TypeScript로 개발할 때 코드를 실행하는 방법은 크게 두 가지입니다. 하나는 TypeScript를 JavaScript로 변환한 후 실행하는 방법(tsc)이고, 다른 하나는 TypeScript를 바로 실행하는 방법(ts-node)입니다.

    tsc가 필요한 이유¶

    tsc는 TypeScript의 공식 컴파일러입니다. TypeScript 코드를 JavaScript로 변환하는 것이 주요 역할이지만, 그 과정에서 다음과 같은 중요한 기능들을 수행합니다.

    타입 검사와 정적 분석 컴파일 시점에 코드의 타입 오류를 감지합니다. 런타임에 발생할 수 있는 오류를 미리 찾아내어 안정성을 높입니다. 또한 코드 구조를 분석하여 잠재적인 문제를 경고해줍니다.

    프로덕션 배포 브라우저나 Node.js 환경에서 실행 가능한 JavaScript 파일을 생성합니다. 이 과정에서 타입 정보는 제거되고, 타겟 환경에 맞는 JavaScript 버전으로 변환됩니다. 최적화된 코드를 만들어 배포 환경에서 효율적으로 동작하게 합니다.

    코드 변환과 호환성 최신 JavaScript 문법을 구버전 JavaScript로 변환할 수 있습니다. 예를 들어 async/await 같은 최신 문법을 ES5 환경에서도 동작하도록 변환합니다. 이를 통해 다양한 실행 환경에서 코드를 동작시킬 수 있습니다.

    ts-node가 필요한 이유¶

    ts-node는 개발 과정에서 생산성을 높이기 위한 도구입니다. TypeScript 파일을 중간 과정 없이 바로 실행할 수 있게 해줍니다.

    개발 속도 향상 코드를 수정할 때마다 컴파일하고 실행하는 과정은 번거롭습니다. ts-node는 이 과정을 하나로 합쳐서 즉시 결과를 확인할 수 있게 합니다. 특히 작은 변경사항을 테스트할 때 유용합니다.

    REPL 환경 대화형 실행 환경을 제공하여 TypeScript 코드를 즉석에서 테스트할 수 있습니다. JavaScript의 Node.js REPL처럼 TypeScript를 바로 실험해볼 수 있는 환경을 만들어줍니다.

    테스트와 디버깅 테스트 코드를 작성하고 실행할 때 컴파일 단계를 거치지 않아 빠른 피드백을 받을 수 있습니다. 디버깅 시에도 TypeScript 코드를 직접 실행하면서 문제를 파악할 수 있습니다.

    핵심¶

    1. tsc의 동작 방식¶

    tsc는 TypeScript 소스 코드를 읽어서 JavaScript 파일을 생성합니다. 이 과정은 크게 세 단계로 나뉩니다.

    파싱과 타입 검사 먼저 TypeScript 코드를 분석하여 추상 구문 트리(AST)를 만듭니다. 이 과정에서 문법 오류가 있는지 확인합니다. 그 다음 타입 정보를 기반으로 코드의 타입 안정성을 검사합니다. 인터페이스, 제네릭, 타입 별칭 등 TypeScript의 타입 시스템을 모두 검증합니다.

    변환과 최적화 타입 검사가 완료되면 TypeScript 고유의 문법을 제거합니다. 인터페이스, 타입 별칭, enum의 타입 정보 등은 런타임에 필요 없으므로 삭제됩니다. 그리고 설정된 타겟 JavaScript 버전에 맞게 코드를 변환합니다. 예를 들어 ES2022 문법을 ES5로 변환할 수 있습니다.

    파일 생성 변환된 JavaScript 코드를 파일로 저장합니다. 설정에 따라 소스맵(.map 파일)과 타입 선언 파일(.d.ts)도 함께 생성할 수 있습니다. 소스맵은 디버깅 시 원본 TypeScript 코드를 참조할 수 있게 해주고, 타입 선언 파일은 다른 프로젝트에서 이 코드를 사용할 때 타입 정보를 제공합니다.

    # 기본 사용법
npm install -g typescript

# 단일 파일 컴파일
tsc app.ts

# 프로젝트 전체 컴파일
tsc

    컴파일 예시 

    // app.ts
interface User {
    id: number;
    name: string;
}

const user: User = { id: 1, name: '홍길동' };
console.log(user.name);

    위 코드를 컴파일하면 interface와 타입 정보가 제거된 JavaScript가 생성됩니다:

    // app.js
"use strict";
const user = { id: 1, name: '홍길동' };
console.log(user.name);

    2. ts-node의 동작 방식¶

    ts-node는 TypeScript 파일을 메모리상에서 즉시 컴파일하고 실행합니다. 별도의 JavaScript 파일을 생성하지 않습니다.

    JIT 컴파일 ts-node는 Just-In-Time 방식으로 동작합니다. TypeScript 파일을 읽으면 내부적으로 tsc를 호출하여 JavaScript로 변환하지만, 그 결과를 파일로 저장하지 않고 메모리에 유지합니다. 그리고 변환된 JavaScript를 Node.js에서 바로 실행합니다.

    캐싱 메커니즘 매번 전체 파일을 컴파일하면 느리므로, ts-node는 변경되지 않은 파일은 캐시를 사용합니다. 파일이 수정되었을 때만 다시 컴파일합니다. 이를 통해 초기 실행 후에는 빠른 속도를 유지할 수 있습니다.

    모듈 후킹 Node.js의 모듈 시스템을 확장하여 .ts 파일을 인식하게 만듭니다. require()나 import를 통해 TypeScript 파일을 불러올 때 자동으로 컴파일하여 제공합니다. 따라서 JavaScript와 TypeScript 파일을 섞어서 사용할 수 있습니다.

    # 기본 사용법
npm install -g ts-node

# TypeScript 파일 직접 실행
ts-node app.ts

# REPL 모드
ts-node

    3. tsconfig.json의 역할¶

    두 도구 모두 tsconfig.json 설정 파일을 참조합니다. 이 파일은 TypeScript 컴파일러의 동작 방식을 제어합니다.

    컴파일 옵션 compilerOptions에서 타겟 JavaScript 버전, 모듈 시스템, 출력 디렉토리 등을 지정합니다. strict 옵션을 활성화하면 엄격한 타입 검사를 수행합니다. sourceMap 옵션으로 디버깅을 위한 소스맵 생성 여부를 결정합니다.

    파일 포함/제외 include로 컴파일 대상 파일을 지정하고, exclude로 제외할 파일을 명시합니다. 일반적으로 node_modules나 빌드 결과물 디렉토리는 제외합니다.

    ts-node 특화 설정 ts-node 전용 설정을 추가할 수 있습니다. transpileOnly 옵션을 활성화하면 타입 검사를 건너뛰고 변환만 수행하여 실행 속도를 높일 수 있습니다.

    {
  "compilerOptions": {
    "target": "ES2022",
    "module": "CommonJS",
    "outDir": "./dist",
    "strict": true
  },
  "ts-node": {
    "transpileOnly": true  // 빠른 실행을 위해 타입 검사 생략
  }
}

    예시¶

    실제 개발 워크플로우¶

    일반적인 TypeScript 프로젝트에서 두 도구를 함께 사용하는 방법을 살펴보겠습니다.

    개발 단계 코드를 작성하면서 빠른 테스트가 필요할 때는 ts-node를 사용합니다. 파일을 수정하고 즉시 실행해보면서 결과를 확인할 수 있습니다. 예를 들어 새로운 함수를 작성했다면 ts-node app.ts로 바로 실행해서 동작을 확인합니다.

    # 개발 중 빠른 테스트
ts-node src/index.ts

# 코드 수정 후 즉시 재실행
ts-node src/index.ts

    테스트 단계 단위 테스트를 작성할 때도 ts-node가 유용합니다. 테스트 프레임워크와 함께 사용하면 TypeScript 테스트 코드를 직접 실행할 수 있습니다. 컴파일 단계를 거치지 않아 테스트 실행 속도가 빠릅니다.

    // package.json
{
  "scripts": {
    "dev": "ts-node src/index.ts",
    "build": "tsc",
    "start": "node dist/index.js"
  }
}

    배포 단계 프로덕션 환경에 배포할 때는 반드시 tsc로 컴파일합니다. 타입 검사를 완료하고, 최적화된 JavaScript 파일을 생성합니다. 생성된 JavaScript는 타입 정보가 없어 더 작고 빠르게 실행됩니다.

    # 프로덕션 빌드
tsc

# 컴파일된 JavaScript 실행
node dist/index.js

    성능과 최적화¶

    tsc의 성능 특성 tsc는 전체 프로젝트를 컴파일하므로 초기에는 시간이 걸립니다. 하지만 한 번 컴파일하면 그 결과물을 계속 사용할 수 있습니다. 대규모 프로젝트에서는 증분 컴파일 기능을 활용하면 변경된 부분만 다시 컴파일하여 속도를 높일 수 있습니다.

    // tsconfig.json
{
  "compilerOptions": {
    "incremental": true,  // 증분 컴파일 활성화
    "tsBuildInfoFile": "./.tsbuildinfo"
  }
}

    ts-node의 성능 특성 ts-node는 실행할 때마다 컴파일 과정을 거칩니다. 캐싱을 사용하지만 프로덕션 환경에서는 권장하지 않습니다. 개발 환경에서 속도를 높이려면 transpileOnly 옵션을 사용할 수 있습니다. 이는 타입 검사를 건너뛰고 변환만 수행하여 실행 속도를 크게 향상시킵니다.

    // tsconfig.json
{
  "ts-node": {
    "transpileOnly": true,  // 타입 검사 생략으로 속도 향상
    "files": false
  }
}

    언제 어떤 도구를 사용할까 개발 중에는 ts-node로 빠르게 코드를 테스트합니다. 하지만 주기적으로 tsc를 실행하여 타입 오류가 없는지 확인하는 것이 좋습니다. CI/CD 파이프라인에서는 항상 tsc로 빌드하여 타입 안정성을 보장합니다. 이렇게 하면 개발 속도와 코드 품질을 모두 유지할 수 있습니다.

    운영 팁¶

    타입 검사와 실행 속도의 균형¶

    개발하다 보면 타입 검사와 실행 속도 사이에서 고민하게 됩니다. ts-node는 기본적으로 타입 검사를 수행하면서 실행하기 때문에 느릴 수 있습니다.

    transpileOnly 옵션 이 옵션을 활성화하면 타입 검사를 건너뛰고 단순히 TypeScript를 JavaScript로 변환만 합니다. 실행 속도가 크게 향상되지만, 타입 오류를 감지하지 못합니다. 따라서 개발 중에는 transpileOnly를 사용하고, 커밋 전에는 tsc로 타입 검사를 수행하는 것이 좋습니다.

    캐싱 메커니즘 ts-node는 컴파일 결과를 캐시에 저장합니다. 파일이 변경되지 않으면 캐시된 결과를 재사용하여 빠르게 실행됩니다. 캐시 디렉토리를 지정하면 여러 실행 간에도 캐시를 공유할 수 있습니다.

    # 캐시 디렉토리 지정
ts-node --cachedir ./node_modules/.cache/ts-node app.ts

    에러 처리 전략¶

    타입 오류와 런타임 오류의 차이 TypeScript의 타입 시스템은 컴파일 시점의 오류를 잡아냅니다. 하지만 런타임에 발생하는 오류는 다릅니다. tsc는 타입 오류가 있으면 컴파일을 중단하지만, ts-node는 설정에 따라 타입 오류가 있어도 실행을 계속할 수 있습니다.

    엄격 모드 설정 tsconfig.json의 strict 옵션은 타입 검사를 엄격하게 수행합니다. 이를 활성화하면 더 많은 오류를 사전에 발견할 수 있습니다. noImplicitAny, strictNullChecks 같은 세부 옵션도 함께 활용하면 코드의 안정성이 높아집니다.

    타입 검사만 수행하기 코드를 컴파일하지 않고 타입 검사만 하고 싶을 때가 있습니다. tsc --noEmit 명령을 사용하면 JavaScript 파일을 생성하지 않고 타입 검사만 수행합니다. CI/CD 파이프라인에서 타입 검사 단계로 활용하기 좋습니다.

    # 타입 검사만 수행
tsc --noEmit

    상황 추천 도구 이유

    정리¶

    tsc와 ts-node는 서로 대체하는 관계가 아니라 보완하는 관계입니다.

    개발할 때는 ts-node로 빠르게 코드를 작성하고 테스트합니다. 수정사항을 즉시 확인할 수 있어 생산성이 높아집니다.

    하지만 프로덕션 환경에서는 반드시 tsc로 빌드해야 합니다. 타입 검사를 완료하고 최적화된 코드를 생성하여 안정성과 성능을 보장합니다.
