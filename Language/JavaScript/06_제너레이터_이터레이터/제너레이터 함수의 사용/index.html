    JavaScript 제너레이터(Generator) 함수 가이드¶

    1. 제너레이터 함수란?¶

    제너레이터 함수는 ES6에서 도입된 특별한 함수로, 함수의 실행을 일시 중지하고 나중에 다시 재개할 수 있는 기능을 제공합니다. 이를 통해 비동기 프로그래밍을 더 쉽고 직관적으로 작성할 수 있게 되었습니다.

    1.1 기본 문법¶

    제너레이터 함수는 function* 키워드를 사용하여 선언합니다:

    function* generatorFunction() {
    yield 1;
    yield 2;
    yield 3;
}

    2. 제너레이터의 핵심 개념¶

    2.1 yield 키워드¶

    yield 키워드는 제너레이터 함수의 실행을 일시 중지하고 값을 반환합니다. 다음 호출 시 중단된 지점부터 실행을 재개합니다.

    function* numberGenerator() {
    console.log('시작');
    yield 1;
    console.log('첫 번째 yield 이후');
    yield 2;
    console.log('두 번째 yield 이후');
    yield 3;
    console.log('종료');
}

const generator = numberGenerator();
console.log(generator.next()); // { value: 1, done: false }
console.log(generator.next()); // { value: 2, done: false }
console.log(generator.next()); // { value: 3, done: false }
console.log(generator.next()); // { value: undefined, done: true }

    2.2 next() 메서드¶

    제너레이터 객체의 next() 메서드는 다음 yield 표현식까지 실행하고, { value: 값, done: boolean } 형태의 객체를 반환합니다.

    function* fibonacci() {
    let [prev, curr] = [0, 1];
    while (true) {
        yield curr;
        [prev, curr] = [curr, prev + curr];
    }
}

const fib = fibonacci();
console.log(fib.next().value); // 1
console.log(fib.next().value); // 1
console.log(fib.next().value); // 2
console.log(fib.next().value); // 3
console.log(fib.next().value); // 5

    제너레이터 객체는 한 번 쓰면 끝이다. 함수가 아니라 진행 중인 상태이기 때문에 되감을 방법이 없다.

    function* nums() { yield 1; yield 2; }
const gn = nums();

[...gn];   // [1, 2]
[...gn];   // []   ← 두 번째는 비어 있다
gn.next(); // { value: undefined, done: true }

    이걸로 실제로 겪는 상황은 이렇다. 제너레이터를 변수에 담아 두고 for...of 로 한 번 돌린 뒤, 다른 곳에서 같은 변수를 다시 돌리면 아무것도 안 나온다. 에러가 없어서 "데이터가 비어 있다"로 오진하기 쉽다. 여러 번 순회해야 하면 제너레이터 객체가 아니라 제너레이터 함수를 넘기고 쓰는 쪽에서 nums() 로 새로 만들거나, 애초에 배열로 받아 둔다.

    next() 에 인자를 넣는 것도 첫 호출만 다르다.

    function* h() { const x = yield 1; console.log(x); }
const gh = h();
gh.next('무시됨');   // 이 값은 어디에도 전달되지 않는다
gh.next('전달됨');   // '전달됨' 이 x 에 들어간다

    첫 next() 는 함수를 시작시키는 호출이라 값을 받을 yield 가 아직 없다. 두 번째부터 직전 yield 의 결과가 된다. 값이 한 칸씩 밀린 것처럼 보이는 코드는 대개 이 규칙을 놓친 것이다.

    3. 제너레이터 vs async/await¶

    3.1 기본적인 차이점¶

    // async/await 방식
async function fetchData() {
    const user = await fetchUser(1);
    const posts = await fetchUserPosts(user.id);
    return posts;
}

// 제너레이터 방식
function* fetchDataGenerator() {
    const user = yield fetchUser(1);
    const posts = yield fetchUserPosts(user.id);
    return posts;
}

    주요 차이점: 1. 실행 제어: - async/await: 자동으로 Promise를 처리 - 제너레이터: 수동으로 실행 흐름 제어 가능

    1. 메모리 효율성:
    2. async/await: 모든 Promise가 메모리에 유지

    3. 제너레이터: 필요한 시점에만 데이터 생성

    4. 유연성:

    5. async/await: Promise 기반으로만 동작
    6. 제너레이터: 다양한 데이터 타입 yield 가능

    3.2 실제 사용 사례 비교¶

    3.2.1 데이터 스트림 처리¶

    // async/await 방식
async function processStreamAsync() {
    const stream = await getDataStream();
    for await (const chunk of stream) {
        await processChunk(chunk);
    }
}

// 제너레이터 방식
function* processStreamGenerator() {
    const stream = yield getDataStream();
    for (const chunk of stream) {
        yield processChunk(chunk);
    }
}

    3.2.2 무한 시퀀스¶

    // async/await는 무한 시퀀스에 적합하지 않음
async function* infiniteSequenceAsync() {
    let i = 0;
    while (true) {
        await new Promise(resolve => setTimeout(resolve, 1000));
        yield i++;
    }
}

// 제너레이터는 무한 시퀀스에 적합
function* infiniteSequenceGenerator() {
    let i = 0;
    while (true) {
        yield i++;
    }
}

    3.3 성능 비교¶

    // async/await 방식
async function measureAsyncPerformance() {
    console.time('async');
    const results = [];
    for (let i = 0; i < 1000; i++) {
        results.push(await someAsyncOperation());
    }
    console.timeEnd('async');
    return results;
}

// 제너레이터 방식
function* measureGeneratorPerformance() {
    console.time('generator');
    for (let i = 0; i < 1000; i++) {
        yield someAsyncOperation();
    }
    console.timeEnd('generator');
}

    이 두 코드는 비교 대상이 아니다. 위쪽은 1,000개의 비동기 작업을 끝까지 기다리고, 아래쪽은 someAsyncOperation() 을 호출해 프로미스를 내놓기만 하고 결과를 기다리지 않는다. 하는 일이 다르니 시간이 다른 것은 당연하다.

    게다가 아래 제너레이터의 console.timeEnd 는 소비자가 1,000번 next() 를 다 부른 뒤에야 실행된다. 아무도 안 부르면 영영 안 찍히고, 천천히 부르면 소비자가 쉰 시간까지 포함된다. 제너레이터 안에서 잰 시간은 제너레이터의 시간이 아니라 소비자의 시간이다.

    같은 이유로 위쪽 §3.1 의 "async/await 는 모든 Promise 가 메모리에 유지"도 맞지 않는다. for 안에서 await 로 하나씩 처리하면 앞의 프로미스는 처리된 뒤 참조가 끊긴다. 한꺼번에 만들어 두는 것은 Promise.all 을 쓸 때이고 그건 문법이 아니라 코드의 선택이다.

    제너레이터를 고를 진짜 이유는 속도나 메모리가 아니라 누가 진행을 통제하느냐다. async/await 는 함수가 스스로 끝까지 달리고, 제너레이터는 소비자가 한 걸음씩 시킨다. 중간에 멈추고 취소하고 값을 되먹여야 하는 흐름이면 제너레이터가 맞고, 그렇지 않으면 async/await 가 짧고 에러 처리도 자연스럽다.

    바로 아래 §3.2.2 의 서술도 다시 볼 만하다. "async/await 는 무한 시퀀스에 적합하지 않다"고 써 놓고 예제는 async function* — 비동기 제너레이터다. 비동기 무한 시퀀스는 그쪽이 정답이고, for await...of 로 소비한다. 동기 제너레이터와 대립하는 개념이 아니라 둘을 합친 것이다.

    4. 제너레이터의 고급 활용¶

    4.1 제너레이터와 Promise 조합¶

    function* asyncOperation() {
    try {
        const user = yield fetchUser(1);
        const posts = yield fetchUserPosts(user.id);
        const comments = yield fetchPostComments(posts[0].id);

        return {
            user,
            posts,
            comments
        };
    } catch (error) {
        console.error('작업 실패:', error);
    }
}

// 제너레이터 실행을 위한 헬퍼 함수
async function runAsyncGenerator(generator) {
    const iterator = generator();

    try {
        while (true) {
            const { value, done } = iterator.next();
            if (done) return value;

            const result = await value;
            iterator.next(result);
        }
    } catch (error) {
        iterator.throw(error);
    }
}

    이 러너는 동작하지 않는다. 한 번 도는 동안 next() 를 두 번 호출한다.

    const { value, done } = iterator.next();   // ① 값을 꺼내고
const result = await value;
iterator.next(result);                     // ② 결과를 넣어 재개하는데, 그 반환값을 버린다

    ②에서 제너레이터가 다음 yield 까지 진행하며 내놓은 값이 버려지고, 루프가 다시 ①을 부르면 인자 없이 또 재개된다. 결과적으로 값이 하나 걸러 사라진다.

    function* g() {
  const a = yield 'A';  console.log(a);
  const b = yield 'B';  console.log(b);
}

// 문서의 러너:   a = 'A',  b = undefined
// 올바른 러너:   a = 'A',  b = 'B'

    호출은 한 바퀴에 한 번이어야 하고, 보낼 값을 다음 회차로 넘겨야 한다.

    async function run(genFn) {
  const it = genFn();
  let sent;
  while (true) {
    const { value, done } = it.next(sent);
    if (done) return value;
    sent = await value;
  }
}

    catch 절도 문제가 있다. iterator.throw(error) 는 제너레이터 안으로 에러를 되던지는 것이라, 제너레이터가 그 에러를 잡지 못하면 runAsyncGenerator 밖으로 다시 던져진다. 잡았다고 생각한 자리에서 다시 터진다. 그리고 제너레이터가 잡아서 복구했다면 throw() 가 돌려주는 {value, done} 을 봐야 하는데 그것도 버리고 있다. 실행 흐름이 여기서 그냥 끝난다.

    이 러너를 제대로 짜기 어렵다는 것 자체가 async/await 가 나온 이유다. co 같은 라이브러리가 하던 일을 언어가 흡수했다. 제너레이터로 비동기를 굴리는 코드를 지금 새로 쓸 일은 없고, 옛 코드를 읽을 때만 필요하다.

    4.2 제너레이터 위임 (Generator Delegation)¶

    function* subGenerator() {
    yield 1;
    yield 2;
    yield 3;
}

function* mainGenerator() {
    yield '시작';
    yield* subGenerator(); // 제너레이터 위임
    yield '종료';
}

const gen = mainGenerator();
console.log(gen.next().value); // '시작'
console.log(gen.next().value); // 1
console.log(gen.next().value); // 2
console.log(gen.next().value); // 3
console.log(gen.next().value); // '종료'

    yield* 는 값을 흘려보내기만 하는 게 아니라 하위 제너레이터의 return 값을 표현식의 결과로 준다.

    function* sub()  { yield 'a'; return 'SUBRET'; }
function* main() { const r = yield* sub(); console.log(r); }   // 'SUBRET'

    yield 하는 값과 return 하는 값이 서로 다른 통로라는 뜻이다. 이 차이는 for...of 에서 드러난다.

    function* g() { yield 1; yield 2; return 'RET'; }

[...g()];                 // [1, 2]        ← 'RET' 이 없다
for (const v of g()) {}   // 1, 2 만 방문

    return 값은 { value: 'RET', done: true } 로 마지막에 딸려 나오는데, for...of 와 스프레드는 done: true 인 순간 멈추면서 그 값을 버린다. 제너레이터에서 "최종 결과"를 return 으로 내보내고 for...of 로 받으려 하면 아무것도 안 온다. 소비자가 for...of 라면 결과도 yield 해야 한다.

    return 값을 쓰려면 next() 를 직접 부르거나 yield* 로 위임받는 쪽뿐이다.

    5. 실제 사용 사례¶

    5.1 상태 관리 시스템¶

    function* stateManager() {
    let state = {
        count: 0,
        isRunning: false,
        history: []
    };

    while (true) {
        const action = yield state;

        switch (action.type) {
            case 'INCREMENT':
                state = {
                    ...state,
                    count: state.count + 1,
                    history: [...state.history, 'INCREMENT']
                };
                break;
            case 'DECREMENT':
                state = {
                    ...state,
                    count: state.count - 1,
                    history: [...state.history, 'DECREMENT']
                };
                break;
            case 'TOGGLE':
                state = {
                    ...state,
                    isRunning: !state.isRunning,
                    history: [...state.history, 'TOGGLE']
                };
                break;
            case 'UNDO':
                if (state.history.length > 0) {
                    const lastAction = state.history[state.history.length - 1];
                    state = {
                        ...state,
                        history: state.history.slice(0, -1)
                    };
                    // 이전 상태로 되돌리기
                    if (lastAction === 'INCREMENT') state.count--;
                    if (lastAction === 'DECREMENT') state.count++;
                    if (lastAction === 'TOGGLE') state.isRunning = !state.isRunning;
                }
                break;
        }
    }
}

    5.2 데이터 파이프라인¶

    function* dataPipeline() {
    // 데이터 수집
    const rawData = yield fetchData();

    // 데이터 전처리
    const processedData = yield* preprocessData(rawData);

    // 데이터 변환
    const transformedData = yield* transformData(processedData);

    // 데이터 저장
    yield saveData(transformedData);
}

function* preprocessData(data) {
    for (const item of data) {
        yield {
            ...item,
            timestamp: new Date(),
            processed: true
        };
    }
}

function* transformData(data) {
    for (const item of data) {
        yield {
            id: item.id,
            value: item.value * 2,
            metadata: {
                processed: item.processed,
                timestamp: item.timestamp
            }
        };
    }
}

    6. 주의사항과 모범 사례¶

    6.1 메모리 관리¶

    function* memoryEfficientGenerator() {
    try {
        for (let i = 0; i < 1000000; i++) {
            yield i;
        }
    } finally {
        console.log('제너레이터 정리 완료');
    }
}

const gen = memoryEfficientGenerator();
for (let i = 0; i < 1000; i++) {
    console.log(gen.next().value);
}
gen.return(); // 제너레이터 강제 종료

    6.2 에러 처리¶

    function* errorHandlingGenerator() {
    try {
        yield 1;
        throw new Error('테스트 에러');
        yield 2;
    } catch (error) {
        console.error('에러 발생:', error.message);
        yield '에러 복구';
    } finally {
        yield '정리 작업';
    }
}

const gen = errorHandlingGenerator();
console.log(gen.next().value); // 1
console.log(gen.next().value); // '에러 복구'
console.log(gen.next().value); // '정리 작업'

    출력은 주석대로 나오지만, finally 안의 yield 는 위험한 코드다. 정리 작업이 소비자의 손에 맡겨지기 때문이다.

    finally 블록은 yield 에서 멈추고, 소비자가 next() 를 한 번 더 불러야 그 뒤가 실행된다. 소비자가 중간에 그만두면 정리 코드의 나머지가 영영 안 돈다. 리소스 해제를 finally 에 넣는 이유가 "무슨 일이 있어도 실행된다"인데, yield 를 넣는 순간 그 보장이 사라진다.

    정리가 실제로 도는 경로는 return() 이다.

    function* fin() {
  try { for (let i = 0; i < 1e6; i++) yield i; }
  finally { console.log('finally 실행됨'); }
}

const g = fin();
g.next();
g.return('강제종료');
// 'finally 실행됨'
// { value: '강제종료', done: true }

    for...of 를 break 로 빠져나올 때도 엔진이 return() 을 대신 불러 준다.

    for (const v of fin()) { if (v === 2) break; }
// 'finally 실행됨'  ← 자동으로 정리된다

    그래서 무한 제너레이터를 for...of 로 쓰다 break 해도 뒷정리가 된다. 반대로 while 루프에서 next() 를 직접 부르다 조건으로 빠져나오면 return() 이 안 불려서 finally 도 안 돈다 — 그 경우엔 손으로 gen.return() 을 불러야 한다. 문서의 memoryEfficientGenerator 예제가 마지막 줄에 gen.return() 을 둔 이유가 이것이다.

    finally 에서 yield 하는 대신, 정리 결과를 알리고 싶으면 return 값으로 넘긴다. for...of 는 제너레이터의 return 값을 무시하지만 러너에서는 {done: true} 와 함께 받을 수 있다.

    7. 결론¶

    제너레이터 함수는 JavaScript에서 강력한 도구로, 특히 다음과 같은 상황에서 async/await보다 유용합니다:

    1. 무한 시퀀스 처리: 메모리 효율적으로 무한한 데이터 스트림을 처리할 수 있습니다.
    2. 세밀한 실행 제어: 함수의 실행을 정확한 시점에 중단하고 재개할 수 있습니다.
    3. 복잡한 상태 관리: 상태 변화를 추적하고 관리하는 데 유용합니다.
    4. 메모리 효율성: 필요한 시점에만 데이터를 생성하고 처리할 수 있습니다.

    하지만 다음과 같은 경우에는 async/await를 사용하는 것이 더 적절할 수 있습니다:

    1. 단순한 비동기 작업: Promise 기반의 비동기 작업을 처리할 때
    2. 에러 처리: try-catch를 사용한 직관적인 에러 처리
    3. 코드 가독성: 더 간단하고 직관적인 코드 작성이 필요할 때

    제너레이터와 async/await는 각각의 장단점이 있으므로, 상황에 맞게 적절한 방식을 선택하는 것이 중요합니다.
