    Node.js 로깅¶

    개요¶

    로깅은 애플리케이션의 동작을 추적하고, 문제를 진단하며, 성능을 모니터링하는 핵심 도구입니다. 구조화된 로깅은 운영 환경에서 필수적입니다.

    로깅의 목적¶

    mindmap
  root((로깅))
    디버깅

      문제 진단
      스택 트레이스
    모니터링

      시스템 상태
    감사

      규정 준수

    분석

      사용 패턴
      비즈니스 인사이트

    성능 벤치마크¶

    성능 테스트 결과 (100,000 로그): - Winston: ~2.5초 (동기 로깅) - Pino: ~0.3초 (비동기 로깅)

    메모리 사용량: - Winston: ~50MB - Pino: ~10MB

    위 숫자는 출처가 없다 — 직접 재보면 순위가 뒤집힌다¶

    어떤 하드웨어에서, 어디로(콘솔·파일), 무엇을 로그해서 나온 값인지가 없다. 그래서 실제로 재봤다.

    const N = 100000;
const rec = { userId: '123', action: 'login', ip: '192.168.1.1', userAgent: 'Mozilla/5.0' };

// 루프가 반환한 시점과, 파일에 다 쓰인 시점을 따로 잰다
for (let i = 0; i < N; i++) logger.info(rec, 'User action');
const loop = sec();
dest.flush(() => console.log('루프 반환:', loop, ' 기록 완료:', sec()));

    같은 파일 출력, 같은 레코드로 세 가지를 돌린 결과다.

    설정 루프 반환 기록 완료
    pino sync: false (기본) 0.260 0.260
    pino sync: true 0.626 0.626
    winston File transport 0.150 0.655

    (단위 초. Node v22.21.1 / pino 10.3.1 / winston 3.19.0, 10만 줄 · 세 파일 모두 100000줄 기록 확인)

    루프만 재면 winston 이 제일 빨리 끝난다. 버퍼에 넣고 곧장 반환하기 때문이다. 기록이 끝나는 시점까지 세면 순서가 달라진다. 원 문서의 "Winston 2.5초 / Pino 0.3초"와도 자릿수가 다르다.

    여기서 얻을 건 "누가 빠른가"가 아니라 무엇을 재고 있는지 모르면 벤치마크는 아무 말도 하지 않는다는 것이다. logger.info() 가 반환하는 시점은 로그가 저장된 시점이 아니다. 그래서 이런 걸 먼저 정해야 한다.

    • 응답 지연에 영향을 주는가를 알고 싶다 → 호출이 반환하는 시간을 잰다
    • 프로세스가 죽을 때 로그가 남는가를 알고 싶다 → 기록 완료 시점과 버퍼 크기를 본다

    두 번째가 실무에서 더 자주 문제가 된다. 버퍼에 있던 로그는 프로세스가 비정상 종료하면 사라진다. 장애 직전 몇 초의 로그가 가장 중요한데 정확히 그 구간이 비는 것이다. pino 는 이 절충을 sync 옵션으로 드러내 놓았다(기본은 sync: false, 위 표에서 실측으로 확인).

    그리고 로깅 라이브러리 선택이 성능에서 갈리는 경우는 생각보다 드물다. 로그를 무엇에 얼마나 쓰는지가 훨씬 크게 작용한다. 요청마다 JSON 을 몇 KB 씩 찍고 있다면 라이브러리를 바꿔도 별 차이가 없다.

    Winston 구현¶

    Winston은 유연한 설정과 다양한 Transport를 제공하는 로깅 라이브러리입니다. 프로덕션 환경에 맞게 구성하는 것이 중요합니다.

    Winston 설정¶

    기본 설정 구성 요소:

    graph TD
    LOGGER[Winston Logger] --> LEVEL[로그 레벨]
    LOGGER --> FORMAT[포맷 설정]
    LOGGER --> TRANSPORT[Transport 설정]
    LOGGER --> META[기본 메타데이터]

    LEVEL --> ENV[환경별 레벨]
    FORMAT --> TIMESTAMP[타임스탬프]
    FORMAT --> JSON[JSON 형식]
    FORMAT --> ERROR[에러 스택]

    TRANSPORT --> FILE[파일 출력]
    TRANSPORT --> CONSOLE[콘솔 출력]
    TRANSPORT --> REMOTE[원격 전송]

    FILE --> ROTATE[로그 로테이션]
    FILE --> SEPARATE[레벨별 분리]

    style LOGGER fill:#4fc3f7
    style FORMAT fill:#66bb6a
    style TRANSPORT fill:#ff9800

    환경별 설정:

    개발 환경: - 콘솔 출력 활성화하여 즉시 확인 가능 - 색상 포맷 사용하여 가독성 향상 - DEBUG 레벨까지 로깅하여 상세 정보 확인

    프로덕션 환경: - 파일 출력만 사용하여 성능 최적화 - JSON 형식으로 구조화된 로그 생성 - INFO 레벨 이상만 로깅하여 로그 볼륨 관리

    로그 로테이션: - 일일 로그 파일로 분할하여 관리 용이성 향상 - 파일 크기 제한 (예: 20MB) 설정 - 보존 기간 설정 (일반 로그: 14일, 에러 로그: 30일)

    예외 처리 설정: - 처리되지 않은 예외를 별도 파일에 기록 - Promise 거부를 별도 파일에 기록 - 애플리케이션 크래시 시에도 로그 보존

    참고: - 서비스 이름과 환경 정보를 기본 메타데이터로 포함 - 에러 로그는 별도 파일로 분리하여 모니터링 용이 - 로그 포맷을 일관되게 유지하여 파싱 효율 향상

    Pino 구현¶

    Pino는 성능에 최적화된 로깅 라이브러리로, 비동기 로깅을 통해 높은 처리량을 제공합니다.

    Pino 설정¶

    Pino의 핵심 특징:

    graph LR
    PINO[Pino] --> FAST[빠른 성능]
    PINO --> ASYNC[비동기 로깅]
    PINO --> JSON[기본 JSON]
    PINO --> CHILD[Child Logger]

    FAST --> PERF[높은 처리량]
    ASYNC --> NON_BLOCK[논블로킹]
    JSON --> PARSE[파싱 용이]
    CHILD --> CONTEXT[컨텍스트 전파]

    style PINO fill:#4fc3f7
    style FAST fill:#66bb6a
    style ASYNC fill:#ff9800

    환경별 설정:

    프로덕션 환경: - 기본 JSON 출력으로 구조화된 로그 생성 - 표준 시리얼라이저 사용 (req, res, err) - 서비스 이름과 환경 정보를 base에 포함

    개발 환경: - pino-pretty를 사용하여 가독성 향상 - 색상 출력으로 로그 레벨 구분 - 타임스탬프를 사람이 읽기 쉬운 형식으로 변환

    파일 로깅: - multistream을 사용하여 여러 출력 대상 설정 - 콘솔과 파일을 동시에 출력 - 에러 로그는 별도 파일로 분리하여 관리

    성능 최적화: - 기본적으로 비동기 로깅을 사용하여 메인 스레드 블로킹 방지 - JSON 직렬화가 최적화되어 있어 빠른 처리 속도 - Child logger를 사용하여 컨텍스트를 효율적으로 전파

    참고: - 프로덕션에서는 pino-pretty를 사용하지 않아 성능 오버헤드를 방지합니다 - Child logger를 활용하여 요청별 컨텍스트를 유지합니다 - 로그 레벨을 환경변수로 관리하여 유연하게 조정합니다

    구조화된 로깅¶

    구조화 로깅의 장점¶

    graph TD
    A[구조화된 로깅] --> B[JSON 형식]
    A --> C[메타데이터 포함]
    A --> D[검색 가능]

    B --> E[로그 분석 도구]
    C --> F[컨텍스트 정보]
    D --> G[필터링 및 집계]

    style A fill:#4fc3f7
    style E fill:#66bb6a

    구조화 로깅 구현¶

    // Winston 구조화 로깅
const logger = winston.createLogger({
  format: winston.format.combine(
    winston.format.timestamp(),
    winston.format.json()
  ),
  transports: [
    new winston.transports.Console()
  ]
});

// 구조화된 로그 작성
logger.info('User action', {
  userId: '123',
  action: 'login',
  ip: '192.168.1.1',
  userAgent: 'Mozilla/5.0...',
  timestamp: new Date().toISOString()
});

// Pino 구조화 로깅 (기본)
const pino = require('pino');
const logger = pino();

// 구조화된 로그 작성
logger.info({
  userId: '123',
  action: 'login',
  ip: '192.168.1.1',
  userAgent: 'Mozilla/5.0...'
}, 'User action');

    로깅 헬퍼 함수¶

    // 로깅 헬퍼 클래스
class LoggerHelper {
  constructor(logger) {
    this.logger = logger;
  }

  // 요청 로깅
  logRequest(req, res, responseTime) {
    this.logger.info({
      type: 'http_request',
      method: req.method,
      path: req.path,
      statusCode: res.statusCode,
      responseTime,
      ip: req.ip,
      userAgent: req.get('user-agent'),
      userId: req.user?.id
    }, `${req.method} ${req.path} ${res.statusCode}`);
  }

  // 에러 로깅
  logError(error, context = {}) {
    this.logger.error({
      type: 'error',
      error: {
        message: error.message,
        stack: error.stack,
        name: error.name,
        code: error.code
      },
      ...context
    }, error.message);
  }

  // 비즈니스 이벤트 로깅
  logBusinessEvent(event, data = {}) {
    this.logger.info({
      type: 'business_event',
      event,
      ...data
    }, `Business event: ${event}`);
  }

  // 성능 메트릭 로깅
  logPerformance(metric, value, unit = 'ms') {
    this.logger.info({
      type: 'performance',
      metric,
      value,
      unit
    }, `Performance: ${metric} = ${value}${unit}`);
  }
}

// 사용 예시
const loggerHelper = new LoggerHelper(logger);

// Express 미들웨어
function requestLogger(req, res, next) {
  const startTime = Date.now();

  res.on('finish', () => {
    const responseTime = Date.now() - startTime;
    loggerHelper.logRequest(req, res, responseTime);
  });

  next();
}

// 에러 로깅
app.use((error, req, res, next) => {
  loggerHelper.logError(error, {
    path: req.path,
    method: req.method,
    userId: req.user?.id

    const { v4: uuidv4 } = require('uuid');

// Express 미들웨어
function correlationIdMiddleware(req, res, next) {
  // 요청 헤더에서 Correlation ID 가져오기 또는 생성
  const correlationId = req.headers['x-request-id'] || uuidv4();

  // 요청 객체에 저장
  req.id = correlationId;

  // 응답 헤더에 추가
  res.setHeader('X-Request-ID', correlationId);

  // 로거에 Correlation ID 추가
  req.logger = logger.child({ correlationId });

  next();
}

    실무 운영 시나리오: 로그 수집¶

    시나리오 1: 단일 서버 환경 - 파일 기반 수집이 가장 안정적입니다 - 로그 로테이션을 통해 디스크 공간을 관리합니다 - Filebeat를 사용하여 중앙 집계 시스템으로 전송합니다

function createSampledLogger(baseLogger, sampleRate = 0.1) {
  return {
    debug: (...args) => {
      if (Math.random() < sampleRate) {
        baseLogger.debug(...args);
      }
    },
    info: (...args) => {
      if (Math.random() < sampleRate) {
        baseLogger.info(...args);
      }
    },
    // ERROR는 항상 로깅
    error: (...args) => baseLogger.error(...args),
    warn: (...args) => baseLogger.warn(...args)
  };
}

    프로세스가 급히 죽으면 마지막 로그가 사라진다¶

    가장 중요한 로그는 죽기 직전의 로그인데, 그게 제일 잘 사라진다. 로그 한 줄을 남기고 즉시 process.exit(0) 한 결과다.

    구성 결과
    pino() → stdout 남는다
    pino(pino.destination('p.log')) → 파일 0바이트. 종료 훅에서 sonic boom is not ready yet 예외
    winston File transport 파일이 생기지도 않았다 
    $ node b2.js && wc -c w.log
wc: w.log: No such file or directory

    uncaughtException 핸들러에서 로그를 남기고 process.exit(1) 하는 패턴이 정확히 이 모양이다. 크래시 원인이 담긴 그 한 줄만 유실된다. 종료 전에 flush를 기다려야 한다.

    // pino — 종료 직전 동기 flush
const dest = pino.destination({ dest: '/var/log/app.log', sync: false });
const logger = pino(dest);

process.on('uncaughtException', (err) => {
  logger.fatal({ err }, 'uncaught');
  dest.flushSync();          // 이 줄이 없으면 위 로그가 사라진다
  process.exit(1);
});

    winston은 transport의 finish 이벤트를 기다린 뒤 종료한다. logger.end()를 부르고 콜백에서 process.exit() 한다.

    앞 벤치마크 절에서 확인한 대로 pino() 기본 스트림은 sync: false다. 그런데 stdout으로 나간 로그는 살아남았다 — 동기라서가 아니라 pino가 종료 훅에서 flush를 시도하기 때문이고, 파일 대상에서는 그 flush가 실패했다. 판단 기준은 "동기냐 비동기냐"가 아니라 "종료 경로에서 flush를 보장했느냐"다.

    pino.stdSerializers.req는 Authorization 헤더를 그대로 찍는다¶

    "실전 예제"의 로거는 serializers: { req: pino.stdSerializers.req }를 쓴다. 이 시리얼라이저에 요청을 넣으면 이렇게 나온다.

    {
 "method": "POST",
 "url": "/login",
 "headers": {
  "authorization": "Bearer eyJhbGciOi.SECRET-TOKEN-VALUE",
  "cookie": "session=abc123; refresh=xyz789",
  "x-api-key": "sk_live_51H...",
  "content-type": "application/json"
 },
 "remoteAddress": "1.2.3.4"
}

    헤더를 통째로 담는다. 이 문서의 주의사항 5번이 "민감한 정보 로깅 금지"인데, 표준 시리얼라이저를 그대로 쓰는 순간 액세스 토큰·세션 쿠키·API 키가 전부 로그 저장소로 넘어간다. 로그는 보통 애플리케이션 접근 권한보다 넓게 열려 있고 보관 기간도 길다. 토큰이 만료돼도 세션 쿠키와 API 키는 살아 있다.

    redact로 막는다. 경로를 지정하면 값이 [Redacted]로 치환된다.

    const logger = pino({
  redact: ['req.headers.authorization', 'req.headers.cookie', 'req.headers["x-api-key"]',
           'req.body.password', 'res.headers["set-cookie"]'],
  serializers: { req: pino.stdSerializers.req },
});

    {"authorization":"[Redacted]","cookie":"[Redacted]","x-api-key":"[Redacted]","content-type":"application/json"}

    redact는 경로를 문자열로 정확히 맞춰야 한다. 오타가 나도 에러가 안 나고 그냥 안 가려진다. 적용한 뒤 실제 로그 한 줄을 눈으로 확인한다. 더 안전한 방법은 시리얼라이저에서 필요한 헤더만 골라 담는 것이다 — 이 문서의 두 번째 통합 예제가 그렇게 하고 있다.

    요청 하나가 두 번 로깅된다¶

    "실전 예제"는 pinoHttp({...})를 등록하고 그 아래에 res.on('finish') 미들웨어를 또 등록한다. pino-http는 응답 완료 시점에 이미 한 줄을 쓴다. 같은 요청이 request completed 한 줄과 type: "http_request" 한 줄로 두 번 남는다.

    로그량이 두 배가 되는 것보다, 집계가 두 배로 잡히는 게 더 문제다. Kibana에서 요청 수를 세면 실제의 두 배가 나오고 응답 시간 분포도 왜곡된다. pino-http를 쓰면 수동 미들웨어를 지우고, 필요한 필드는 customProps로 붙인다.

    같은 예제에서 라우트 안의 logger.child({ correlationId: req.id })도 중복이다. pino-http는 req.log에 이미 요청 ID가 붙은 child logger를 넣어준다. req.log를 쓰면 된다.

    샘플링이 요청 추적을 끊는다¶

    info: (...args) => { if (Math.random() < sampleRate) baseLogger.info(...args); }

    이 방식은 로그 한 줄 단위로 독립 추첨을 한다. 한 요청에서 세 줄을 남기면 셋 다 남을 확률이 0.1%, 하나만 남을 확률이 24%가 넘는다. 장애를 조사할 때 "요청은 들어왔는데 그 다음이 없다", "결과만 있고 시작이 없다" 같은 반쪽 로그를 보게 된다. 샘플링의 목적이 비용 절감인데 남은 로그가 쓸모없어진다.

    샘플링은 요청 단위로 결정한다. 요청 진입 시 한 번 뽑아서 그 요청의 로그를 전부 남기거나 전부 버린다.

    app.use((req, res, next) => {
  const sampled = Math.random() < 0.1;
  req.log = sampled ? logger.child({ correlationId: req.id }) : silentLogger;
  next();
});

    에러가 난 요청은 샘플링에서 제외해야 한다. 그러려면 로그를 요청 단위로 버퍼에 모아뒀다가 응답 시점에 "에러였거나 추첨에 뽑혔으면 전부 flush"하는 방식이 필요하다. 구현 비용이 있으므로, 그 전에 로그 레벨 조정만으로 볼륨이 잡히는지 먼저 본다.

    또 이 헬퍼는 child(), fatal(), trace()를 안 갖고 있다. 기존 코드에서 logger.child(...)를 부르던 곳이 있으면 TypeError가 난다.

    성능 수치는 출력 대상에 따라 달라진다¶

    "성능 벤치마크" 절의 수치에는 측정 조건이 없다. 로깅 처리량은 대상이 stdout인지 파일인지 파이프인지, sync 설정이 무엇인지에 따라 크게 갈린다. 컨테이너에서 stdout을 수집기가 읽어가는 구성이면 수집기가 느릴 때 write가 블로킹되는지가 실제 병목이라, 라이브러리 자체 속도보다 그쪽이 먼저 문제가 된다.

    직접 재는 게 빠르다. 두 라이브러리를 같은 대상·같은 건수로 놓고 비교한다.

    node bench.js > /dev/null      # stdout 을 버리고 순수 직렬화 비용
node bench.js > /tmp/out.log   # 파일 write 포함
node bench.js | cat            # 파이프 — 컨테이너 수집 구성에 가깝다

    세 결과가 다르면 그 차이가 곧 "우리 환경에서 로깅이 어디서 느린가"의 답이다.
